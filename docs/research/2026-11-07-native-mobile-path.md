# Native mobile path: what the phone app carries over (RT-1136)

Which native iPhone and Android route the PWA work (PW.3 to PW.8 in [mobile-app.md](../plans/mobile-app.md)) should be shaped for, so its effort is not thrown away. External facts carry their source URL; repo facts name the file and symbol.

## What the PWA is today

- `apps/pwa/src/protocol.ts`: the wire types, generated by `tools/protocol-ts` (a `syn` reader over `crates/protocol`'s source that emits TypeScript and refuses serde attributes it does not know; staleness test `generated_protocol_ts_is_current`). No protocol type carries a derive for it, so a second emitter (Swift, Kotlin) is a sibling module over the same parse, not a change to the protocol crate.
- `apps/pwa/src/connection-machine.ts`: a pure reducer (`ConnectionState`, `ConnectionEvent`, `ConnectionEffect`, `StepResult`) over idle, connecting, handshaking, ready, backoff, hidden and notApproved. No socket, timer or DOM. `backoff.ts` and `hello.ts` are pure too.
- `apps/pwa/src/socket.ts`: the driver; socket, timers, visibility and token store are injected.
- `apps/pwa/src/token-store.ts`: the `TokenStore` seam PW.3 fills (IndexedDB plus `navigator.storage.persist()` in the plan).
- `apps/pwa/src/sw.ts`, `sw-strategy.ts`: the service worker and its cache rule; web-only by nature.
- Daemon side: the tailnet listener with `tailscale cert` TLS, whois owner rule (`crates/tailnet`), device tokens and the pairing connection (`crates/daemon/src/server/pairing.rs`, `handshake.rs`), and the planned Web Push sender with VAPID keys (PW.6).

The connection logic is already mirrored once in Rust: the native client's `apps/native/src/connection.rs` (`State::NotApproved`) and `apps/native/src/net.rs` (`attempt_tailnet`), with the device token store in `crates/daemon-client/src/device_tokens.rs`. That matters for route 4.

## Platform facts every native route shares

- **Push needs a paid Apple Developer Program membership.** Push notifications are an ADP capability; a free Apple Account team cannot sign it ([Apple, Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios/)).

  Free signing also expires a build after 7 days and allows 3 apps per device ([Expo, Apple Developer Program explained](https://expo.dev/blog/apple-developer-program-explained-free-vs-paid)). The current plan's "no Apple Developer account" ruling holds only for the PWA.
- **APNs is sent with a team key.** Token auth is an ES256 JWT signed with a `.p8` key from the developer account, carrying the 10-character Team ID and key ID, reused for up to an hour ([Apple, Communicating with APNs](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CommunicatingwithAPNs.html), [Apple, token-based auth](https://developer.apple.com/help/account/capabilities/communicate-with-apns-using-authentication-tokens/)).

  Requests are HTTP/2 POSTs to `/3/device/<token>` with `apns-topic` the bundle ID and an optional `apns-collapse-id` ([Apple, Sending notification requests to APNs](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns.md)).

  The daemon's P-256 signing for VAPID carries over; the HTTP/2 transport and the per-push-service error map are new.
- **FCM is sent with a Firebase service account.** The HTTP v1 API authorizes with a service account JSON file or an OAuth token derived from it when not on Google Cloud ([Firebase, HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api)).
- **Who holds the push key is the hard problem.** The app is released and used by more than its owner (CLAUDE.md, "Saved user data survives every update"). A store-distributed app has one bundle ID and one APNs team key; every user's self-hosted daemon would need that key to push, which cannot ship in the installer. The usual answer is a vendor-run push relay, which is outside the "Tailscale only, nothing else in the path" ruling.

  Web Push has no such problem: each daemon signs with its own VAPID key. For an owner-only build (owner's own team, owner's own key on his own hosts) direct APNs works.
- **Android has a key-free option.** UnifiedPush is now specified over Web Push (RFC 8030/8291/8292), so a daemon that speaks Web Push can push to a UnifiedPush distributor such as ntfy or Sunup with no Google key ([UnifiedPush news](https://unifiedpush.org/news/20221218_unifiedpush/), [UnifiedPush distributors](https://unifiedpush.org/users/distributors/), [UnifiedPush Android spec](https://unifiedpush.org/developers/spec/android/)).

  It needs a distributor app on the phone. iOS has no equivalent.
- **Reaching the tailnet.** With the Tailscale app, any app on the phone reaches tailnet hosts through its VPN; iOS and Android allow one VPN at a time ([Tailscale, other VPNs](https://tailscale.com/docs/reference/faq/other-vpns)), and iOS VPN On Demand keeps it up ([Tailscale, VPN On Demand](https://tailscale.com/docs/features/client/ios-vpn-on-demand)).

  Without it, an app can embed a node: `libtailscale` compiles Tailscale into a process in userspace ([tailscale/libtailscale](https://github.com/tailscale/libtailscale/)), and its `swift/TailscaleKit` offers a `URLSessionConfiguration` proxied through the node ([URLSession+Tailscale.swift](https://github.com/tailscale/libtailscale/blob/main/swift/TailscaleKit/URLSession%2BTailscale.swift)).

  A third-party ADR reports it needs no Network Extension and adds tens of MB, with App Store acceptance unproven ([dmon ADR-017](https://github.com/daemonicai/dmon-core/blob/main/docs/adrs/ADR-017-ios-embedded-tailscale.md), secondary). An embedded node is its own tailnet device with its own login, so the daemon's whois owner rule sees a new node, not the owner's phone.
- **Background sockets.** A `URLSessionWebSocketTask` is suspended within seconds of the app leaving the foreground, and background URL sessions do not support WebSocket tasks (secondary: [myrobotaxi swift-lifecycle contract](https://github.com/myrobotaxi/telemetry/blob/main/docs/contracts/swift-lifecycle.md)). An embedded tailnet node dies with the process too (dmon ADR-017).

  So a native app keeps the PWA's model: reconnect and resync on foreground, alerts by push. Nothing in a native app buys a live background socket.
- **Token storage.** Native apps get the Keychain and Android Keystore; Expo wraps both as `expo-secure-store`, noting some iOS releases refused values above about 2048 bytes ([Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/)). A 256-bit device token fits. This removes the PWA's Safari-eviction re-pair case.
- **App Store review.** Review needs full access, a demo account or demo mode, and live backends (guideline 2.1); an app should be more than a repackaged website (4.2) and work without installing another app (4.2.3(i)) ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), [complete review help](https://developer.apple.com/help/app-review/before-submitting-for-review/complete-review/)).

  A tailnet-only app that needs the Tailscale app and a self-hosted daemon collides with 2.1 and 4.2.3(i); it needs a demo mode (a scripted fake daemon in the app) or an embedded node plus a reviewer host. TestFlight and ad hoc for the owner's own devices avoid review of that kind but still need ADP.
- **Android sideloading.** Developer verification went live on 30 September 2026 in Brazil, Indonesia, Singapore and Thailand and goes global in 2027; a free limited-distribution account covers up to 20 devices without ID, and adb installs stay exempt ([Android developer verification](https://developer.android.com/developer-verification/guides), [Android Developers Blog, June 2026](https://developer.android.com/blog/posts/android-developer-verification-building-a-safer-ecosystem-together)).

  The unverified "advanced flow" has a 24-hour wait ([Android Authority](https://www.androidauthority.com/android-sideloading-developer-verification-first-wave-rollout-3717921/), secondary).

## The routes

### 1. SwiftUI and Compose apps, wire types generated per language

- **Carries over unchanged:** nothing as code. The design carries: the reducer's states, events and effects, the backoff numbers, the Hello shape, the pairing flow, the screen rules and the daemon's rendered-rows stream (PW.5).
- **Rewritten:** everything, twice: the reducer, the driver, every screen, in Swift and in Kotlin. The pure-reducer tests become the spec to port, test by test.
- **Generator:** `tools/protocol-ts` gains Swift (`Codable` enums with a custom tag decoder and an `unknown` case) and Kotlin (`kotlinx.serialization` sealed classes with a class discriminator and a default) emitters over the same `syn` parse, each with its own staleness test. The "refuse unknown serde attributes" rule is what makes three emitters safe.
- **Daemon adds:** APNs sender, FCM (or UnifiedPush) sender, a per-device push registration that names its kind (`web_push`, `apns`, `fcm`, `unified_push`), and the push-key question above.
- **Cost:** highest. Two full apps plus two emitters; each later phase (terminal, chat, files, accounts) is built three times. Best native feel (real terminal view, widgets, notification actions, which the PWA gives up per its "Accepted losses").

### 2. React Native / Expo, reusing the PWA's TypeScript

Expo SDK 58 is current (React Native 0.88, built for iOS 27, released 15 October 2026) ([Expo changelog](https://expo.dev/changelog), [How to upgrade to SDK 58](https://expo.dev/blog/how-to-upgrade-to-sdk-58)).

- **Carries over unchanged:** `protocol.ts`, `connection-machine.ts`, `backoff.ts`, `hello.ts`, and `socket.ts` if its injected socket stays the WHATWG `WebSocket` shape (React Native ships a global `WebSocket`), plus any pure list, tray and prompt-sheet models PW.4 and PW.5 write, with their vitest suites. One TypeScript codebase for iOS and Android.
- **Rewritten:** the views (DOM and CSS to React Native components), the `TokenStore` implementation (`expo-secure-store`), push registration (`expo-notifications`, `getDevicePushTokenAsync` for a raw APNs or FCM token, sending without Expo's service ([Expo, send with FCM and APNs](https://docs.expo.dev/push-notifications/sending-notifications-custom/))), the QR scanner (a camera module), and the full terminal (PW.9: xterm.js needs a WebView, or a native terminal view).
- **Daemon adds:** the same APNs/FCM senders and push-key question as route 1. Web Push stays for the PWA.
- **Cost:** medium. The logic layer is free if it stays DOM-free; the view layer is a rewrite. A JS runtime and Expo's yearly SDK cadence to keep up with (SDK lifetimes are about a year, [Expo SDK 57](https://expo.dev/changelog/sdk-57)).

### 3. Capacitor wrapping the PWA

Capacitor 8 is current, with `@capacitor/push-notifications` 8.1.x registering APNs on iOS and FCM on Android ([Announcing Capacitor 8](https://ionic.io/blog/announcing-capacitor-8), [push-notifications plugin](https://ionicframework.com/docs/v8/native/push-notifications), [capacitor-plugins releases](https://github.com/ionic-team/capacitor-plugins/releases)).

- **Carries over unchanged:** almost all of `apps/pwa/src`, views included, if the bundle is shipped inside the app. Loading the daemon's served page with `server.url` is documented as "not intended for use in production" ([Capacitor config](https://capacitorjs.com/docs/config)) and can lead to rejections (Ionic maintainer, [discussion 5183](https://github.com/ionic-team/capacitor/discussions/5183)).
- **Rewritten:** the storage, push and scanner seams get native-plugin implementations; the service worker does not apply (the bundle is local); the socket URL is no longer "its own origin" but the paired host's `wss://{name}:{port}/ws`, so the daemon's exact-`Origin` check (invariant 6 in `remote-access.md`) must accept the Capacitor origin (`capacitor://localhost` on iOS, `https://localhost` on Android by default, per the config doc). Store review risk under 4.2 for a wrapped site.
- **Daemon adds:** APNs/FCM senders and the push-key question; an `Origin` allowance for the app's scheme, which reopens the CSRF reasoning the same-origin rule settled.
- **Cost:** lowest to ship; the app stays a web app with web limits (WKWebView terminal, no widgets). A good owner-only bridge, a weak end state.

### 4. Shared Rust core through uniffi, Swift and Kotlin UIs

uniffi 0.32.2 is current (22 September 2026), generating Swift and Kotlin with async, recursive enums and field renames ([uniffi CHANGELOG](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md), [tags](https://github.com/mozilla/uniffi-rs/tags)).

- **Carries over unchanged:** `crates/protocol` itself (serde types used as-is; no per-language generator for the core's own use), and logic the native desktop client already has in Rust (connection states, device token handling in `crates/daemon-client`). The PWA's TypeScript does not carry over; its reducer is reconciled with the Rust one.
- **Rewritten:** the core's FFI surface (a session-list store, the connection machine, pairing, effects as callbacks), and the views in SwiftUI and Compose. The WebSocket and TLS run in Rust (tokio, rustls with the system roots) or through a foreign-implemented transport trait (`#[uniffi::export(foreign)]`, per the changelog).
- **Daemon adds:** the same push senders and push-key question.
- **Cost:** high up front (FFI build for iOS and Android targets, a Mac builder for the XCFramework, which this repo has), lower per phase than route 1 since logic is written once and shared with desktop. Two thin UIs remain.

## Comparison

| | Logic reused from `apps/pwa` | Views | Per-phase cost later | Push key problem | Store fit |
|---|---|---|---|---|---|
| 1 Swift + Kotlin | none (design only) | 2 native | ×3 | yes | good |
| 2 Expo | reducers, types, driver | 1 RN | ×2 (PWA + RN) | yes | good |
| 3 Capacitor | nearly all | the PWA's | ×1 | yes | weak (4.2) |
| 4 Rust core + uniffi | none (Rust core shared with desktop) | 2 native | ×2 to ×3 | yes | good |

## Recommendation

Shape the PWA for **route 2 (Expo)**, with route 3 as the zero-cost fallback if the owner wants an installed native shell for himself before any rewrite. Reasons: the PWA's logic is already TypeScript in pure reducers behind injected seams, which is exactly what an Expo app imports unchanged; it is one codebase for iOS and Android; and the TypeScript generator already exists, so no new emitter is needed.

Route 4 is attractive only if the native desktop client and the phone are meant to share one Rust state core, which would mean rewriting the PWA's reducers rather than reusing them. Route 1 costs most and buys native feel the owner has so far ruled not worth it (mobile-app.md "Accepted losses").

Whatever the route, the gating decision is not the UI stack but **push for a released, self-hosted product**: Web Push (and UnifiedPush on Android) keep per-daemon keys; APNs and FCM need either an owner-only build or a vendor relay. That decision should come before any native work starts.

## Conventions for the PWA now

1. **Logic in pure modules, no DOM.** Every PW phase puts its state in a reducer like `connection-machine.ts` (pairing flow in PW.3, list and tray model in PW.4, prompt sheet and answer keys in PW.5, subscription compare in PW.6), tested with vitest, with no `window`, `document`, `navigator` or `indexedDB` import.
2. **Views thin.** A view renders state and dispatches events; no protocol decoding, timers or storage in view code.
3. **Platform behind injected seams.** `TokenStore` already is; add the same shape for push registration (returns an opaque registration the daemon stores), QR scanning (returns a decoded string, so `BarcodeDetector` or a decoder library is an implementation), badge (`setAppBadge`), visibility/foreground, and share. Each seam has a web implementation and a test fake.
4. **Socket as WHATWG `WebSocket` only.** `socket.ts` uses only `new WebSocket(url)`, `send`, `close` and the four events, which React Native provides; no `Blob`/`ArrayBuffer`-only paths.
5. **Host URL is data, not `location`.** Keep the daemon URL a value the pairing result stores beside the token, even though the PWA's is its own origin today. A native app pairs with a named host; the stored record should be `{host, port, token}`.
6. **Push registration is tagged by kind.** Make PW.6's wire message carry a kind (`web_push` now) and a kind-specific body, so `apns`, `fcm` or `unified_push` are new variants, additive on the wire, rather than a second message. Keep the declarative payload's fields (title, body, session id, badge count) defined once on the daemon and mapped per push service.
7. **Wire types only from the generator.** Keep `protocol.ts` the only source of wire shapes in the PWA, with default branches on every tag switch; if route 1 or 4 is chosen, the generator grows per-language emitters, never hand mirrors.
8. **Deep links by session id.** Keep `/s/<session id>` as the one navigation target a notification carries; native apps map it to a universal link or intent.

## Open questions for the owner

- **Push for released users** (changes PW.6): is the phone app owner-only for good (direct APNs with the owner's key is fine later), or will released users get a native app (needs a push relay, which breaks "nothing else in the path", or Web Push and UnifiedPush only)? PW.6 should at least add the `kind` tag to its registration message now.
- **Apple Developer Program** (changes the "no Apple Developer account" ruling): any native iPhone route with remote push needs ADP; is that acceptable when native work starts?
- **Tailscale app or embedded node** (changes PW.3's identity model only for native): an embedded TailscaleKit node is a separate tailnet device; should the whois owner rule accept it as the owner's, or does the native app require the Tailscale app as the PWA does?
- **Stored pairing record** (small PW.3 change): store `{host, port, token}` rather than a bare token, so the record carries to a native app and to more than one host.
- **One state core for desktop and phone?** If yes, route 4 wins and the PWA's reducers become a stopgap; if no, route 2.
