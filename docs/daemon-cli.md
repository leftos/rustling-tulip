# Daemon CLI and supervision

The `rustling-tulipd` subcommands, and how a client starts, retires or refuses a daemon.

## Subcommands

`rustling-tulipd pair` prints a one-time device pairing code from the running daemon (it needs the daemon already running, reads `daemon.json` and takes no instance lock; `crates/daemon/src/cli_pair.rs`); the owner types the code on a device whose pairing request is waiting.

`rustling-tulipd shutdown` stops the running daemon the way the client retires one: it sends `/shutdown` only to a listener that has proven it holds the token, leaves every tracer alive, creates no folders and starts no log (`crates/daemon/src/cli_shutdown.rs`, `daemon_client::shutdown_in`); the installer runs it on install and uninstall; its failures print to stderr. The `/proof` key context and the `/proof` and `/shutdown` routes are therefore a contract with every released daemon.

`rustling-tulipd apply-update --from <staging> --to <dir> [--old-version <v>] [--update] [--relaunch] [--restart-daemon]` is what the installer runs from the staged daemon to swap the installed files (`crates/daemon/src/cli_apply_update.rs`, `docs/auto-update.md`): it stops the daemon, renames each file to `.old` and the staged one into place, rolls every file back on a failure, writes `last-result.json`, and with `--relaunch` or `--restart-daemon` starts the client or the daemon again.

With `--to <name>.app` it replaces the whole bundle by rename instead: `--from` must then be a `.app` too (usage error `--from must be a .app bundle when --to is one`), the old bundle moves to `<name>.app.old`, the new one is renamed into place, a failure puts the old app back, and the old copy is removed after success. The new bundle must sit on the same volume as the installed one. Before the daemon stops it exits 5 when the bundle is translocated or its folder is not writable (`rustling-tulip.app runs from a place the update cannot replace; move it to Applications and update again; nothing was changed`). The client wait and the in-use refusal look at `<to>/Contents/MacOS`, and `--relaunch` starts `<to>/Contents/MacOS/rustling-tulip-native --updated-from <v>`.

Its exit codes: 0 applied, 1 bad arguments, 2 the daemon would not stop, 3 an exe still runs from the install folder, 4 another update holds the lock, 5 a file failed and was rolled back. `rustling-tulipd --version` and `-V` print `rustling-tulipd <version>` and exit 0.

The daemon is a GUI-subsystem exe, so `--version`, `pair`, `sessions`, `shutdown` and `apply-update` attach the parent console before writing (`attach_parent_console` in `crates/daemon/src/cli_pair.rs`). A valid redirected stdout or stderr is kept, so `> out.txt` captures the output even when the caller has a console (`ssh host cmd /c`); only a null handle gets the console, opened as `CONOUT$` (`crates/daemon/tests/cli_console.rs`).

The daemon starts for no arguments or for `--detach` alone (the login Run entry and the logon task). The plain start also takes `--start-failure-file <path>`, at most once and in any position: the daemon writes the error it failed to start with there, before it opens any log, and only for a failure before it publishes `daemon.json`.

The client that started it ends its wait on that text instead of a generic timeout. `--detach` refuses the option, since the launcher hands over to a cached child that never sees it (`crates/daemon/src/detach.rs`, `crates/daemon-client/src/supervisor.rs`).

**Login PATH on macOS.** In a start form that runs the daemon in this process (no arguments, or `--start-failure-file`; never `--detach` or a subcommand), a daemon whose inherited PATH is launchd-minimal (unset, empty, or only `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`) runs the user's login shell once before the async runtime starts: `$SHELL -ilc` (else `/bin/zsh`), printing `printenv PATH` between sentinel lines (`crates/daemon/src/login_path.rs`, called from `crates/daemon/src/main.rs`). It sets the process PATH to the login shell's entries followed by the inherited ones not already present. The probe has a 5 s deadline: the shell runs in its own process group, killed only if the shell is still running at the deadline, so an rc-file job left running after a good answer is left alone. A failure keeps the inherited PATH. Windows and Linux are unchanged.

Any other argument list that no subcommand took prints one stderr line and exits 2, before any folder, lock, log or daemon start:

`rustling-tulipd: unknown argument "<arg>"; usage: rustling-tulipd [--start-failure-file <path>] | --detach | --version | <command> ..., where <command> is apply-update, bridge, kill, pair, read, screen, send, sessions, shutdown, spawn, wait or watch`

`<arg>` is the offending argument: an unknown one, `--detach` given twice, `--start-failure-file` with no value after it, given twice, or beside `--detach` (`crates/daemon/src/detach.rs` `launch_form`, `crates/daemon/src/main.rs`).

`rustling-tulipd bridge` is what an SSH client runs on the host: it relays one compact JSON protocol message per line between its stdin and stdout and the loopback daemon's WebSocket, starting the daemon first when none runs (`daemon_client::ensure_running_for_bridge`, "How a client starts and retires the daemon") and filling the `Hello` token from the host's handshake so the token never leaves the host (`crates/daemon/src/cli_bridge.rs`).

It exits 0 when the daemon closes the WebSocket, and after stdin EOF once the daemon has closed or 5 s have passed (it relays replies still in flight and sends its Close only then, since the daemon drops queued replies once it reads one); a daemon it starts on Windows inherits none of its handles (see "How a client starts and retires the daemon"), so `ssh host rustling-tulipd bridge` that started a daemon returns about 2 s after the bridge exits. On failure it prints one stderr line `rustling-tulipd bridge: <error>`, leaves stdout empty and exits 1. It starts no tracing, takes no instance lock, rotates no log, creates no folders and attaches no console.

`rustling-tulipd screen <session id> [--fixture <path>]` shows how the running daemon reads one session's screen (it needs the daemon already running and proves the token like `pair`; `crates/daemon/src/cli_screen.rs`, the daemon's side in `crates/daemon/src/server/screen.rs`). It prints one line per rule (`<priority>  <name>  <region>  matched|vetoed by guard N|no match  <preview>`), `winner: <name> (<verdict>)` or `winner: none (no_match)`, any `rejected:` lines, `title: <title>` when there is one, then `grid <cols>x<rows>:` and the rows.

With `--fixture` it then writes the trimmed rows (LF) to exactly that path, refusing an existing file, and prints `wrote <path>`. It refuses at once against a daemon whose `Welcome.features` lack `screen_dump`, and on any failure prints one stderr line `rustling-tulipd screen: <error>` and exits 1.

### Session-driving verbs

`rustling-tulipd sessions`, `read`, `spawn`, `send`, `kill`, `wait` and `watch` work against the running daemon over the protocol every client speaks (`crates/daemon/src/cli_drive/`, on the shared connection in `crates/daemon/src/cli_client.rs`). They create no folders, take no instance lock, start no log and never start a daemon. They act on whichever daemon `daemon.json` in the active config dir names, so `RUSTLING_TULIP_CONFIG_DIR` picks an isolated one and nothing else guards the choice. They send no `Resize` and no client id, so the user's panes and the user's clients' layouts stay as they are.

A bare `--` ends the flags: what follows is positional text, so text may start with a dash, and `--json` after it is text.

**Isolating an experiment.** Every verb acts on the daemon the active config dir names, the user's own included. An agent running an experiment starts its own daemon with `RUSTLING_TULIP_CONFIG_DIR`, `RUSTLING_TULIP_BINARIES_DIR` and `RUSTLING_TULIP_WORKTREES_DIR` pointing under a `.tmp` folder, and runs each verb with `RUSTLING_TULIP_CONFIG_DIR` set the same way. Over an elevated SSH logon, do not pre-create the isolated config dir: the daemon refuses a protected root whose permissions inherit from the parent folder. Run the verbs with the worktree's own build of `rustling-tulipd`, never an older installed one on `PATH`: a release before these verbs treats an unknown verb as a plain daemon start, in the real profile. An isolated bridge run over SSH is checked by `ssh` returning promptly after a cold-start bridge.

`rustling-tulipd sessions [--json]` prints one tab-separated line per session: id, status (`spawning`, `idle`, `working`, `awaiting_input`, `stopped`, `error`), `bg` or `-`, agent id or `shell` (also for a session whose agent was started in its shell and has ended: its `program_name` is no longer the agent's tag), title, repo, branch. The title is the user's label, else the terminal title, else the canonical label, and a tab or line break in it prints as a space. Repo and branch come from the first member, else `-`. With `--json` it prints one array of objects with `id`, `label` (that same title), `status`, `status_since`, `background`, `agent`, `repo` and `branch`; the last three are `null` where the text shows `shell` or `-`. The snapshot's own `agent` is unchanged after such an agent ends; only this verb reports `null` then.

`rustling-tulipd read <session id> [--scrollback] [--json]` prints the session's screen as the daemon's grid has it, one row per line, at the daemon's current size. With `--json` it prints `{id, cols, rows, title, lines}`. It refuses at once against a daemon whose `Welcome.features` lack `screen_dump`.

With `--scrollback` it prints the session's scrollback as UTF-8 text: a cursor-forward sequence prints as spaces (at most 512 each), a cursor-position or next-line sequence as one line break, `\r\n` and a lone `\r` as `\n`, and every other escape sequence is dropped. Bytes that are not valid UTF-8 print as U+FFFD. With `--json` it prints `{id, truncated, text}`. It closes the connection as soon as the reply arrives, since that request also starts streaming the session's output to this connection.

`rustling-tulipd spawn [--agent <id>] [--repo <name>] [--cwd <folder>] [--prompt <text>] [--label <label>] [--json]` starts a session and prints its id, or `{id, label, status}` with `--json`, once the daemon reports it, within 30 s. It takes exactly one of `--repo` and `--cwd`. `--cwd` runs in that folder, a relative one meaning relative to the caller. `--repo` looks up the registered repo of that name and runs in its checkout on the branch it has out, with no worktree and no branch change; a repo with no branch checked out fails. With no `--agent` the session is a plain shell; `--agent` names a registered agent, run interactively with its default options, and only it takes `--prompt`. An unknown repo or agent fails with `not_found`.

`rustling-tulipd send <session id> <text> | --keys <spec> [--raw] [--json]` delivers input and prints nothing, or `{"id":…}` with `--json`. A successful `send` means the daemon took the input, not that the agent acted on it. Text for an agent session goes through the chat composer. An unknown session, a session with no screen and invalid text fail the verb, and a stopped session fails with `ended` on every path. A composer refusal (a waiting prompt, a busy lane) happens after the verb returns and is not seen, so check with `read` or `wait`. Text with `--raw`, or for a plain shell, is typed with a carriage return after it.

`--keys` types the bytes of its spec and does not take `--raw`. Plain text stands for itself. The escapes are `\r \n \t \e \xHH`, and the names `<Enter> <Esc> <Tab> <Up> <Down> <Right> <Left> <Backspace> <Space>` and `<C-a>` to `<C-z>` are one key each. A `<` with no `>` after it is plain text. An unknown name or escape is a usage error.

`rustling-tulipd kill <session id> [--json]` stops the session and keeps its record, printing nothing, or `{"id":…}` with `--json`, once the daemon reports it stopped or gone. An already stopped session succeeds at once.

`rustling-tulipd wait <session id> (--status <status> | --text <regex>) [--timeout <seconds>] [--json]` returns when the session has the status or its screen matches. The default timeout is 300 s; running out exits 4 with the code `timed_out`. A session that disappears or whose status is over fails at once with the code `ended`, except that `--status stopped` and `--status error` keep waiting for their own status. `--text` takes one last look at an ended session's screen first, so text already there still matches.

`--status` takes `spawning`, `idle`, `working`, `awaiting_input`, `stopped` or `error`, and prints the status, or `{id, status}` with `--json`. `--text` matches the regex over the screen's rows joined by `\n`, and prints the row where the match starts, or `{id, line}` with `--json`. While it waits, the session's output streams to this connection.

`rustling-tulipd watch <session id> [--timeout <seconds>] [--json]` prints one line per change in the session's status or `background`, flushed as it comes, the first being the current state: `<status_since RFC 3339> <status> <bg|-> seq=<status_seq>`, with `-` for a `status_since` the daemon never set. With `--json` each line is an object with `status_since`, `status`, `background` and `status_seq`. It reads snapshots, so changes the daemon's broadcast dropped print as one line for the net change. It has no default timeout, exits 0 when the session is removed or the timeout passes, and exits 1 if the connection closes.

Exit codes: 0 ok, 1 any failure, 2 usage, 4 `wait` timed out, 5 no daemon running (`daemon.json` is missing, or no connection opens on the port it names, as after a crash). A listener that does not prove it holds the token is exit 1, and so is the elevated daemon's refusal (below), printed as the verb's error. A failure prints one stderr line `rustling-tulipd <verb>: <error>` and nothing on stdout. With `--json` it prints `{"error":{"code":"<code>","message":"<text>"}}` on stdout instead, the code being the daemon's (`not_found`, `no_screen`) when it sent one, else `failed`, `usage`, `no_daemon`, `timed_out`, `ended` or `checkout_confirm`.

## An elevated daemon

A daemon whose token is at High integrity or above is elevated. It writes `daemon.json` with a High label (`docs/on-disk.md`) and admits on `/ws`, `/shutdown` and `/hook` only a loopback peer whose integrity is at or above the lower of its own level and High; it finds the peer from the established loopback TCP row and refuses when that lookup fails (`crates/daemon/src/integrity.rs`). It logs `daemon integrity level` (fields `integrity`, `elevated`) at start and `loopback request refused` per refusal. An ordinary daemon is unchanged, and an elevated caller still reuses a running ordinary daemon.

The refusal text is `daemon_client::ELEVATED_DAEMON_REFUSAL`: "this rustling-tulip daemon runs as administrator; start this app or command as administrator to use it, or stop that daemon from an elevated terminal with \"rustling-tulipd shutdown\"". A failed lookup appends " (could not check this process's elevation: <error>)". `/ws` answers `AuthFailed`; `/shutdown` and `/hook` answer 403. An ordinary caller meets this refusal only when it shares one `RUSTLING_TULIP_CONFIG_DIR` with the elevated daemon: with the real profiles it never looks in the elevated one, so its verbs report that no daemon is running (exit 5) and its `shutdown` that there is nothing to stop.

Every client reads `daemon.json` through `daemon_client::read_handshake_file` (the supervisor, the CLI verbs, `pair`, `bridge`, `shutdown`, `stop` and `apply-update`). An access-denied read is retried 5 times, 20 ms apart. Still denied, it probes the instance lock (`daemon.lock`). Held: the refusal. Free: the stale file an elevated daemon left is removed and the client goes on as if no daemon ran, logging "removed the daemon.json an elevated daemon left behind; no daemon holds the instance lock". When the removal fails the error reads "a rustling-tulip daemon that ran as administrator left {path} behind; delete it from an elevated terminal, then start the app again". The CLI verbs print the refusal and exit 1.

## How a client starts and retires the daemon

The native client auto-spawns the daemon on first connect via `daemon_client::ensure_running` (`crates/daemon-client`), passing the protocol versions it speaks. The spawn breaks away from the caller's job; when that job forbids breakaway it launches the daemon through WMI `Win32_Process.Create` with the caller's full environment, outside the job (`wmi_launch.rs`, bounded at 30 s), and only if that fails starts it inside the job, logging which path ran. The daemon writes `port` + `auth_token` + `pid` + `supported_versions` + `build_version` to `daemon.json` in the config dir below; clients read that to connect.

A daemon sharing none of the client's versions is retired and replaced. The native client speaks only the current version, and the daemon's `supported` (`protocol-version.json`) lists only the current version too.

A daemon whose `build_version` is older than the client's own (a missing one counts as older) is retired and replaced too, with the reason `older build`; one whose `build_version` is newer is never retired, and `ensure_running` fails with `DaemonIsNewer` ("daemon is newer … update the client") instead.

`ensure_running` chooses by the caller's own integrity. An ordinary caller looks in the ordinary profile only. An elevated caller first looks in the ordinary profile and reuses a running ordinary daemon whose protocol it speaks, whatever its build: that daemon gives no elevation, and the SSH workaround of starting the desktop daemon first keeps working (info `reusing an ordinary daemon from an elevated client`, fields `port`, `protocol_version`, `daemon_build`; only the native client's log shows it, since `bridge` writes no log). An ordinary daemon it cannot talk to is never retired, and no elevated daemon starts beside it: `ensure_running` fails with "an ordinary rustling-tulip daemon is running that this app cannot talk to; stop it from an ordinary terminal with \"rustling-tulipd shutdown\", then start this app again".

An elevated daemon an earlier release left in the ordinary profile is the caller's own integrity: the elevated caller reads the integrity of the daemon's process, retires it (info `retiring an elevated daemon left in the ordinary profile`, fields `pid`, `port`, `daemon_build`, `config_dir`) and goes on to its own profile. A daemon whose integrity cannot be read counts as ordinary (warn `could not read the integrity of the daemon in the ordinary profile; treating it as ordinary`); one whose pid no process has also reads as ordinary, logged at debug, not as that warning.

Only when no ordinary daemon runs does an elevated caller use its own protected profile (`docs/on-disk.md`, "An elevated daemon's protected profile"; warn `an elevated client may not read the ordinary profile's daemon.json; using its own profile`, field `config_dir`, when it falls back). It creates or checks the protected root first, caches the daemon binary under the profile's `binaries` folder, and starts or reuses the daemon there. It finds the daemon only beside its own exe, never in `target\debug` or `target\release`, and errors when none is there. It hashes the bytes of its first copy and refuses to start a daemon whose template changed since, with "...Start the app again as administrator to use the new build." After a spawn it waits on every profile it may use, and `wait_for_handshake: daemon ready` names the file in its `handshake` field. The start passes `--start-failure-file <path>` naming `<config>/logs/daemon-start-failure-<client pid>-<start>.txt`, under the first config dir the wait watches, where `<start>` counts the starts this client process has made; the client removes the file when the wait ends, either way. A daemon that fails before it writes `daemon.json` ends that wait at once with `the daemon failed to start: <text>`, the daemon's own error chain (warn naming the file).

`rustling-tulipd bridge` starts through `daemon_client::ensure_running_for_bridge`, which differs from `ensure_running` only in where a daemon it must start runs. A reusable daemon already running is reused and the task below is not touched. Otherwise, from an SSH logon (session 0) when the same user has an Active or Disconnected session on the host, it registers (replacing any earlier registration) and runs the scheduled task `\leftos\rustling-tulip\daemon-{user SID}` (`crates/daemon-client/src/logon_task.rs`): run only while the user is logged on, least privilege, hidden, no trigger, no time limit, action `{install dir}\rustling-tulipd.exe --detach`. It waits up to 20 s for that daemon's handshake in the user's ordinary profile and relays to it, so the daemon runs in the user's own logon at their ordinary integrity: sessions run without administrator rights and Credential Manager works (`docs/env-secrets.md`). The task stays registered and is reused; the uninstaller deletes it (`docs/on-disk.md`).

A bridge with any of `RUSTLING_TULIP_CONFIG_DIR`, `RUSTLING_TULIP_BINARIES_DIR`, `RUSTLING_TULIP_WORKTREES_DIR`, `RUSTLING_TULIP_TAILNET_DIR` or `RUSTLING_TULIP_ACCOUNTS_DIR` set never uses the task, since the task's daemon would get the user's logon environment instead (info `an override folder is set; starting the daemon here`), and the task runs at normal priority. If the user has no such session, the task fails, or no daemon appears in 20 s, the bridge starts the daemon directly as `ensure_running` does. A daemon the task starts after the 20 s may then run beside the one the bridge started. The bridge writes no log, so these show only where a log is captured: info `starting the daemon in the user's logon through a scheduled task` (fields `task`, `session`), info `daemon started in the user's logon` (fields `pid`, `port`), warn `could not start the daemon in the user's logon; starting it here` (field `err`), warn `could not read this process's session; starting the daemon here`, warn `could not look for the user's interactive session; starting the daemon here`.

A High SSH user cannot stop that ordinary daemon (it refuses, per the rules above); it idle-exits or is stopped from the desktop.

One locator, `daemon_client::locate_daemon()` (`LocatedDaemon { profile, config_dir }`), picks the `daemon.json` every other caller reads: it looks in the caller's candidate profiles, the ordinary profile first for an elevated caller, and returns the first holding a `daemon.json`; with none it names the caller's own profile. `handshake_file()`, `read_handshake()`, `stop()`, `rustling-tulipd shutdown`, `pair`, `screen`, the session-driving verbs and the bridge's error text all use it, so an elevated caller with no ordinary daemon running names the elevated profile's file. `pair` and `screen` create no folder and, with no daemon, fail on the missing `daemon.json` as before.

An elevated caller may read from an ordinary daemon but never stops it (`daemon_client::may_stop`, error `DaemonIsOrdinary`), judged by the integrity of the daemon's process, not the folder its `daemon.json` is in: `rustling-tulipd shutdown` from an elevated terminal against an ordinary daemon prints `could not stop the daemon: the running rustling-tulip daemon runs without administrator rights; stop it from an ordinary terminal with "rustling-tulipd shutdown"` on stderr and exits 1, and the native client's Stop stops nothing.

A native client's Stop marks This PC's connection stopped before it asks (`Net::stop`), so whatever the outcome the client neither reconnects nor starts a daemon until Restart. When the stop fails (this refusal, no handshake on disk, a listener that is not the daemon's), it shows an error toast titled `Could not stop the daemon` with the reason (`NetEvent::StopFailed`). A socket to a daemon still running stays open, and the flyout keeps its port and pid until the connection reads stopped.

The refusal covers a running ordinary daemon and one whose integrity cannot be read. A `daemon.json` whose pid no process has is stale: an elevated `shutdown` or Stop removes it instead (`profile_of_process` returns `Ok(None)` for such a pid), and `shutdown` prints `no daemon was running; removed a stale daemon.json` and exits 0. An ordinary caller against an elevated daemon gets the refusal above, unchanged. `apply-update` is unchanged: the per-user installer runs at ordinary integrity and retires only the ordinary profile's daemon.

On Windows a retire (`ensure_running`, `rustling-tulipd shutdown`, `apply-update`) or a stop (`daemon_client::stop`, the native client's Stop) force-terminates the pid `daemon.json` names only when that pid is the sole process listening on `127.0.0.1:<port>`, read from the system TCP listener table after the token proof (`crates/daemon-client/src/listener_owner.rs`): every `127.0.0.1` or `0.0.0.0` listener on the port has that pid, and at least one is on `127.0.0.1`. An unreadable table counts as not owned (warn `cannot read which process owns the daemon's listener; not force-stopping it`).

A retire that does not own the listener warns `the pid daemon.json names does not own the proven listener; asking it to shut down only`, still sends the graceful `/shutdown` and waits, and fails with "the daemon (pid {pid}) did not stop after a shutdown request, and its pid does not own the proven listener on 127.0.0.1:{port}, so it was not force-stopped". A stop refuses with "pid {pid} named by {path} does not own the daemon's listener on 127.0.0.1:{port}; nothing was stopped" and keeps `daemon.json`. Other platforms are unchanged.
