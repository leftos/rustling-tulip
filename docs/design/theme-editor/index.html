RT-583 · Theme selector and editor: layout lanes

Pick one lane for the selector and one for the editor. Everything is drawn in the app's real shapes and the Contrast (direction C) palette; each theme preview below is drawn from that theme's own token values, so Paper shows light. The 7 themes: built-ins Contrast (default), Graphite, Paper, High contrast, Dim; user themes Teal night (duplicated from Contrast) and Ember dim (from Dim). The editor lanes edit Teal night, where Subtle was darkened until it fails AA on Popover. Every contrast badge on this page is computed from the hex values shown.

Surface 1 · The selectorbrowse and pick; the window repaints live on hover or keyboard move, and Esc reverts

S1Cards at the top of Settings → Appearance

Good: no new place to learn: Appearance already owns colour, and every theme sits side by side with the accent, background and font overrides right under the grid.

Bad: a card is a 120 px thumbnail, so menus, modals and a real terminal are guessed; the Settings modal covers most of the window, so the live repaint shows only around its edges.

Worst case: after importing 20 themes the grid pushes the overrides and fonts several screens down the page.

S2Its own "Themes" modal: list and a large live preview

Good: a large preview of the whole app (sidebar, menu, panes, footer) at near real size, with room for a contrast summary and the terminal's source before you commit.

Bad: another modal and a new entry point (app menu, Appearance link) to find; the preview is a second drawing of the window that has to be kept in step with it.

Worst case: the preview draws only the main view, so a theme that breaks the diff view or the dashboard looks fine until after "Use".

S3Quick switcher popover from the footer

Good: fastest. Arrow keys repaint the real window, so whatever view is open is the preview, and it works from anywhere without leaving the work.

Bad: no room for actions or details (contrast, terminal source); a small footer item is easy to miss, so it still needs a Settings home; mouse hover repaints the window as the pointer crosses rows.

Worst case: arrowing from Paper to High contrast repaints every window and pop-out on each key, a full light-to-dark flash per press.

Surface 2 · The editoropened by "Duplicate and edit"; editing Teal night (from Contrast)

E1Grouped tokens beside a live mini-preview

Good: every token is findable by name, each text and surface pair carries its badge beside the colour it judges, and the preview draws parts that are rarely on screen (a menu, a modal).

Bad: the user has to know what "Row card" or "Popover edge" means; the preview is small, and the list is long enough to scroll.

Worst case: tuning a token whose only use is in a view the preview does not draw (a diff wash, a toast) gives no feedback except the window behind the modal.

E2Edit in place: the window is the preview, docked inspector

Good: the most direct: click what you see, change it, and judge it at full scale in the real window, with the tokens that element uses listed together.

Bad: only what is on screen can be clicked (Danger, Asking, a modal edge need the "All tokens" list); the docked panel narrows the window being judged; pick mode takes over normal clicks.

Worst case: a token used only by a state you cannot summon on demand (an error toast, a failed spawn) is reachable only through the fallback list, so this lane needs lane E1's list anyway.

E3Two panes: UI tokens | terminal palette, preview strip below

Good: the terminal palette gets first-class room: the 16 colours over real ls, diff and test output is how terminal themes are judged, and the split matches the theme file (UI part, terminal part).

Bad: UI tokens get a compact grid with room only for a fail dot, not a ratio per row; the strip preview is wide but short.

Worst case: in a narrow window the two panes cramp and the 16-colour grid wraps; a UI-only tweak leaves half the editor (the terminal pane) idle.
