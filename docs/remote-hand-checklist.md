# Remote access hand checklist

This checklist verifies remote access over a real tailnet, which the automated tests cannot reach: the live e2e tier (`.\rt.ps1 native-e2e`) runs the real daemon against a fake `tailscale` on loopback, so it never meets a real `tailscale cert`, real `whois` answers, other Tailscale users or a firewall. Likewise its multi-host specs reach the second host through a fake `ssh` on one machine, so section 12 checks several real hosts in one window.

Run it by hand before a release that touches remote access (the daemon's tailnet listener, pairing, devices, the host picker, file fetch or autostart), and note each failure on the release's Linear issue. The design and its rulings are in [plans/remote-access.md](plans/remote-access.md).

## Before you start

- Two Windows PCs, signed in to the same tailnet as the same Tailscale user, both running Tailscale. Below, **the host** is the PC whose sessions are reached, and **the device** is the PC that reaches them.
- HTTPS certificates turned on for the tailnet in the Tailscale admin console (DNS page).
- For section 8: a node of another tailnet user, a tagged node, a node shared across tailnets, and a second Windows account on the host. A node that is not Windows can stand in where a step says `curl`.
- The same build of rustling-tulip on both PCs (the daemon serves only the current protocol version), from `.\rt.ps1 installer` or `.\rt.ps1 build -Release`.
- On the host, the logs to watch: `%APPDATA%\leftos\rustling-tulip\config\logs\daemon.log` and `native.log` beside it.
- `<host>` below is the host's full MagicDNS name without the trailing dot (`box.tail1234.ts.net`), and `<short>` its first label (`box`).

## 1. The Remote access switch on the host

- [ ] Open Settings → Remote access on the host with remote access never turned on. **Expect:** the section `Remote access (Tailscale)`, the switch `Allow remote access over Tailscale` off, and the line `Remote access is off.`
- [ ] Quit Tailscale on the host (system tray → Exit) and turn the switch on. **Expect:** `Tailscale is not running. Start it and remote access connects on its own.`
- [ ] Start Tailscale again without touching Settings. **Expect:** the line passes through `Starting…` and reaches `Serving on your tailnet.` by itself, with `Address: https://<host>:8787` and `Certificate expires in <n> days` under it.
- [ ] Sign out of Tailscale on the host (Tailscale menu → Log out). **Expect:** `Tailscale is signed out or stopped. Sign in to Tailscale to turn remote access on.` Sign in again. **Expect:** `Serving on your tailnet.` returns by itself.
- [ ] In PowerShell on the host, run `Get-NetTCPConnection -LocalPort 8787 -State Listen`. **Expect:** listeners on the host's `100.x.y.z` and `fd7a:115c:a1e0:…` addresses only, never `0.0.0.0` or `::`.
- [ ] Turn the switch off. **Expect:** `Remote access is off.`, the Address and certificate lines gone, nothing listening on 8787, and `daemon.log` showing `tailnet listener closed`. Turn it back on for the next sections.
- [ ] Optional, since it changes the whole tailnet: turn HTTPS certificates off in the admin console and turn the switch off and on. **Expect:** `HTTPS certificates are off for your tailnet. Enable HTTPS in the Tailscale admin console (DNS page).` and nothing listening on 8787. Turn HTTPS back on. **Expect:** serving resumes by itself.
- [ ] Optional: tag the host in the admin console. **Expect:** `This PC is tagged in Tailscale, so it has no owner to admit. Remote access stays down.` Remove the tag. **Expect:** serving resumes.
- [ ] Optional, needs a slow CLI: while serving, make `tailscale whoami` alone take longer than 10 seconds (a wrapper script, named by `RUSTLING_TULIP_TAILSCALE` before the daemon starts, that passes every other subcommand straight through and sleeps on `whoami` only while a flag file exists, so the daemon first comes up serving and `whois` and `cert` stay fast). **Expect:** `Serving on your tailnet.` stays, and the hint `The Tailscale CLI is slow to answer. Remote access keeps serving, and connected devices stay connected.` shows under it, above `Address`. Make the CLI fast again. **Expect:** the hint goes away by itself.
- [ ] Hold the port: with the switch off, run `python -m http.server 8787 --bind <host's 100.x address>`, then turn the switch on. **Expect:** `Port 8787 is in use on this PC's tailnet address. Choose another port.`
- [ ] Type `8788` in the `Port` field and press `Apply`. **Expect:** `Serving on your tailnet.` and `Address: https://<host>:8788`. Type `0` and press `Apply`. **Expect:** `Enter a port from 1 to 65535.` Set the port back to `8787` and stop the Python server.
- [ ] Close the host's window with `Keep sessions running in background` and wait a minute. **Expect:** the daemon keeps running (the hint `While remote access is on, the daemon keeps running when no window is open.`), and `Get-NetTCPConnection -LocalPort 8787 -State Listen` still lists the listeners.

## 2. The certificate

- [ ] In an unelevated PowerShell on the host, as the Windows user that runs Tailscale, run `tailscale cert --cert-file $env:TEMP\t.crt --key-file $env:TEMP\t.key <host>`. **Expect:** exit code 0 and both files written, with no UAC prompt. Delete the two files afterwards.
- [ ] With remote access serving, open `%LOCALAPPDATA%\leftos\rustling-tulip\data\tailnet\`. **Expect:** `<host>.crt` and `<host>.key`, and `daemon.log` showing `tailnet listener: certificate loaded`.
- [ ] On the device, open `https://<host>:8787/` in a browser. **Expect:** no certificate warning: the certificate is a public one for `<host>` (the page itself may be an error, since the listener serves only the client's WebSocket).
- [ ] When the host's certificate line reads `Certificate expires in 14 days` or fewer, leave the daemon running for a day. **Expect:** `daemon.log` shows `tailnet listener: certificate reloaded`, the line jumps back to about 90 days, and connected devices stay connected.

## 3. Pairing the device

- [ ] On the device, press `Connections` in the footer. **Expect:** the `Connections` dialog shows `Looking for your devices…` under `On your tailnet`, then `This PC` (chip `Connected`) and `<host>` among the online peers.
- [ ] Press `+ Add host`, type `box` (a bare label) as the Name in Tailnet mode and press `Add and connect`. **Expect:** `Use the full name, for example box.tail1234.ts.net.` and nothing dialled.
- [ ] Pick the `<host>` row. **Expect:** the host is saved, switched on and connected, and its row's chip reads `Not paired` with `Pair` and `Reconnect now` buttons; no dialog opens by itself.
- [ ] Press the row's `Pair`. **Expect:** the "Pair with `<host>`" dialog opens with `<host> does not know this PC.` and the buttons `Ask to pair` and `Close`.
- [ ] Press `Ask to pair`. **Expect:** the device shows `Approve this PC on <host>.` with an `expires in m:ss` countdown and `Cancel`; the host raises the Windows toast `A device asks for remote access` with `Approve…` and `Deny`, and Settings → Remote access on the host shows `Waiting devices · 1` with the device's name, its Tailscale login and an `m:ss left` countdown.
- [ ] On the device, press `Have a code?` (it is also reachable with Tab). **Expect:** a `6 digits` field with `Pair` and `Cancel` appears under the line and the countdown keeps running. Type `000000` and press `Pair`. **Expect:** `That code is not right.` in the same place as after approval, and the request keeps waiting (the host's Waiting devices row stays).
- [ ] On the host, press `Deny` on the toast. **Expect:** the device ends on `<host> turned this PC down.` with `Ask again` and `Close`, and the host's Waiting devices row is gone.
- [ ] On the device, press `Ask again`. **Expect:** a new toast and Waiting devices row on the host, as above.
- [ ] On the host, press `Approve…` on the toast. **Expect:** the window comes forward with the dialog `Approve <device>`, the line `Approving shows a one-time code for this device.` and `Approve`, `Deny` and `Close`; nothing is sent until `Approve` is pressed.
- [ ] Press `Approve`. **Expect:** the host shows a QR code, a six-digit code such as `735 160`, `or type on the phone` and `expires in m:ss · this request only`; the Waiting devices row reads `Approved · waiting for the device`; the device's dialog moves to `Type the code <host> shows.` with a `6 digits` field and `Pair`.
- [ ] Type a wrong code on the device and press `Pair`. **Expect:** `That code is not right.` under the field. Type the right code and press `Pair`. **Expect:** the dialog closes, the device connects, and the host's row chip reads `Connected`; the host's Waiting devices row is gone.
- [ ] On the host, open Settings → Remote access. **Expect:** the `Devices` section lists the device with `Connected` and a `Block` button.
- [ ] On the host, in a terminal, run `rustling-tulipd pair` (the daemon must be running). **Expect:** `Pairing code: <six digits>` and `Type it on the device's pairing screen within <n> minutes. It works once, for one device.`, and `daemon.log` shows `pairing: a CLI code was minted`. The device types such a code under `Have a code?` while its request waits (section 5), and the phone types it on its pairing screen (see the last section).
- [ ] Close the device's client and open it again. **Expect:** it connects to `<host>` at launch with no Pair dialog, since `native-ui.json` keeps the host in `saved_hosts` (switched on) and the device token is in Credential Manager.

## 4. Driving the host from the device

- [ ] On the device, press `+ Shell` on the host's header in the sidebar and run `hostname`. **Expect:** the host's computer name; the host's window shows the same session in its sidebar.
- [ ] Attach on the device to a Claude session started on the host and type a prompt. **Expect:** the output appears on both PCs, and the session's status moves to Working and back as on the host.
- [ ] On the device, open a session's menu. **Expect:** `Reveal worktree` and `Open in Explorer` are shown disabled, with the tooltip `Not available on a remote host: this opens files on this PC`.
- [ ] On the device, look at the host's sidebar header dot and its `Connections` row. **Expect:** the state shows there, with `Reconnect now` on the row in place of a restart and no Stop; the footer pill and daemon flyout are the device's own (This PC's).
- [ ] On the device, open Settings and choose the host in its `Host` selector. **Expect:** the host's agent pages, launch command, worktrees root and keep-awake mode, and no `Remote access` tab while the host is chosen: it configures This PC only.
- [ ] Close the device's window. **Expect:** the device's own quit flow runs, which concerns the device's daemon only, and the host's sessions keep running.

## 5. Block, forget and pair again

- [ ] With the device connected, press `Block` on its row in the host's `Devices` section. **Expect:** the dialog `Block <device>?` with `Its live connections end now, and it cannot pair again until you forget it.` and `Cancel` and `Block`.
- [ ] Press `Block`. **Expect:** the device's connection drops at once and, on its next connect, the host's row chip on the device reads `Not paired`; the host's row shows `Blocked` with a `Forget` button.
- [ ] On the device, press the host row's `Pair` in `Connections`. **Expect:** "Pair with `<host>`" opens with `<host> no longer accepts this PC's pairing.`
- [ ] Press `Ask to pair`. **Expect:** `<host> did not accept this PC's request.` with `Ask again` and `Close`; the host raises no toast and shows no Waiting devices row.
- [ ] On the host, press `Forget` on the blocked row. **Expect:** the row is gone (`No device has paired yet.` when it was the only one).
- [ ] On the host, run `rustling-tulipd pair`. On the device, press `Ask again`, then `Have a code?`, type the printed code and press `Pair`, without approving on the host. **Expect:** the dialog closes and the device pairs and connects, and the host's Waiting devices row is gone.
- [ ] Block and forget the device again, then on the device press `Ask again` and approve on the host as in section 3. **Expect:** the device pairs and connects, and the host's `Devices` row reads `Connected` again.
- [ ] Close the device's client and look at the host's row. **Expect:** `Last seen just now`, and later a longer `Last seen` time.

## 6. Turning remote access off while connected

- [ ] With the device connected, turn the host's switch off. **Expect:** the device's connection drops at once and the host's sidebar header reads `Offline` and then `Connecting…` as it retries, its rows dimmed and the device's own sessions unaffected; nothing listens on 8787.
- [ ] With the device still connected, look at the host's Settings → Remote access `Devices` section as the switch goes off. **Expect:** the device's row stops saying `Connected` without reopening Settings.
- [ ] Turn the host's switch back on. **Expect:** the device reconnects by itself, with no Pair dialog.
- [ ] Change the host's port to `8788` and `Apply` while the device is connected. **Expect:** the device drops and keeps retrying 8787. On the device, add `<host>` with Port `8788` under `+ Add host` (Tailnet). **Expect:** it connects. Set the host's port back to 8787 afterwards.

## 7. A device removed from the tailnet

- [ ] With the device connected and a shell running on it, remove the device (or expire its key) in the Tailscale admin console and time how long the host's sidebar header keeps its online dot and the host's row keeps showing `Connected`. **Expect:** both drop; record the seconds each took on the release issue. Add the device back to the tailnet afterwards.

## 8. Peers that are refused

- [ ] Open Tailscale's IP address doc (kb/1033) and compare the ranges it gives with `in_tailscale_range` in `crates/tailnet/src/rule.rs`. **Expect:** the doc states `100.64.0.0/10` and `fd7a:115c:a1e0::/48`, as the code does.
- [ ] From a node of another Tailscale user in the same tailnet, dial the host (the client's `+ Add host` with `<host>`, or `curl -v https://<host>:8787/`). **Expect:** the connection is dropped before TLS: the client never reaches the Pair dialog, `curl` fails in the handshake rather than receiving an HTTP status, and `daemon.log` shows `tailnet listener: peer refused by the owner rule` with `reason=peer node belongs to another Tailscale user`.
- [ ] From a tagged node (`tailscale up --advertise-tags=tag:<tag>`), dial the host the same way. **Expect:** dropped the same way, with `reason=peer node is tagged`.
- [ ] Share the host to another Tailscale account (admin console → Share) and dial it from that account's node. **Expect:** dropped the same way; record which reason the log gives (`peer node belongs to another Tailscale user`, `peer node is shared in by another user` or `peer node is a sharee node`).
- [ ] With a node shared into the tailnet from another account, open `Connections` on the device. **Expect:** that node is not listed, and no tagged or offline node is either.
- [ ] Sign in to the host as a second Windows account, open the client there and add `<host>` under `+ Add host`. **Expect:** dropped, with `reason=peer is the host node itself` in the first account's `daemon.log`.
- [ ] In that second account, open Settings → Remote access and turn the switch on. **Expect:** `Tailscale belongs to another Windows user or runs in server mode.` Turn it off and sign out of the account.
- [ ] After each refused dial, check the host's Settings. **Expect:** no toast and no Waiting devices row: a refused peer never reaches pairing.

## 9. Firewall and login launch

- [ ] In Fort Firewall on the host, allow the folder `%LOCALAPPDATA%\leftos\rustling-tulip\data\binaries\` rather than one exe. **Expect:** the device connects.
- [ ] Rebuild and restart the host's daemon (`.\rt.ps1 restart`, which runs a new content-addressed copy from that folder). **Expect:** the device reconnects with no new Fort Firewall prompt or rule, and no Windows Defender Firewall rule is needed.
- [ ] On the host, turn on `Start the daemon when I log in` (hint `So remote access works before you open this app.`). **Expect:** the switch stays on, and `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` holds `rustling-tulip-daemon` naming the daemon with `--detach`.
- [ ] Sign out of Windows on the host and sign in again, without opening the client. **Expect:** `logs\autostart.log` is rewritten, a `rustling-tulipd` process runs, and the device connects and lists the host's sessions.
- [ ] Turn the switch off. **Expect:** the `rustling-tulip-daemon` Run value is gone.

## 10. Fetched files from a remote repo

- [ ] On the device, connected to the host, Ctrl+click a path such as `src/main.rs:42` in a terminal of a session in a registered repo. **Expect:** the toast `Fetching main.rs from <host>`, then the file opens at line 42, saved under `%LOCALAPPDATA%\leftos\rustling-tulip\data\remote-files\<host>\<repo-name>\src\main.rs`.
- [ ] Open the sidebar's ⋯ menu → `Fetch file…`. **Expect:** the `Fetch file` dialog with the hint `Relative to <repo>. Add :line to open at a line.` and the placeholder `src/main.rs:42`; a fetch shows `Waiting for <host>…`, then its progress, and opens the file.
- [ ] Fetch an `.html` page in that repo whose images and stylesheet sit in relative folders. **Expect:** `Fetching <page> and its media (n of m)`, which goes when the page opens, and the page opens with its images and styles, each file saved at its repo-relative place under the same folder.
- [ ] Fetch a page that names a missing image. **Expect:** `Some of <page>'s media didn't load`, and the page still opens.
- [ ] Start a large page fetch and turn the host's switch off mid-fetch. **Expect:** `Couldn't fetch <page>'s media` with `The connection was lost.`, the page does not open, and no `.fetch-*.part` file is left beside the targets.

## 11. The SSH bridge on a Windows host

These need Windows OpenSSH Server running on the host and key login from the device (`ssh <host> echo ok` works with no prompt).

- [ ] Install with the installer, then open a new SSH session: `ssh <host> where rustling-tulipd`. **Expect:** `%LOCALAPPDATA%\Programs\rustling-tulip\rustling-tulipd.exe`, and `HKCU\Environment\Path` on the host keeps its other entries unexpanded and its value kind.
- [ ] With no daemon running on the host, from the device: `echo {"type":"hello","protocol_version":25,"protocol_versions":[25],"auth_token":""} | ssh -T <host> rustling-tulipd bridge`, with the host's current protocol version. **Expect:** a `welcome` line, the host's initial state one message per line, and the command back at the prompt about 5 s later.
- [ ] Within 30 s of that, on the host: `Get-Process rustling-tulipd-*`. **Expect:** the daemon the bridge started is still running once the SSH session has ended, and so are any `rt-tracer-*` of the sessions it hosts; with no session and no client it exits by itself 30 s after the client left (`idle for the full grace period` in `daemon.log`).
- [ ] Run setup again and pick another folder. **Expect:** the old folder is gone from the user PATH and the new one is on it.
- [ ] Uninstall. **Expect:** the install folder is gone from the user PATH and every other entry is as it was.
- [ ] From the native client on the device, open Connections, press `+ Add host`, switch to SSH, type the host and press Test connection. **Expect:** `Connected: <short name>`; then press `Add and connect`. **Expect:** the client connects the host beside This PC with no pairing prompt, and its row reads `SSH · …` and never `Not paired`.
- [ ] In the same form, test a host whose key the device's ssh does not offer or the host does not authorize. **Expect:** ssh's own `Permission denied (publickey).` text under the form, and no row added until you press `Add and connect`.

## 12. Several hosts in one window

These need the device paired with the tailnet host (section 3) and the SSH host reachable by key login (section 11), so that This PC, one tailnet host and one SSH host are all saved and switched on.

- [ ] Open the client on the device. **Expect:** the sidebar's Repos view groups by host under a header each: This PC, then the SSH host and the tailnet host in saved order, each with a state dot and a `+ Shell` button.
- [ ] Press `+ Shell` on each header in turn and run `hostname` in each. **Expect:** each shell shows its own host's computer name, and each lands in a pane whose header carries the host's chip (none for This PC).
- [ ] Drag a remote session's sidebar leaf into a tab that holds a This PC pane, then drag the other host's leaf into the same tab. **Expect:** one tab with panes of two or three hosts, its pill showing no host chip, and typing in each pane reaching only its own host.
- [ ] Kill one host's connection (turn the tailnet host's remote access off, or end the SSH host's `ssh` process). **Expect:** only that host's header reads `Offline`, its rows and panes dim with their last frame frozen, and the other hosts' panes keep working.
- [ ] Bring that host's connection back. **Expect:** the header returns to online, the panes resume with no pane rebuilt, and nothing was pruned from the tab.
- [ ] Save the tailnet host a second time as an SSH alias that reaches the same machine, with the SSH name saved after it. **Expect:** the later row's chip reads `Same daemon as <short>`, and only the first-saved host shows the sessions.
- [ ] Press `Forget` on the owner of such a pair. **Expect:** the tab's panes of that machine stay and move to the remaining name instead of closing.
- [ ] Restart the client with a remote pane popped out. **Expect:** the pop-out reopens once that host's session list arrives.
- [ ] Press `Forget` on a host that has panes in a tab and no other name. **Expect:** its panes leave the tab and its rows leave the sidebar.

## 13. The iPhone

These need an iPhone on iOS 16.4 or later with Tailscale signed in as the same Tailscale user, the host serving (section 1), and the build's `pwa` folder installed beside the daemon (`.\rt.ps1 installer`, or `.\rt.ps1 build -Pwa`). The steps are described for a user in [phone-app.md](phone-app.md). `<host>` is the host's MagicDNS name, as above.

- [ ] In Safari on the iPhone, open `https://<host>:8787/`. **Expect:** the page loads with no certificate warning. Tap Share, then Add to Home Screen, and open the app from its icon. **Expect:** it opens standalone, with no Safari address bar or toolbar.
- [ ] In the Home Screen app, tap `Ask to pair`. On the host, press `Approve…` on the toast, then `Approve`, and scan the QR code with the phone. **Expect:** the phone says `Paired. Connecting…` and then Home opens; the host's `Devices` section lists the phone as `Connected`.
- [ ] On the host, press `Forget` on the phone's row (`Block` it first if the row has no `Forget`). **Expect:** the phone shows the pairing screen. Tap `Ask to pair`, approve on the host and type the six digits under `Six-digit code` instead of scanning. **Expect:** it pairs and Home opens.
- [ ] Forget the phone again, tap `Ask to pair`, run `rustling-tulipd pair` on the host and type the printed code on the phone without approving. **Expect:** it pairs and Home opens, and the host's Waiting devices row is gone.
- [ ] Look at Home. **Expect:** the host's sessions are listed, grouped as in the desktop sidebar. Start a Claude session on the host and leave it waiting on a prompt. **Expect:** it appears in the `Needs you` tray; answer it from the tray. **Expect:** the answer reaches the session on the host.
- [ ] Tap Home's `Notifications` button and turn `Allow notifications` on. **Expect:** iOS asks for permission once, and `Needs you`, `Finished` and `Hold while I'm at my computer` appear on. Turn `Finished` off, tap `Done`, close the app and open it again, then reopen the panel. **Expect:** the switches stand as set, and iOS does not ask again.
- [ ] Turn `Hold while I'm at my computer` off, lock the phone and leave a session waiting on the host. **Expect:** a push arrives on the Lock Screen at once. Tap it. **Expect:** the app opens on that session's screen.
- [ ] Turn Tailscale off on the phone and leave another session waiting. **Expect:** the push still arrives, since Web Push goes through Apple; Tailscale on the phone is needed to open the app, not to receive the push. Turn Tailscale back on.
- [ ] Turn `Hold while I'm at my computer` on. On the host, keep the app's window focused and type in it, and leave a session waiting. **Expect:** no push arrives. Stop typing for 3 minutes, or focus another window. **Expect:** the held push arrives. Repeat with the switch off. **Expect:** the push arrives at once.
- [ ] Turn `Finished` on and let a session's turn end. **Expect:** a Finished push arrives. Turn `Finished` off and let another turn end. **Expect:** none arrives.
- [ ] Leave two sessions waiting. **Expect:** the Home Screen icon's badge reads 2. Answer both. **Expect:** the badge clears; note whether it clears at once or only when the app is next opened.
- [ ] Delete the Home Screen app, add it again from Safari, pair, and turn `Allow notifications` on. **Expect:** a waiting session pushes to the new install only, and `subscriptions.json` in the daemon's `push` folder (`docs/on-disk.md`) holds one subscription for the phone, with the new endpoint in place of the old one.
- [ ] On the iPhone, open Settings → Safari → Advanced → Website Data and remove `<host>`. Open the Home Screen app. **Expect:** it asks to pair again; after approving, Home and the notification switches work.
- [ ] On the host, press `Block` on the phone's row. **Expect:** the phone's connection ends and a waiting session sends it no push. Press `Forget`, pair again and turn `Allow notifications` on. **Expect:** the connection and the pushes come back.
- [ ] Open a session from Home, type in the composer and tap `Send`. **Expect:** the text reaches the session. Send one reply each from `Keys` and `Quick`. **Expect:** each reaches the session. Raise a prompt. **Expect:** the prompt sheet shows numbered buttons and an answer reaches the session. Tap `Terminal`. **Expect:** the terminal shows the session with its key bar; `Chat` returns to the chat. **Expect:** with the on-screen keyboard up, the composer stays visible above it.
- [ ] Ask Claude in a session for an answer with a heading, a list, a table, inline code (one long enough to need more than a line) and a fenced code block. **Expect:** each shows rendered, not as raw Markdown; the table and the code block scroll sideways on their own while the page stays put, and the long inline code wraps. Your own message and the tool rows stay plain.
- [ ] On a session's screen, tap the composer so the keyboard opens. **Expect:** the header (Back and the session's name) stays on screen above the chat, and the composer sits just above the keyboard. Dismiss the keyboard. **Expect:** the screen fills the display again.
- [ ] With a session's screen open, turn Remote access off on the host. **Expect:** a red `Reconnecting…` bar shows under the header. Turn it back on. **Expect:** the bar goes away once the connection is open. Tap `Send` while the connection is down. **Expect:** the bar can read `Offline` after the refused send.
- [ ] On a host with no sessions, open Home. **Expect:** it says `No sessions`. Start one. **Expect:** the line goes away and the session is listed.
- [ ] Open the page in a Safari tab, not the Home Screen app. **Expect:** `Open this page from your Home Screen to finish setting up.` shows until Home appears. Open the Home Screen app. **Expect:** that line shows on no screen.

## 14. The native iPhone app's push

These need the phone app from TestFlight on an iPhone with Tailscale signed in as the same Tailscale user, paired with the host, and a host daemon that lists `relay_push` (one built from the release that ships it, or `.\rt.ps1 restart` from a checkout with the installed app's window closed). The phone registers with `Hold while I'm at my computer` on, so each step that waits for a push first focuses another window on the host.

- [ ] Open the app and tap `Settings`, then `Notifications`. **Expect:** a `Notifications` switch for the host. Turn it on. **Expect:** iOS asks for permission once; after `Allow` the switch stays on with no text under it, and `daemon.log` logs `push: the device's subscription was stored`.
- [ ] On Settings' `Notifications` page, look below the host switches. **Expect:** a `Finished alerts wait` row with five choices, `None`, `2 s`, `5 s`, `10 s` and `20 s`, the current one filled. Pick `20 s`, then finish a turn on the host. **Expect:** the Finished notification arrives about 20 s after the session goes idle.
- [ ] With a host whose notifications have a problem (for example turn notifications off in iOS Settings for the app, then open the app). **Expect:** Home's `Settings` button and the Settings list's `Notifications` row show an amber dot, and it goes once the problem is fixed.
- [ ] Lock the phone and leave a session waiting on the host. **Expect:** a push on the Lock Screen naming the session, not `A session changed. Open the app to see it.` (the fallback alert, which means the notification extension did not run or could not decrypt), and the app icon's badge equal to the number of sessions in Needs you.
- [ ] Tap the push. **Expect:** the app opens on that session's screen on that host.
- [ ] Force-quit the app in the app switcher, then tap the push for a session waiting on the host. **Expect:** the app launches onto that session's screen on that host, not Home, once the host's list arrives.
