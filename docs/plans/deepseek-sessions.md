# Claude sessions on DeepSeek

The user runs Claude Code on DeepSeek with `~/.claude/bin/claude-deepseek.ps1`: it reads `DEEPSEEK_API_KEY` (process environment, else the Windows user scope), clears `ANTHROPIC_API_KEY`, and sets `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`, `ANTHROPIC_AUTH_TOKEN=<key>`, `ANTHROPIC_MODEL` and every `ANTHROPIC_DEFAULT_{FABLE,OPUS,SONNET,HAIKU}_MODEL` to `deepseek-flash`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `CLAUDE_DEEPSEEK_SESSION=1`. The `dispatch` skill's backend table (`~/.claude/skills/dispatch/scripts/dispatch/dispatch/backends.py`) holds the same routing for headless runs. This subplan makes rustling-tulip spawn such sessions itself: a **provider** on Claude sessions, chosen in the spawn dialog, carried through every path that respawns a session, and shown as a chip. Index line: [MAIN.md](./MAIN.md), "Claude sessions on DeepSeek". Step ids are `DK.n`, and the chip reads `DeepSeek`: `DS` is taken by [dispatch-follow.md](./dispatch-follow.md)'s dispatch leaf tag, and `DF.n` by its steps.

## Rulings

- **A provider on Claude sessions (user).** Anthropic or DeepSeek, as an additive field on the spawn request, `SpawnConfig` and `SessionSnapshot`, with a serde default of Anthropic and a `#[serde(other)] Unknown` on the enum. Not a new `Agent` variant: `Agent` has no unknown fallback, and protocol 22 must keep decoding for the installed Tauri app (CLAUDE.md "When to bump", `cargo test -p protocol v22_compat`). The daemon adds the routing variables at spawn from a built-in provider table in code, not user-editable, merged with `extra_env` (precedence below).
- **Key (user).** `DEEPSEEK_API_KEY` from the daemon's process environment, else the Windows user scope (`HKCU\Environment`), read at each spawn. A missing key refuses the spawn with an error naming the variable, never a value. The key is never written to `meta.json`, history, logs, `state.json` or the wire: it goes only into the child's environment at spawn, never into the stored config.
- **Carry-over (user).** The provider is saved in the spawn config and the session history, so Recover, Restart and the sidebar's Resume stay on DeepSeek; Duplicate, the Shift-duplicate prefill (P4.12c) and Launch last copy it; a visible `DeepSeek` chip on the leaf and the pane header; a default provider in Settings → Spawn defaults.
- **Timing (user).** Queued after Petal (Wave 1); the chip and the dialog row use Petal's tokens and the P4.12 / PT.6 / PT.8b layouts.
- **Claude only (orchestrator).** The provider applies to Claude sessions, interactive and headless. The dialog hides it for Codex, Cursor and Plain shell, and the daemon refuses a non-Anthropic provider on a plain shell.
- **Precedence (orchestrator).** The routing keys that choose the endpoint and the credential are locked: `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_DEEPSEEK_SESSION` and `DEEPSEEK_API_KEY`. A DeepSeek spawn whose `extra_env` names one is refused ("`ANTHROPIC_BASE_URL` is set by the DeepSeek provider; remove it from the environment rows"). The tuning keys (the five model variables, `CLAUDE_CODE_MAX_CONTEXT_TOKENS`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`) are defaults that an `extra_env` row overrides. Worst case: a row setting `ANTHROPIC_MODEL` to a Claude model id on a DeepSeek session gets an unknown-model error from DeepSeek on the first turn, shown in the terminal. The alternatives are Open question 2. Anthropic sessions keep today's behaviour: `extra_env` overrides the keep-list.

## Design

### What the code does today (measured)

- `AgentOptions::Claude { permission_mode }` (`crates/protocol/src/lib.rs`) rides on `SpawnRequest`, `SpawnConfig` and `PresetEntry`. `SpawnConfig::from_request`, `to_clone_request` and `to_duplicate_request` copy `agent_options` verbatim, and history's `claude_request` (`crates/daemon/src/history.rs`) replays `config.to_clone_request()`. A field inside the Claude variant is therefore carried by Restart and Duplicate (`DuplicateSession` → `to_duplicate_request`), the sidebar's Resume (`resume_abandoned` → `to_clone_request`), Recover (`claude_request`), Launch last (`RepoEntry.last_spawn_config` in `state.json`), presets and `GetSpawnConfig` / `SpawnConfigReply` without new plumbing.
- `extra_env` is persisted verbatim: in `SpawnConfig` (which goes into `meta.json` through `orphan::meta_from_record`, into `history/<id>.json` as `spawn_config`, and into `state.json` as `last_spawn_config`) and on the wire in `SpawnConfigReply`. The routing therefore never passes through `extra_env` or `SpawnConfig`; it is built after `SpawnConfig::from_request` has captured the stored config.
- PTY sessions: `tracer_client::tracer_command` builds a `std::process::Command` with no `env_clear`, so the tracer inherits the daemon's whole environment and `spec.env` only overrides it; the tracer forwards its own environment to the child (`crates/tracer/src/supervisor.rs`), logging only `forwarded_env_count`. `ANTHROPIC_API_KEY` in the daemon's environment therefore reaches every PTY child today, and clearing it needs an explicit `env_remove`. Headless sessions (`headless.rs`) call `env_clear` and pass only `merged_env`, whose keep-list (`passthrough_env` in `server.rs`) includes `ANTHROPIC_API_KEY`.
- `PtySpawnSpec` (`pty.rs`) and `HeadlessSpec` (`headless.rs`) derive `Debug` over `env`. Nothing logs them today (the spawn logs print `args` only), but one `?spec` would print the key.
- Cost: only headless Claude sessions report cost, from the CLI's own `total_cost_usd` in the stream-json `result` (`agents/claude.rs`), a client-side estimate at Anthropic list prices; the native headless view shows it as COST (`headless_view.rs`). Interactive sessions report no tokens or cost. Nothing in the repo prices a jsonl itself. Spoken alerts' Dashboard header (SA, not built) plans to sum `metrics.cost_usd`.
- Status, hook status ([hook-status.md](./hook-status.md)) and subagent streams read the Claude Code TUI, its hooks and its jsonl under `~/.claude/projects`, which are the same whichever endpoint the CLI calls; `CLAUDE_CONFIG_DIR` is unchanged, so a DeepSeek conversation's jsonl lands where `claude --resume` and the recover dialog look.
- No registry code exists in the daemon today; `windows` 0.61 is already a dependency (features `Win32_Foundation`, `Win32_System_Power`, `Win32_System_RestartManager`).

### Protocol

- `ClaudeProvider { Anthropic (default), DeepSeek (#[serde(rename = "deepseek")]), #[serde(other)] Unknown }`, with `as_label()` (`anthropic` / `deepseek`) and `display()` (`Anthropic` / `DeepSeek`).
- `AgentOptions::Claude { permission_mode, #[serde(default, skip_serializing_if = "ClaudeProvider::is_anthropic")] provider }`. Skipping the default keeps every Anthropic message, `state.json` and sidecar byte-identical to today. `AgentOptions::claude(permission_mode)` builds the Anthropic variant, and `AgentOptions::claude_provider()` returns the provider (Anthropic for Codex and Cursor). The field lives inside the Claude variant rather than beside `agent_options`, so a Codex or Cursor spawn cannot carry one and every carry path above gets it for free.
- `SessionSnapshot.claude_provider: ClaudeProvider` with `#[serde(default)]`, derived in `SessionRecord::snapshot` from `spawn_config` the way `elevated_authority` is; a record with no spawn config reports Anthropic.
- Protocol 22: the Tauri app ignores the new fields; a v22 `SpawnSession` without `provider` decodes as Anthropic. The Tauri app's own Launch last re-sends the `SpawnConfig` it decoded, which has dropped the provider, so a DeepSeek config relaunched from the Tauri app runs on Anthropic; its Duplicate, Restart and Resume go through the daemon and keep it. The Tauri app is being retired, so this is stated and not fixed.
- Not a protocol bump: additive fields and a new enum with an unknown fallback.

### Daemon: provider table and environment

- New `crates/daemon/src/agents/providers.rs` holds the table: for `DeepSeek`, the key variable `DEEPSEEK_API_KEY`, the variables to remove (`ANTHROPIC_API_KEY`), the locked variables to set (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` = the key, `CLAUDE_DEEPSEEK_SESSION=1`) and the tuning defaults (the five model variables on `deepseek-flash`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`). Anthropic has no entry: its spawns are built exactly as today.
- `spawn_env(extra_env, provider, resolve_key) -> Result<SpawnEnv, SpawnFailure>` returns `SpawnEnv { set: Vec<(String, String)>, remove: Vec<String> }`: the keep-list, then the tuning defaults, then `extra_env`, then the locked variables, with the removed variables dropped from `set` and listed in `remove`. It refuses an `Unknown` provider ("this daemon does not know the requested Claude provider"), a locked key in `extra_env`, and a missing key.
- `spawn_session` (`server.rs`) calls it right after the standalone and pin checks and before any git work, so a refused spawn leaves no branch or worktree behind. `SpawnArgs.extra_env` becomes `SpawnArgs.env: SpawnEnv`. `spawn_interactive_session` and `spawn_headless_session` use it; `spawn_plain_shell_session` refuses a non-Anthropic provider as it refuses a `permission_mode`.
- `PtySpawnSpec` gains `env_remove: Vec<String>`, which `tracer_command` applies with `Command::env_remove`, so the inherited `ANTHROPIC_API_KEY` never reaches the tracer or its child. Headless needs no removal (it clears the environment), only the dropped entry.
- `PtySpawnSpec`, `HeadlessSpec` and `SpawnEnv` get hand-written `Debug` impls that print variable names and never values.
- The refusal is a `spawn_plan::SpawnFailure`, sent through the existing `send_spawn_failure` as `ActionFailed` with the request's `request_id`: title "Couldn't start the DeepSeek session", detail "DEEPSEEK_API_KEY is not set in the daemon's environment or in the Windows user environment (HKCU\Environment).", hint "Set it with `setx DEEPSEEK_API_KEY <key>`; the next spawn reads it, no restart needed." Recover shows the same detail on the item, and Restart and Resume on their existing failure path.

### Key resolution

- New `crates/daemon/src/user_env.rs`: `Secret` (a `String` newtype with no `Display`, no `Serialize` and a `Debug` that prints `Secret(<redacted>)`, exposing its text only through `expose()` to `spawn_env`), and `resolve(name) -> Option<(Secret, Origin)>`, with `Origin { Process, UserScope }` so a log line can say where the key came from without its value. An empty value counts as unset. On Windows the user scope is read with `RegGetValueW(HKEY_CURRENT_USER, "Environment", name, RRF_RT_REG_SZ | RRF_RT_REG_EXPAND_SZ)` (expanded), which needs only the `Win32_System_Registry` feature on the `windows` 0.61 dependency, no new crate; elsewhere, the process environment only. `resolve_with(name, process, user_scope)` takes both lookups as closures so tests never touch the real registry.
- Spoken alerts' SA.2 ([spoken-alerts.md](./spoken-alerts.md), Wave 7) plans the same env-then-`HKCU\Environment` `KeySource` resolution and a redacting key type. This item lands first (it follows Wave 1; SA is Wave 7), so it adds the small shared helper above, and SA.2 calls `user_env::resolve` and reuses `Secret` instead of writing its own; the landing commit adds that note to SA.2's line.
- The key lives in the daemon's memory for the length of one spawn, then in the tracer's and the child's environment, as it does under `claude-deepseek.ps1`. Any same-user process can already read a process's environment, so this adds no exposure beyond the script's.

### Persistence

- Stored: the provider, inside `SpawnConfig.agent_options`, in `meta.json`, `history/<id>.json`, `state.json`'s `last_spawn_config` and presets. Never stored: the key or any routing variable, since they are built after `SpawnConfig::from_request` and live only in `SpawnEnv`.
- Scrollback: the terminal's own output is stored as today; Claude Code does not print its token, and the live-tier fake prints only a hash.
- Imported history entries (tracer-log backfill, for sessions whose daemon died before recording them) have no spawn config and so no provider; Open question 5 decides whether they recover on DeepSeek.

### Native client

- **Spawn defaults:** `SpawnDefaults.claude_provider` (`sidebar.rs`, saved in `native-ui.json` as `spawn.claude_provider`; an older file or an unknown value loads as Anthropic) and a "Claude provider" `choice_row` (Anthropic / DeepSeek) in Settings → Spawn defaults under "Claude approval mode", with its `SettingsControl` and focus-ring stop. It is not locked by Trusted launch, which says nothing about the endpoint.
- **Spawn dialog:** a "Provider" segmented row (Anthropic / DeepSeek) directly under Runtime, shown only for the Claude runtime; not in Advanced, because it decides which account is billed and a hidden choice seeded from a default could spend on the wrong one unnoticed. `SpawnForm` keeps the choice across runtime switches like the Advanced values, seeds it from the Spawn defaults, and takes it from a prefill (Launch last's `last_spawn_config` today, P4.12c's Shift-duplicate once it lands) that beats the defaults. `agent_options()` sends it only for the Claude runtime. When DeepSeek is chosen, the Model field's placeholder reads `deepseek-flash`. It uses PT.8b's field and segmented-control layout, with `Control::Provider(ClaudeProvider)` in the focus ring after the runtime buttons.
- **Chip:** `DeepSeek` in Petal's chip style (PT.7: 20 px, 5 px radius, Geist Mono 11 px at 400), on `CHIP` with `TEXT_2` text, no new token (PT.2 froze `palette.rs`): on the pane header after the runtime chip (`grid_view.rs` `header_parts`, tooltip "Claude Code routed to DeepSeek"), and on the leaf in PT.6b's chip row (Comfortable) or inline (Compact). The runtime tag stays `claude` in its runtime colour. The leaf's hover tooltip gains a "Provider: DeepSeek" line. Tab pills are Open question 3. An `Unknown` provider shows a `provider?` chip, so a session a newer daemon routed elsewhere is never shown as plain Anthropic.
- Headless DeepSeek sessions: Open question 4 settles the COST cell.

## Glossary terms this subplan coins

- **Claude provider**: the service a Claude session's `claude` CLI talks to, Anthropic (the default) or DeepSeek, chosen per spawn and kept by every respawn; not an agent.
- **Provider table**: the daemon's built-in, not user-editable list of the environment variables each non-Anthropic provider sets, removes and locks (`crates/daemon/src/agents/providers.rs`).
- **Routing variables**: the `ANTHROPIC_*` and `CLAUDE_*` environment variables that point Claude Code at another endpoint, credential and model; built at each spawn, never stored.
- **Locked key**: a routing variable choosing the endpoint or the credential, which a session's environment rows may not set; a spawn that tries is refused.
- **DK.1**: step ids in `deepseek-sessions.md` (DeepSeek Claude sessions), distinct from dispatch-follow's `DF` steps and `DS` leaf tag.

## Open questions

Answered (user): Q1 (a) a DeepSeek entry recovers as Claude only; Q2 (a) endpoint and credential keys locked, tuning keys overridable; Q3 (a) no marker on tab pills; Q4 (a) cost shown as `—` for DeepSeek headless sessions and left out of the Dashboard sum; Q5 (a) DeepSeek spawns pass `--model`, and the importer infers the provider from it; Q6 (a) `deepseek-flash` only, the Model field free text.

1. **Recover as shell for a DeepSeek entry.** Today it types `claude --resume <id>` into a plain shell, which would resume the conversation on Anthropic.
   - (a) Recommended: for a DeepSeek entry the dialog offers Recover as Claude only (the shell choice disabled, with "DeepSeek sessions recover as Claude"). Worst case: a user who wanted a shell around the resumed conversation opens one beside it.
   - (b) The recovered shell gets the routing variables in its own environment, so the typed command runs on DeepSeek. Worst case: every `claude` the user later runs in that shell also goes to DeepSeek, and `$env:ANTHROPIC_AUTH_TOKEN` shows the key in that shell.
   - (c) Leave it: the shell resumes on Anthropic. Worst case: a conversation silently switches provider and bills the Anthropic account.
2. **Precedence between the provider and `extra_env`.**
   - (a) Recommended (the design above): endpoint and credential keys locked and refused in `extra_env`; tuning keys overridable. Worst case: an Anthropic model id in a row fails the first turn with a DeepSeek error.
   - (b) Provider wins on every key it sets, silently. Worst case: a user's `ANTHROPIC_MODEL=deepseek-pro` row is ignored and they cannot tell why.
   - (c) `extra_env` wins on every key. Worst case: a stale `ANTHROPIC_BASE_URL` row sends the DeepSeek key to another host.
3. **The chip on tab pills.**
   - (a) Recommended: no; tab pills stay 9 px glyph plus label, and the leaf and pane header carry the chip. Worst case: in the Tabs view a DeepSeek session is known only by opening it or hovering its leaf.
   - (b) A small `DS`-free marker (a 6 px `TEXT_2` dot) on the pill. Worst case: one more mark on the densest element, easily confused with the status glyph.
4. **Cost for DeepSeek headless sessions.** The CLI's `total_cost_usd` is its own estimate at Anthropic prices, so it is wrong for DeepSeek (by how much is unmeasured).
   - (a) Recommended: the client shows COST as `—` with a tooltip for DeepSeek sessions, and SA's Dashboard sum skips them. Worst case: no spend figure for DeepSeek headless runs in the app.
   - (b) A DeepSeek price in the provider table, and the daemon computing cost from the stream's token counts. Worst case: a hard-coded price that goes stale without anyone noticing.
   - (c) Show the CLI's number as is. Worst case: a confidently wrong dollar figure.
5. **Imported history entries (tracer-log backfill) have no provider.**
   - (a) Recommended: the DeepSeek spawn always passes `--model deepseek-flash` (or the chosen model) on the command line, which the tracer log records; the importer maps a model named in the provider table to that provider, stored as a new `HistoryEntry.provider` (additive, skipped when absent), and `folder_claude` uses it. Worst case: a DeepSeek session run on a model not in the table imports as Anthropic and its recovery fails on an unknown conversation or model, visibly.
   - (b) The tracer logs the names (never values) of a fixed set of marker variables it sees in its own environment, such as `CLAUDE_DEEPSEEK_SESSION`, and the importer reads that. Worst case: a change to the tracer, a separately cached binary, for a rare path.
   - (c) Leave them Anthropic. Worst case: after a daemon crash, recovering a DeepSeek session resumes it on Anthropic and bills that account.
6. **Models on offer.**
   - (a) Recommended: `deepseek-flash` only, as the script does; the Model field stays free text for anyone who wants another DeepSeek model. Worst case: a user types a model id DeepSeek does not serve and sees the error on the first turn.
   - (b) The table lists DeepSeek's models and the dialog offers them as choices when DeepSeek is picked. Worst case: a list in code that goes stale when DeepSeek renames models.

## Findings outside this item

- `extra_env` is persisted verbatim in `meta.json`, `history/<id>.json`, `state.json` (`last_spawn_config`) and returned by `SpawnConfigReply`, and `SpawnRequest.extra_env`'s own doc comment suggests overriding `ANTHROPIC_API_KEY` there: any secret a user types into the environment rows is stored in plain text and sent to every client that asks. This design keeps the DeepSeek key out of it, but the general case is its own item for the orchestrator to put to the user.
- PTY children inherit the daemon's whole environment (no `env_clear` in `tracer_command`), so `passthrough_env`'s keep-list only governs headless sessions; the comment in `crates/tracer/src/supervisor.rs` says the daemon populated the tracer "with the passthrough keep-list", which is not what happens. A docs-drift line for the orchestrator.
