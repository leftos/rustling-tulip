# Recover Codex and Cursor sessions as their own agent

Design for the "Recover brings a Codex or Cursor session back as Claude" line in [MAIN.md](./MAIN.md). Found while drafting [reboot-resume.md](./reboot-resume.md#findings-outside-this-item). Builds on session recovery (`crates/daemon/src/history.rs`, `RecoverSessions` in `server.rs`, the native Recover dialog in `apps/native/src/recover.rs` / `recover_view.rs`). The CLI facts come from the research note `D:/rustling-tulip/.tmp/research-agent-resume.md` (Codex from its source at the installed 0.156.1, Cursor from cursor.com docs plus a local check of `agent` 2026.09.28-64d2043). Step ids are `RA.n`, plus the Cursor spike `CR.0`.

## Problem

A Codex or Cursor history entry with a spawn config recovers as a Claude session: `claude_request` (`history.rs` ~825) swaps its `agent_options` to `AgentOptions::Claude` (lines 838-842), and `history_item` (~610) offers whatever Claude transcripts the folder has in the session's time window, so the Recover dialog can bring a Codex session back as an unrelated Claude conversation. The test `claude_from_a_shell_or_codex_config_is_forced_to_interactive_claude` (~2038) pins that behaviour. Neither agent's conversation id is recorded: `claude_session_id` is set only for Claude (`server.rs` ~3675), Codex's headless `thread.started` event is parsed as a unit variant that drops `thread_id` (`agents/codex.rs` ~255), and Cursor has no id path at all.

## Settled

- A Codex or Cursor entry recovers as a session of its own agent in the same folder: resumed when that CLI can resume its conversation, else a fresh run. It is never offered Claude transcripts.
- Each agent's conversation id is captured at spawn, by the mechanism its own source or docs support.
- The dialog asks for it with an additive `RecoverAs::OwnAgent`. A fresh run carries no first prompt. An entry without spawn settings is disabled with a reason.
- DeepSeek is a Claude provider, not an agent ([deepseek-sessions.md](./deepseek-sessions.md)); its entries have `agent: Claude`, so its rule "a DeepSeek entry recovers as Claude only" (its Q1) is untouched: `OwnAgent` is refused for every Claude entry.

## Design

### The conversation id field

A new `agent_conversation_id: Option<String>` on `SessionRecord` (`session.rs`), the sidecar `OrphanMeta` (`orphan.rs`) and `HistoryEntry` (`protocol`), each `#[serde(default)]` (and `skip_serializing_if = "Option::is_none"` on the wire). It holds the id the agent's own CLI resumes with, and is set only for Codex and Cursor sessions. `claude_session_id` keeps its meaning and stays Claude-only.

Kept distinct, not unified, because: `claude_session_id` is read today as "a Claude conversation" by `conversation_candidates` (`history.rs` ~645), by the native `default_conversation` (`recover.rs` ~263) and by `SessionSnapshot` (`protocol` ~526); putting a Codex UUID there would make any reader that does not also check `agent`, including an older daemon reading a newer history file after a downgrade, run `claude --resume <codex id>`. A second field costs one `Option` on three structs. `SessionSnapshot` does not get the field: no client needs it while the session runs.

The id is set on the record through `registry.update`, and reaches the sidecar as a field of `orphan::RecordMirror` through `SessionRegistry::sync_sidecar`, like every other mirrored field; it is copied back by `session.rs`'s `insert_orphan`, `insert_abandoned` and `insert_reattached` from the meta, and by `history::entry_from_record` into the entry. [reboot-resume.md](./reboot-resume.md)'s `entry_from_meta` (RB.1) copies it too when that step lands.

### Codex: capture

Codex has no caller-chosen id flag; it generates a UUID v7 (`protocol/src/thread_id.rs` line 30) and writes `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<YYYY-MM-DDTHH-MM-SS>-<thread id>.jsonl`, the date in local time (`rollout/src/recorder.rs` 1699-1719, `rollout_file_name.rs` 62-73; a reverted thread's name adds `_<rollout id>`, and old files may be compressed to `.jsonl.zst`). Its first line is `{"type":"session_meta","payload":{... "id", "cwd", ...}}` (`history/src/rollout_payload.rs` 22-27; the exact flattening of `payload` is unverified live, RA.0). The file is created lazily on the first user message (`core/src/session/mod.rs` 1415-1430), so a session where nothing was sent has no file and nothing to resume.

New module `crates/daemon/src/codex_rollout.rs`, plain functions plus one task:

- `codex_home(extra_env)`: the spawn's resolved `CODEX_HOME` row, else the daemon's `CODEX_HOME` (interactive children inherit the daemon's whole environment, `tracer/src/supervisor.rs` ~132), else `%USERPROFILE%\.codex`.
- `id_from_file_name(name)`: the text after `rollout-`, the 19-character timestamp and `-`, up to `_` or `.jsonl`.
- `find_rollout(home, cwd, since, taken) -> Option<String>`: lists the day folders for `since`'s local date and today's (a spawn near midnight), keeps `rollout-*` files modified at or after `since` minus 5 s whose id is not in `taken`, reads each new file's first line only, and returns the id whose `payload.cwd` equals `cwd` under `paths::normalize_path_key`. File names already read are cached by the caller.
- `rollout_exists(home, id)`: whether any `sessions/**/rollout-*-<id>*` file name exists (names only, no reads).
- `watch(registry, dirs, session_id, cwd, since, home)`: a tokio task started right after a fresh interactive Codex spawn. It polls `find_rollout` every 2 s for the first 5 minutes, then every 10 s, and stops when the id is found, the session leaves the registry or stops running. `taken` is every `agent_conversation_id` already on a record. On a find it sets the record's field through `registry.update`, which syncs the sidecar. Polling rather than a `notify` watcher: one `read_dir` of one or two folders per tick, no watcher lifecycle, and testable against a temp folder; its cost per tick is unmeasured.
- Two uncaptured Codex sessions sharing one cwd (in-place spawns in one repo, or two sessions pinned to one folder) cannot be told apart by the file alone; Open question 1 decides. The design below assumes its option (a).
- `history::record_session_end` runs `find_rollout` once for a Codex record still without an id before writing the entry, so a message sent in the last poll interval is not lost.
- `server::reattach_orphans` starts `watch` for a reattached interactive Codex session without an id, `since` = its `started_at`.
- Headless: `ExecEvent::ThreadStarted { thread_id: String }`, and `handle_headless_line` sets the record's `agent_conversation_id` from it (the event's doc: "Can be used to resume the thread later", `exec/src/exec_events.rs` 12-14, 40-43). The history lists no headless entries (`history_items` filters them), so this only fills the record and sidecar.

### Codex: resume

`codex resume [OPTIONS] [SESSION_ID] [PROMPT]` accepts the session flags of bare `codex`: `-m/--model`, `-s/--sandbox`, `-a`, `--dangerously-bypass-approvals-and-sandbox`, `-C/--cd`, `--add-dir` (`codex resume --help`, 0.156.1). When the launch cwd differs from the recorded one the TUI prompts for a directory unless `-C` is passed (`tui/src/session_resume.rs` 34-43, 61-111). With `common.resume_conversation` set, `codex.rs` `build_args` emits `resume -C <cwd> [--add-dir P]... [--model M] [--dangerously-bypass-approvals-and-sandbox | --sandbox S] <id>`, and no positional prompt or workspace prelude (the conversation already holds them). `--dangerously-bypass-approvals-and-sandbox` replaces `--yolo` on resume because `--yolo` is not listed in `codex resume --help` (unverified whether the alias works, RA.0). Whether a resumed thread keeps its sandbox without the flags is unverified, so they are always re-passed. `CommonSpawnFields` gains `cwd: Option<&str>` for `-C`. A resumed spawn sets the record's id to the resumed id at once, as Claude does.

### Cursor

Cursor's store is undocumented; its documented way to know the id up front is `agent create-chat`, "Create a new empty chat and return its ID", followed by `agent --resume <chatId>` (cursor.com/docs/cli/reference/parameters). Checked locally: `create-chat` prints a bare UUID line on stdout at once, even logged out, and does not exit (still running after 30 s).

- `agents/cursor.rs` `create_chat(program, prepend, cwd, timeout)`: runs the resolved program (`resolve_agent_program`, so the `.cmd` shim resolves as for spawns) with `create-chat` in the session's cwd, stdout piped, reads the first line with a 5 s timeout, requires it to parse as a UUID, then kills the process tree with `taskkill /T /F /PID` (the shim's child keeps running if only the top process is killed).
- A fresh interactive Cursor spawn calls `create_chat` first and spawns `cursor-agent --resume <id> [--model M] [--plan] [--yolo | --sandbox S] [prompt]`; the record gets the id. When `create_chat` fails (timeout, no UUID, not installed) the daemon logs a `warn!` and spawns exactly as today with no id; that session later recovers as a fresh run.
- Resume: the same argv with the recorded id and no prompt, in the recorded folder (before the July 6, 2026 release, resuming from another directory loaded an empty conversation, per Cursor's changelog). Flags are re-passed; whether they stick from the chat is undocumented.
- Headless: Cursor has no headless path in this daemon (`cursor.rs` header), so there is nothing to capture; a future headless path takes `session_id` from the `system`/`init` stream-json event (cursor.com/docs/cli/reference/output-format).
- Unverified, pending `agent login`: that an empty pre-created chat opens cleanly in a PTY through `--resume <id>` with a positional prompt, that `--plan`, `--model` and `--sandbox` combine with `--resume`, what `--resume` of an unknown id does, and whether `create-chat` must run in the target folder. CR.0 checks these, and RA.6 (the spawn change) does not land until it passes.
- `rollout_exists` has no Cursor counterpart: a recorded Cursor id counts as resumable.

### Recovery planning (daemon)

- `RecoverAs::OwnAgent` (unit variant, tag `own_agent`). `RecoverItem.conversation_id` carries the entry's own `agent_conversation_id` to resume it, or `None` for a fresh run.
- `plan_recovery` (`history.rs` ~756): for an entry with `agent != Claude`, only `OwnAgent` is accepted (`Claude`, `RegisterRepoThenClaude` and `Shell` fail with "a Codex session recovers as Codex"); `OwnAgent` on a Claude entry fails with "a Claude session recovers as Claude". `OwnAgent` needs a spawn config ("no spawn settings recorded"); a `conversation_id` must equal the entry's recorded id ("not this session's conversation") and exist.
- The existence closure becomes `Fn(Agent, &str, &str) -> bool` (agent, folder, id): Claude checks the transcript as today, Codex `rollout_exists`, Cursor `true`.
- The request: `config.to_clone_request()` with the target pinned exactly as `claude_request` pins it (`pin_recorded`, else `folder_target`; shared as one `recorded_request` helper), `initial_prompt: None`, `resume_conversation` = the item's id.
- `claude_request` keeps forcing interactive Claude only for a plain-shell config (a plain shell's record says `agent: Claude` while its stored config may carry the dialog's Codex options). The old test is split: `claude_from_a_shell_config_is_forced_to_interactive_claude` and `a_codex_entry_refuses_claude_recovery`.
- `history_item`: a non-Claude entry gets no candidates, and a new `SessionHistoryItem.own_agent_resumable: bool` (`#[serde(default)]`): Codex, an id recorded and `rollout_exists`; Cursor, an id recorded. `history_items` takes the Codex home.
- `SpawnRequest.resume_conversation`'s doc (`protocol` ~791) widens to "the agent's conversation to resume"; an older daemon ignores it for Codex and Cursor and starts a fresh run.
- The sidebar's Resume of an abandoned session (`resume_abandoned`, `server.rs` ~5210) stays a fresh run with its last prompt for every agent, as it is for Claude today.

### The Recover dialog (native)

`recover.rs` (plain Rust): for an entry with `agent != Claude`, `recover_options` returns one option, `RecoverOption { how: OwnAgent, label: "Codex session" | "Cursor session", resumes: own_agent_resumable }`. A resumable row's `conversations` is the one pair `(agent_conversation_id, "its own conversation")`, so `Row::item` sends the id; a fresh-run row has none and sends `None`. `Row` gains `fixed_how: Option<String>`, the text shown where a Claude row shows nothing: "Codex session, resumes its conversation", "Codex session, fresh run: no conversation recorded", or "…, fresh run: its conversation is gone" (id recorded, not resumable). An entry without a spawn config is disabled with "no spawn settings recorded" in place of "no conversation found". `shows_recover_as` stays false (one choice). Pre-ticking follows Open question 2. `recover_view.rs` renders `fixed_how` muted in the row's details line.

### Protocol (additive, no bump)

`HistoryEntry.agent_conversation_id`, `SessionHistoryItem.own_agent_resumable`, `RecoverAs::OwnAgent`, and the widened `resume_conversation` doc. `RecoverAs` already has `#[serde(other)] Unknown`: an older daemon fails an `own_agent` item with "unsupported recovery kind". Protocol 22 keeps decoding; `supported` does not change.

## Glossary terms this subplan coins

- **Own-agent recovery**: recovering a Codex or Cursor history entry as a session of the same CLI in the same folder, resuming its recorded conversation when that CLI can, else a fresh run.
- **Agent conversation id**: the id a Codex or Cursor session's own CLI resumes with, recorded on the session and its history entry; Claude's stays in `claude_session_id`.
- **Rollout file**: Codex's per-thread transcript under `$CODEX_HOME/sessions/YYYY/MM/DD/`, whose name carries the thread id.
