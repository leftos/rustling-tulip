# Session runtime

How the daemon keeps sessions alive and knows what they are doing: recovery across restarts, status, the chat mirror, workspace spawns, tracers and the git watcher. Components and the task index are in [architecture.md](architecture.md).

## Orphan recovery and tracer reattach

On startup, `main.rs` reads all `meta.json` sidecars and partitions live vs dead via `orphan::is_session_alive`, which uses sysinfo.

A tracer-backed sidecar's `tracer_pid` must still be an `rt-tracer` process whose start time equals the sidecar's `tracer_started_at`, stamped at spawn, so a reused pid is neither reattached nor killed (a sidecar without the stamp, from an older build or an unreadable start time, falls back to the name check). A sidecar without tracer fields matches its `pid` against its `program_name`, which otherwise just names the program the user runs, the leaf's label.

For sidecars with `tracer_pid` + `tracer_pipe` set (post-C.3 spawns), `server::recovery::reattach_orphans` (`crates/daemon/src/server/recovery.rs`) connects to the still-running `rt-tracer.exe` over its named pipe and rebuilds a fully-functional `PtyHandle` — IO, resize, and kill all work as if the session had been freshly spawned.

The sidecar also keeps the session's `busy_excluded` flag (absent means false), kept current on every registry update and restored on reattach, and its last `status`, `status_since` and `status_seq` (the snapshot's status sequence), rewritten on every status change. A reattached session comes back `Idle` or `AwaitingInput` with its old stamp and sequence, and any other stored status comes back `Idle` stamped now with the sequence raised by one.

Its status watcher then reads the replayed screen once its startup hold ends: a visible spinner makes it `Working`, an idle prompt box with no dialog clears `AwaitingInput`, and a screen no rule matches leaves the restored status.

A hook-reported prompt's `pending_input` is written beside `status` (absent when nothing is pending) and restored only with a restored `AwaitingInput`, which reads as a prompt main raised (`pending_owner` is not stored). Every sidecar write goes through `SessionRegistry::sync_sidecar`, which writes the record's mirrored fields under one lock. Reattach failures route the session to the abandoned bucket (sidebar Resume button, B.2 UX).

A reattached interactive session with no conversation id, whose plugin discovers its conversation after launch, gets its discovery waiter and poller again once every orphan has reattached and every abandoned sidecar is inserted, so a sibling's held id is never claimed (`reattach_baseline`, `restart_discovery` in `server/recovery.rs`).

A session that ended before then gets none. In the restarted discovery, launch time is the session's start time, the baseline is empty and the folder is the one it started in, so a conversation created while no daemon watched is still found.

A session whose exit arrives while Windows is logging off or shutting down (`GetSystemMetrics(SM_SHUTTINGDOWN)`, `host_shutdown.rs`) and that the user did not stop is not ended: the daemon writes no history entry, marks it abandoned, takes a final look for its conversation and keeps its sidecar with `ended_during_host_shutdown` set, so the next start records it as `TracerLost` whatever its exit code. A sidecar whose tracer is gone is recorded as ended at start (see the history entry in [on-disk.md](on-disk.md)), and once the daemon has bound and written its handshake, `recovery::auto_resume` resumes the qualifying ones by itself, one at a time, with no prompt, off switch or retry (`claude --resume <that id>`), then broadcasts `ResumeReport`.

A qualifying one is an interactive Claude session with a spawn config, its own conversation id and an existing transcript, its worktrees still pinned to their folders, its in-place checkout still on its branch. The rest stay abandoned, listed in Recover.

A recover or rerun plan for a folder that is not a git repository (register-then-agent, an already-registered plain repo, or a session recorded with a single spawn config in a plain repo) is an unpinned spawn in place with no branch.

Pre-C.3 sidecars without tracer fields fall through to the read-only `insert_orphan` path; their underlying children almost never survive a daemon death, so that branch is effectively only for downgrade scenarios.

## Session status

A Claude session's status comes from its hooks and from rules over its rendered screen (`pty_state.rs`, `screen.rs`, `screen/rules.rs`; design in `docs/plans/screen-status.md`).

The watcher feeds each session's PTY output into a per-session grid (`alacritty_terminal`, the crate the client renders with) and reads it with the session's own agent's rules (`screen/rules.rs`: `CompiledRules` compiles the plugin's `ScreenRules`, `rules_for(agent)` caches one set per agent; Claude's table is data in `crates/agents/claude/src/rules.rs`) a short debounce after output pauses.

A rule table fails closed: one bad rule (a structural problem, an unknown part, an empty pattern, over 128 rules, a pattern over 512 characters, over 8 guards, a regex that does not compile) refuses the whole table (`ScreenRules::validate` in agent-api, `CompiledRules::try_compile`), the daemon logs one error "screen rules: the agent's table is refused; its screen has no rules", and that agent's screen reading sets no status. To see why a live session reads as it does, run `rustling-tulipd screen <session id>`: it prints the rule trace (`CompiledRules::explain`) and the grid.

There is no output/input volume classifier, no title heartbeat and no silence demotion for a Claude session: a quiet screen that still shows the spinner stays `Working`.

A session turns hook-driven on its first mapped hook event that passes the ordering check, from Claude Code's hooks, injected through the settings file its spawn writes. A hook event applies at once, except a main-agent `Stop`, whose `Idle` is held (below). A session whose hooks never run is screen-driven only.

A screen-derived change publishes at once when it enters `AwaitingInput` from a dialog footer (Claude's dialog rules, all but the question review step's, read from the last `❯` row down, so a footer quoted in a reply above the idle box reads `Idle`, and Esc over a question with such a quote on screen ends the wait) or when a spinner line promotes the session to `Working`. Leaving `AwaitingInput` and `Working` to `Idle` publish only after hysteresis: 3 agreeing checks at least 150 ms apart, or the first agreeing check 700 ms after the first. A hook-driven `Working` that no `Stop` has ended reads `Idle` only after its idle screen has held for `IDLE_WITHOUT_STOP` (3 s), however many checks agree: while a task runs, each model step opens on a spinner row no rule reads for about a second. A lost `Stop` lands the same way; an interrupted turn, which fires no `Stop`, shows the interrupt row and keeps the short window. A spinner row can wrap on a long task name, and the rules read physical rows, so no rule may match for as long as the task runs. The title is the second witness: when the screen reads idle but the terminal title still says a turn runs (a `Title`-region rule with verdict `Working`, `CompiledRules::title_reads_working`), the window is withheld while the terminal keeps writing, and each repaint re-arms it. Once the terminal has been silent for `TITLE_QUIET_LIMIT` (equal to `TURN_END_CEILING`), the title stops vetoing and the 3 s window applies, so a dead or hung CLI reads `Idle` about 63 s after its last output. Silence only lifts the veto, never ends a turn by itself. A held `Stop`, an interrupt row and a lost `Stop` under the idle title keep the short window, and a plugin with no title rule behaves as before.

The frame that publishes `Idle` carries its own `background` reading in the same write, so no broadcast reads `Idle` with no flag while the screen shows background work (a compact over a background shell included).

Every screen write is refused when a hook event, a chat answer or an exit moved the record (status, main hook stamp or hook-driven flag) since the read. The main hook stamp, the runtime-only `SessionRecord.main_hook_time`, moves only on a main-agent hook event; a subagent's hook moves only `last_hook_time`, the ordering stamp every hook event moves, so subagents firing hooks neither refuse a screen write nor start the 700 ms hold. After any such foreign write, and when the watcher starts, the screen is left unread for 700 ms: the hold holds status writes and screen-driven status, not the chat mirror (see "Chat mirror"). A reading from the title alone, an overlay or a screen no rule matches never writes.

The screen reads only the view in force. While the plugin's view reading says another agent (a subagent) is in view, the watcher writes neither the status nor the `background` flag: every screen verdict becomes `Keep` (rule `agent_in_view`), except that a dialog's `AwaitingInput` still publishes, since either agent's dialog needs the user. The view reading is taken on every agent-mode screen read. A rule showing the session's own name (Claude draws it as the last row under a named session's permission dialog) is the main view, not a subagent's: `read_view` in `screen/dialogs.rs` drops an `agent_in_view` equal to the terminal title with its leading glyph stripped (`Screen::title`, `agent_title_text` in `osc_title.rs`), and the plugin's reader skips a trailing rule with only blank rows below it so the dialog above stays readable. A held `Stop` still lands on its first settled frame; one still held at `TURN_END_CEILING` while a subagent's view is up keeps its hold and writes no `Idle` until the main view is back.

A plain shell keeps its own classifier (command output outpacing echo promotes to `Working`, `SHELL_IDLE_AFTER` of silence ends it) until it is hook-driven or its screen has shown Claude for a whole confirmation window; it then runs the same screen check.

A plain shell with no `hook_agent` (from spawn or recovery) becomes an agent session while its screen watcher recognises an agent's TUI, whatever started it (the agent's command, an alias or function, a wrapper, a full path). The record keeps its plain-shell mode; its snapshot reports mode interactive, `agent` the agent whose screen rules matched and `program_name` that agent's tag, so Chat and Summary turn on. A recovered shell with a `hook_agent` is never promoted by the screen.

A user-source `SessionStart` (the tracer's `hook --from-env`, header `X-RT-Hook-Source: user`) on a plain shell with no hook agent also promotes it, with no discovery waiter, and maps the event; its conversation id wins, and any hook-set conversation id removes the session's discovery waiter at once. A user-source `SessionStart` that would be dropped (no usable or newer hook time, a stopped or errored session) does not promote. While a shell is hook-driven, a user-source event naming another conversation is dropped (a nested agent run below the shell); a new `SessionStart` pins again after the pinned run's `SessionEnd`.

Every PTY session's child gets `RUSTLING_TULIP_SESSION_ID` (the session id) and `RUSTLING_TULIP_HOOK_CONFIG_DIR` (the spawning daemon's config dir), which `hook --from-env` reads; it does nothing without the id, with an empty config dir, or with `RUSTLING_TULIP_HOOKS_INJECTED` set. That marker (`1`) is set only on spawns whose hook files were written (interactive agent spawns and recovered shells resuming an agent) and removed from every other spawn, even when inherited, so a hook is never posted twice. Pre-create agent runs strip all three from the daemon's own environment. They are internal, not user overrides, so `CLAUDE.md`'s table leaves them out.

The conversation id comes from the plugin's transcripts, looked for by folder (`current_cwd`, else the start folder) in a window starting 10 s before the screen showed the agent; a restart excludes the previous run's conversation. One discovery poller runs per session and its waiter ends when the agent exits. Known limit: another agent session in the same folder (another terminal) can be guessed; opt-in user-layer hooks (RT-940) resolve it. A sighting that changes nothing sends no update, and the sidecar's `hook_agent` is mirrored on every record sync.

When the agent exits, the session stays interactive with Chat disabled ("The agent isn't running") until the agent is seen again, and a later run restarts it; a promoted shell with no program name shows "shell" meanwhile. `daemon.log` says "plain shell: the screen shows an agent running in it" (`session_id`, `shown`: `Promoted`, `Restarted` or `Redetected`); discovery warns when the promoted shell names no folder or no plugin is registered for the agent, and logs at debug "discovery: poller ends; another waiter took the session". The `screen` dump names the agent for a promoted shell.

A shell a spawn has just typed an agent's launch line into (`ShellLaunch::AgentTyped`) keeps that classifier and its idle tick off until the agent shows on screen, its hooks take over or it ends, or for at most `LAUNCH_HOLD` (the injector's agent-start limit): the injector writes the line straight to the PTY with no input pulse, so its echo and the agent's first paint would otherwise read as a command and publish a stray `Working`, which a client counts as a finished turn. A plain shell and a reattached session start with no hold.

The shell's prompt is back when the grid's last line (soft-wrapped rows joined) matches a prompt pattern (`PS <path>>`, `PS>` and a nested `>>`, cmd's `<drive>:\<path>>`, or a POSIX line ending in `$`, `#` or `%`, which may be the sigil alone), or when a shell that marks its commands with OSC 133 last sent a prompt-start mark after a command's start or end (`PromptMarks` in `osc_title.rs`; a lag forgets the mark).

The POSIX pattern needs a line starting in the first column, so Claude's statusline and footer rows, drawn two columns in, never match it. Once the prompt has been back for that window, `claude` has ended: the shell leaves hook-driven mode (clearing `background` and ending a `Working` or `AwaitingInput` turn at `Idle`) and returns to its classifier.

An interactive Claude session whose agent is typed into the user's shell (`agent_in_shell`; see "Tracer-backed PTY sessions") runs that same shell watcher. The daemon announces the agent's end once per run with `DaemonMessage::AgentExited { session_id }` on the session-event stream: on its `SessionEnd` hook (a `/clear` reason is not an exit) or, when no hook said so, when `hand_shell_back` sees the prompt return.

The record's `program_name` becomes the shell's label then and `claude` again on the next `SessionStart`; the session itself ends only when the shell exits.

After the hand-back the snapshot's `agent` stays set (the native client and the `send` verb rely on it), so `program_name` is what says whether the agent is up: the agent's registry tag while it runs, the shell's own name after. The native client greys Chat and Summary from `program_name` in the `SessionUpdated` the hand-back broadcasts, and does not fold `AgentExited`. The `rustling-tulipd sessions` verb reports such a session as a plain shell once `program_name` is no longer the agent's tag (`agent_up` in `cli_drive/render.rs`); a missing or empty `program_name`, or an agent with no registered plugin, counts as up.

The hand-back also clears the record's terminal title, on the screen path and on the `SessionEnd` hook path, but only a title the agent painted: the agent descriptor's title rules decide (`is_agent_title` in `osc_title.rs`: its placeholder, or a leading title glyph followed by whitespace). A title the shell set for itself is kept. The OSC title watcher judges "unchanged" against the record's current title inside the registry update, so after a clear the next title goes through even when it is identical.

A subagent's hook event (an `agent_id` in its input) never ends or replaces the main agent's pending prompt, never promotes the session to `Working` and never ends a turn at `Idle`, and a subagent `PermissionRequest` raises one only when none is pending.

The record keeps who owns the pending prompt, the runtime-only `SessionRecord.pending_owner` (`PromptOwner`: `Main`, `Subagent` or `Unknown`). A hook that raises a prompt owns it as `Main` or `Subagent` by its `agent_id`. A label-less `Notification` (no `agent_id`) that fills an empty slot owns it as `Unknown`, never `Main`, and one that finds a prompt pending changes neither the prompt nor its owner. A main `Stop` or `StopFailure` ends an `AwaitingInput` only when its prompt is `Main`'s: a prompt owned by a subagent or `Unknown`, or raised by the screen with nothing pending, stays, and the turn's report is still taken.

A hook-raised prompt (`PermissionRequest`, a question's or plan's `PreToolUse`, `Elicitation`) stays `AwaitingInput` against the screen until a dialog for it has been seen on screen, or until `DIALOG_DRAW_DEADLINE` (10 s) after the hook: the hooks are async and Claude draws the dialog seconds after one (2.6 to 3.2 s measured for a subagent's), so the idle box or spinner between them does not end it, and the dialog that then draws matches the status already set and raises no second Attention. A hook, a chat answer or the agent's exit still ends it before that. A prompt no dialog ever drew reads `AwaitingInput` up to the deadline and then leaves like any other.

The watcher's memory of the last dialog it read (`subagent_dialog`, `prompt_dialog_read`) belongs to the one raised prompt and is forgotten when a new one is raised. In a subagent's view, after a dialog was read in that same view, the screen ends a prompt that is not `Main`'s (`Subagent`, `Unknown` or none pending); with no dialog read there it ends only a `Subagent`'s, and only after the draw deadline. A tool's `PostToolUse` or `PostToolUseFailure` ends a pending prompt only when it's the prompt's own tool, since tools in one message can overlap and a sibling can finish after a question's `PreToolUse`.

A main-agent `Stop` does not land `Idle` itself: it parks its report in the runtime-only `SessionRecord.turn_end` (`TurnEnd`), the status stays `Working`, and the `background` flag and any `WaitingAlert` wait in it, so a stop that a Stop hook blocks never reads as finished. A subagent's `Stop` never holds, and `StopFailure` lands `Idle` at once, keeping what a hold already carries.

The screen watcher is the only resolver of a held turn end. The `turn_hooks_running` rule (verdict `hooks_running`) keeps the hold while the hooks row is up; a screen that reads idle lands `Idle`; and with no sign of hooks on the screen, the first settled frame after the foreign-write hold (about 700 ms after the `Stop`) lands it.

`TURN_END_CEILING` (60 s) lands `Idle` on a settled frame that shows no spinner, and drops the hold on a spinner or a title-only `Working` reading, writing no `Idle` on either. An overlay that hides the screen at the ceiling keeps the hold and the `background` flag the `Stop` carried, writing nothing, until the overlay closes and the next reading resolves it or a weak idle lands it with its flag.

A main hook event during the hold drops it, since the turn went on, and a later `Stop` replaces it, keeping an earlier alert unless a new one arrives. Any status change takes the hold, and any move to `Idle` lands the alert and the `background` flag it carried, except `hand_shell_back`, which lands the alert and leaves `background` false.

The log says `turn end held`, `turn end landed` (`how`: `screen`, `ceiling`, `no_evidence`, `weak_idle`, `agent_end`, `hand_back`, `status_change`) and `turn end dropped` (`why`: `ceiling_spinner`, `hook`, `replaced`, `status_change`). The summarizer's refresher skips a record with a held turn end, so it makes no billed call.

A main-agent `Stop` whose `background_tasks` lists a running task, or whose `session_crons` holds a one-shot cron, sets the snapshot's `background` flag beside `Idle` (RT-84); any status change, a stop, a park or an exit clears it, and it is never written to the sidecar.

The screen sets it too, with no hook: while the record is `Idle` and the screen body reads `Idle`, a background-count item on the mode line under the prompt box or a running-subagent row in the panel (the Claude table's `background_shell` and `background_subagents` rules, verdict `background`, read apart from the state rules by `CompiledRules::read_background`) sets the flag after the same confirmation window as a state change. The mode line's counts are `· N shell(s)`, `· N monitor(s)`, `· N MCP task(s)`, `· N shell(s), N monitor(s)` for shells and monitors together, and `· N background tasks` for mixed kinds.

A live dispatch run whose `session_id` names the session's `conversation_id` also reads as background work, at snapshot time only: `SessionRecord::snapshot()` reports `background` as the record's own flag or a link in the registry's `DispatchLinks` (`dispatch_runs/links.rs`, a count of live runs per conversation), and the record's flag is never written for it. The dispatch-run watcher updates the links when a run is listed, replaced or removed, then sends a `SessionUpdated` for each session on a conversation whose link appeared or went (`SessionRegistry::notify_conversation`), with no runs or links lock held. Every reader of the snapshot's flag sees it (the sidebar, the push trigger's Finished decision, keep-awake's busy set); the turn-end hold and the Dashboard's now line read the record's own flag, not the link; a linked run reaches the now line through its rule 3 (`Waiting on dispatch run "<title>"`, `docs/plans/dashboard.md` "The now line") instead.

The screen clears only a flag it set itself, so a hook-set flag survives a footer-less frame, and after a reattach the flag comes back from the replayed screen.

A `Notification` `idle_prompt` does not leave `AwaitingInput` while a hook-reported prompt is pending.

Claude Code fires `Notification` type `permission_prompt` once per dialog, a question's too, about 6 s after the dialog draws and deferred by keystrokes, and for a subagent's dialog it carries no `agent_id`, so it says nothing more about the prompt and the status never depends on it. `/compact` fires `SessionStart` with source `compact` and no `Stop`.

### Status decision log

Each status change logs its cause at debug under the `status_trace` target, which the default log filters leave out: a hook-driven change names the hook event (`hook_status.rs`), a screen-driven change names the rule that fired, logged only when a screen read changes the status (`pty_state.rs`), the session record logs what it stamped (`session.rs`), and the hook route logs each hook it receives, holds for its spawn or drops (`server/hooks.rs`). The native client logs each notification it raises or skips, with the skip's reason (`notify.rs`). A `pty_state screen check` line carries `title_working=<bool>`, so an `Idle` withheld by the title shows in the log. A hook event with `from=Idle`, `subagent=false` and not `UserPromptSubmit` means the `Idle` before it was false. `RUST_LOG=status_trace=debug` shows them; the Detailed logging switch turns them on from Settings.

## Phone pushes

The daemon pushes Needs you and Finished to every subscribed device for its whole life, with or without a client connected (`push/trigger.rs`, started by `start_hub_tasks`; design in `docs/plans/mobile-app.md` "Push"). It watches the registry's `SessionEvent`s and judges each snapshot against the status it last saw of that session, by the desktop's `needs_you` and `finished` rules and its Finished grace (`apps/native/src/notify.rs`), not its toast settings or window focus.

Needs you fires when a session enters `AwaitingInput` from another status and is neither inactive nor abandoned. Finished fires when an agent session (never a plain shell) lands `Idle` with no `background` work, from `Working` or from `Idle` with `background` set. The push waits a 5 s grace (`FINISHED_GRACE`, the desktop's `hold_finished` default) and is dropped if the session leaves `Idle` or starts background work meanwhile; its Needs you badge and the at-desk check are read when it is sent. A session seen for the first time raises nothing, so one already awaiting input when the daemon starts raises nothing until it next changes; a removed session is forgotten, so its next appearance is a first sighting, and no Needs you push is raised or counted for a session the registry has already removed, whether in the event step or when a held push is delivered later. After a lagged event stream the trigger re-seeds from the registry and raises nothing for what it missed.

While the owner is at the desk, the pushes of subscriptions whose `hold_at_desk` is on are held (`presence.rs`). The owner is at the desk while any live connection last reported `active` through `ReportPresence` (the native client sends it to a host listing `client_presence`, reading the machine's idle time on Windows and macOS and counting window focus alone elsewhere, `docs/native-client.md` "Presence reports"; a closed connection stops counting; nothing is stored, so a restarted daemon starts with the owner away). A held Needs you push is delivered to those subscriptions when the owner leaves the desk, if its session still needs the user then (a session answered or removed meanwhile sends nothing); a held Finished push is dropped. Subscriptions with `hold_at_desk` off get every push as before.

Nothing is sent while the tailnet listener is not serving. The body is the session's label and the badge is the Needs you count. A delivery round's pushes go out concurrently, at most 8 in flight, and the answers keep target order. A throttled or failing push service is backed off per push-service origin (30 s, doubling to 10 min), once per round at the longest `Retry-After` it asked for, and a service that both accepted and throttled in one round is backed off. A 404 or 410 deletes the subscription. A round skips the stored subscription of a revoked or unknown device.

The log says error `push: the HTTP client did not build; no push is sent until the daemon restarts`, warn `push: the session event stream lagged; re-seeded`, and debug `push: a round is done`, `push: a round is done` (`answered`), `push: the owner is at the desk; the round's held pushes wait for the owner to leave` and `push: a held Needs you push is delivered`.

## Chat mirror

The chat mirror serves a Claude session's chat from its transcript and its screen, and types into its PTY (`chat_mirror.rs`, `transcript_tail.rs`, `server/chat.rs`, the plugin's `chat_entries.rs` and `dialogs.rs`; design in `docs/architecture.md` "Chat mirror").

The terminal stays the source of truth and each fact has one source: history from the tailed transcript, the open dialog with its numbered options and the composer state from the status watcher's screen grid read by the plugin's dialog parsers, live answer text from the MessageDisplay hook, and "a prompt is pending" from `pending_input`. No fact falls back to a second source, except two: a Plan prompt card whose screen body is empty (the plan box's rules scrolled off) takes the hook's plan text as its body, and its first non-blank line as the subject when that is empty too, only while the record is `AwaitingInput` on a `PlanApproval`; the screen's own body wins when it has one, and the fill comes after the prompt's identity is computed, so the prompt id never depends on it. A question card read without its tab bar takes the hook's whole question as its subject when the rows it still shows are that question's end, only while the record is `AwaitingInput` on a single `Question`, and that fill comes after the identity too. The mirror builds no second grid.

The status watcher's 700 ms hold after a foreign write (a hook, a chat answer) does not hold the chat: every check inside that hold hands the grid to the mirror, whether its output has settled or it ran at the max wait under continuous output such as a blinking tool marker (`check_during_hold`, `look_during_hold` in `pty_state.rs`, flag `Confirm::chat_through_hold`), and a hold that starts on an already quiet grid books such a check at once. So a loaded Chat shows a dialog card (plan, permission, question) within a debounce or a max wait of the hook that flips the status. The hold still keeps every status rule and status write until it ends.

Only a hold a foreign write starts feeds the mirror: the watcher's starting hold and the holds after a resize or lagged output feed it nothing until they end. A resized frame (its size differs from the last executed check's) and Shell mode feed the mirror nothing.

A chat message or answer is typed into the PTY as keys under the session's typing lane, gated on the settled screen, and refused (`busy`, `chat_refused`, `invalid_request`) rather than queued by the daemon. A recipe runs group by group with a screen check after each and stops when the screen does not move, the owner types or 30 s pass. The chat never resizes the PTY, and a send or answer is never an owner key.

The phone's Allow and Deny match the pending hook to the dialog on screen (`server/dashboard.rs`, `shows_summary`, `deny_option`). An Edit or Write hook summary is an absolute path while the dialog shows the path relative to the session's folder, so Allow accepts either the dialog showing the summary or its subject being the summary's tail after a separator (`\` and `/` alike). Deny takes the option labelled exactly `No`, else the last one starting with `No` that is not `No, …`, because Claude's repaint at narrow widths can leave stale characters on that row (`Nohift+tab)`); the terminal shows what Claude drew, and `No, and tell …` alone is refused.

The running-work strip (`ChatWork`) and the summary view (`Summary`, `SummaryAppend`) ride on the same loaders. Summary lines are written by the Dashboard's summarizer service through its queue, cache and daily cap, and stay template lines (the turn's first non-blank user line, its duration and tool count) when no model text comes back. Only the Claude plugin supplies the mirror's parts, so a session of any other agent is refused a chat with `unsupported_message`.

The status watcher also returns the terminal to the main conversation for every Claude session when an agent is in view and a Heads up notice is up, an AskUserQuestion closes, or the box holds the notice's own draft (`view_drive.rs`; design in `docs/architecture.md` "Chat mirror"). It types its keys straight into the PTY, never as owner input: one key per settled read, at most 12 keys and 10 s per drive, no key while a dialog is up. A draft in the agent's box is stashed with ctrl+s only when no stash is held (the stash is one slot), restored in the agent's view afterwards or returned to main's box, and clients hear of it through `DaemonMessage::SessionNotice` on the session-event stream. Every multi-key writer to a PTY (this view switch, the spawn injector, a chat send) takes the session's typing lane (`typing_lane.rs`), and the watcher skips its view return while another writer holds it; the user's own keys never take the lane.

Owner input alone never writes the status: a key, a click or a wheel report sent with `SendInput` leaves `AwaitingInput` and `pending_input` as they are, so the tab badge, taskbar count and Needs You row stay until the agent ends the prompt. A key that answers a question moves the status at the hook's `PostToolUse`, Esc ends it through the screen's `idle_prompt_box`, and a key that does not answer (Down) leaves it.

A permission dialog whose footer lost its hint (` Esc to cancel` alone) reads `dialog_permission`, in main's view and in a named session. A question dialog in a pane under 49 columns reads `dialog_question` although its footer wrapped; `Enter to select · Esc to go back` and `Enter to select · Esc to continue` are not questions. With Claude's vim editor mode on, the question dialog's footer on its `Type something` row is headed `-- INSERT -- · ` and has no `Esc to` hint; `dialog_question` accepts that head, so the open question reads `AwaitingInput`, and the chat mirror's dialog reader finds the same footer and shows the question's card. The prompt box's own `-- INSERT --` status line still reads `Idle`.

A subagent's hooks leave a pending prompt alone and its view writes no status, so the screen ends an answered subagent dialog: `AwaitingInput` ends on the first settled reading in that view showing no dialog, once the view itself reads no dialog. A dialog seen during the foreign-write hold counts, and a clear refused by a hook landing at that moment is tried again at the next reading. Peeking at a subagent while main's question is pending keeps Needs You, since the view moved and that dialog may still be up.
A prompt a subagent's hook raised is owned by the subagent in the runtime-only `SessionRecord.pending_owner`, which `clear_pending()` resets with `pending_input` on every path. While a subagent is in view, a settled reading with no dialog ends that prompt as long as no reading has seen a dialog since the session started waiting, in main's view or any subagent's (`ScreenWatch.prompt_dialog_read`), so a prompt answered before any reading saw its dialog leaves Needs You and chat sends are accepted again. The last read subagent dialog's view is kept across a switch to another subagent's view: there the prompt is kept, and back in the first view with its dialog gone the prompt ends. An answered subagent dialog never ends a prompt main raised: no flip to `Idle` and back, no second attention or toast, and the phone and chat keep main's prompt.
Two limits: a prompt restored by a reattach reads as main's, so a subagent's view never ends it (a dialog answered while the daemon was down stays pending until main's own screen or hook ends it), and a prompt one subagent raised whose dialog was never read ends on the first settled reading of another subagent's view when that view is shown, since the record does not say which subagent raised it.

A status watcher write (a screen read or the shell classifier) that moves a session off `AwaitingInput` clears `pending_input` in the same update.

Token and cost figures exist only for headless runs, where they come from the CLI's stream-json (`crates/agents/claude/src/lib.rs`, `parse_headless_line`, applied by `crates/daemon/src/headless.rs`), so an interactive session's snapshot carries none. Headless mode (`claude --print --output-format stream-json`) uses `crates/daemon/src/headless.rs` for structured events.

## Subagent list

The subagent list service (`crates/daemon/src/subagents/mod.rs`, `SubagentList`, started in `start_hub_tasks` beside the Dashboard's ticker) keeps each session record's `subagents`, which `SessionSnapshot.subagents` carries to clients, and each listed dispatch run's, which `DispatchRunSnapshot.subagents` carries.

Discovery stays in the agent plugin: the daemon reads `ActivitySnapshot.subagents` through `agent_registry::plugin(&agent)?.activity_reader(&source)` and names no file, field or agent. Files are the only source; the `SubagentStart` and `SubagentStop` hooks are not used, so sessions started without hooks are covered.

One task runs for the daemon's life. While a client is connected it makes a pass every `TICK` (2 s); with no client it parks and reads nothing, and a returning client gets one catch-up pass (the `git_watch` and `transcript_tail` pattern). Each pass keeps one activity reader per owner, a session or a run, and reads them on the blocking pool.

A reader is keyed by conversation id, folder and process start, and a change of any makes a fresh one. The readers are the service's own, not the Dashboard's: the Dashboard reads only while watched, and the list must read whenever a client is connected.

A session is live when it runs an agent with a conversation id and a folder, is not parked or abandoned, has not stopped or failed, and its agent has not ended inside its shell. A session that stops being live gets an empty list once. The record's `SessionRecord.subagents` is runtime-only (never in the sidecar or history); a daemon restart starts it empty and the first pass refills it.

A first-layer subagent is listed with its whole subtree while it or a descendant runs. A finished or failed one stays listed while it ended after both the session's newest typed prompt and its agent process's start, the newest five finished first-layer subagents at most. The next typed prompt, a restart of the agent, or a sixth finish removes it. When no typed prompt is known (it lies before the reader's first-read tail) only the process start and the cap count.

Not "gone when it finishes", because a short subagent would vanish before it could be clicked. Not "until the host's next turn", the Dashboard's rule, because a background subagent's finish wakes the main agent at once, so its row would vanish the moment it finished. The typed prompt is where the user has moved on; the cap keeps a loop that never sees one from growing the list without end.

The typed-prompt time comes from the plugin: `ActivitySnapshot.last_typed_prompt_at` is the newest main-thread `user` record the plugin's `line_facts` calls a prompt whose `origin.kind` is not `task-notification`. The daemon compares times only.

In the Claude plugin, a subagent sidecar's `finished: true` counts only when the sidecar was written at least as late as the transcript's last write (an unknown time still counts), so a resumed subagent reads as running again, and a sidecar without the field keeps the transcript rules.

The list is in tree order (each first-layer subagent, oldest first, then its subtree) and carries only fields that change when a subagent starts, finishes or first replies, never its open call or last text, since each change costs a `SessionUpdated`. It is written through `SessionRegistry::update` only when it changed, and a reading for a session that stopped or changed conversation while it was read is dropped; a pass whose lists match the records sends nothing.

### A dispatch run's own subagents

A dispatch run that starts subagents has them in its own conversation: `<claude home>/projects/<encoded worktree>/<agent_session_id>/subagents/`, where the worktree is the run's and `agent_session_id` is `DispatchRunSnapshot.agent_session_id`.

The live-run file records no Claude home, so the env rows that find it are the stored `extra_env` of the first listed session whose conversation is the run's `session_id` (the dispatch tool inherits its caller's environment), else none, the daemon's own home (`subagents::host_env`).

The same pass reads each listed run that has named its `agent_session_id` and has not ended, with a reader per run listing (a run listed again, as a resume is, gets a fresh one) and the same listing rule, the run's `started_at` standing for the process start.

A run with no `agent_session_id` yet, or `Ended`, reads nothing and has its list emptied once. `DispatchRuns::set_subagents(run_id, generation, list)` compares and stores under the runs lock and sends `DispatchRunUpdated` only on a change; a stale generation is dropped, and no file is read under the runs lock.

## Subagent tails

A client follows a subagent's transcript with `FollowTranscript` (`TranscriptSource::Subagent` for a session's, `RunSubagent` for a run's; the wire shape is in [wire-protocol.md](./wire-protocol.md)). `server/transcripts.rs` takes both follow messages and routes by source: a dispatch run's own to `DispatchRuns`, a subagent's to `SubagentTails` (`crates/daemon/src/subagents/tail.rs`, a `Hub` field), an unknown source to `Error` `unsupported_message`.

`SubagentTails` keys one tail by an owner (`Owner::Session` or `Owner::Run`) plus the agent id. Each holds a `TranscriptLog` (shared with the dispatch-run follow), the `TailHandle` of a `transcript_tail::spawn` from byte 0 and the plugin; `Line` events fold through `TranscriptLog::fold` under the tails lock and `Restarted` calls `restarted`.

The path comes from the plugin's `subagent_transcript_path(folder, conversation_id, agent_id, rows)`, defaulted to `None`, which the Claude plugin builds from `transcripts::transcript_path` and `subagents_dir`, refusing ids that are not plain.

Only the agent id comes from the client: a session follow takes the folder, conversation and env rows from the session's record, a run follow from the run entry (worktree, `agent_session_id`, and the host's rows above), so a client never hands the daemon a path, and the subagent need not be in the list. A follow whose owner is not held, whose agent has no transcript path, or whose agent id is refused answers `Error` `not_found` with the `request_id`. A tailnet client may follow: it is read-only.

The tail lives exactly while followed. The first follow starts it; the last unfollow, the last follower's connection closing (a guard dropped with the connection) or the owner's removal stops it and drops its log, and a later follow replays the file from byte 0. With no client connected a tail parks. Removing a session, or a run from the run list, first sends each follower `TranscriptAppend { ended: true }`; a daemon shutdown ends none.

`ended` means the owner is gone, never that the subagent finished: a resume appends to the same file, and a finished subagent's state shows in the pane's header from its snapshot, not from the transcript messages. The follow always reads from byte 0; the log keeps the newest `CHAT_REPLY_CAP` entries and counts the rest in `hidden`, and a tool result whose call was dropped is dropped.

At daemon start, after sessions are restored, `tabs::prune_subagent_follows_not_in` clears a local pane's `Subagent` follow whose session did not survive, and `tabs::prune_follows_not_in` clears a `DispatchRun` or `RunSubagent` follow whose run is not live, as for a dead run; a pane of another host is not this daemon's to judge, and a follow of a session that survived is kept.

A Resume of the host (`tabs::rebind_session`: a resume, rerun or recovery) moves a pane following one of the old session's subagents to the new session id, and `tabs::rehost_panes` moves it with its session's panes; a `RunSubagent` follow stays where it is.

### Rules the code keeps

Actors: the agent process (appends the transcript and sidecar files), the list service's task (one pass per tick, readers on the blocking pool), one tail task per followed subagent, the connection tasks (follow, unfollow, the guard dropped on close), the session registry (status, conversation id, process start, removal), daemon startup (session restore, then the tab prune) and the clients (fold updates, follow, re-follow after `Welcome`).

- **A file growing.** Every complete line reaches a follower exactly once, in file order: the backfill is built and the follower registered under the tails lock that `fold` takes, so a line is in the backfill or in a later append, never both and never neither. A partial line is never parsed.
- **A new subagent.** It is listed on the first pass after its files exist and a launch joins it; a sidecar that does not parse yet keeps it out until it does. A tail followed before its file exists waits for it and sends an empty backfill first.
- **An owner ending.** A session whose agent process stops gets an empty list on the next pass; its removal, or a run's, sends `ended: true` to every follower and stops their tails. Panes keep their content and close only when the user closes them.
- **A daemon restart.** Nothing is persisted: lists start empty and the first pass after a client connects rebuilds them; subagents last written before the agent process started read finished. Clients re-follow after `Welcome` and each tail replays from byte 0, and the prune runs after session restore, so a follow of a surviving session is kept.
- **A conversation change.** A `/clear` or resume gives the record a new conversation id or process start, so the next pass uses a fresh reader and lists the new conversation's subagents; a tail already running keeps its resolved path until it is unfollowed.
- **Lock order.** The record lock and the runs lock are never held while reading files, and the tails lock, a leaf, is never held while taking either (a follow reads the record or run entry, releases it, then takes the tails lock).
- **No idle traffic.** With no client connected the service and every tail read nothing.
- **Agent seam.** `SubagentSnapshot`, `SA`, `subagents` and `subagent_transcript_path` name no agent; every path, field and file name stays in `crates/agents/claude/`.

## Multi-repo workspace sessions

Multi-repo workspace sessions spawn one `claude` process with `cwd = members[0].worktree_path` and `--add-dir <path>` for every additional member. Worktrees are created/reused per member via `git -C <repo> worktree add` under the shared `<worktrees-root>/wt.<branch-slug>/<workspace-slug>/` directory (see [on-disk.md](on-disk.md) — the layout preserves inter-member relative paths within a workspace).

A member that is not a git repository (`RepoEntry.is_git` false) runs in its own folder with an empty branch, gets no worktree, and is left out of the spawn preview rows; `daemon.log` notes it as "resolve_workspace: plain member runs in its own folder".

The "reuse-or-create" policy is encoded in `workspace.rs`. VS Code `.code-workspace` files are auto-detected when adding a repo and surfaced as a `VscodeWorkspaceSuggestion` event.

## Tracer-backed PTY sessions

Every interactive and plain-shell PTY child is spawned under a per-session `rt-tracer.exe` supervisor process. The daemon talks to it over an `interprocess` local socket (`tracer_protocol::socket_name`: `\\.\pipe\rt-tracer-<session-id>` on Windows, a Unix socket elsewhere).

The tracer owns the master ConPTY handle and survives daemon restarts — when the daemon dies the tracer keeps draining child output to its internal ring buffer (4 MB cap, oldest-bytes-drop on overflow), and a freshly-started daemon reattaches via `tracer_client::reattach` and replays the ring to catch up. Spawn and reattach both refuse a pipe served by any process but the session's tracer pid (`tracer pipe {pipe} is served by pid {pid}, not the session's tracer pid {expected}`, or `tracer pipe {pipe}: the server's pid could not be read`): the spawn fails, and the reattach is abandoned like a lost tracer.

On macOS every child, headless ones too, inherits the daemon's process PATH, which a daemon started with launchd's minimal one has replaced at start with the login PATH (`docs/daemon-cli.md`, "Login PATH on macOS"), so the agent, shells, git, gh and the tracer resolve programs through it; the keep-list passes that PATH on, and no other login-shell variable is imported.

Spawn site: `crates/daemon/src/tracer_client.rs::spawn`. Tracer ABI: `crates/tracer-protocol/src/lib.rs` — frozen surface; additive changes (new fields with `#[serde(default)]`, new variants with `#[serde(other)] Unknown`) are not a bump. Headless (`claude --print`) does NOT go through the tracer — it's piped stdio and lives in `crates/daemon/src/headless.rs`. The tracer binary must be present next to `rustling-tulipd.exe`: `cargo build` emits both into `target/<profile>/`.

A session's exit means its direct child's exit. Descendants the child left outlive it until the tracer exits (a short grace, up to its reader join), and can pin their working directory meanwhile, which is why removing a folder a session ran in can fail until then.

An interactive Claude session's tracer child is the user's shell (`RUSTLING_TULIP_SHELL`, else the host's Default shell setting, else Automatic: the platform's usual shell), not `claude`; the tracer never runs or knows the agent, and only logs an optional `--agent-note <json>` (given before the program, for an agent typed into the shell and never for env rows) as the line `rt-tracer agent note agent_note=<json>` after `rt-tracer starting`, which the tracer-log import reads (`server/spawn.rs` `shell_agent_note`, `tracer_log.rs`).

`server/spawn/shell.rs` `resolve_shell_program` reads the setting at each spawn, so Restart, Resume and Recover take the current one. A chosen shell that is unavailable, or a Custom program that does not resolve, falls back to Automatic with the warn `shell: chosen shell unavailable; using automatic`. A Custom command is split by the Windows command-line rules on Windows (backslashes kept, `"` groups) and as POSIX shell words elsewhere; a command that names an existing file whole is the program, a path program must exist and a bare name goes through PATH. WSL plain shells run `wsl.exe --cd <cwd>`, and Git Bash gets bash's integration. A Recover that types a resume line into a shell that cannot host it (WSL) runs Automatic instead, with the info log `shell: chosen shell cannot host the resume line; using automatic`. The plugin's `shell_resume` returns the program and its arguments, and the daemon quotes that resume line for the shell's family; a recovered session whose shell has no family (an env override or a Unix `$SHELL` such as tcsh) is refused with "{label} cannot resume conversation {id} in a shell: its shell family is unknown", and a cmd shell that cannot carry the resume argument with "…: the shell cannot carry the resume command".

Once the prompt is quiet the daemon clears the input line and types `<cd to the start folder> && <quoted claude command line>` (`server/spawn/shell.rs` plans and quotes it per shell family, `inject.rs` `run_chain` types it). Nushell and fish have their own forms: fish types `cd '<dir>' && '<program>' '<arg>'…` (single quotes, `\` as `\\`, `'` as `\'`), Nushell `cd '<dir>'; ^'<program>' '<arg>'…` (an argument holding `'` as a raw string `r#'…'#`, with more `#` as needed). A bare user program word is typed bare in fish and as `^word` in Nushell, and both clear the input line with Ctrl+U.

The initial prompt or a preset's script is typed into Claude's TUI only after Claude is up (`wait_for_agent`, `pty_state::agent_up`), and dropped after 15 s with the warn "the agent did not start; the initial prompt was not typed".

The first prompt of an interactive session reads the record's screen three ways: starting, dialog (a status rule says awaiting input, or the composer reads a dialog or overlay) or ready (the composer reads ready). While a startup dialog is up (Claude's folder-trust dialog, or "New MCP server found in this project") the prompt is held: the typing lane is released, so a chat answer from Chat or the phone goes through, the dialog's time does not count against the 15 s cap, and the prompt is typed once the composer reads ready. The info logs are "the first prompt waits behind a dialog" and "the first prompt is typed".

A held prompt is dropped when the shell prompt returns or the session is removed, stopped or errored (the warn above, with `agent_exited=true`), or after 10 minutes held, with the warn "the first prompt waited 10 minutes behind a dialog; it was not typed". A chat send while the first prompt is held is refused `busy` with "This session's first prompt is still waiting to be typed."

Claude shows its trust dialog in any folder it has not trusted, a fresh worktree and a bypass-permissions session included. It keys trust on the main repo root, so every worktree of a trusted repo is trusted afterwards.

A shell outside pwsh, powershell, cmd, nu, fish, sh, bash, zsh, dash and ksh (WSL, including its bash, stays on the direct spawn until RT-956), a cmd line carrying `%` or `!`, and legacy PowerShell's argument passing host no agent: Claude is then the PTY child, as it is for a plugin without `shell_resume`.

So does an agent that runs through cmd.exe (a `.cmd` or `.bat` shim, or cmd.exe itself) typed into pwsh, powershell, Nushell, fish or a POSIX shell when an argument holds `%`, `!`, `"`, `^`, `&`, `|`, `<`, `>`, CR or LF; the direct spawn then refuses any such argument with a `Couldn't start session` failure naming the character and the argument, before the tracer starts (`direct_args` in `server/spawn/shell.rs`).

`daemon.log` says which fallback ran ("the agent's command line cannot be typed into this shell; spawning the agent directly", "the agent cannot be typed into this shell; spawning the agent directly", "no shell to host the agent; spawning the agent directly").

A hosted launch logs "spawn_interactive_session: the agent is typed into the shell".

ConPTY sends a cursor-position query (`ESC[6n`) at startup and paints nothing until it is answered. On Windows the tracer answers that one query with `ESC[1;1R` and removes it before the ring (`cursor_query.rs`), since a session may start with no pane, no client or no daemon: a preset, an auto-resume, another device or `rustling-tulipd spawn`.

The daemon cannot answer in its place, because `clients` is normally empty at the first chunk, holds forwarders with no terminal, and looks empty during a resync. The tracer stops looking at the first byte outside a CSI sequence, so a child's own query is never eaten. A client's terminal answers every later query, and `feed_history` still answers the startup query of a session on an older tracer.

## Live git watcher

The watcher is `crates/daemon/src/git_watch.rs`. Each registered repo gets a recursive `notify`-based watcher with a 750 ms debounce. Inside the debouncer callback, `classify_event` filters paths against a hand-maintained allowlist: only `.git/index`, `.git/HEAD`, `.git/refs/**`, `.git/reftable/**` (a reftable-backend repo's refs; it wakes the stash refresh too), a handful of in-progress operation markers, and any non-excluded working-tree path can wake the refresher.

`.git/objects/`, `.git/logs/HEAD`, `FETCH_HEAD`, lock files, and well-known build/cache dirs (`target/`, `node_modules/`, `dist/`, `.next/`, `.venv/`, `__pycache__/`, …) are ignored so a `cargo build` or `pnpm install` doesn't spin up `git status` forever.

A registered folder with no `.git` (judged by `git::folder_has_git`) gets only a cheap init watcher; when `.git` appears the watcher is promoted to the full one and the daemon refreshes every `is_git` flag, broadcasting `Repos` when one changed.

The refresher tracks two flags — `status` and `stash` — and only invokes `git stash list` when a stash ref actually changed. The refresher parks while `Hub.client_count` is 0 (an RAII `ClientCountGuard` in `client_session` maintains the count); the next reconnect triggers one catch-up `repo_status` + `stash_list` before resuming event-driven refresh. The daemon accepts multiple WS clients, so each client window opens its own connection.
