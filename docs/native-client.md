# Native client

The desktop client is `apps/native` (binary `rustling-tulip-native`): GPUI (Zed's UI framework) with `alacritty_terminal` for the terminal grid. It replaced the Tauri/WebView2 app, which is retired and kept as history on the `tauri` branch (tag `tauri-last`). The daemon, tracer and `crates/protocol` are shared and unchanged by the client.

This doc records the decisions a change to the client needs to know; what each feature must do is in the [parity checklist](./plans/native-client-parity.md), and open work is in [plans/MAIN.md](./plans/MAIN.md). How the pieces fit together: [architecture.md](./architecture.md).

## Stack

- **GPUI 0.2.2 + `alacritty_terminal` 0.26.** The client moved off the web stack; GPUI draws natively and `alacritty_terminal` supplies a mature VT parser and grid. Iced is the fallback if GPUI's API churn becomes a problem.
- **Crate rules.** `apps/native` is a main-workspace member under the workspace lints, prek clippy, `cargo nextest run` and `cargo deny check`. `main.rs` is a thin binary over the library `rustling_tulip_native`, so specs link the library.
- **Testable core, thin view.** State a feature adds (sidebar tree, split tree, tab list, key mapping, span building, forms, dialogs' focus rings) lives in plain-Rust modules with unit tests; the GPUI `*_view.rs` renders it and forwards events. Every feature mounts into `RootView` (`lib.rs`), the hotspot concurrent items rebase over.
- **Clipboard** goes through GPUI's own API (no `arboard`).
- **Folder picker**: `folder_picker.rs` is the client's own Windows folder and file dialog, copied from GPUI 0.2.2's `file_open_dialog` (Apache-2.0) because GPUI's `PathPromptOptions` has no start folder. It adds `SetFolder`, so Add repo opens at the folder the last added repo sits in (`last_repo_dir`), Shell… at its typed folder or the quick-shell folder, and the worktrees Browse at its field.

  Its file mode filters to the file types the caller names (a `FileFilter`): `.code-workspace` for the workspace creator's Browse, which remembers its own folder (`last_vscode_dir`) separately from the repo folder, and `.txt` / `.md` or a variable's own extensions for the preset wizard's pickers.

  A start folder is checked off the UI thread and dropped when it is missing or takes over 2 s (an offline share). Off Windows it falls back to GPUI's picker with no start folder.
- **Repos and the no-repos states**: + Repo ("Add repo…") and + Workspace sit in the sidebar toolbar's `⋯` menu beside Shell…; the 30 px row stays + Session, + Shell, `⋯`.

  With no repos or workspaces the sidebar shows "No repos or workspaces yet." over an Add repo button, the main area's empty state gains Add repo beside Spawn a session and Open shell, and the spawn dialog (Ctrl+Shift+N, or any entry without a locked target) opens in a no-repos state with Add repo and Spawn disabled, turning into the form on the first repo that arrives; + Session and Spawn a session stay disabled. `AddRepo` carries no `request_id`, so a refusal is the generic error toast.

  Right-clicking a repo's or workspace's row opens its container menu, whose last row, below a separator, is a danger `Remove repo` / `Remove workspace`. With no live session the first click arms the row (`Confirm: remove repo…` / `Confirm: remove workspace…`) and the second unregisters.

  With live sessions the first click opens `Remove repo?` / `Remove workspace?` instead, naming the container over a body reading `Running sessions move to Detached.` and one row per owned live session as `label (agent)`, answered with `Cancel` (focused), `Remove anyway` (unregister, leaving them running under Detached) or `Stop and remove` (a cleanup-free `StopSession` each, then the removal).

  A workspace's own sessions are those whose `workspace_id` is it; a repo's are those whose first member repo is it, outside any workspace; a plain shell is never listed. A removal is silent and closes the dialog once the daemon's list no longer holds the container, a refusal is the generic "Daemon error" toast with the dialog left open and the arm dropped, and Esc, Enter, Space and Tab drive the dialog without reaching the terminal.

  The menu's first row is `Spawn session ▸`: a submenu that replaces the rows with `‹ Back` and, a separator between each group, `Last (<launch summary>)` (only with a stored launch; dimmed with `Headless runs aren't supported in this client` when that launch is headless), one row per agent of the container's host by descriptor label, `Shell` (dimmed with `This container has no folder` on a workspace) and the preset rows as in the top-level menu.

  `Last` and the stored agent's own row replay the stored launch into the tab on screen, exactly as `Launch last again` does; any other agent row opens the spawn dialog held on that container with that agent chosen (the target picker showing the container alone and Open in left free); `Shell` spawns a plain shell in the repo's folder at once, in the tab on screen.

  When the container has a stored config, `Launch last again ▸` follows: that submenu replaces the rows with `‹ Back`, `Current tab`, `New tab`, one row per grid tab by name, then `Edit first…` (the spawn dialog prefilled and locked to the container instead of a replay).

  Then `Appearance…` and `Launch preset…`, `Launch preset…` lists the container's presets (repo and workspace containers alike): a loading row until the `Presets` reply carrying that menu's own request id arrives, a failed row when the `Error` carrying that id answers instead (an error without the id toasts on its own and leaves the row loading) and a none-defined row; picking a preset opens the preset wizard.

  Below a separator sit `Open in Explorer`, `Open in VS Code` and `Copy path`; the danger Remove row follows below another separator. Explorer and Copy path act on a repo's folder; a workspace has no single folder, so both are disabled with the tooltip `This container has no folder`, as is VS Code when a workspace yields neither a linked file nor a folder.

  Opening the menu checks off the UI thread that each target still exists; the rows stay enabled while it runs, and a gone target disables its row with `This folder no longer exists`, `This workspace file no longer exists` or `None of this workspace's folders exist` (Copy path is never disabled, and a host that opens no local files runs no check). A workspace whose member folders are partly gone opens only the ones that exist, and an open whose target vanished after the check toasts `Couldn't open` with `{path} no longer exists`.

  VS Code opens a repo's folder; a workspace opens its linked `.code-workspace` file when one is set, else its member folders in member order as one multi-root window (`--add` for each after the first), skipping members with no folder. When VS Code is missing, the folder opens in the file manager or the workspace file in its default app, under the `VS Code not found` warning toast.

  A repo or workspace whose stored spawn config has launched before draws a two-line 46 px row.

  The name line sits over a muted last-launch summary (`container-<key>-summary`) of the agent's descriptor label, run mode and target, then each field set away from its default in the descriptor's order (a choice's label, a typed value, a toggle's label), then `N env`, absent parts omitted (`Claude · Interactive · new worktree from main · Accept edits · opus · 2 env`). The row's tooltip is `Last launch: <summary>`, and a never-launched row stays 30 px.

  A click focuses the container row and folds it; while the sidebar holds keyboard focus the focused row draws the 2 px `ACCENT` ring (`container-<key>-focus`), Up and Down move that focus among the visible container rows, Enter and Space fold, and Esc clears it and returns the keyboard to the terminal.

  The focus also clears on a Repos/Tabs switch, a Repo filter change, a switch of the activity rail away from Sessions, a fold of the sidebar, and when its container leaves the list, so the keys never act on a row that is not drawn.

  A repo's or workspace's row shows a launch ▶ at its right while the pointer is over it or it holds the keyboard focus (`container-<key>-launch`, hover `Launch last again in the current tab`); it replays without folding the row.

  The ▶ goes once the pointer leaves the window (`sidebar::shown_hovered_row`; Windows sends no mouse-exit event, only the window's hover change) and when the sidebar folds or switches away from Sessions; the row's own hover background is GPUI's `.hover()` and can stay until the pointer next moves in the window.

  A double-click on the row replays into the current tab too: its first click still folds or unfolds the row, and its second replays instead of folding again. Two launch gestures for one container within 500 ms count as one, so a double-click or a repeated ▶ launches once.

  With no stored config, both open the spawn dialog locked to the container; a config in Bypass permissions mode replays like any other, with neither toast nor dialog; a worktree config waits for the daemon's fresh `SuggestBranchName`, replaying with that name (a reply is matched by its `request_id`, and a timeout raises `Couldn't pick a branch name for launch-last`), while an in-place config replays at once.

  A stored config that is headless (`SessionMode::Headless`) is never replayed: the row gesture (double-click or ▶) launches nothing, opens no dialog and raises a Warning toast `Headless runs aren't supported in this client` with no detail, and `Launch last again ▸` is dimmed with that text as its tip, its click doing nothing.

  A captured config drops the one-shot answers a launch gave — the worktree-collision policy (back to `Reuse`) and an in-place target's `checkout_strategy` (back to `None`) — so a replay, a duplicate, a recovery or a resume never acts on a collision or dirty tree nobody was shown.

  A tab container's row has its own right-click menu, one row, `Spawn session here`, on a grid tab only; a diff tab's menu has no rows. It fixes Open in to that tab and starts the dialog on the target of the tab's first session, when it has one, leaving the target picker free; if the tab goes while the dialog is open, the lock drops and placement falls back to the current tab, else a new one.

  A DIR or SH container draws a folder banner under its row while expanded (`container-<key>-banner`): the folder path on one truncated line (`container-<key>-path`), then `Add repo` (`container-<key>-add-repo`, hover `Add repo: <folder>`) and, once the folder's scan answers with a suggestion, `Add workspace` (`container-<key>-add-workspace`, hover `Add workspace: <suggested name>`). The links keep their room while the path ends in `…`.

  The banner folds with its container, and only DIR and SH containers draw one: a repo, workspace, tab, Unbound or Detached container never does, nor an SH with no cwd.

  A registered folder that is not a git repo is a repo container tagged `DIR` with the folder icon, where a git repo keeps `REPO` and the branch icon; its menu, ordering and drag are the repo container's, and the jump palette's row for it reads `[DIR]`. Source Control and Stashes leave it out of their repo lists.

  `Add repo` registers that folder straight away (`AddRepo { path, name: None }`), opening no picker and leaving the toolbar's Add repo… start folder (`last_repo_dir`) alone. `Add workspace` accepts the scanned `VscodeWorkspaceSuggestion` as it stands (`AcceptVscodeWorkspaceSuggestion { watch: false }`), with no creator dialog and no `needs 2 repos` gate.

  The client sends `ScanVscodeWorkspaces` once for each distinct DIR or SH folder on a connection, keyed by the folder's normalized path (case-folded on Windows): a folder first seen in a session list or update, or regrouped by a repo or workspace registry change, is scanned then, and the same folder is never rescanned. Answers for a folder are dropped on `Welcome` and while the connection overlay is up, so a reconnect scans again.

  An expanded Detached container shows: `These sessions are still running, but their repo or workspace is no longer registered.` The toolbar's `⋯` menu gains `Resume all abandoned (N)` under a separator when N ≥ 2, sending `ResumeAllAbandoned`.

  While one of its leaves still runs, the banner also carries a two-click `Stop all` chip (`detached-stop-all`, hover `Stop every session still running in this container`): the first click arms it to `Confirm: stop all` (`Click again to stop every running session`), the second stops every leaf that still runs, and Esc disarms it.

  The chip is absent while every leaf is stopped or the activity rail is on another panel, and an arm is dropped when the container or the sidebar folds, or the rail leaves Sessions.

- **Workspace creator** (`workspace_creator.rs` model, `workspace_creator_view.rs` view): `Add workspace…` follows `Add repo…` in the `⋯` menu; under two repos it draws muted with `needs 2 repos` and does nothing, and the menu's tooltip names only the rows shown. It opens `New workspace`, with `From repos` and `From VS Code workspace` tabs; From repos needs a name and at least two ticked members, and says `No repos registered yet.` when none exist.

  From VS Code workspace parses the picked `.code-workspace` file, showing `Parsing workspace file…` then the suggested name and its folders in file order with `registered` / `will register` badges under the `Workspace name` label; a parse failure shows the daemon's message inline, else `Failed to parse workspace file.`.

  The file picker filters to `.code-workspace` on Windows and opens at `last_vscode_dir`, else `last_repo_dir`, storing the picked file's folder. On a remote host the tab shows the label `Workspace file on {host}` and a path field (`workspace-creator-file-input`) in place of the file line and Browse: Enter sends `ParseVscodeWorkspace` with the typed host path, a refusal shows inline, and From repos says `No repos on {host} yet.` when none exist.

  Create keeps the dialog open until a `Workspaces` broadcast holds the trimmed, case-insensitive name; an `Error` with no `request_id` shows inline with the typed name and ticks intact and raises no toast, while a routed `Error` takes the generic path.

- **VS Code workspace detected** (`vscode_suggestion.rs` model, `vscode_suggestion_view.rs` view): the daemon's suggestions queue and show one at a time. The prompt shows the file path in monospace, `<path> references N folders. Create a rustling-tulip workspace named <name> with these members?` with the name bold, then the folder badges.

  The buttons are `Not now` / `Create` / `Create & watch` (tooltip `watch the file and re-sync members`), dismissed by ✕ (`Dismiss suggestion`) or Esc; `Create & watch` sends the watch flag, and answering shows the next queued prompt.

- **Preset wizard** (`preset_wizard.rs` model, `preset_prompts.rs` prompt parsing, `preset_launch.rs` preview grouping, job registry and toast text, `preset_wizard_view.rs` view): a modal opened from the container menu's `Launch preset…`.

  Its stages walk the preset's prompt source (a prompts file through a filtered file picker, a folder, inline text or GitHub issue ranges, limited to the sources the preset allows) and then its prompted variables (text, folder and file with `Pick…` and `Clear`, case-insensitive toggles).

  The last stage is Preview: `{n} prompt(s) ready to spawn.` (plus ` → {t} tab(s).` when the preset groups by tab), the prompts as `[n] first line` under `Tab i of m` headers, a `Max panes per tab` field (hidden without tab grouping; blank takes the preset's cap, a preset cap of 0 counts as 1; input that is not a whole number of 1 or more disables Launch with an inline message; read-only while scripts run) and a `Scripts to run` section listing each script command with its variables filled in.

  Launch runs the scripts on the daemon first, then sends `LaunchPreset` with a client-made job id and closes the dialog; a script failure stays on Preview with the error inline and the failing script's row marked in the danger colour, and the button reads `Retry script(s) & launch …`. Esc, Cancel and Back wait while the scripts run.

  The wizard belongs to its host. Opening it on an offline remote host toasts "{host} is offline" instead. This PC's connection overlay and This PC's new `Welcome` close a This PC wizard only; a remote host's wizard closes when that host's connection drops or resets, and stays open while This PC is down.

  This PC's overlay still covers the whole window, so a remote wizard cannot be used until This PC returns (RT-865). A notice closing hands the keyboard back to the wizard, not the terminal.

  Opened from a remote host's repo, the wizard's folder and path rows take typed paths on that host, and a folder source's default is under that repo's path on the host.

  Progress outlives the dialog. A job registry in `RootView` tracks only the jobs this window started, so another window's launch raises no toast here.

  Each job has one sticky toast, `Launching {preset}` with `{created} of {total} sessions · {tabs created} of {tabs} tabs`, a thin progress bar (`notice_view.rs`) and a red `Cancel` button (`CancelPresetLaunch`), replaced in place by a `Launched {preset}` or `Cancelled {preset}` toast; a failed job raises one sticky warning, `Preset launch failed: {preset}`, with the daemon's reason. Closing a running job's toast keeps it closed until the job ends.

  A job's `Cancel` and `Stop all` send `CancelPresetLaunch` to the host the job runs on.

  Success and canceled toasts stay timed and keep `Select` and a red `Stop all` until they fade; a failed launch's toast is sticky until ×. A job leaves the registry when its terminal toast closes, times out or is pushed out. On `Welcome` running jobs and their toasts drop, and ended ones keep theirs. Toast buttons are generic (`ToastSpec::actions`, selectors `toast-action-<toast id>-cancel|select|stop-all`).

  `Select` tints the job's sessions in the sidebar (palette `LAUNCHED_TINT`) and shows the Sessions view; on a running launch the tint follows the job, so sessions it makes later are tinted as they arrive. A user's session click (sidebar leaf or Needs You row) or `Welcome` clears the tint; a programmatic selection does not.

  It only highlights. `Stop all` stops the job's live created and partial sessions with no confirm and keeps their worktrees; on a running launch it sends `CancelPresetLaunch` first. `Cancel` leaves the toast once pressed. For a tab-grouping launch the first tab the job creates is shown once its id is known.

  A non-optional prompted variable is required and a toggle never is: `Next` stays disabled with the tooltip `Fill in: <labels>` until each is filled. The last stage's `Next` is disabled with the tooltip `Preview and launch arrive with the next update`. Esc, or its host's lost connection or new `Welcome`, closes the wizard.

## Daemon connection and protocol

- The client ensures the daemon through `crates/daemon-client` (`ensure_running`, passing `NATIVE_PROTOCOL_VERSIONS` from `net.rs`). A running daemon is reused when its supported versions intersect the client's, even from another build, so the client never fights another client over a stale binary; a daemon sharing none is retired through `/shutdown` and replaced, and its tracer sessions reattach.
- daemon.json carries `supported_versions` (`#[serde(default)]`; an older file reads as its scalar `protocol_version`).
- The native client speaks only the current protocol version, and the daemon's `supported` lists only that version; there is no TypeScript mirror on `main`.
- **Client identity**: the native client keeps its id in the file `client-id-native` and sends it in `Hello`; the daemon keys its tab layout on it.
- **Reconnect**: backoff 0.5 s → 10 s, a standby-resume watchdog, a connecting overlay with "Restart daemon" (This PC's only), and a footer pill with a troubleshooting flyout (This PC's). After a user-chosen shutdown the client never reconnects or respawns the daemon.
- **Connection target** (`target.rs`): `Target::Local` is the loopback daemon above (`ensure_running`, `ws://127.0.0.1:{port}/ws`, the `daemon.json` token). `Target::Tailnet(TailnetHost)` names a MagicDNS host (lower-cased, trailing dots trimmed, port default 8787) and dials `wss://{name}:{port}/ws` over TLS that trusts the OS certificate store (rustls, config built once per net thread); there is no plaintext or self-signed fallback, and an empty store fails closed.

  A tailnet target never runs `ensure_running` and never sends `Shutdown` or Stop; its `Hello` carries the device token read from the `DeviceTokenStore` (`NetDeps.tokens`), and a host with no stored token, or an unreadable store, is dialled with an empty one. The client holds one connection per host, each with a generation: events from a replaced connection are dropped. There is no target switch.

  `Target::Ssh(SshHost)` names an `~/.ssh/config` alias or `user@host[:port]`, kept exactly as typed; one that is empty, starts with `-` (ssh would read it as an option), holds whitespace or a control character, or has an empty side of its `@` is refused (`Target::parse_ssh`). The client runs `ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ConnectTimeout=10 -o Compression=no -- <host> <remote command>` with no console window (`ssh.rs`), the remote command defaulting to `rustling-tulipd bridge` and a saved host's `remote_command` replacing it, and speaks the protocol as one JSON message per line over its stdio.

  The SSH login is the owner: there is no device token and no pairing, because the bridge on the host fills the `Hello` token. `BatchMode` means ssh never prompts, so an unknown host key or a key needing a passphrase fails with ssh's own text; when ssh's stdout ends the connection closes with `daemon closed the connection: ` and the last 2 KB of ssh's stderr, trimmed. The ssh binary is `RUSTLING_TULIP_SSH` (empty counts as unset), else `ssh` on PATH, else `%SystemRoot%\System32\OpenSSH\ssh.exe`; none found closes with `ssh was not found: install the OpenSSH client or set RUSTLING_TULIP_SSH to its path`.

  An SSH target is a remote host like a tailnet one: no `ensure_running`, no Shutdown or Stop, local-file actions off, Restart reads "Reconnect now". The pairing views never act on it: a `PendingDevices` the daemon pushes on a loopback connection is ignored there (no Waiting devices rows, no toast).

  On a remote host Restart becomes "Reconnect now" (reconnect without touching the host's daemon, and the way out of `AuthFailed` and of `NotApproved`) and Stop is unavailable. A remote host's state shows in its Connections row chip and on its sidebar header's dot (see Host groups), not in the footer pill, the overlay or the flyout, which are This PC's.

  **Remote mode** (`remote_mode.rs`): views ask a capability table per host (`RootView::capabilities_of(&HostKey)` over `Capabilities::for_target`), never a target; the window has no remote mode of its own, only hosts whose capabilities are remote.

  Local-file actions (Reveal, Open in Explorer or VS Code, the Browse buttons and the preset wizard's Pick… buttons; these pickers go through `RootView::pick_local`) stay visible but disabled with the tooltip "Not available on a remote host: this opens files on this PC", and a refused click toasts "Couldn't open" with that detail; a Ctrl+click on a terminal path link fetches the file instead (see "Fetched files").

  Where a path must name a file or folder on the host, the view takes it typed instead: Add repo, the workspace creator's `.code-workspace` file and the preset wizard's file and folder rows (source and variables, the folder row prefilled with its default) and the Shell… dialog's folder are text fields checked by the same host-path rules (`repo_add.rs`, `check_host_path_rules`: not empty, absolute in Windows or POSIX form, no `..`), and a failing row shows its refusal and holds Next.

  Copy path stays, since it touches no file. Stop, the Handshake file row and Open daemon.log are hidden, because they act on the host's process and files. Closing the window runs This PC's quit flow: it stops This PC's daemon (or leaves it running) as it always did, and every remote host is only disconnected, sent nothing.

  **Host path prompt** (`host_path_prompt.rs` model, `host_path_prompt_view.rs` view): Add repo is the one local-file action a remote host keeps, as a typed path. Its five entries (the sidebar note button, the ⋯ menu row, the empty-pane button and the spawn dialog's no-repos button, by click or Enter/Space) open a modal "Add a repo on {host}" instead of the folder picker, which stays the local behaviour; the ⋯ row's tooltip reads "Type the path of a folder on the host to register as a repo".

  The field (placeholder "Full path on {host}", hint "A git repo or any folder on {host}.") has Cancel and Add after it: Tab cycles field, Cancel, Add; Enter adds and Esc closes. Add sends `AddRepo { path: the trimmed text, name: its last segment }` and closes, and a daemon refusal arrives as the usual error toast.

  The host may run another OS, so the client checks the text by string rules only (`repo_add.rs`, `RepoAdd::from_host_path`, `HostPathProblem`, `host_workspace_file`): empty, not a full path (a drive letter, `\\server` or `/` start) and a `..` segment are refused inline with the field kept, and the workspace creator's file field also wants a `.code-workspace` name. A typed host path never reads or writes `last_repo_dir` or `last_vscode_dir`.

  The remembered quick-shell folder is this PC's: on a remote host `+ Shell` and an empty pane's Shell here send no folder (the host daemon's default), and the Shell… dialog neither prefills it nor offers to save or clear it.

  Its folder is judged by those host-path rules: the hint reads the Add repo prompt's refusal for that host ("Use a full path on {host}, starting with a drive letter, \\server or /." or "Use a path without .. in it.") and the placeholder reads "A full path on {host}". On this PC the check stays this PC's full-path rule, with the hint "Enter a full path, like C:\Users\you".

  The daemon itself refuses a standalone shell or agent folder that is not a full path by its own OS's rules, answering with "Couldn't start session" / "The folder must be a full path on this host.".

  On a tailnet target `Welcome` is held until the next frame: `Welcome` then `DevicePairFailed` "device not approved" gives `State::NotApproved { reason, had_token }`, the socket is kept, nothing reconnects on close, and only Reconnect now redials. The host's row chip reads "Not paired" and offers `Pair` and `Reconnect now`.

  **Pair dialog** (`device_pairing.rs` model, `device_pairing_view.rs` view): "Pair with {host}" opens only from that host's row `Pair` button, never from the footer pill and never by itself at launch or on a reconnect. A not-approved tailnet host still reports its daemon id, so a duplicate of another connection is dropped before it offers Pair.

  Intro ("{host} does not know this PC." or "{host} no longer accepts this PC's pairing.") offers Ask to pair and Close. Asking ("Asking {host}…", Cancel) becomes Waiting ("Approve this PC on {host}.", `expires in m:ss`, a keyboard-reachable `Have a code?` link, Cancel) until the owner approves on the host PC.

  `Have a code?` reveals the 6-digit field with Pair and Cancel while the wait continues: Pair sends `DevicePairRedeem`, so a code minted by `rustling-tulipd pair` on the host can be typed there.

  A wrong or expired code shows in the same refusal line as CodeEntry's and the request keeps waiting, while a failure that ends the request (remote access off, too many attempts, device not approved) ends it with its reason.

  An approval meanwhile moves the dialog to CodeEntry with an empty field (a code typed while waiting is cleared, since the approval has its own code). CodeEntry ("Type the code {host} shows.", a 6-digit field, `code expires in m:ss`, a refusal line, Pair, Cancel). Paired closes the dialog: the net thread stores the token and reconnects.

  When the host refuses a request that has gone out (the net thread emits `NetEvent::PairRequestSent` after writing it; a blocked device is refused this way), the dialog ends on "{host} did not accept this PC's request." with Ask again and Close, instead of spinning.

  Denied, expired, superseded, ended, a dropped connection, "Could not save this device's token; pair again." and the host's own reason end on a line with Ask again and Close; a failed redial after Ask again withdraws the request. Esc sends `PairCancel` while a request is out. The typed code never reaches a log. One token store (`RootDeps.tokens`) is shared by the net thread and the view: the production `Transport` captures it for `NetDeps::production`.

  `native.log` records at info "device pairing: the dialog opens" (fields `host`, `had_token`), "… asking the host", "… sending the code", "… withdrawing the request" and "… paired; the dialog closes", and warns "device pairing: the token was lost with no dialog open".

  **Several hosts**: one window shows This PC and every saved tailnet and SSH host at once. Tabs can mix hosts, so one tab may split panes from different hosts. This PC's daemon is the layout home: it holds every tab of the window, a pane names its session as `{host, session_id}`, and a remote daemon supplies sessions only (its own per-client layout for this client is ignored). This PC is always connected.

  Every enabled saved host connects at launch and stays connected, and Connections gives each an on/off switch that is remembered; there is no target switch, no remembered last target and no boot target. An offline host keeps its sidebar group and panes, dimmed, with its last frame frozen, and the other hosts are unaffected; only This PC, the layout home, has a window-wide connecting overlay.

  Entry points with no host of their own reach every host: the spawn dialog's picker lists every connected host's repos and workspaces grouped by host, the quick shell goes to the focused session's host (else This PC), and a container's menus spawn on its own host. Settings has a host selector (below). Notifications, Needs You and the Dashboard span every host, their rows carrying a host chip when more than one host is configured, and pairing is per host: a host that is not approved shows `Pair` on its sidebar header and Connections row, never a window overlay.

  The host key is `Target::host_key()` (`HostKey::of(&Target)`): a tailnet host's lower-cased MagicDNS name or `ssh:<host string>`, and `None` on the wire for This PC. One formatter serves `host_session_counts`, `HostKey` and the wire `host`, so a tailnet port change does not orphan that host's panes.

  **Launch and daemon-id dedupe** (`hosts.rs`: `connect_saved_hosts`, `connect_host`, `disconnect_host`, `on_host_closed`): launch connects This PC (always local, always connected, with no switch) and then each enabled saved host in saved order.

  Two keys that reach one daemon are ranked (`hosts.rs` `rank`, `drop_if_duplicate`): This PC first, then a saved host by its index in `saved_hosts` (switched on or off), then any other key by its text. The lower rank owns the daemon, whichever said `Welcome` first, and a key whose connection is not open (a pairing connection) never owns.

  The other key is disconnected and its rows cleared, its row reads "Same daemon as {owner}", and it redials when its owner goes; a lower-ranked key that welcomes later takes the daemon back and drops the owner the same way.

  When This PC's connection drops, its remote alias is not redialled. `native.log` records at info `two connections reach one daemon; keeping the first by saved order` (fields `owner`, `duplicate`).

  **Rehost** (`hosts.rs` `rehost_target`, `rehost_stranded_panes`): panes keep a fixed owner. When a dedupe drops a key, when This PC's tab list arrives and before each prune, the client sends `RehostPanes { from, to, session_ids }` to This PC, which rewrites the host of each pane in this client's layout only whose host is still `from` and whose session is in `session_ids` (`to` absent is This PC).

  The moved sessions' remembered views (`session_views`) move with them to the target's key as the message is sent, the target's own entry winning, so a session remembered in Chat or Summary reopens there.

  A changed tab answers with its `TabUpdated`. No match sends nothing, and a failed layout write answers `Error` code `tab_refused`. A refusal that holds a session refused for the first time is sent again at once; one naming only sessions refused before waits for the next pass.

  `session_ids` holds only sessions the owner currently lists, so a pane of an ended session stays on its old key and is pruned there.

  Forget in Connections on a host whose daemon another saved, switched-on host reaches moves its panes to that host instead of closing them, and switching such a host off moves them the same way and back when it is switched on and takes the daemon again. Forgetting a host in favour of one that was itself forgotten records the later target (`record_forgotten_rehost` keeps the map one hop deep), and forgetting the target later passes its forgotten hosts on to the new one.

  The stale-host sweep skips a host with a rehost target or a rehost in flight.

  A saved session pop-out of such a host reopens at launch on the owner (its `native-ui.json` `popouts` entry is rewritten to that key), an open one keeps its window and re-attaches on the owner's connection, and undo restores such a pane on the owner instead of empty.

  **Per-host state** (`hosts.rs`, `sidebar.rs`): sessions, repos, workspaces, agent descriptors, daemon-settings mirrors and capabilities are kept per host, and notifications, held toasts and Needs You are keyed by (host, session) across every host. A remote host's Welcome runs `reset_host` for that host alone, and its disconnect clears nothing.

  A host's new connection or removal drops only that host's queued cleanup failures (with the labels remembered per host and session) and its running preset-launch jobs and their toasts; This PC's reconnect leaves a remote host's alone, and when a remote host's cleanup-failed dialog is up the dialog keeps the keyboard.

  This PC asks its layout question with the first-connect chooser. A remote host's is answered Start empty at once, with no chooser: Open all, Adopt previous layout and Copy another client's layout would only seed that host's own layout, which this client never shows, since This PC is the layout home. This PC's tab list works as before.

  The Dashboard watches every connected host and its rows show together; the header's day figures are This PC's. Source control keeps one model per host and shows the focused session's host when that session names repos, else the pinned repo's host, else This PC; reads and writes go to the shown host, and a message from another host never touches the commit box. File fetches record their host, and a host's disconnect ends only its own. Recover lists history per host (a muted host name heads each host's rows when there are several), sends `RecoverSessions` per host, closes once every host answered, and fails a silent host's rows with "Recovery did not answer" (the timeout keeps watching the hosts still out). A remote host's `Devices` and `PendingDevices` lists are ignored, and the cleanup-failed dialog keeps its failure's host (Retry goes there; Open folder is off for a remote host).

  A remote host that is offline, connecting, switched off, not approved or a duplicate keeps its sidebar rows, drawn at 0.55 opacity (still clickable); This PC's never dim. A dimmed host's leaves do not drag, and a drop of one already in flight when its host drops is refused, so no pane is bound to a session its host cannot show. Each pane, pop-out and banner names its agent from its own host's descriptors. Forget drops the host's connection, device token, sidebar rows and session count. A saved remote-session pop-out waits for its host's session list instead of being dropped at launch.

  **Host groups** (`sidebar.rs` `host_groups`, `sidebar_view.rs`; `tab_bar.rs` and `grid_view.rs` for the chips): when This PC plus at least one saved host are configured, the Repos view groups by host under a 26 px header per host: This PC first, then saved hosts in saved order, then other connected hosts by key. A header has a chevron, a 6 px state dot, the name ("This PC" or the short name), the state text "Connecting…", "Offline" or "Not paired" where it applies, and a `+ Shell` button (tooltip "Open a shell on {name}", disabled "{name} is offline" unless the host is online) or, on a not-approved host, `Pair` (tooltip "Pair this PC with {name}"). A host's repos, workspaces and Shell, DIR and Detached containers nest under it, and the toolbar Shell button is hidden while the groups show. The Tabs view does not group by host: a tab lists the sessions its panes show on any host, each looked up on its own host, This PC's first in the tab's stored order and other hosts' after them in pane order, and a leaf from another host ends its name row with that host's Host chip (`sidebar-host-<short name>-<session id>`); Unbound lists This PC's sessions only. Headers are not keyboard stops: the keyboard walks the containers of the unfolded hosts. A host's fold is saved in native-ui.json `collapsed_containers` as `host:local` or `host:<host key>`.

  `+ Shell` on a remote header sends a plain shell with no folder straight to that host (`quick_shell_on`); This PC's is the toolbar's quick shell. A remote session's pane header and pop-out header carry a host chip with the host's short name (full name on hover), and a tab whose session panes all sit on one remote host shows it on its pill (`sole_remote_host`). This PC never gets a chip, and neither does a tab that mixes hosts.

  **Mixed tabs** (`tabs.rs` `SessionRef`, `hosts.rs` `HostSender`, `spawns.rs`, `drag.rs`): a pane names its session as a (host, id) pair, `SessionRef`, so two hosts' sessions with one id are two panes, two tab-pill counts and two slots.

  Layout messages (`CreateTab`, `SplitPane`, `MovePane`, `ExtractToNewTab` and the rest) go to This PC with the session's host in the message; session messages go to the session's own host. A remote spawn or duplicate is placed into This PC's layout, and a restart keeps its original host. A remote session drags into any tab, and the sidebar leaf, the Move to ▸ menu and undo all compare pairs. A sidebar leaf dropped into a tab (on a pane or a pill) sends the tab request with its session's host named in the message (`host` absent for This PC's session), and sends nothing while that host is not connected (`drag::leaf_drop`).

  A remote repo's or workspace's container menu acts on the host whose row was right-clicked, so each entry (Spawn session, Shell, Launch edit, Explorer, VS Code, Copy path, Remove, Launch last and its "Last (…)" summary, presets and the preset wizard) goes there, and Copy path copies that host's path; the menu closes when its own host drops the container. The delete-worktree dialog from a remote session's menu asks that host for branch fates, ignores a preview from another host and sends the delete there. The spawn dialog asks its target's host for env names, again when the target moves to another host. A restart is blocked only by a restart of the same session on the same host, a pane header's Stop arms only the pane clicked, and the cleanup-failure queue keeps separate entries for two hosts' sessions sharing an id.

  A remote host's sidebar leaves have selectors `leaf-<host key>::<id>` (and `-label`, `pill-`, `provider-`, `state-`, `glyph-`, `badge-`, `runtime-`, `busy-excluded-`, `subline-`, `chips-`, `resume-`, `dismiss-` alike); This PC keeps `leaf-<id>`. A leaf's click, Resume, Dismiss and pill, the Needs You row click, a toast's Go to pane, session notices (toast key `session-notice:<host key>::<id>` for a remote host), stale-session cleanup, in-flight appearance sends (a remote reconnect clears its own), pop-out, the quit walk and Remove's session count all act on the session's own host. Opening a session clears attention and unseen marks on its own host only. The pane-close dialog records its host when it opens, stays open while that host is offline, closes once the host no longer lists the session, and never falls back to This PC.

  A pane's input, resize and query replies go to its own host through that host's `HostSender`, a handle the host's connection fills and clears, so a reconnect needs no pane rebuilt. A remote host's panes re-attach once, at its first `Sessions` after `Welcome`. A remote host's `Welcome` leaves This PC's pending diff and viewer opens alone, and the Fetch file dialog closes and deletes its part when the host it fetches from drops.

  **Pruning** (`hosts.rs` `prune_remote_panes`, `forget_host_panes`): on a remote host's `Sessions` or `SessionRemoved` and on any This PC tab fold, the client first looks for a session whose `resumed_from` holds a pane's id and, when one is listed, sends `RebindHostSessions` to This PC, which replaces the id in this client's layout only (the host-less rebind a resume, auto-resume or recovery makes still spans every client's layout), compare-and-set on (host, old id); a refusal is retried by the next prune. It then sends `ForgetHostSessions` to This PC with the ids that are missing and have no successor. It is level-triggered and sent once per (host, id) pair per This PC connection, and never for a host that is offline, switched off, a duplicate (its panes are rehosted, see above) or not approved.

  Forget in Connections sends `ForgetHostSessions` with `all: true` (queued while This PC is offline), and a sweep once per This PC connection forgets every host that is no longer saved. `native.log` records at info "forgetting every pane of the host on This PC" (field `host`) and "forgetting the panes of sessions the host no longer lists" (fields `host`, `missing`).

  **Host picker** (`connection_picker.rs` model, plain Rust; `connection_picker_view.rs` view): the footer's `Connections` button, left of the daemon pill on every target, and a `Connections` link beside `Reconnect now` in the first-connect overlay open a centred modal drawn above that overlay, and no key reaches a layer under it.

  The modal is one 440 px panel kept 24 px inside the window, its list scrolling, in three sections: "This PC", "Saved hosts" (with its count; hidden when empty) and "On your tailnet" (its note beside the title reads "N online" or "Looking for your devices…"; a failed scan's error is drawn on its own lines under the title instead; hidden once a scan offers no unsaved peer).

  Every host is a row with a kind icon (`assets/icons/host-pc.svg`, `host-tailnet.svg`, `host-ssh.svg`): the name (a tailnet suffix greyed) over a second line ("This PC's daemon · 7 sessions", "Tailnet · port 8787 · 3 sessions last time", "SSH · rustling-tulipd bridge", "Online · port 8787 · connecting saves it"), and a state chip. A host that reported a parseable release ends its second line with it in the mono face ("Tailnet · port 8787 · v0.9.0"), and one on an older release than this client wears an amber `Behind` tag (`connections-behind-{key}`) at the row's trailing edge, the state chip keeping its own state; a host not yet paired shows no version.

  Every row's second line wraps between whole pieces, each "·" staying with the piece after it, and a piece wider than the row wraps inside itself. A connected host shows its live session count without "last time". A saved host's row also has an `On` switch (`connections-row-{key}-enabled`) and, on a third line when they apply, `Pair` and `Reconnect now` buttons. Every row whose connection is open, This PC's included, has an `Open shell` button (tip `Open a shell on {host name}`, `connections-row-{key}-shell`) after those two in the row and its Tab order, which opens a plain shell on that host as the sidebar's `+ Shell` does.

  The chip reads `Off` (switch off), `Same daemon as {This PC | short name}` (a dedupe duplicate), the live state ("Connected", "Connecting…", "Disconnected") or `Not paired` (a not-approved tailnet host, or a saved tailnet host with no stored device token; a saved SSH host is never "Not paired"). Tokens are read once, when the modal opens; an unreadable store warns "reading the host's device token for the picker: …".

  Picking a saved row flips its switch. Picking a peer saves it on and connects it, and `Add host` saves the typed host on and connects it (a known host's saved port is updated); each writes `saved_hosts` in `native-ui.json`. Switching a host off disconnects it, and on connects it. The modal stays open. The header X is mouse-only. Esc closes an open add form first, then the picker.

  One `+ Add host` opens an inline form with a Tailnet | SSH switch. Tailnet has Name and Port (prefilled 8787) fields with Cancel and `Add and connect`, and a refusal shows under them and sends nothing. Each mode keeps its own typed fields when the switch moves away; Cancel and Esc drop the typed text.

  Forget sits on a saved row and shows on hover or when Tab reaches Forget itself (focus on the row keeps the chip); while hidden it still takes a click. It rewrites `saved_hosts`; for a tailnet host it also deletes the host's device token (a failure warns "deleting the forgotten host's device token: …" and toasts "Couldn't forget this host's device token"), and for an SSH host it deletes no token and drops the `ssh:<name>` session count.

  Forget also drops the host's connection, sidebar rows and session count, and sends `ForgetHostSessions` with `all: true` to This PC so the host's panes leave every tab of this client's layout. An SSH host and a tailnet host of one name are listed and forgotten separately.

  The SSH mode of the add form has Host (placeholder `devbox or user@host`, an alias from the SSH config or `user@host`) and Remote command (placeholder `rustling-tulipd bridge`) fields, the test result line and the buttons Cancel, `Test connection` and `Add and connect`. Refusals show under the fields and send nothing: "Type an SSH host: an alias from your SSH config, or user@host.", "An SSH host cannot start with a dash.", "An SSH host cannot contain spaces or control characters."

  `Test connection` runs ssh as a connection would, sends a `Hello` with an empty token and no client id or name (so it keys no tab layout), and shows "Testing the connection…", then `Connected: <short name>`, ssh's stderr verbatim, the daemon's `AuthFailed` reason, "ssh ended without an answer." (or "…: <error>"), or "No answer from the host in 20 s." with the stderr so far. The 20 s guard sits on top of ssh's own 10 s connect timeout, and the button reads `Cancel` while the test runs, killing the ssh child. Enter in an SSH field runs the test; editing a field cancels a running test and clears its result, and so does switching to Tailnet mode.

  `Add and connect` needs no passing test: it saves `{"kind":"ssh","name":…,"remote_command":…}` with no port, replacing any record of that name whole, and connects it. An SSH host never asks for pairing.

  The model: the rows are This PC, then the saved hosts in saved order, then the owner's peers from `tailscale status` that are online, untagged and not shared in (peers pass the DNS-name check and dial port 8787; a peer that is also saved is listed once, with the saved port).

  A typed host is checked as the name first, then a port of 1 to 65535, and each refusal's `Display` is the message shown. A failed scan keeps the saved rows and shows `TailnetError`'s `Display` text. The scan runs on a one-shot thread with its own current-thread runtime behind the `PeerSource` seam, so neither the UI nor the net thread waits on it.

  **Saved hosts**: `native-ui.json` keeps `saved_hosts`, each entry with a `kind` (`"tailnet"` when missing, or `"ssh"`) and an optional `"enabled": false` (only a disabled host writes the key; a missing key means enabled): `{name, port}` for a tailnet host, `{kind, name, remote_command}` with no port for an SSH host. The client reads them before it starts the net thread and connects each enabled one after This PC, never running `ensure_running` for a remote host; a saved host that cannot be reached is still connected and shows its state.

  The per-host session count for an SSH host is keyed `ssh:<host string>`. A hand-edited `saved_hosts` entry that fails the DNS-name check or has a port outside 1 to 65535 is dropped on load with a warn, its name normalised otherwise.
  On a remote host the empty-registry notes name the host (`No repos or workspaces on {host} yet.` in the sidebar, `No repos on {host} yet.` in the spawn dialog); the sidebar note shows only once that host's repo list has arrived (`SidebarModel::repos_loaded_of`), not while it is still connecting. Reconnect now in the flyout or the overlay redials the same host.
- **Request ids**: a client that must match a reply to its request sets the optional `request_id` (spawn, duplicate, scrollback, appearance, git reads, spawn previews, checkout prompts, session history, recovery, env names, branch-name suggestions, and the tab requests `CreateTab` / `MergeTabs` / `MovePane` / `ExtractToNewTab` / `SplitPane`), and the daemon echoes it only to the requester ([wire-protocol.md](wire-protocol.md)).

  A tab request's id comes back only on the refusing `Error`, which a refused split also logs at warn as `tab layout request failed`.

  A new tab, merge or move-to-new-tab arms a pending create (an ordered queue of request ids; the oldest is consumed when a new tab arrives, which becomes active); the refusing `Error` disarms its id and a `Welcome` forgets every armed one, so a refused request never makes the next arriving tab active.

  The client also keeps tab-layout requests in flight per tab (a split; a move, for its source and destination tab): the tab's next `TabUpdated` ends the oldest entry, `TabRemoved` ends all of them, the refusing `Error` ends its own, and `Welcome` forgets every one; closing a tab's last pane while one is in flight does not mark the tab closing. Adding one is additive; a reply without one (an older daemon) falls back to matching by content.

  The spawn dialog's `SuggestBranchName` asks without one, so every suggestion for its target still reaches it, while a launch-last wait takes only the reply carrying its own id.

- Unknown daemon message types are logged with their tag and skipped; a frame that fails to decode is logged as an error.
- The client logs to `logs/native.log`, rotated on each launch.
- On Windows a build without debug assertions (release, test-release) is a GUI-subsystem exe, so an installed launch opens no console window; a debug build keeps the console and its stderr log.

## Persistence

Machine-local UI state lives in native-ui.json in the config dir (`UiState` in `sidebar.rs`; the field list is in [on-disk.md](on-disk.md)). Tab layouts, session appearance overrides and host settings such as the keep-awake mode and the worktrees root live on the daemon, so every client sees them. Saves are debounced (layout and tab font sizes 500 ms) and flushed on quit.

Settings → Worktrees edits the daemon's worktrees-root override, (a draft sent by OK or Apply), and shows `Saved` only once the daemon has echoed the last send. Manage worktrees (opened from that tab, and offered only while This PC is the chosen host, since it manages This PC's worktrees) lists the root's groups titled by their `.rt-group` name, deletes one group or every stale one, and "Launch session here" opens the spawn dialog with the target locked and that worktree pinned (the spawn form's `Lock`, which a duplicate prefill reuses).

On a remote host the path field stays enabled with the hint "Created on {host} if it does not exist." and Browse stays disabled. Folder and file pickers go through `RootDeps.pick_folder` / `RootDeps.pick_file`, so specs inject fakes: GPUI's test platform cannot prompt. In a cloaked or driven client (`offscreen::requested()`) the deps hold `folder_picker::offscreen_*_picker` instead, which open no dialog, since the desktop would show it: Add repo, Browse, the preset wizard's picks and Settings' picks act as a cancel, Themes Export shows "native dialogs are off in a cloaked client", and each attempt logs a warning.

## Start guard

The client always opens, whatever its saved state holds. `start_guard.rs` marks each run in `start-guard.json` (`{"failed_starts", "last_panic", "run"}`, [on-disk.md](on-disk.md)) and counts the starts that died before the run was stable. The run marker is `{"state", "pid"}`: `starting` when a run starts, `stable` at the stable window, `asking` when a clean end comes while the prompt below is up, `crashed` after a panic past stable; a clean end clears it, and an unknown state reads as `stable`. A run is stable 60 s after the user's choice at the prompt below (on a start that asks nothing, after the first tab list from This PC); a cloaked run waits an hour, so a stalled machine never lets a driven spec's panic land after it. Reaching stable zeroes the count and writes `stable`, and the file stays; a clean end with no prompt up removes it when the count is 0. `main` reads the guard first (`start_guard::begin`) and passes the resulting `StartMode` to `open_main_window`.

- **An unclean end of the previous run** makes the next start ask before it opens any tab (`StartMode::Ask`): a kill from Task Manager, a hard crash, a power cut, or a panic at any time, before or after stable; the user knows better than a count whether the saved layout caused it. A clean quit, Restart to update, Cmd+Q on macOS (the app's quit handler) and a Windows shutdown, restart or log-off (`session_end.rs` hooks `WM_ENDSESSION` on the main window) end the run cleanly and ask nothing. Only a run that died before the stable window adds to the count; a kill after stable asks without counting.
- **A second client** started on the same config dir while the first runs (the marker's pid is alive) neither asks nor counts. A `crashed` marker counts as dead whatever its pid.
- **The prompt** holds This PC's first tab list undrawn (`start_guard_view::HeldStart`) and offers Open tabs or Start without tabs; Enter and Esc mean Start without, the safe answer. Pop-out windows are held until the choice. Open tabs draws the saved layout with its saved views and pop-outs and closes nothing. Start without tabs (the safe start) saves the held list to `layout-set-aside-<UTC stamp>`, sends `CloseTab` per tab, drops the restored views (`active_tab_id`, pop-outs, session views, the Dashboard's view; other settings stay) and clears the saved pop-outs, then shows a "Started without your tabs" toast naming the copy. Sessions keep running either way.

  A newer tab list arriving while the prompt is up replaces the held one. After Start without tabs the closed tabs stay remembered (`start_guard::ClosedTabs`) until the daemon no longer lists them: a reconnect's tab list has them taken out and `CloseTab` sent again, and a `TabUpdated` in flight for one draws nothing. Quitting with the prompt up marks the run `asking`, so the next start asks again without counting.
- **Exactly three failed starts** also move `native-ui.json` to `native-ui.json.corrupt-<UTC stamp>`, once only: `start-guard.json` records it as `ui_set_aside` when the file has gone, so a kill during that start does not repeat it, and a move that failed is tried again. Later failed starts touch no file. Three newest copies are kept per prefix.
- **The stable window starts at the choice**, not at the first tab list, so a crash while the prompt is up still counts.
- **A run that never gets a tab list** (no tabs, or the layout chooser) shows no prompt and writes `stable` once its window passes, 10 minutes (2 hours cloaked), on the app's executor rather than its own thread: a panic then reads as an ordinary crash. A first tab list arriving later starts the 60 s window again. With no tabs to ask about, the third failed start's settings reset is told in a "Window and sidebar settings were reset" toast.
- **The prompt's look** is a modal titled "The last start crashed" (`start_guard_view.rs`) over a backdrop that takes every click; it also says so when the settings went back to their defaults, with the copy's path.
- **A window that fails to open** leaves the run marked, so the next start asks.
- **A main-thread panic** shows a message box from a helper thread (`MessageBoxW` on Windows, `osascript` on macOS), at most once per process, and none in a cloaked run. After a panic past stable the box says the next start asks about the tabs. A background thread's panic stays log-only, since the process carries on.
- **A `native-ui.json` that does not parse** keeps a copy, keeps each top-level field that still reads, and is saved back (`sidebar.rs` `load_ui_state`). The daemon makes a loaded tab list safe in the same spirit (`sanitize_loaded_tabs`), and the client clamps a split ratio when drawing (`drawn_ratio`).

Decisions and rejected alternatives:

- Only a panic counts. Counting every unfinished start was rejected: a kill, an update or a power cut would close the user's tabs. Non-panic crashes are not counted.
- The message box runs on a helper thread. A modal loop on the panicking thread was rejected: it would re-enter GPUI's window procedure.
- The panic is not caught around the draw. It aborts through a Win32 callback, so unwinding cannot be relied on there; the panic hook is the one place that sees it.

Specs: `ui_safe_start.rs`; `native-smoke` holds `two_panics_at_start_ask_about_the_tabs_on_the_next_start`, which uses the driver's `panic` method, panics with the prompt up and expects the count to be 2; `native-shot safe-start` draws the prompt.

## Tab layouts

A client's tabs and their split trees are daemon-side and keyed by client id (`state.rs` `ClientLayout`), so two clients can show the same sessions in different tabs and layouts. A tab's layout type is a `RearrangeLayout`; `TabEntry.picked_layout` records the type last picked for that tab, and holds only while the user has not arranged the tab's panes by hand since.

**Shown tab name** (`tab_name.rs`; `sidebar.rs` `tab_display_name`, `shown_tabs`): a tab nobody named (its stored name is blank, `Tab` or `Tab {n}`, the daemon's default) shows the repo and workspace names of its sessions in pane order, without repeats, joined with ", "; a renamed tab keeps its name. A plain shell counts by the repo or workspace the sidebar files it under; a shell in no repo and an unknown session add nothing, and when nothing adds a name the stored name shows. Remote sessions read plainly. The shown name is display-only, never stored or sent, and every place a tab's name appears uses it: the pill, drag ghost, jump palette, undo message, pop-out cards and their OS window titles, the sidebar Tabs view, per-session tab pills, menus, the Move-panes hint, the spawn form's Open in list, Settings, the window title and the driver's `title`. The pill's label is capped at 240 px and ends in an ellipsis, with the whole name in its tooltip. The rename box starts with the shown name, and confirming it unchanged sends nothing.

A tab's content is a grid, a diff, a viewer or the Dashboard. A viewer tab (`TabContent::Viewer { path }`) stores only the path of the file it shows, in the connected daemon's layout for the client id; it has no panes, so `TabEntry::grid()` and `grid_mut()` return `None` and every pane operation refuses it ("not a grid tab").

A pane can follow a dispatch run instead of holding a session (`Pane.follow`). Such a pane counts as bound everywhere a free pane is looked for (`Pane::is_bound`): spawn and unbound-leaf placement, a moved pane's drop target, a spawn aimed at an empty pane, the tab badge and the close confirm.

A dispatch-run follow draws the run's view (`dispatch_view.rs`): a stats line `{status} · {cost} · {in} in · {out} out` (status `starting`, `working`, `stopping`, `ended` or `unknown`; cost and tokens through `dashboard_rows::format_cost` and `format_tokens`), then the run's transcript in the terminal font, newest at the bottom, following the bottom until the user wheels up (a scroll per pane, reset when the pane follows another run).

The view is read-only: it has no input box.

The pane follows the run's transcript (`RootView::follow_transcripts` sends `FollowTranscript` on open and after each reconnect, and `UnfollowTranscript` once no pane follows the run).

`transcript_view.rs` draws it like Claude Code's terminal: an answer is `● {answer}`, a tool call is `● {Tool}({summary})` with its output under it as `  ⎿  {line}` then `     {line}`, the first 5 lines and `     … +{n} lines` unless expanded, `  ⎿  Running…` while its result is awaited, and a failed output in the danger colour.

`… {n} earlier entries not shown` leads when entries were dropped; thinking and turn-end records draw nothing.

A click on any line of a tool call expands or collapses its output (the expanded set survives a fresh transcript). The client and the daemon each keep the last 500 entries of a run's transcript, an append upserting by entry id.

The snapshot's recent actions (the last 200 the daemon keeps) show until the host answers the follow, on a host that refuses it with anything but `not_found` (an older host's `unsupported_message`), and on a host that does not list `dispatch_runs`; a `not_found` refusal keeps the transcript held. The run folder the sidebar menu copies holds the full stream. A follow kind this client does not know draws a muted note, "This pane needs a newer app.".

A subagent follow draws the same transcript column under its own header (`subagent_view.rs`, `RootView::subagent_body`): the label (description, else agent type, else "Subagent"), `SA · {agent type} · {model}` with the missing parts left out (just `SA` when both are), and the state word `running`, `queued`, `finished`, `failed` or `unknown`, followed by ` · {end status}` when one is set. The pane title stays "Subagent", and it has no input box and no stats line.

Two notes show under that header: "Its session has ended" after a `TranscriptAppend` with `ended: true`, and "This subagent is no longer available" for a refused follow with nothing held.

While a pane follows a subagent the client keeps its last `SubagentSnapshot`, refreshed from each session message and kept when the subagent leaves the list or its session is removed, so the header outlives the row. A Resume that moves the pane's follow to the new session unfollows the old key and follows the new one with no ended note.

The client sends `FollowTranscript` and `UnfollowTranscript` with `TranscriptSource::Subagent` to the pane's host with no feature gate, only while that host connection is open, and follows again after `Welcome`.

Either takes focus on a click.

A followed run's pane header (`dispatch_view::run_title`, `run_stop_controls`) reads the run's title, a `DS · {backend} · tier {n}` chip that truncates down to the session-chip floor, and the status word, with a fixed Stop beside the buttons: Stop arms (`RootView.run_stop_armed`, keyed by host and run id), Confirm stop re-reads the status and sends `StopDispatchRun` with a `request_id` to the run's host, and Stop is disabled with the sidebar menu's tips while the run is stopping or has ended.

The run Stop and a session Stop clear each other's arm, and Escape counts only an arm whose run is still stoppable. `header_fit` counts the chip, status and Stop, so a narrow run pane collapses its buttons into ⋯. A run the client knows nothing of reads "Dispatch run" in its header and drag ghost; an unknown follow kind reads "Unknown pane".

  When the run goes (`DispatchRunRemoved`, or a whole `DispatchRuns` list that leaves it out) the pane keeps the run's last snapshot (`KeptRuns` on `RootView`): the stats line starts with `ended` and a line reads "Ended. Run folder: {run_dir}". A followed run the client never saw reads "This run has ended: {run_id}". A host's `Welcome` snapshots its followed runs before the slice is forgotten (an address change does the same before the remote slice clears), so the re-list decides; a reconnect to a daemon without `dispatch_runs` ends them. The live list wins over a kept snapshot (`shown`), and `prune_kept_runs` drops entries no pane follows once the tabs change. The tab menu's "Move panes to new tab…" row counts session panes only (`session_pane_count`).

`OpenViewerTab { id, path }` opens or focuses by exact string match on the path, as `OpenDiffTab` does: a new path creates the tab, named after the path's basename (splitting `/` and `\`, else the whole path), and broadcasts `TabUpdated`; a path already open only focuses its tab and broadcasts nothing.

The reply is `ViewerTabOpened { id, tab_id }`, and an empty path is refused with an `Error` carrying the open's id. The daemon compares the path as sent, so a client trims and normalises it first.

Viewer tabs survive a `state.json` reload and are copied verbatim when a client clones another client's layout. The path is the client's own local path: on a remote host it puts a local path in the host's `state.json`, which the daemon never reads. The client draws the tab's body as the text viewer (see "Text viewer").

A client has at most one Dashboard tab (`TabContent::Dashboard`, a non-grid tab like a viewer). The activity rail's Dashboard button sends `OpenDashboardTab` only when no Dashboard tab is listed and otherwise activates the listed one; the daemon answers `DashboardTabOpened`, names the tab "Dashboard" and adds it last. `RestoreTab` and `RestoreTabSnapshot` skip a Dashboard while another is listed (logged at info), and Undo of a closed Dashboard while one is open focuses the open one.

The tab body draws one of two views, chosen by the header's `Compact | By status` toggle and saved per client in `native-ui.json` `dashboard.view` (default `compact`; a file without the key loads as compact): Compact (`dashboard_compact.rs` the model, `dashboard_compact_view.rs` the drawing) and By status (`dashboard_view.rs`). By repo is designed in `docs/plans/dashboard.md` and not built.

Above either view sit a header strip (its `issues Done` figure is drawn only once the issue cache has synced) and a queue strip. In a narrow view the header drops its day figures first, then clips the pills, so the toggle stays visible. The toggle is one keyboard stop: held Enter or Space on it does nothing, and Escape on it clears the armed one-click actions.

Compact draws one block per sidebar container that lists a session, in sidebar order: a repo cell (name, REPO, WORKSPACE or FOLDER tag, session count, a tally per state), a row per session and a wrapping cell of chips, one per agent-tree node. Nothing scrolls: when the estimated height exceeds the view, the repo with the most foldable sessions (Idle with nothing running) folds them into a `+N idle` fold row, and ended sessions show as `+N ended`. Its sizes follow the UI text size. A row click opens the session's pane, and a queue chip clicked in Compact opens By status scrolled to that row. The model is plain Rust with unit tests and the view only renders it. Layout rules and driver ids are in `docs/plans/dashboard.md` ("Compact").

By status then draws a sticky column header and the Needs you, Working, Idle and Done groups of two-line session rows, with nested agent-tree rows under Working rows, a subagent's row showing its model and effort after its name when known (`Opus 5.5 · high`; design and wording rules in `docs/plans/dashboard.md`).

A By status row's click toggles a drawer under it instead of opening the pane; Compact rows, the need-you band and queue chips still open the pane. The drawer shows the running summary, the prompt and recent work with `Go to pane` and `Open diff` buttons (driver ids `dashboard-drawer-{id}` and suffixes). The client sends `GetSessionDetail` (request ids `dashboard-detail-N`) when it opens and when the session's facts or summary change, at most once per 5 s per drawer, a change inside the window being fetched when it ends. Drawer state is keyed by host and session, and a stopped session's drawer reads `Session ended` and fetches no more. Nested agent rows under an open drawer are planned (RT-789).

The client keeps a facts store (`dashboard_facts.rs`) that merges `DashboardFacts` deltas, is pruned to the listed sessions, is cleared on `Welcome` and unwatch, and drops facts that arrive while unwatched. The rules and number formats live in `dashboard_rows.rs` as plain Rust with unit tests, and `dashboard_view.rs` only renders what it returns. The view repaints every second while any age is under a minute, else every 30 s.

Under a waiting Dashboard row an ask block (driver ids `dash-ask-{session}`, `-text`, `-command`) shows the prompt: a label (`Question ·`, `Permission ·`, `Plan ·` or `Waiting ·`), its text (a permission reads `Allow <tool>?` with its command in a mono box) and buttons. A single question's options are hinted `1` to `n` (`dash-ask-choice-{session}-{n}`); a permission offers Allow, Always allow and Deny following the chat card's rules when the session's chat card is held, else Allow and Deny unhinted; `Go to pane` (`dash-ask-go-{session}`) is last. A multi-question, multi-select, plan or other prompt, and a question whose options carry previews (`PendingQuestion.preview`, drawn only by the agent's own dialog in the pane), shows its text and `Go to pane` only: no buttons and no `Type something` box. An option's description (`PendingQuestion.option_descriptions`, parallel to `options`) shows in a hover tooltip on its button, wrapping at most 320 px wide. A choice sends `AnswerPrompt`, and a refusal toasts "Couldn't answer the prompt" with the daemon's message.

The client sends `WatchDashboard { on }` as the Dashboard tab becomes or stops being the active tab, sends on again after a new `Welcome`, to each connected host in turn, since every host has its own watch. The tab pill shows a dashboard icon and the need-you count, with no busy pill; the rail button carries the Needs You count as its badge and is lit while the Dashboard tab is active.

Dashboard and viewer tabs cannot be renamed (no Rename row in the tab menu, and a double-click on the pill starts nothing), and a Dashboard tab cannot be popped out (a saved pop-out key naming one is not opened).

A pick marks the tab with `RearrangeTab`; an `ExtractToNewTab` that names a layout marks its new tab too (the first-connect chooser's overflow tabs, the Move-panes dialog; the chooser's first tab is rearranged). The remembered type is the one the daemon actually built, so a wire layout it does not know is kept as `Balanced`.

While a tab is untouched since its pick, the daemon rebuilds it on every pane addition or removal: an automatic `SplitPane`, `ClosePane`, a session-removal close across each client's tabs (`close_session_panes`), the source of `ExtractToNewTab`, and both sides of a cross-tab `MovePane` that does not set `touch`. A rebuild keeps pane ids, their order and unbound panes.

A split by hand (a pane header's split button, its ⋯ menu or a leaf edge drop, `SplitPane` with `touch`) splits the pane asked for and ends the pick, as a divider drag does.

A concrete grid keeps its column count (a three-column pick with a fourth pane is three plus one) and carries `aspect: None`.

The tab menu offers the rearrange section (Auto, the Grid submenu, Side by side, Stacked) only for a tab whose panes are on screen: the active tab, or a tab popped out into its own window. Any other tab's menu leaves the section out; "Move panes to new tab…" stays on every tab, since it moves panes out rather than re-laying the tab.

The automatic pick names no count at all: the tab menu's `Auto` row (the Grid submenu's, and the flat row a two-pane tab shows), the first-connect chooser's `Auto` shape, the Move panes dialog's `Auto` shape and Ctrl+Shift+G all send `RearrangeLayout::Grid { cols: 0, aspect: Some(<pane area width / height>) }`, on an additive `#[serde(default)]` field and without a protocol bump.

The daemon keeps the tab automatic and fits the columns to that aspect with the aspect-aware best fit (`crates/daemon/src/tabs.rs::best_fit_grid_cols`, moved there from the client), falling back to `ceil(sqrt(N))` when no aspect is known: an older client's bare `cols: 0`, the `AutoGrid` preset and the all-sessions `InitLayout` build. Every later rebuild re-picks from the aspect the tab remembers, so adding or removing a pane keeps the grid fitting its area.

While a tab stays automatic, a window resize re-sends its automatic layout with the pane area's new aspect after a 250 ms debounce (`apps/native/src/lib.rs::schedule_auto_grid_resend`, `AUTO_GRID_RESIZE_DEBOUNCE`; `apps/native/src/tabs.rs::auto_grid_resends` skips a tab whose stored aspect is within 0.01 of the new one), so a drag settles as one re-pick.

The daemon treats a repeat automatic rearrange of an already-automatic tab as a re-fit: it rebuilds over every pane the tab holds, keeping the empty (unbound) panes and the tab's untouched mark and adopting the new aspect, where a first pick and any fixed pick still drop the unbound panes as a tidy-up. A tab pinned to a fixed count keeps it, and a resize never touches it.

`SetPaneRatio` (a divider drag), any same-tab `MovePane`, a swap included, a cross-tab `MovePane` with `touch` set (it clears the destination's flag; the source tab, which lost a pane, is still rebuilt) and a `SwapPanes` (it clears both tabs') clear the flag, after which panes keep the sizes they have. `MergeTabs`, `CreateTab` and `InitLayout`'s own build leave it unset, a preset launch clears it, and undo snapshots and cloned layouts carry it as is.

The client sends no `SetPaneRatio` for a divider press that stays within 3 logical px of where it landed, so a click on the handle does not count as a resize. A tab update that rebuilds the dragged tab's split tree renumbers its splits, so the client ends the in-flight drag instead of sending its held path.

**Remote session counts**: the client records each saved remote host's session count in `native-ui.json` as `host_session_counts` (`{"<lower-cased MagicDNS name>": <count>}`), kept from that host's own session list and only while the host is in `saved_hosts`; Forget drops the entry. It is written on the host's first session list after `Welcome`, on every later full `Sessions` list (a resync) and, debounced, after a session is added or removed. The Connections row of a switched-off host reads it as "N sessions last time". A remote host's reconnect offers no import of its sessions.

## Drag model

`apps/native/src/drag.rs` is the plain-Rust half of every drag. `DragPayload` is a `Pane`, a `Tab`, a `Container`, a session `Leaf`, a dispatch run's `Run` or a subagent's `Subagent`.

`drop_edge` maps the pointer's fraction of a pane to a `PaneDropEdge`: the outer band (`OUTER_BAND`, 0.12) on a side that touches the grid boundary (`tabs::outer_edges`, within 0.5 px), the nearer outer edge at a corner; the centre box (`CENTRE_LOW` 0.35 to `CENTRE_HIGH` 0.65) is `Replace`; otherwise the half on the nearer axis.

`pane_drop` builds a `PaneDrop` with its undo label: `undo::SWAPPED_PANES` for a centre drop onto a pane that shows a session, in the same tab or another, `undo::MOVED_PANE` otherwise. Every edge or centre drop on a pane sets `MovePane.touch`, so the daemon counts the destination as arranged by hand; a pill drop and the pane menu's Move to ▸ tab do not (the daemon rebuilds both tabs).

A cross-tab centre drop onto a bound pane sends `SwapPanes` (one atomic request: the two panes exchange sessions, both tabs keep topology and pane ids and are touched, each broadcasts a `TabUpdated`), and onto an empty pane sends `MovePane` `Replace` with `touch`.

A swap focuses the destination pane, never marks its source tab closing, and is in flight on both tabs until a reply or an update settles it. Undo restores each tab's snapshot, focusing the pane that holds the session the tab had. `pane_drop` sends nothing for a diff or missing tab, a pane a grid does not hold, a self-drop, a non-pane payload, or a same-tab drop onto the facing half of the source's own split sibling, which would rebuild the same tree.

A pane drag starts from the header's drag area: the title, the glyph and the empty stretch, not the buttons, chips, Stop or exit code, whose press goes to `press_on_header_control`. `drag::pane_target` finds the pane under the pointer and its edge from the pane rects, so the shown tab's grid carries one drop layer over it (`grid_view.rs`): it does not occlude the panes, and it stops mouse propagation only while a drag runs, so terminals get no mouse reports then.

A refused drop (what `pane_drop` sends nothing for) shows no overlay and sends nothing; an accepted one goes out through `send_pane_move`, the path the pane menu's Move to ▸ shares.

The overlay (`drag::drop_overlay`) is the accent at 22% over the half with a 1 px border, a strip 14% deep at 40% with a 2 px border for an outer edge, or the centre inset 12% on every side with a `Swap panes` badge. The ghost is a pill of the header's label (`Empty pane` for a pane with no session) on `GROUND` at 78% with the pane's accent border.

Esc cancels the drag whichever element has focus (the root's key capture), and a tab update that arrives mid-drag ends it when it touches the drag's source tab or the shown tab. A pane drag over a grid pill activates its tab, so a drop lands in the shown tab, which may not be the tab the drag started in.

`reorder` moves one id before or after another (`Side` from the pointer's half of the row or pill); `reorder_tabs` and `reorder_containers` build `ReorderTabs` / `ReorderContainers` and give none when the order would not change.

A pill reorder applies locally at once and carries a `request_id`; the client remembers each pending reorder's previous order. The daemon echoes the id only on the `Error` that refuses it. A refusal of the only pending reorder snaps the strip back to its order before the drop (tabs created since keep their place after); with newer reorders pending, a refused one hands its remembered order to the next and leaves the strip.

A `TabsReordered` echo settles only the reorder whose sent order it matches, and does not move the strip while a newer reorder is pending. A fresh tab list or a reconnect forgets pending reorders. The toast is the generic daemon error.

The sidebar drags use the same payloads. In the Repos view a workspace or repo container header drags as a `Container`. A drop on another host's row is refused (no drop line, nothing sent); otherwise the shown containers are split by host and each host whose order changed is sent a `ReorderContainers` with its own containers in the new order, so a host whose order did not change is sent nothing. In the Tabs view a tab container header drags with the strip's `Tab` payload, so a pill and a tab container drop on each other and send `ReorderTabs` (a refusal puts the strip back, as above).

A leaf of a workspace, repo or tab container reorders inside its own container and sends `ReorderSessions` with that container's whole shown order, which the Tabs view also applies from the stored session order; in a tab only This PC's leaves reorder, and a drag of another host's leaf there sends nothing. SH, DIR, Detached and Unbound rows neither drag nor take drops, their leaves drag (below) but never reorder (`drag::leaf_reorders` is true only inside workspace, repo and tab containers), and a leaf dropped on a container header does nothing.

A leaf drags to the grid and the tab pills whatever its container. Over the grid it shows the pane-drop overlay (`drag::leaf_drop`, sent by `grid_view.rs` `send_leaf_drop`). A bound leaf moves its pane: the active tab's pane showing the session, else its first binding in tab order (bindings in a tab being closed do not count), and records `undo::MOVED_PANE`, or `undo::SWAPPED_PANES` for a swap.

An unbound leaf is placed with `SplitPane` on a half edge, where an outer edge acts as the same-side half of the hovered pane and the overlay shows that half, or `ReplacePaneSession` on the centre or on any edge of an empty pane; it records no undo entry, as placing a leaf by click does not. A headless or unknown session drops nowhere.

On a tab pill (`drag::leaf_pill_drop`, `tab_bar.rs` `on_pill_drop`) an unbound leaf goes where `pane_target_for_session` puts it in that tab, and a bound leaf's pane moves to that spot (`MovePane` with `touch: false`, "Moved pane"), or nothing happens when the tab already shows the session.

This differs on purpose from a pane dropped on a pill, which uses `pick_balanced_drop_target`: a leaf carries a session, not a pane position, so it follows the placement a click would give. A diff, missing or closing tab refuses the drop and shows the no-drop cursor (`pill_no_drop`). Hovering a pill with a leaf does not switch to that tab, unlike a pane drag.

The pointer's half of the target group picks the side: an insertion line, a 2 px accent line, draws at its top or bottom, and the dragged group fades to 0.4 with a ghost of its label. The new order shows at once and holds until the daemon's broadcast; a refused reorder shows the error toast and the local order stays until the next broadcast or reconnect. A container may be dropped on a collapsed container, which does not auto-expand. Esc cancels.

Under a non-manual Sort repos the Repos view shows the sorted order, while the stored order stays the manual one. A drop onto a row in another sort group is refused and draws no line (`SidebarModel::same_sort_group`).

Inside a group the line follows the displayed order and the drop moves the dragged container next to the target in the manual order (`RootView::sidebar_drop_message`). Under Manual a drag is unchanged, and with the Active filter on it reorders the full manual list, so hidden repos keep their place.

## Settings

The Settings modal's tab list reads General, Notifications, Dashboard, Worktrees, Remote access, Appearance and App title, then a non-selectable `Agents` group row and one tab per agent the daemon lists, in the daemon's order, each labelled with the descriptor's label (selector `settings-tab-{tag}`). The group row is a label only: no page, click, hover or keyboard stop. With no agents listed (disconnected) there is no `Agents` row and no agent tab.

Remote access (Tailscale) is absent from the list while the client's target is a remote host, and Settings falls back to General.

A search box tops the tab list column (placeholder "Search settings", selector `settings-search`). While its query has a word, the list shows only the tabs with a match, each as `{label}  {count}` with the count muted; the `Agents` group row stays only while one of its pages is listed, and with no match the list is one muted line, "No settings match".

A query matches a setting when every word is a case-insensitive substring of its label, its section heading, its tab title or one of its aliases; hints are not searched, and only rows drawn in the current state count. Agent pages are searched from their descriptors.

The catalogue of searchable settings is hand-kept in `settings_search.rs`, with the aliases and the gates that say when a row is drawn. Drift guards (its unit tests and the UI spec `every_ring_stop_on_every_tab_has_a_catalogue_entry`) fail when a drawn control has no catalogue entry, so a new setting is added there.

The shown tab's first match gets a 1 px accent outline and scrolls into view on every query change and on a pick. Typing keeps the shown tab if it still matches, else opens the first listed tab; while a query is set, Up and Down in the list walk only the listed tabs.

Enter in the box moves the keyboard to the highlighted control without pressing it. Esc in a non-empty box clears it, and Esc in an empty box closes Settings. Ctrl+F, only while Settings is open, moves the keyboard to the box and selects its text. The query is cleared on every open and close.

Every edit is a pending edit until OK or Apply: text rows, toggles, choices and resets (the worktrees "Reset to default" empties the draft), and on the Accounts page the aliases, the rotation order and the auto-switch block (the Accounts page's action buttons act at once; see "Settings › Accounts"). Enter and leaving a field apply nothing, and there are no per-row Save or Apply buttons.

Appearance (the theme, UI font family, text size and weight, terminal font with its size and weight, and frame width) still draws at once, but as a preview of a look not yet saved. The saved look (`RootView.appearance_saved`, taken when Settings opens) is what `native-ui.json` keeps: OK and Apply count as pending while the shown look differs from it (`appearance_previewed`), go dim again when it is stepped back, and save the shown look (`commit_appearance_preview`). Every close of Settings (Cancel, the title-bar X, Esc, a host switch, the quit ask dialog, the worktrees manager launch) draws the saved look again (`close_appearance_editor`, `revert_appearance_preview`). The session, repo and workspace appearance editors act and save at once. Action buttons with their own side effects stay immediate: Check now, Open logs folder, the notification settings link, sound Play, worktrees Browse (it fills the draft) and Manage, and the Dashboard's Test, which is disabled with "Apply your changes first to test them." while the page holds a pending change. The Dashboard's "Delete stored key" is a pending edit: it holds the deletion (the key line reads "No key" and the button becomes "Undo delete"), a key typed for the same provider replaces it, and Apply sends it. A held deletion belongs to the provider shown as chosen (pending, else saved): on another provider's row, for a provider that takes no key, or behind the Environment variable key source it shows nowhere, disables nothing, and Apply does not send it; it stays held, so switching back before Apply shows it again.

The footer is OK, Apply and Cancel, right-aligned (`settings-ok`, `settings-apply`, `settings-cancel`). OK and Apply are dimmed and out of the Tab ring while nothing is pending or a pending row fails local validation (an invalid port or cap, an Environment-variable key source with no variable).

The Tab ring ends OK, Apply, Cancel, the search box, then the tab list; Shift+Tab from the tab list reaches the search box, and Settings still opens with the keyboard on the tab list. Cancel, the title-bar X and Esc discard every pending edit and close.

Apply sends to every host that has pending edits, each host only its own. Drafts are per host where the page is per host, survive tab and host switches, and are dropped only when Settings closes. The state is runtime-only (`PendingSettings` in `settings_view.rs`): no saved-file shape and no protocol message changed.

OK applies, then closes at once after local-only edits; after daemon sends it waits for each host's echo, matched by message kind (agent settings, agent commands, worktrees root, keep-awake, default shell, remote status, summarizer status, and the Accounts page's writes, each answered by an `Accounts` carrying its `request_id`; `OwedEcho`). A refusal (an error carrying a sent request id, or any id-less error from a host OK waits on), a failed remote state (anything but Starting, Off or Serving) or the host dropping keeps Settings open with the drafts kept and the refused row marked; Remote access's Starting keeps OK waiting. An edit made while OK waits keeps Settings open. `native.log` records "settings: OK waits for the daemons' echoes", "settings: a daemon refused an Apply; OK stays open", "settings: a host OK waited on closed; OK stays open", "settings: edits made while OK waited are pending; OK stays open" and "settings: a This PC setting could not be applied; OK stays open" (a login-launch write that failed stays pending).

It lets the user's other devices on their tailnet connect to this PC's sessions. A switch `Allow remote access over Tailscale` mirrors the daemon's last `RemoteStatus` and sends `ConfigureRemote` on toggle.

Beside it are a status line per `RemoteState`, `Address: https://{name}:{port}` and the certificate's expiry while serving, a Port field (1-65535, inline error; sent by OK or Apply), and hints that changing the port or the PC's Tailscale name changes the iPhone app's address and that the daemon keeps running while remote access is on.

The tab also lists the tailnet devices asking to connect, so the owner approves a new device on the host PC (the device gets its token only then). A `Waiting devices · {n}` section shows one row per request (name, Tailscale login, a `m:ss left` countdown, Approve… and Deny; an approved row reads `Approved · waiting for the device` with only Deny), and the tab carries an amber count badge (`99+` cap, approved requests included).

Approve… opens an approval dialog that sends nothing until Approve is pressed, then shows the QR code, the code as `735 160` and `expires in m:ss · this request only`, and closes by itself when the code runs out; disconnecting from the host closes it and forgets the waiting requests.

A `Devices` section (`devices.rs` model, `devices_view.rs` view) follows Waiting devices, shown only on this PC's daemon when its `Welcome` lists `device_block`. It lists the approved devices (`ListDevices` on `Welcome` and on selecting Remote access, folded from `Devices`), one row each with name, login and a status: "Connected", "Connected (N)", "Last seen just now / Nm ago / Nh ago / Nd ago", "Never connected", or the "Blocked" tag.

Rows sort connected first, then by last seen (newest first, never-seen last), then blocked, ties by name; an empty list reads "No device has paired yet." An unblocked row has Block and a blocked one Forget (`ForgetDevice`). Block opens a confirm, "Block {name}?" with "Its live connections end now, and it cannot pair again until you forget it.", Cancel (focused first) and Block (danger); Tab and Shift+Tab move, Enter presses, Esc cancels, and Block sends `RevokeDevice`.

A request is asked for only on a connect to this PC's daemon whose `Welcome` lists `device_pairing`, never on a tailnet or SSH host. Each new unapproved request raises a toast, "A device asks for remote access" with the body `{name} · signed in to Tailscale as {login}`, with Approve… and Deny, only while connected to this PC's daemon. Pairing toasts do not consult the Notifications tab's toggles.

Approve… on a toast brings the window forward and opens the dialog without opening Settings, and only when no pairing dialog is open and the request is still listed and unapproved: an open dialog is never replaced from a toast.

Deny sends `DenyDevice` for a listed request, and a press on the toast body only brings the window forward. `native.log` records a press as "pairing: a toast was pressed" (field `action`), and one that arrives after its window closed as the warning "a pairing toast was pressed after its window closed".

A button pressed from Action Center reaches the running client through the toast activator (see Notifications): Approve… is a foreground activation (the window comes forward, the Confirm dialog opens), Deny is a background activation. A press while the client is closed starts it with `-ToastActivated -Embedding` (logged "started by a toast press"; the flags are never read as a session id).

Approve and Deny presses that arrive before the pending-devices list are held (`ToastActionQueue`) and applied when it arrives; a press for a request no longer listed is dropped with a log line, and held presses are dropped with a log line on a remote target, a daemon without device pairing, or a host switch.

`Start the daemon when I log in` registers the HKCU Run value (a LaunchAgent on macOS) through `daemon_client::autostart`, behind the `Autostart` seam in `remote_access.rs` (`RootDeps.autostart`). The switch is a pending edit applied by OK or Apply; a write that fails keeps Settings open with `Could not change start on login: {reason}.` under the switch and the change still pending, and Cancel leaves the login launch as it was. The switch is inert while the login launch could not be read. The page's controls are inert until the first `RemoteStatus` arrives, and a new connection forgets it.

Running an agent with its permission prompts bypassed is its Bypass choice on its own page (`AgentDescriptor.bypass`; Claude's Permission mode "Bypass permissions"), saved on the daemon like any agent setting and opening every spawn dialog on it.

A Trusted launch default an older release saved in `native-ui.json` (`spawn.trusted`, or `spawn.last_trusted` when present) moves there: when a host's agents and their Settings values arrive while that saved choice was trusted, `move_trusted_default` (`settings_view.rs`) sends each agent's bypass choice to that host with `SetAgentSettings`.

The move logs `settings: moving the saved trusted-launch default into the agents' bypass choice` (field `host`), and records the host in `spawn.trusted_moved` (`@local` for This PC), so each host takes it once. A host whose agents name no bypass choice (an older daemon) is not recorded, and is tried again on its next connect. Any change this client sends to a host's agent Settings records that host too, so the old default never lands on top of what the user chose there.

An agent page's first section, titled with the descriptor's label (Claude's reads "Claude"), draws one row per descriptor field marked `settings: true`, in descriptor order, with the descriptor's choice labels (Claude: "Permission mode", then "Provider", then "Effort", which hides while the provider is DeepSeek).

A Toggle is a checkbox row, a Choice a segmented row, and a Text or Model field an input whose edit pends until OK or Apply; a field of a kind this client does not know shows the note "Update the client to change this". The model is not a Settings field for Claude; it is chosen per spawn. A text field's placeholder follows the page's values.

Those rows read the connected daemon's `AgentSettings` for the page's agent and change it with `SetAgentSettings` (the current map merged with the changed key), so the setting follows the connected daemon, not this machine. A row changes only when the daemon's broadcast arrives; two quick changes are merged so neither is lost. While disconnected or before this connection's agent settings arrive, the page shows no option rows.

A change logs `settings: setting an agent option` (fields `agent` and `key`) in `native.log`; a press whose control no longer matches its field logs at debug `settings: pressed control does not match its field; ignored`, and a text apply with no value logs `settings: the text field takes no value now; nothing sent`.

Selectors are `settings-{tag}-{field}-{choice}` for a choice (the field id's `_` becomes `-`: `settings-claude-permission-mode-{cli-default|default|accept-edits|bypass-permissions|plan}`, `settings-claude-provider-{anthropic|deepseek}`), and `settings-{tag}-{field}` for a toggle, a text input and the unknown-kind note.

A page whose agent a connected daemon no longer lists gives way to General and its drafts are dropped; a dropped connection keeps the page and its drafts until the next `Welcome`, which closes Settings.

Each agent page ends with a "Launch command" section with a Program field (placeholder the agent's tag) and an Extra arguments field. Drafts and pending applies are per agent, and `SetAgentCommand` names the page's agent; an apply logs `settings: applying an agent's launch command` (field `agent`). OK or Apply sends both, trimmed, as `SetAgentCommand`; both empty clears the command.

`Saved` shows after the daemon's echo, only while both fields still match what was stored. Notes say the command is used for new sessions, Restart and Resume and not for headless runs, and that extra arguments follow POSIX shell rules (quote a Windows path or double its backslashes; in cmd a doskey macro is not expanded, so set Program to a `.cmd` file).

While an apply waits, the daemon's launch-command refusal shows under Program (when its text starts "The launch command's Program") or under Extra arguments (the other refusals) instead of a toast. It clears on the next edit and shows again on return if another Settings tab was open. Any other daemon error during an apply ends it and still toasts.

With the agent's override variable set on the host (`RUSTLING_TULIP_CLAUDE` for Claude; the name comes from the daemon's `program_env`), Program is read-only, out of the Tab ring, and says "Set by RUSTLING_TULIP_CLAUDE". A daemon without the `agent_commands` feature shows both rows dimmed with the tooltip "Restart the daemon to set the launch command: .\rt.ps1 restart". Before `AgentCommands` arrives, or while disconnected, the section is not drawn.

Drafts follow another client's `AgentCommands` only while untouched; text typed after an Apply survives the echo, and re-selecting an agent's tab keeps its drafts and a pending apply. Selectors: `settings-agent-program`, `settings-agent-args`, `settings-agent-saved`, `settings-agent-program-error`, `settings-agent-args-error`, `settings-agent-program-env`.

After Launch command, an agent whose descriptor has `user_hooks` gets a "Hooks" section with one switch, "Install hooks in {label}'s user settings", and a note: "Lets {label} runs you start by hand in a shell report their conversation and status. Applies to shells opened afterwards." The switch is a pending edit: OK or Apply sends `SetAgentUserHooks` with a request id to the host shown in the selector and logs `settings: setting an agent's user hooks`, and OK waits for the matching `AgentUserHooks` reply, staying open when it carries an error. Cancel, the close button and Escape drop it. The client asks with `GetAgentUserHooks` (log `settings: asking for an agent's user hooks`) for each such agent whenever an `Agents` list arrives on a connection that lists `agent_user_hooks`. "Edits {path}" shows once the daemon has answered; for `partial` or `stale` the section adds "Some entries are missing or out of date. Turn it off and on to repair." The reply's error shows in the danger colour until the next reply and logs a warn `settings: the daemon could not edit an agent's user hooks`. A daemon without `agent_user_hooks` shows the switch dimmed and inert with the tooltip "This host's daemon is too old for this setting. Update rustling-tulip there to use it."; for `unsupported` or `unknown` there is no section. Selectors: `settings-agent-user-hooks`, `settings-agent-user-hooks-unsupported`, `settings-agent-user-hooks-repair`, `settings-agent-user-hooks-path`, `settings-agent-user-hooks-error`.

## Terminal

- **Scrollback-first attach**: `LoadScrollback` with live output buffered meanwhile; an 8 s request timeout with retries after 2 s and 4 s, each with its own `request_id`, and a reply to an older id dropped. When the daemon restarts the forwarder (`forwarder_restarted: true`) the held-back output is discarded, since it is already in the history. The logical scrollback cap is 5000 lines.
- **Size and replies**: only one pane per session (its size driver) answers terminal queries, so a session shown in two panes gets each reply once. Colour queries (OSC 4, 10, 11, 12) are answered with the program's own colour override when it set one, else the pane's palette (indexed 0–255, text colour, background, caret); each reply sits in the reply stream where its query arrived, so a later device-attributes answer still follows it, and replayed history answers none.

  Across clients, the daemon lets only the client with recent input own a session's size. Every `Resize` carries `claim`, true when the pane had input in the last 5 s (typed keys, IME text, paste, Re-run command, mouse presses, releases that end a gesture, wheel and pointer moves to a new pixel) or when this client just resized the pane.

  Such a resize is the client's window resized or maximized, a split divider dragged (one claimed `Resize` per painted size), the sidebar dragged, folded or unfolded (Ctrl+B or the activity rail; a rail click that only switches panels claims nothing), or a font-size change made on this client.

  Each such action marks the panes it resizes, and only the next measure of a marked pane claims. The first input after 5 s idle re-sends the pane's size with `claim: true`, ahead of the input.

  A bind the user makes in this client claims: the unbound pill, Add to new tab, Add to current tab, a leaf click that places a session, a jump-palette or notification placement, or a drop on a pane or tab pill. The client sends the session's `Resize` with `claim: true` as soon as the daemon's layout update carries the bind, so the PTY takes the new pane's size at once instead of keeping its old viewport until the pointer moves over the pane. A pending bind waits for the request that carries it (new tab, split; dropped if that request is refused) or, for a pane-replacing bind with no request id, for the next layout update that shows the session in that pane (dropped otherwise); a reconnect drops all pending binds.

  An attach, an automatic re-bind (a reconnect, a layout restore, another client's change), a tab switch or showing a hidden tab, a focus change, and another client's layout or appearance change send `claim: false`, which the daemon ignores for a session another client has already sized; the client that owns the size has its unclaimed size applied, so a client relaunched into a different window size, or a pane re-bound to another tab, gets its PTY at the pane's size at once, without a keypress. A pane that does not own the size draws as before, with no indicator, and when the owner disconnects the next client to claim wins.

  ConPTY repaints the whole screen on every resize, even one to the size the PTY already has, so the daemon skips a `Resize` that matches the size it last applied (a skipped claim still makes its client the size owner). A pane whose grid differs from the PTY's applied size misdraws all ConPTY output, history and live alike, until a resize that is actually applied. A test that parses the PTY stream must replay it through a terminal grid rather than strip escapes.

  A query that ends the loaded history is answered unless live output follows it, which covers a session on an older tracer: a current tracer answers ConPTY's startup query itself.
- **Copy and paste**: Ctrl+C copies with a selection, else sends ^C; Ctrl+Shift+C copies; copy on select is a saved setting (default on); paste on Ctrl+V and Ctrl+Shift+V, bracketed when the child asks; a right-click pastes too, and is never reported to the program, so a session on another host pastes this machine's clipboard; with nothing on the clipboard it sends nothing, and Shift+right-click sends the press to a program that asked for mouse reports.
- **The press that brings focus**: the setting `Clicking an inactive pane also acts in it` (Settings → General → Terminal behavior, `settings-terminal-click-through`, saved per client as `general.click_through_inactive_pane`, default on, a missing key reads on) decides what the first press on a pane that is not its tab's focused pane does.

  On, it focuses the pane and also acts there, a mouse-mode terminal included: the press reaches the program.

  Off, the first press of any button in the pane's body only focuses it, through the path a keyboard pane switch takes (so Chat and Summary panes are focused too), and does nothing else in it; it still runs the app's usual click dismissal (a palette or menu closes, an armed Stop disarms). The wheel, the pane header's buttons, chips and drag act as before. A press on the tab's own focused pane while a palette or menu holds the keyboard only dismisses it.

  The listener is a capture-phase mouse-down on the pane body built in `render_pane` (`focus_inactive_pane` in `grid_view.rs`), and `TerminalPane` makes its own first-press check in the capture phase too, since the palette's close hands focus back before the press arrives; both read the setting from the `mouse::ClickThrough` global.

  When the press is held, its release and drag send nothing, and the next press is reported. A selection, a Ctrl+click on a link and a right-click paste act on that first press as usual.

  The press that brings the window forward is held the same way in a mouse-mode terminal whichever way the setting is, even on the pane that still holds the keyboard, and an activating right-click pastes nothing.

  The platform marks that press as `first_mouse`: macOS does so from `acceptsFirstMouse:`, and the vendored GPUI does so on Windows from a `WM_MOUSEACTIVATE` whose hit test is the client area, so an Alt+Tab or a press on the title bar marks nothing. A window that opened behind another app and is then clicked gets no `WM_MOUSEACTIVATE`, so that press still reaches the program.

  A key paste with no text on the clipboard sends the agent's image-paste key (Alt+V for Claude on Windows, Ctrl+V elsewhere and for a shell) to a session on this machine, so the agent pastes the clipboard image. To an agent running on another host that key would read the host's clipboard, so the client uploads the image instead: with an image on the clipboard (on Windows, when GPUI's clipboard has none, a copied bitmap) a key or right-click paste sends `UploadFile` named `paste.<png|jpg|webp|gif|svg|bmp|tiff>` (`paste.png` for a bitmap), and when the host answers `FileUploaded` its path is typed into the same pane, in double quotes when it contains a space and bracketed when the program asked for bracketed paste. A pending upload is forgotten when its host reconnects. Toasts: a host without the `upload_file` feature says "This host can't receive pasted images or files until it is updated"; an image over the upload limit says "The image is larger than 8 MiB."; a daemon error shows its own message under "Couldn't paste the image". With no image nothing is sent, and a shell there still gets Ctrl+V.

  Dropping files from the desktop onto a terminal pane of the shown tab pastes their paths, separated by a space, a path with a space in double quotes. On a local session the dropped paths paste as they are. On a remote session each file uploads in turn (`UploadFile`, under its own name) and the host paths paste together after the last answer; folders are skipped with the toast "Folders can't be dropped into a remote session". A file over the 8 MiB cap shows a warning "Couldn't drop the file" ("{name} is larger than 8 MiB."), an unreadable one an error with the read error, and a host that refuses answers an error with the daemon's message, which abandons the rest of the drop and pastes the paths already returned. A host without `upload_file` shows the same "can't receive pasted images or files" toast. A drop on a popped pane's card, on a pane with no session or in a pop-out window does nothing.

  On macOS Cmd takes those roles (`term_input::CopyKeys`): Cmd+C copies a selection and otherwise does nothing, Cmd+Shift+C copies without clearing it, Cmd+V pastes, and Ctrl keys always send their control bytes, so Ctrl+C always interrupts. Text fields bind select all, copy, cut and paste with GPUI's `secondary` modifier: Cmd on macOS, Ctrl elsewhere. Shift+drag selects even under mouse reporting. OSC 52 `c` stores reach the system clipboard; reads are answered empty and stores in replayed history are dropped.

  A selection that crosses a box-drawn TUI panel (such as Claude Code's) copies only its text, via `strip_box` in `copy_text.rs` (called from `Term::selection_text`). The panel's borders, rules and padding are left out, the text keeps its relative indent, and the top rule's title is kept as the first line.

  A `├─┤` divider becomes one blank line, and text is never joined across it. Paragraphs the panel wrapped are rejoined with a space, measured in terminal columns against the panel's width minus its right padding, except rows that start with a box-drawing character, a line number or a diff marker, hold an inner bar, or end in `;`, `{` or `}`.

  Box-drawn tables, ASCII `+--+` art, a literal `│` in a sentence and a selection with no panel copy exactly as selected. A triple-click (Lines) copy keeps its trailing newline, tabs copy as `\t`, and OSC 52 stores are unchanged.
- **Keys and text input**: Shift+Enter sends the bytes the session agent's descriptor names in `shift_enter` (`lf` sends LF; `backslash_cr`, an unknown value, a plain shell and an agent with no descriptor send `\` + CR). GPUI gives Space no `key_char`, so `keys.rs` maps Space and Shift+Space itself; Alt+Space stays unmapped so Windows opens the system menu.

  An arrow, Home/End, Insert/Delete, PageUp/PageDown or function key held with Shift, Alt or Ctrl sends xterm's modifier-parameter form, as Windows Terminal does: `ESC [ 1 ; m X` or `ESC [ n ; m ~`, where `m` is 1 plus 1 for Shift, 2 for Alt and 4 for Ctrl (`keys.rs` `modified_key`). These forms stay CSI in application-cursor mode, and Ctrl+Left / Ctrl+Right (`ESC [ 1 ; 5 D` / `C`) are what programs read as a word left or right.

  Text arrives through an `EntityInputHandler` on the pane, so dead keys, AltGr and IME composition work: a composition is drawn underlined at the cursor even when the program hides it, and dropped on blur or stop; a dead key is not reported to GPUI as a composition, because GPUI would then hide Enter, Backspace, Esc and arrows from the pane. Ctrl+Alt with a non-alphanumeric character types it (AltGr on layouts GPUI doesn't know); Ctrl+Alt+letter or digit sends ESC+char.
- **Links**: `links.rs` ports the Tauri detector (URLs, absolute, UNC and relative paths with `:line:col`, stitched across soft and hard wraps and TUI borders within ±64 rows). A soft-wrapped row that opens with a box frame is stitched like a hard break, frame stripped, since ConPTY flags a TUI's redrawn rows as one autowrapped run. Links underline only while Ctrl is held; Ctrl+click wins over mouse reporting.

  Rows stitch into one link only when the upper row reaches the right border (within the tolerance). A pair that reaches only a bordered box's text edge is a stitched reading too, a candidate: ui-themes caps reply text at 100 columns inside a full-width box, so a path broken there still joins. Two short path rows in a box never join.

  An absolute path match also gets spaced readings, for paths with spaces: single-space-joined tokens ending on a token with `\` or `/`, stopping at a double space, at any of `<>"'|`, or after 8 tokens. A quoted `"..."` or `'...'` run is a reading too (a relative path resolves against the pane's base folders), and a quote may lead a path. Readings are ordered stitched, then quoted, then word-by-word, and ride on the link (`TerminalLink.spaced`); text alone never underlines one.

  On a local pane, Ctrl+hover checks the readings of every link covering the hovered cell for existence on the background executor, and the first that exists widens the underline and the click to the whole path. Up to 16 confirmed readings per pane are kept, keyed by the reading's text and its rows' text, so a widen survives new output and a hover or click on another row of the same path. A reading never covers or removes an OSC 8 hyperlink. On a remote pane a click tries the readings first, unchecked; a click on a word only a reading covers finds no link (known limit).

  Ctrl+click on a URL opens it in the browser at once. Ctrl+click on a path opens it at once in its default app (a path with `:line` in VS Code at the line, a plain path in the OS default handler; a runnable file such as a `.bat` goes straight to the "Run <name>?" confirm). Ctrl+Shift+click on a path opens the **link menu** at the click point (`link_menu.rs` the state and rows, `link_menu_view.rs` its window layer, `PaneEvent::LinkMenu`), with the rows "Open in default app" (a path with `:line` reads "Open in VS Code" and opens with `-g` at the line, a plain path goes to the OS default handler), "Open in viewer" (a viewer tab at the line, see "Text viewer") and "Open containing folder" (reveals the file; it never shows the "Run <name>?" confirm). The first row is highlighted; Up and Down move it, Enter picks, and Esc, a click outside or a wheel over its backdrop closes it. Opening another link menu closes it, and it works the same in a pop-out. A Ctrl+click or Ctrl+Shift+click in a pane that does not hold the keyboard moves the keyboard there. Driver selectors: `link-menu`, `link-menu-default`, `link-menu-viewer`, `link-menu-folder`.

  A pick is a `LinkAction` (`DefaultApp`, `Viewer`, `Folder`) that rides the open through `PaneEvent::OpenLink`, `LinkSource`, `Opening`, `FetchRequest` and `PendingAsk`; a Ctrl+click is a `DefaultApp` open with no menu, and the viewer is reached only through the menu's "Open in viewer" row. A remote path is fetched once, after the Ctrl+click or the pick, and the fetched copy is opened by the action (Open containing folder reveals the copy under the download root).

  A path Windows flags as dangerous, or with a script or executable extension, asks "Run <name>?" first. A UNC path opens only for a host behind a mapped drive or listed in `unc_hosts` in native-ui.json, which the client reads on each click and never writes.
- **Shell integration**: OSC 133 and 633 marks drive per-command gutter dots (ok / fail / unknown) anchored to absolute rows through scroll, reflow and trim, with a menu to copy the command, the output or both, and to re-run (typed without Enter).

  Under ConPTY, a mark a shell writes inside a synchronized, hidden-cursor paint (nu's reedline) arrives with the cursor parked on the last row before it moves to the prompt, so a `133;A` that lands below its own `133;B` is moved up to the row the `133;B` arrives on (`Records::input` in `shell_marks.rs`), and a repaint's `133;A` on that parked row counts as a redraw of the same prompt.
- **Prompt jumps** (`prompt_nav.rs`): two header buttons on Interactive and PlainShell panes, between "Move this pane to a new tab" and close, `↑` ("Previous prompt", `pane-prompt-prev-<pane>`) and `↓` ("Next prompt", `pane-prompt-next-<pane>`). Previous scrolls the nearest sent prompt above the top row to the top; Next scrolls to the next prompt, or from the newest to the live bottom.

  A prompt is a Claude pane's `❯ ` row (slash commands included; the live prompt box and `❯ N.` dialog options excluded) or a plain shell's OSC 133 prompt mark; the client scans its own grid, so the daemon is not involved. The buttons scroll the terminal directly (nothing reaches the child, even under mouse reporting) and close an open shell-dot menu. With nowhere to go a button is drawn at 45% opacity, never hidden, so the buttons never move; there is no keyboard shortcut.
- **Theme and fonts**: every UI colour is a token in `palette.rs`, the built-in look's data, read at runtime through a `UiTheme` (`ui_theme.rs`: one field per token, `UiTheme::CONTRAST` the Contrast built-in); views call `theme(cx)` for the active one (an `ActiveTheme` global set in `RootView::with_transport`, changed by `RootView::set_theme`, which refreshes every window, the way `UiFont` works), and a function with no `cx` takes `&UiTheme`.

  The default theme is Nord (`theme_store::DEFAULT_ID`); a first launch, or a `native-ui.json` with no `theme`, draws it.

  The built-ins, in order, are Contrast, Nord, Catppuccin Mocha, Catppuccin Latte (light), Rose Pine, Dracula, TokyoNight and One Half Dark (`builtin_themes.rs`, generated by `docs/design/theme-defaults/gen_builtin_themes.py` from the published schemes' terminal colours, with the interface colours solved from them to meet the `contrast.rs` floors; attribution in `apps/native/assets/themes/NOTICE.md`).

  The Contrast look was chosen in `docs/design/ui-language/README.md`: a near-black ground, floating layers well above it, session rows as cards, ruled menu groups; contrast floors pinned by its tests, every text step at WCAG AA or better, and quiet text lifted to secondary on a hovered row.

  The terminal's palette is the active theme's `terminal` part (`UiTheme.terminal`, a `TerminalPalette`: foreground, background, caret, selection and 16 ANSI colours), drawn as given; a background override at the session or container level instead builds a palette whose ANSI colours are contrast-adjusted against that background (`theme.rs` `resolve_palette`, `build_theme`). Setting a theme repaints open terminals in place. Contrast's terminal ground is #070609 and its session accent is Coral #F07A62; the diff view's ground is the active theme's terminal background.

  There are six accent presets (Theme, Rose, Ochre, Periwinkle, Sky, Lilac) and six background presets (Default, Slate, Ink, Evergreen, Aubergine, Paper): the first of each shows the active theme's own colour, and picking it clears that level's override (the accent preset also clears its frame override) instead of storing a colour. The App level of Settings › Appearance has no accent or background rows: a custom app accent or terminal background is set in a theme (Themes modal › Duplicate and edit). A program's OSC 11 background and OSC 12 caret colour win. Per-session, repo and workspace appearance overrides stay as modifiers on the theme, and layout values (sizes, spacing) are not themeable.

  The frame round a session's terminal is a band of the resolved **frame width** (whole px 0 to 6, `Off` at 0; built-in 1 px), set by the editor's Frame width row at the session, repo or workspace level (`AppearanceOverrides.terminal_frame_width`) or at the app level (`native-ui.json` `terminal_frame_width`). The band paints in the frame colour, and the terminal's background fills the rest of the fixed 6 px padding, so the text's inset and the grid size never change with the width (`term_view.rs` render; a const assertion keeps `PADDING` at least the widest width). The options were mocked in `docs/design/frame-width/` (RT-651).

  Themes come from `ThemeStore` (`theme_store.rs`): the compiled-in `BUILT_INS` (the eight above; a user file cannot take their ids, it gets a `-2` suffix) and the user's, one `<config dir>/themes/<slug>.json` per theme, `{name, base?, terminal_source?, ui, terminal}` stored resolved (every `ui` token and every `terminal` colour present, as `#rrggbb`, or `#rrggbbaa` where the token has alpha).

  `save` writes `.<slug>.json.tmp` and renames it into place, never overwrites (it picks a free slug, `slug-2`, `slug-3`, …), and ids outside `[a-z0-9-]` are refused.

  The selection is `native-ui.json`'s `theme` (absent or null is Nord), read at boot by `resolve_selection` and written by `RootView::select_theme`, which changes nothing when the theme does not load; a saved theme that does not load at boot logs `the saved theme "<id>" does not load: <err>; drawing the built-in theme "nord"` and draws Nord. A failed `save` removes its `.<id>.json.tmp` (logging if it cannot). A `themes/*.json` whose name is not a valid id is listed with the error `"<name>" is not a theme id: only a-z, 0-9 and - are allowed`, unread, and one named after a built-in is listed with `themes/<id>.json has the id of a built-in theme; rename the file to use it`, unread.

  A `native-ui.json` from a release (v0.5.1-alpha on) that holds `app_appearance` colours is migrated at the first start by `theme_store::migrate_app_colors`: with no `theme` set, a user theme "My colours" (a taken name gets " 2", …) is saved, Nord with that accent and terminal background, and selected, and the file is re-saved without `app_appearance`; a file that already selects a theme just drops them.

  A stored terminal frame colour is not kept, since a theme holds none (logged as `the app's terminal frame colour "<v>" is not kept: a theme holds no frame colour`). A failed theme write logs `saving the app colours as the theme "My colours": <err>; they are kept for the next start` and keeps `app_appearance` for the next start.

  The **Themes modal** (`themes.rs`, `themes_view.rs`) opens from the Theme row at the top of Settings › Appearance, at the App level, on a remote host too, since the theme is client-local. Its list groups Built-in and Yours; a row whose file does not load shows its error and cannot be used. The preview is a miniature drawn from the theme's values alone, at fixed sizes, for the hovered row, else the cursor's. `ActiveTheme` is one App global with no subtree scope, so the window takes a theme only on Use or Enter. Use previews the theme until OK or Apply saves it (Cancel or any close of Settings draws the saved theme again); Use on the theme in use changes nothing. Save, Delete, Import and Export still write theme files at once, and deleting the theme the saved look names moves the saved look to Nord and writes it at once (`forget_saved_theme`). The modal closes with Settings, and Esc returns the keyboard to the Theme stop. "Live" means the editor's own preview; the window takes a theme only on Save of the theme in use or on Use.

  **Export** (the list footer, enabled on any row with a theme; in the editor it exports the working theme under the name field's trimmed text, unsaved edits included) copies the theme's JSON to the clipboard with the "Copied N chars" chip, then opens a Save dialog (filter "Theme (*.json)", suggested `<slug>.json`, asks before replacing); cancelling the dialog keeps the clipboard. **Import** opens a file picker (Theme, `*.json`); a file over 1 MiB is refused before it is read, and a leading UTF-8 byte-order mark is skipped (as it is for files in `themes/`). The theme lands under Yours with the cursor on it, in a new `themes/<slug>.json` under a free slug, and is not applied. Its name loses control characters, is trimmed and cut to 64 characters, becomes "Imported theme" when empty, and a taken name becomes "<name> copy", "<name> copy 2", …; an unknown `base` or `terminal_source` is kept as provenance. A failure shows "Couldn't export the theme: <error>" or "Couldn't import the theme: <error>" in the modal's error row.

- **Truncating text with `…`**: gpui 0.2.2's text element reuses its cached shaping whenever a measure call carries no wrap width (`elements/text.rs`), and taffy's first measure of a flex child never carries a definite one, so `.truncate()` and nowrap + `text_ellipsis` clip mid-letter without an `…`, and wrap + `text_ellipsis` + `line_clamp(1)` can vanish outright in a stacked split, whose panes get a 0-width pass first.

  No view calls `.truncate()`; one-line text goes through `ellipsis.rs`, which has two shapes. `ellipsized(id, text, drawn)` is for a content-sized box that shrinks (the pane title, chips, sublines, the diff path): an invisible copy sizes the box to the whole text, and an absolutely positioned copy, laid out once at the box's final width, draws the `…`.

  `truncating(id, text)` (wrap on, `text_ellipsis`, `line_clamp(1)`) is for a `flex_1` or block row outside the pane grid (panel rows, heads, the footer), where the width is definite once flex settles; a site whose spec shows `truncating` drawing whole text in a narrow box uses the pair instead (the source-control picker went the other way: the pair drew whole there). Text that runs past its box by about a pixel now ends in `…` where the old clip hid the sliver.

  Under a `whitespace_nowrap` parent (a jump palette row), `truncating` inherits the no-wrap and draws its text whole, so the call adds `.whitespace_normal()`.

  A re-measure through `truncating` is what exposed gpui's stale runs: a narrow measure shortened the text element's one `runs` list, and the next, wider measure shaped the whole text with the short list, which panicked when the stale length fell inside a character. The rule now: each measure truncates its own copy of the runs, in the vendored gpui (`vendor/gpui`, `VENDORED.md`), and `truncating` keeps wrapping on because the wrap width is what makes the measure definite. `apps/native/tests/ellipsis_real_text.rs` guards it on the real text system (`docs/testing.md`).

  The source-control section head is two lines, repo then branch, each cut on its own. The in-process harness's fake text layout hides the cause, so specs read the drawn text: in debug builds each helper records its `TextLayout` under its id once a test calls `ellipsis::enable_probe()`, and `ellipsis::drawn_text(id)` returns it; `tests/ui/ui_ellipsis.rs` holds one spec per site.

## Chat and summary panes

A pane showing an interactive agent session that offers a chat has three views: Terminal, Chat and Summary. The view is the pane's, so a terminal pane and a chat pane of one session can be open at once; the session itself does not change. The daemon side is in [architecture.md](./architecture.md) "Chat mirror" (`chat.rs` is the pure model, `chat_view.rs` the pane body, `chat_cards.rs` the cards and composer, `summary.rs` and `summary_view.rs` the summary, `work_strip.rs` the strip, `chat_tail.rs` the Tail boxes).

- **Switching**: the pane header starts with a Terminal | Chat | Summary control (`pane-view-<view>-<pane>`, tips "Show this session's terminal", "Show this session's chat", "Show this session's summary") with the shown view marked, and the header's right-click menu has the other two as "Show terminal", "Show chat" and "Show summary".

  While the session's agent is not running (`sidebar::agent_up`: its `program_name` is not the agent descriptor's tag, as after the agent typed into a shell exits), Chat and Summary are dimmed in the header and the menu with the tip "The agent isn't running", their keys do nothing, a pane on either shows its terminal and its chat unloads; the remembered view is kept, so the pane returns to Chat or Summary once the agent starts again (`chat_view.rs` `chat_available`, `RootView::follow_agent_runs` on every session update). Until the host's agent descriptors arrive, the chat is offered as before.

  `Ctrl+Shift+M` switches the focused pane between terminal and chat and leaves the summary for the terminal; `Ctrl+Shift+U` opens the summary and leaves it for the terminal. In a pop-out the keys act on the pane that window draws. Both keys are always taken and never reach the terminal. A pop-out's toolbar has no control, and a pop-out draws the pane's view.
- **Compact mode**: while the pane shows Chat, the header has a `Compact` button after the Terminal | Chat | Summary switch (`chat-compact-<pane>`, tip "Fold runs of read, search and run calls into one line"), accent-filled while Compact is the mode. A click switches mode and writes `chat_mode` to `native-ui.json` at once; the mode is the app's, not a session's, and Compact is the default. Comfortable draws one card per tool call.

  In Compact, consecutive read, search and run tool calls draw as one line in the terminal's words (`1 read · 2 searched · 1 ran`, plus ` · N failed` when a call failed and a `running` mark while a call runs and its turn has not ended), `▸` collapsed and `▾` open; a click opens the run's cards, and the thinking rows between its calls, under the line. Thinking between two calls stays in the run, thinking before the first or after the last stays outside. Any other tool (edit, write, subagent task), a subagent's child call and a call that names files to tail (it keeps its Tail button) end a run and keep their cards. A call's kind is the plugin's `ChatEntry::Tool.tool_kind`; the app never matches tool names, and a call whose kind is missing or unknown keeps its card (`chat.rs` `display_rows`).

  In both modes a chat pane wider than the cap draws its column capped and centred (`chat-column-{pane}`); a narrower pane is unchanged. The cap is `chat_max_width` in `native-ui.json`, 960 logical px by default, `0` for none (a cap above 65535 acts as none); it includes the column's side padding, and the scrollbar stays at the pane edge. The scroll container lays out as a block and the column centres itself with auto side margins (`chat_column`), never as a flex `items_center` child: there, taffy measures a `w_full()` and `max_w` child's height at the uncapped width, so a long message wraps into more lines than were measured and the scroll range ends inside it.

  Settings > General's Chat section sets it (`Maximum chat width`, any whole number of px, pending until OK or Apply like every Settings edit) beside a `Chat view` choice of Compact or Comfortable, which writes the same `chat_mode` the pane header's `Compact` button does. Each finished turn's last answer, the last `Answer` before a `TurnEnd` or before the next `User` entry that is not a queued `pending` one, draws in a border-only box (`chat-final-{pane}-{id}`: the theme's `line_strong` border, the tool cards' radius); a running turn's latest answer and earlier answers draw as before. A message queued while the agent works does not end the turn, nor clear a Compact run's `running` mark: `ends_turn` in `chat.rs` decides it for both. The summary pane has neither the cap nor the box.
- **Remembered view**: each switch becomes the session's remembered view in `native-ui.json` (`session_views`, per host, `"chat"` or `"summary"`; a terminal is not written). A new pane on that session, a session pop-out included, opens in it, and a new session opens in Terminal. A Restart's copy takes the original's entry as it is placed, so a pane last switched to Chat or Summary comes back on that view, a restart into a pop-out included, and the choice survives a client restart; a copy into a new tab or into a tab still opens on its terminal.

  A session that offers no chat is remembered as Terminal; a pane rebound to another session, or emptied, goes back to Terminal, and a pane a reconnect unbound keeps its view only when the reconnect binds it to the same session.
- **Terminal under a chat or summary**: the pane keeps its terminal fed but undrawn, never resizes the PTY and takes no keys; switching back focuses the terminal. A popped-out chat pane never focuses its hidden terminal either.
- **Loading**: `LoadChat` goes out when the first Chat pane of a session appears and again after a reconnect, and `UnloadChat` when the last one goes (switch away, close, rebind, or the session pop-out closing); a Summary pane does the same with `LoadSummary` and `UnloadSummary`. Neither is sent for a Welcome or after a refusal.

  A session that offers no chat shows its terminal under the muted line "This session offers no chat, so it shows its terminal", and a load that fails for another reason shows "Could not load the chat: {the daemon's message}" the same way, with no toast.
- **Chat body**: a scrolling chat that follows the bottom until scrolled up, on the shared scrollbar.

  Desktop Chat answers draw a single line break as a line break (`md_blocks::SoftBreaks::Line`); the file viewer and the release notes keep it as a space, and image alt text always does. User bubbles sit on the right (a pending one dimmed until its transcript record arrives); answers are Markdown, composed by `stretchtext.rs` (stretchtext drawn as its short form, a faded-underline link that opens its long form in place, one level at a time, with a muted `‹` that closes it and its nested ones; open state per session and answer, in memory, carried from a live answer to its transcript answer), then parsed by `md_blocks.rs` and drawn by `viewer_md_view.rs`'s painter (a live answer has a blue border, a cursor and "writing · N lines", and only `http`/`https` links are clickable).

  "Thought for Ns" is one muted line; a tool card shows its name, one-liner (the name once when the call has nothing to summarise) and running, done or failed state, and a click shows Input and Result or Error, with a Bash or PowerShell card's whole command above them, one statement per line (`shell_lines::split_statements`: split at newlines and top-level `;`, `&&` and `||`, never inside quotes, `$(…)`, backticks, heredocs or here-strings; the one-line summary's statements when the 4 KiB input cap cut the command); system rows are muted pills, a receipt reads "question — answer", a turn's duration reads "Worked for …" and older entries read "N earlier messages".

  Muted lines read "Loading the chat…" and "No messages yet".
- **Prompt cards**: one card for the session's current prompt sits over the chat, with any others stacked behind it as ghosts.

  A permission card offers Allow once, Always allow (when the dialog offers it; its tooltip names the rule and where it is saved) and Deny; an AskUserQuestion card shows one question at a time with its options, Type something, Back, Skip and Next; Review offers Submit and Cancel; plan approval offers Approve (auto), Approve (manual edits) and "Tell <agent> what to change"; folder trust offers Trust this folder and Exit.

  A card can take a typed answer in a single-line box (`CardBoxes` in `chat_cards.rs`). A question card's "Type something" row has the box beside its button (placeholder "Type something"), and a plan card's "Tell <agent> what to change" row has one with that label as placeholder: Enter sends the box's text as Type something, and the button or its digit does the same, or with a blank box puts the cursor in the box. A permission card has a box under its option buttons (placeholder "Tell <agent> what to do instead") with "Allow with text" (only when the prompt can amend) and "Deny with text"; Enter sends Deny with text, and a blank box sends nothing. Esc in a card box moves the cursor to the composer and sends nothing, and digits typed into a card box are typed, in the Chat and Summary panes. While a chat send is in flight a typed answer is not sent and the box keeps its text. A refused typed answer goes back to its card's box with the reason on the card; once the card has gone, it goes to the composer with the reason under it.

  Each option of a card (permission, question, plan, review, trust) is a full-width clickable row, with the option's description under its label in secondary text (`chat-card-option-desc-<n>`); the named actions (Back, Skip, Next, Cancel and the like) stay a wrapped row of buttons under them. The question text is `chat-card-subject` and holds the whole question however the CLI wrapped it. A question card draws every tab of a multi-question prompt above the question (`chat-card-tab-<n>`), answered ones ticked ✔ and the current one as the header chip (`chat-card-header`).

  A Heads up notice and its later steps (the expanded explanation, "Dismissed.") are cards with their digit keys as buttons, pinned over the composer until answered; an explanation too tall for the notice's band has its keys off screen, and shows no card. A prompt the chat cannot answer (previews, Rewind, the detailed transcript, `/model`, `/btw`) says "Open the terminal to answer this".
- **Card keys**: a bare digit answers from an empty composer, and only 400 ms after the card appeared (a digit inside that grace is dropped); Esc denies a permission card, and with no card up interrupts a running turn (one ESC byte, as the terminal's Esc and the phone's Keys → Esc send it) when the chat's last screen reading has the composer Working, whether the composer or only the Chat pane has focus; after one interrupt Esc is taken and sends nothing until the next screen reading, since a second Esc opens Rewind in Claude; Ctrl+Enter allows once from an empty composer; Ctrl+Shift+Enter always allows. A submitted card stays, busy ("Sending…"), until the screen shows its dialog gone, then collapses to its receipt. A card answered in the terminal or on another device closes with "Answered elsewhere".

  A refused answer frees its card with the daemon's reason on it, with no toast.
- **Composer**: a multi-line field under the chat ("Send a message (Ctrl+Enter)"); Ctrl+Enter sends, during a turn too, where the message waits in the CLI's own queue. The composer is for chat messages only: while a card is up its Send is drawn but disabled, and a typed answer goes through the card's own box (see Prompt cards). A refused send gives its text back to the field, before anything typed since, with the daemon's reason under the composer. The field's text outlives the chat view: when the session's last chat pane leaves it (switched to Terminal or Summary, closed, its tab hidden), the text is kept in memory and comes back, caret at the end, when the chat loads again; a reconnect to This PC or to a remote host keeps it the same way, the text coming back once the chat reloads.

  A note replaces the field's ability to send while the screen cannot take a message: "Not connected", "Sending…", "The prompt box has a draft. Send or clear it in the terminal first.", "<overlay> is open in the terminal. Close it there to send." or "Can't read the prompt box right now.". "Sending…" shows from a send until its pending entry arrives; the paste can stay on screen as a draft after that, and a draft the send owns shows no note until the composer moves past it, the turn starts (`Working`), a `Ready` follows the entry, a refusal gives the text back, or a 10-second backstop passes.
- **Notices**: the daemon's `SessionNotice` raises an info toast: "<agent> is waiting in the main conversation." when the daemon did not return the terminal to main because a stash was already held and the box holds a draft, or "Your draft for <agent> is back in the main conversation.".
- **Running-work strip**: a row over the composer of the chat and summary views while the session has subagents, background shells or a wakeup, folded from `ChatWork` (`RunningWork` in `chat.rs`, drawn by `work_strip.rs`). Its present parts are joined with " · ": "1 subagent" or "N subagents", "1 background shell (<command cut to 24 characters>, <age>)" or "N background shells (oldest <age>)", and "wakeup in <time>", or "wakeup due" once the time has passed.

  A segment's tooltip lists its items: a shell's full command, "<agent type>: <description>" for a subagent, or "Counted from the screen; no details reported yet" for an item only the screen counted. The strip repaints every second while a figure reads in seconds, when a countdown drops under a minute, and every 30 s otherwise. Nothing in it responds to a click yet.
- **Tail boxes**: on a host whose `Welcome.features` lists `file_tail`, a tool card in a Chat pane (not Summary) shows one button per `tail_paths` entry, "Tail {file name}", accent-filled while its box is open. The box sits under the card: 12 lines tall, scrolling, in the terminal font, following the file while at the bottom and holding still while scrolled up. It reads "No output yet" before data; ANSI escapes are stripped and the newest 2000 lines are kept.

  A refusal shows the daemon's error in the danger colour and stays until the box is closed. After each (re)sent `TailFile` the client drops chunks until the `reset` one. The box closes with `UntailFile` on a second press, when its card leaves the chat, when the chat unloads (the pane leaves Chat view or toggles to the terminal) and when the session goes; a reconnect re-asks for the open tails once the chat reloads. A background task's output file is outside the session's folders and is not followed.
- **Summary body**: the current prompt's card pinned on top, then one line per stretch of work in the daemon's order, and under them the strip and the composer. A click on a line opens it into the chat entries of its stretch (the same rows as the chat, "Earlier messages aren't loaded" when its first ones are no longer held) and a second click closes it; opening or closing moves no scroll. The pane follows new lines while it sat at the bottom.

  Muted lines read "Loading the summary…" and "Nothing to summarize yet".

## Source control and diffs

- Status, badge counts and diffs are keyed by (repo, worktree path), so worktree and main-tree counts never overwrite each other. Stashes are one list per repo.
- Git reads carry a `request_id`, so a failed read shows in its own section rather than as a toast; a write whose status refresh fails is answered with `GitWriteError`, so pending state always clears.
- **Diff engine**: `similar` computes line and inline word diffs on the client from the full texts `FileSnapshot` sends (Patience under a 2 s deadline; word spans skipped for a side over 1000 bytes). The daemon refuses a side that is binary or over 2 MiB, with the reason in `FileSnapshot.unavailable`.
- **Diff view**: a custom GPUI element, side-by-side only, rendering aligned rows in one `uniform_list` (synced scroll for free; hunk navigation is `scroll_to_item`; F7 / Shift+F7), with a 10 px overview ruler at its right edge marking each hunk (Ochre mixed, `WAITING` insert-only, `DIFF_DELETE` delete-only). Measured in release on 5k lines and 500 hunks: model build 2.6 ms, first drawn rows 58 ms, worst scroll draw 7.2 ms.
- **Diff tab header**: the file name first, whole, then its folder dimmed; the folder truncates with `…` before the name does, and the full path is in the tooltip. Below 900 px of header width the Whitespace and Highlight toggles show icons instead of labels; the change buttons are 24 px icon squares.
- **A remote repo's diff tab** lives in This PC's layout (`OpenDiffTab` to This PC with `host` set; a local tab's `host` stays unset) and reads its snapshots from the repo's host, taking replies only from it. That host's `RepoStatus` and `Welcome` refresh it; while the host is not connected the body reads "{host} is offline", with no change count and the change buttons disabled, and it reads again on the host's next `Welcome`. This PC's own diff tabs never show an offline state. A viewer tab needs no host: a remote file reaches it as a fetched local copy.
- **Syntax highlighting**: syntect 5.3 plus two-face 0.5 with fancy-regex (no C dependency), six token classes in Petal's diff colours (keywords Rose, functions Periwinkle, types and numbers Ochre, comments `SUBTLE`, strings `LILAC`; `TokenClass::color` in `syntax.rs`), independent of the terminal's ANSI palette and each at least 4.5:1 on the diff ground.

  It runs on the background executor after the uncoloured diff shows, stops past 20,000 lines, a line over 10,000 bytes or 2 s, and is a saved toggle. Cost measured in release: +1.29 MB on the exe (+5.6%), 570 ms for 5k lines of Rust. PowerShell is not coloured: two-face drops that grammar without onig.

  pulldown-cmark and the Markdown view add 573,952 bytes to the release exe (31,178,752 before the Markdown core, 31,752,704 with the view: +1.84%).

## Notifications

OS toasts are built as XML (`toast_activation.rs`) and shown through the `windows` crate's `ToastNotificationManager`. When the client runs as the installed copy (the installer's `uninstall.exe` beside the exe), it registers its own app id `leftos.RustlingTulip` and a COM toast activator at startup and raises every toast (Needs you, Finished, pairing) under that id, so they show as rustling-tulip.

A dev build, a build run from `target\` or a failed registration keeps the PowerShell app id and in-process handlers. The registration writes `%APPDATA%\Microsoft\Windows\Start Menu\Programs\rustling-tulip.lnk` (pointing at the running exe, carrying the app id and the activator CLSID), writes `HKCU\Software\Classes\CLSID\{354BE9DC-6D82-4269-8883-D13CE3E38648}\LocalServer32` (`"<exe>" -ToastActivated`) and sets the process's explicit app id; `native.log` records "toast activator registered".

Three toasts exist. `Needs you` is raised when the daemon's `Attention { AwaitingInput }` arrives (a question, a permission prompt or a plan approval); its body is `<label>: <prompt line>`, the line the Needs You panel shows, or `<label>: Waiting for input`. `Finished` is raised when a live `SessionUpdated` leaves an agent `Idle` with no background work over a copy the client held as `Working`, or as `Idle` with background work; plain shells, a session seen for the first time, an `AwaitingInput` to `Idle` change and a relist or reconnect raise nothing. `Accounts` is raised from the account engine's events, titled `Accounts` (`Accounts · <host name>` for a remote host): an auto-switch ("Switched from <name> to <name>" or "Switched to <name>"), all accounts used up ("All accounts are used up; the first is back <time>", or without the time when none is known) and a stopped engine ("Auto-switch stopped: <message>"). A manual switch, a quarantine and an unknown event raise nothing. An all-used-up toast is raised once per host until its reset time changes, a switch happens or the host reconnects.

Every Finished toast is held for the grace the Notifications tab's `Hold a Finished toast for` row sets (`notifications.finished_grace_secs`, `apps/native/src/sidebar.rs`; 5 s by default), since an agent often starts again at once. The setting is read when the hold starts, so a change affects the next hold, not one already running. The hold is dropped when the session leaves Idle, shows background work or is removed, or a `Sessions` resync or `Welcome` arrives, so a turn that went on raises nothing and the next `Idle` starts its own grace.

A Finished toast for an interactive session that names an agent is held on, up to 12 s after the turn ended (`FINISHED_HOLD`) and never before its grace ends, while the last `SummarizerStatus` says summaries are on, under the cap and with a usable key; a 20 s grace raises the toast at 20 s with no further wait for a summary. Its `WaitingAlert` then titles it `<label> needs your answer`, `<label> finished` or `<label> posted an update` with the alert's notification as the body.

An alert that came before the grace ended, background work still running included, is kept until the session works again and words the toast when the grace ends. No alert in time, a template alert, or no status gives `Finished` with the label; toggles and the skip rule are judged when the toast is raised.

A click on the body of a Needs you or Finished OS toast goes to that session, as a sidebar click does: the main window comes forward, the tab holding the pane is shown and the pane gets keyboard focus (a pop-out showing it comes forward instead). The toast carries `launch="go:<session id>"` for This PC, or `go:<session id>:<host wire key>` for a remote host (the key may contain `:`, as in `ssh:box`), XML-escaped. The activator hands that argument back as `PairingAction::GoTo { host, id }` (`PairingAction::go_arg` encodes it, `from_activation` parses it and refuses an empty id or host), and `apply_pairing_action` runs `select_session_on`. An empty argument stays `Open`, which only brings the window forward, as for the pairing toast; the Accounts toast carries none. A click that starts the client, or lands before This PC's sessions and the tab layout have loaded, is held and applied once both have (the hold a command-line session id uses, now carrying a host); a warm client never holds, so a click for a session no host lists does nothing.

Stopped and errored sessions raise no toast: their `Stopped` and `Error` attentions still drive the sidebar `!` badge and the Needs You panel's Ended rows. A stop the owner asked for sends no attention and records no exit code, so it never reaches Needs You; its pane header reads "stopped" and its overlay "Session stopped". A session that exits on its own keeps its exit code and its Ended row.

The Dashboard tab, after Notifications, sets each host's Dashboard summaries (`summarizer_settings.rs` keeps each host's `SummarizerStatus`): Summarize sessions, the provider with its privacy line, the key source (a masked Key field with Clear, or an environment variable; both pend until OK or Apply) and the key state, the daily cap (pends; 0 or more) with today's spend, and Test. Each change is built from the last settings sent to that host, so quick changes never undo each other. A typed key pends like any other draft, per host, and is dropped when Settings closes. A daemon whose key source this app does not know locks every control but Test, with "This host's daemon is newer than this app; update the app to change these settings."

The Notifications tab reads, top to bottom: a `Needs you` toggle, its `Needs you sound` row, a `Finished` toggle, its `Finished sound` row, a `Hold a Finished toast for` row (`None`, `2 s`, `5 s` the default, `10 s` or `20 s`, shown only while the `Finished` toggle is on), an `Account switches` toggle (on by default; it has a Settings search entry), and a `Skip notifications when` row: `Session on screen` (the default), `Window focused` or `Never`. Under it, on Windows only, a `Show toasts as` row: `Windows notifications` (the default) or `The app's own`.

Each sound row is one dropdown listing `Off`, every bundled sound (`BundledSound` in `sound.rs`, sources in `apps/native/assets/sounds/README.md`) and `Custom file…`, with the chosen `.wav` or `.ogg` path under it and a `Play` preview hidden while Off. The list opens below its field at a fixed 240 px and scrolls, one list at a time; Enter or Space opens and chooses, Up and Down move, Esc closes the list and leaves Settings open, and Tab closes it and walks on.

The row's default carries ` (default)`, and choosing it saves `"default"`, so a later change of default follows; any other sound saves its id. The Needs you default is `Mallet, rising fifth`, the Finished default `Mallet, falling fifth`. A custom file over 5 MB, or one that cannot be read or decoded, plays that kind's default and shows why in red.

A sound plays once per toast the toggle and skip rule let through, on its own thread through `sound.rs`, and not while Windows holds the toast back (the app's notifications off, Do Not Disturb or Focus Assist, a presentation or a full-screen app). A summarizer alert worded "needs your answer" plays the Needs you sound; every other Finished toast plays the Finished sound.

`Notifier::user_busy` holds the app's own toasts and every chime back on two reads. `SHQueryUserNotificationState` covers a presentation, a full-screen app and the busy states, but reads `QUNS_ACCEPTS_NOTIFICATIONS` with Windows 11 Do Not Disturb on. So it also reads the shell's quiet-hours WNF state, `WNF_SHEL_QUIETHOURS_ACTIVE_PROFILE_CHANGED`: level 0 is off and any other level holds toasts back, Priority apps not being honoured.

A failed WNF read fails open, so toasts show, and logs one warning per process.

To check this without the Settings UI, switch Do Not Disturb through the shell's `IQuietHoursSettings.UserSelectedProfile` (undocumented COM, CLSID `F53321FA-34F8-4B7F-B9A3-361877CB94CF`) and restore the original profile afterwards.

One clip plays and at most one waits, so a burst plays at most two. A Needs you clip replaces a waiting Finished clip and is never dropped for one, and turning a kind's sound Off drops only that kind's waiting clip.

Session on screen skips when the client window is focused and a pane of the active tab shows the session; an active diff tab, or any dialog, modal or pane menu open over the panes, means nothing is on screen.

Every toast but the pairing toast is raised with `<audio silent="true"/>` (`toast_activation.rs`) and the app plays its own clip beside it (`sound_with_toast` in `notify.rs`): the Needs you sound for Needs you and the Finished sound for Finished, so Windows' own sound never plays beside the app's. Nothing plays when that sound is Off or while Windows holds notifications back. The pairing toast keeps Windows' sound.

Window focused skips whenever the window is focused, and Never never skips, for both toasts. Each window decides for itself, and a session marked "Don't count as busy" still notifies.

The settings are `notifications.awaiting_input`, `notifications.finished` (on unless turned off), `notifications.account_switches` (on unless turned off; it gates the Accounts toast in both styles), `notifications.needs_you_sound` and `notifications.finished_sound` (`"off"`, `"default"` or `{"custom": path}`; a missing or unknown value loads as `"default"`, an unknown one with a warn line), `notifications.toast_style` (`"os"`, the default, or `"app"`; a missing or unknown value loads as `"os"`) and `notifications.skip_when` (`on_screen`, `focused` or `never`) in `native-ui.json`.

An unknown or non-string `skip_when` or `toast_style` loads as its default with a warn line in `native.log`, and the rest of the file still loads. The tab also shows Windows' read-only toast state with a link to Windows' settings.

### The app's own toasts

With `toast_style` `"app"`, the Needs you, Finished and Accounts toasts are the client's own windows and never also the OS's; pairing toasts stay OS toasts. macOS has no OS toasts (`Notifier::has_os_toasts` is false there), so it always shows the app's own and ignores the saved style, which is never rewritten: a `native-ui.json` shared with Windows keeps its choice there. The Settings style row is Windows only.

The two styles share `raise_toast`'s gate: the toggles, the skip rule and the sound. The Accounts toast has a gate of its own in both styles: only its toggle, with no skip rule and no sound. A summarizer-worded Finished toast is the same toast in either style.

An app toast also waits on `Notifier::user_busy` (the Do Not Disturb read above), run off the UI thread, and is not shown when the session's wait ended while that check ran. Windows' per-app toast setting does not apply to it, and no toast window opens in a cloaked (`RUSTLING_TULIP_OFFSCREEN_WINDOW`) run. Its sound is the app's own clip, played once the toast is placed on the stack; it has no OS sound.

Each toast is one GPUI window (`WindowKind::PopUp`, no titlebar, transparent, not movable or resizable) opened hidden. `toast_window.rs` shows it from a short-lived worker thread, since GPUI's window state is borrowed while the window opens: `never_activate` (shared with `offscreen.rs`) gives it `WS_EX_NOACTIVATE`, `SetWindowPos(HWND_TOPMOST, …, SWP_NOACTIVATE)` makes it topmost, and `ShowWindow(SW_SHOWNOACTIVATE)` shows it. A toast never takes focus on its own, and the code never activates the window; the one exception is a click into a text box on the toast (below).

The stack sits in the bottom-right of the work area (`rcWork`) of the monitor holding the main window, else the primary monitor, newest nearest the corner: 360 logical px wide, 8 px apart, 16 px from the edges, at most 4 shown. A fifth drops the oldest Finished toast first, else the oldest of any kind, so a Needs you stays while a Finished could go; a stack too tall for the work area drops the same way. With no readable work area no toast shows.

On macOS the stack sits in the bottom-right of the visible frame (`NSScreen.visibleFrame`, clear of the menu bar and the Dock), in points, of the screen holding the main window, else the menu-bar screen. The window is GPUI's non-activating pop-up panel, opened unshown: the placer first turns `hidesOnDeactivate` and `canHide` off (so it stays up while the app is in the background or hidden) and sets `becomesKeyOnlyIfNeeded` (so a click does not make it key), then orders it in with `orderFrontRegardless` on the main queue. Ordering a hideable panel in while the app is hidden would unhide the app, which is why the window is never shown at open; a toast the placer cannot order in is dismissed rather than kept invisible. Moving an open toast (a restack) is applied on the main queue just after the current UI update, against the screen the stack was placed on. `ToastPlacer` is the seam the placement goes through (`SystemToastPlacer` in `toast_window.rs`), so the UI specs record placements with `PlaceRecorder`.

Toasts are keyed by (host, session id): a later toast for a session replaces its earlier one in place and restarts its timer. A Finished toast lasts 6 s and a Needs you without answer buttons 30 s. A Needs you with answer buttons lasts until it is answered, closed with ×, its session leaves `AwaitingInput` or stamps a new `status_since`, the session is removed, or the skip rule now skips it, with a 10-minute cap. Resting the pointer on any toast holds every timer.

The answer buttons are the Dashboard's ask block (`dashboard_rows::ask_block`): Allow and Deny for a permission, or the options of a single single-choice question when there are no more than 3. They go through `answer_from_dashboard`, so a remote host's session routes as it does from the Dashboard. A sent answer reads `Sent` until the snapshot moves, a refusal brings the buttons back, and a prompt moving to another under the same wait rebuilds the buttons without a new sound. On Windows a single-choice question's toast also carries a text box under its option buttons (placeholder `Type something`, button `Send`) and a permission's one under Allow, Always allow and Deny (placeholder `Tell {agent} what to do instead`, button `Deny with text`): Enter or the button sends `AnswerPrompt` with `PromptChoice::TypeSomething { text }` or `DenyWithText { text }`, a blank box sends nothing, and a refusal brings back the buttons and the box with its text. A click into the box makes that toast the foreground window (`toast_window.rs`: `take_foreground` drops `WS_EX_NOACTIVATE`); Enter, Send, Esc or the toast closing hand the foreground back to the window that had it (`give_back_foreground`) and make the toast non-activating again. macOS, plan approvals, multi-selects, preview questions and `Go to pane`-only toasts have no box.

The box is drawn only when the session's host lists `typed_prompt_answers` (`FEATURE_TYPED_PROMPT_ANSWERS`) in `Welcome.features`, so an older daemon's toast shows its option buttons alone. A new prompt under the same wait empties the box; the same prompt redrawn keeps its text. Any other prompt, a question with previews among them, shows its text and `Go to pane` alone, which brings the main window forward on the session and closes the toast.

An Accounts toast is keyed by host alone: a later one on the same host replaces it. It lasts 8 s, has no `Go to pane` button and plays no sound; a click on its body or × dismisses it, and session messages leave it up.

### Presence reports

The client tells each daemon whether the owner is at the desk, so the daemon can hold phone pushes (`docs/session-runtime.md` "Phone pushes"). It sends `ReportPresence { active }` (`apps/native/src/presence.rs`) only to a host whose `Welcome.features` lists `client_presence`: to that host on every `Welcome`, and to every such host whenever the answer changes, checked on a window focus change and every 10 seconds. An unchanged answer is not sent again.

`active` means the main window is focused and, on Windows (`GetLastInputInfo`) and macOS (CoreGraphics `CGEventSourceSecondsSinceLastEventType`), the machine had keyboard or mouse input in the last 180 seconds. Elsewhere, or when the idle time cannot be read, focus alone decides, so Linux counts focus alone. `set_idle_reader` installs a different idle reader; the UI harness installs "input just now" so specs never see the developer's own idle time (`ui_presence.rs`).

A host's toasts close when it disconnects or sends a new `Welcome`, and every toast closes with the main window. A session's toast title is `{title} · {group} · {host}` (`toast_title`, `toast_group` in `notify.rs`): the group is the session's workspace name looked up on the session's own host, else its first member repo's name, else left out, and the host only when it is not This PC. The OS notification raised in an app toast's place carries the same title, so a remote session's system notification names its host too. The Accounts toast keeps its own title.

A toast is a rounded card in the app's theme: an accent stripe (the rail's Asking colour for Needs you, muted for Finished), a title line (whole, ending in `…` only when wider than the card), the question whole and wrapping on every toast kind, the permission command wrapping whole in a mono box, the answers one per row at full width with their labels wrapping whole, on Windows the text box row where the prompt has one (one row taller), then `Go to pane`, with × at the top right. Each answer's option description shows under its label in smaller text, muted on an outlined button and in the button's own colour on the filled first one. A click on the title-and-body block (`toast_card` in `toast_view.rs`) runs Go to pane; the answer buttons and × keep their own behaviour, × only closing the toast and stopping its press from reaching the card. The card's height is measured with GPUI's line wrapper at the font, size and width the card draws (`card_layout` in `toast_view.rs`), plus fixed paddings, and capped at the work area's height less both margins less 1 px; a capped card cuts its question to the lines that fit, ending in `…`, so the command, the answers and `Go to pane` stay visible. Once an answer is sent the toast shrinks to its single `Sent` row. There is no animation.

## Updates

The client updates itself from published releases; the mechanism (trust model, feed, verify, file swap, daemon takeover) is in [auto-update.md](./auto-update.md). The app's own updater is for this PC only; a paired client can also ask a Windows or macOS (Apple silicon) host's daemon to update itself, over the tailnet or an SSH bridge (`RemoteUpdate`, decision 11 there), which the native client sends from the Connections dialog (below).

When a host's daemon is counting down such an update, the client shows it only for This PC's own daemon (`host_update.rs`, drawn by `update_view.rs` and `notice_view.rs`): a sticky toast `Updating in {n} s` with the detail `Asked by {requested_by}. Updates to {version}; your sessions keep running.` and a `Cancel` button that sends `cancel_host_update`. The toast goes on `host_update_canceled`, and when This PC's connection closes (a reconnect shows only what the daemon then reports); on `host_update_launched` the app quits through the Keep-sessions-running path so the installer can swap its files. A canceled or launched update id is final: a later message for it changes nothing. The `update-countdown` native-shot view draws it.

The Connections dialog's row for a connected tailnet or SSH host that lists `remote_update` in `Welcome.features` and is Behind (not This PC) has an `Update host` action, hidden while an update for that host is pending (`connection_picker.rs`, `connection_picker_view.rs`). It opens a confirm dialog (`host_update_dialog.rs`): `Update {host} to the newest release?`, the body `{host} will download and check the newest official release itself, then restart its daemon. Its sessions keep running.`, the host's sessions with their status (working ones marked) or `No sessions are running on {host}.`, a slot for warning lines, and `Cancel` / `Update {host}`. Esc cancels, Enter does nothing, and the dialog closes when the host's connection closes. The `update-host` and `update-host-breaks` native-shot views draw it.

On open the dialog reads what the update breaks from the same feed the app's own updater reads (`Updater::breaks_since`), against the host's version from its `Welcome`, combining the breaking flags of every release after it up to the newest ([release.md](./release.md) "Mark what a release breaks"). While it checks, the dialog says `Checking what this update changes…` and `Update {host}` is disabled. A sessions flag ends the body with `Its running sessions end.` instead of `Its sessions keep running.` and adds the warning `v{new} ends every session on {name}.`; a protocol flag adds `v{new} can't talk to this app's version, so this app updates itself right after {name}.`. A failed check shows `Couldn't check what this update changes.` and the update may go ahead. A dev build makes no update checks, so it shows no warning and does not update itself afterwards.

After a flagged update, only when this app is older than the newest release, the app waits for the host to come back on the new version (its `Welcome`) or to refuse this app's version (`AuthFailed` whose reason starts with `protocol::NO_COMMON_PROTOCOL_REASON`, which older clients match on). Then it toasts `{name} updated to {version}` and runs its own 10 s update countdown with `Cancel` (`take_self_update` in `remote_update.rs`, run by `update_view.rs`). It never does on a refusal, a host back on its old release, or a host that does not return.

Confirming sends `RemoteUpdate { request_id }`, and `remote_update.rs` keeps one toast per host: `Asking {host} to update…`, then `{host} is updating to {version}…` on `RemoteUpdateStarted`, or `{host} didn't update` with the host's refusal. The host's `Welcome` on the new version turns it into `{host} updated to {version}` (`RemoteUpdates::on_welcome`); when the host came back on its old release, its `HostUpdateResult` turns it into `{host} didn't update; it is still on {version}` with the result's message when one came. `{host} hasn't come back; it may still be updating.` follows 5 minutes with no answer, or 120 seconds after a drop that came after Started.

An SSH host gets the same request over its bridge, and the update runs on after the SSH channel drops. The host reads the SSH request as a connection on this PC, so it always counts down 10 s (RT-1397). An administrator's daemon on a host reached only over SSH runs elevated and refuses with "This host's daemon runs elevated".

The other direction: the client's `Hello` lists `update_yourself` (`net.rs`), so any host it is connected to can send `UpdateYourself` (`ClientUpdateCountdown` in `host_update.rs`, run by `update_view.rs`). The client shows a 10-second sticky toast `Updating this app in {n} s` with the detail `{host} asked this app to update. It downloads the newest release and reopens; your sessions keep running.` and a `Cancel` button that is local only and sends nothing. A repeated update id counts down once. When it ends, the app restarts into a ready update, or checks for one and then restarts, or toasts `This app is already on the newest release.`; a dev build toasts `This build can't update itself.`.

The Connections dialog's This PC row has an `Update connected clients` action when This PC's daemon lists `client_update` in `Welcome.features` (`connection_picker.rs`, `connection_picker_view.rs`). Pressing it sends `UpdateConnectedClients` and toasts `Told {n} clients to update`, with `; {p} phones reload` and `; {k} too old to update this way` appended when non-zero, or `No other clients are connected.`

It checks at launch and every hour, skipped while an update is ready, and downloads a newer release in the background (`update_view.rs`). A dev build checks only when `RUSTLING_TULIP_UPDATE_FEED` is set.

When a verified installer is ready, the footer shows the notice `Update {version} ready` (`footer-update-text`) with an outlined `What's new` button (`footer-whats-new`, which opens the What's new window on the ready update's notes) and a `Restart to update` button (`footer-update`). Nothing installs until the press of `Restart to update`.

The press starts the installer detached and quits through the Keep-sessions-running path, so sessions keep running in their tracers and the new client comes back on the new version. A second update while one runs is refused with the toast `An update is already running`; an installer that cannot be started gives the toast `Couldn't start the update`.

On macOS the press unpacks the zip beside the installed app and starts the staged daemon's `apply-update`, which swaps the whole bundle once the client has quit (`docs/auto-update.md` decision 6). The unpack runs on the UI thread, so the window pauses for a few seconds, and a bundle the update cannot replace (translocated, or in a folder the client cannot write) is refused with the same `Couldn't start the update` toast and nothing changed. There is no update lock off Windows.

Settings → General has an Updates section: a `Check for updates` toggle (`settings-general-check-updates`, saved as `general.check_updates`, default on; off stops the automatic checks and downloads).

The section also has a `Version {version}` line (`settings-update-version`), a last-check line (`settings-update-last-check`: `Not checked yet`, `Up to date`, `Update {version} ready` or `Last check failed: {error}`) and a `Check now` button, which checks whether the toggle is on or off and is disabled while a check runs. While an update is ready the section also has a `What's new` button (`settings-whats-new`) beside `Restart to update`.

General ends with a Diagnostics section, drawn only while This PC is chosen (the two stops are absent against a remote host). Its `Detailed logging` toggle pends like every other control and saves as `general.detailed_logging` (default off); `Open logs folder` is immediate and opens the config dir's `logs` folder, logging a warning and opening nothing when no config folder resolves.

On commit the client sends `SetDetailedLogging` to This PC's daemon only when its `Welcome` lists `detailed_logging`, and OK waits for the `DetailedLogging` echo; an older daemon is sent nothing and OK closes at once.

General's Terminal behavior section holds a "Default shell" row (model in `shell_choice.rs`) that mirrors the host's `DefaultShell` and `ShellChoices`. It is a dropdown of the host's shells in the daemon's order; a shell not installed is dimmed, unpickable and carries the tooltip "Not installed on {host}". Until the choices arrive, or while the connection is not open, the row reads a dimmed, inert "Loading shells…"; against a daemon without `default_shell` it reads a dimmed "Automatic" with the tooltip "Update this host's daemon to choose a default shell" and sends nothing. Choosing Custom shows a command field below it (placeholder "Command line, for example pwsh -NoLogo"); a blank command is not a pending edit, and after a refusal or an echo with no pending edit the field shows the saved command. A note under the row, "Agents start on their own, not inside {label}.", shows while the chosen shell does not host agents. The dropdown and the Custom field (only while Custom is chosen) are Tab-ring stops, and "Default shell" and "shell" find the row in Settings search.

## Session recovery

A "Recover sessions" button sits on the activity rail above the Settings gear, with a badge counting unexpected ends (`TracerLost`) not yet recovered (a session a reboot, a crash or a killed process tree ended gets its entry at the next daemon start, so it counts too); an entry counts until it is recovered, from the dialog or the sidebar's Resume, or pruned after 7 days, and Dismiss does not clear it.

The client asks for the history (`ListSessionHistory`) on every `Welcome` and keeps the daemon's broadcasts.

The dialog (`recover.rs` model, `recover_view.rs` view) lists the last 7 days newest first: losses at an unknown time, then bursts of losses within 60 s of each other ("7 sessions lost at 11:29"), then the other ends collapsed behind "Show N other recent sessions" (shown expanded when they are the dialog's only rows; a refresh keeps a toggle the user or a failed recovery made).

Unrecovered losses are pre-ticked; a row already recovered, or with no conversation to resume, is disabled with its reason. Each row offers its conversation candidates (the known id, else the newest) and, for plain-shell rows and rows with no spawn config, a "Recover as" choice limited to what the folder allows.

The choices read the entry's agent descriptor: `{label} session`, `{label} session in {repo}` and `Register {path} as a repo, then {label} session` (`Register {path} as a folder, then {label} session` when the path is not a git repo; none for an empty path), the shell choice, and "Plain shell" always.

The shell choice shows as the descriptor's `texts.shell_resume_label` (Claude: "Shell running claude --resume") only when the daemon flags the entry (`SessionHistoryItem.shell_resume`: the plugin has the `shell_resume` cap and the entry has a conversation to resume). A row with nothing to resume shows `texts.no_conversation`.

With no descriptor the label is the agent id ("Agent" for a shell entry), the shell choice reads "Shell resume" and the note "no conversation found". A DeepSeek row offers only Claude options ("DeepSeek sessions recover as Claude."), a row that would start a fresh run is not pre-ticked, and one with no spawn settings is disabled with "no spawn settings recorded".

Sessions still in the sidebar's Abandoned group are listed too, and recovering one hands its panes, its name, its look and its sidebar place to the new session (the daemon rebinds and carries them), as the sidebar's Resume does; a per-session claim on the daemon stops the two paths recovering the same session twice.

The rest of a run's recovered sessions are placed once every one of their snapshots has arrived, in one pass so no two share a pane, where a normal spawn would go; an answer that comes after the 120 s timeout or after the dialog closed is still placed. After a partial failure only the failed rows stay, re-ticked, with their messages.

Sessions a reboot, a crash or a killed process tree ended come back on their own: after the daemon binds, it resumes each abandoned Claude session that qualifies in its old panes (see `docs/architecture.md`), so the client simply sees them running again under their old names, looks and sidebar places, and their history entries count as recovered.

When the daemon's resume pass ends, the client shows one toast keyed `resume-report` (from `ResumeReport`, once per client id per daemon run): Info "Resumed N session(s) after restart", with the detail "M stay(s) in Recover" when M > 0, or Warning "No sessions resumed after restart" when nothing resumed but some were left.

The rest (plain shells, no conversation or transcript found, worktrees that no longer pin, a failed spawn, an in-place checkout on another branch, a worktree another session holds) stay abandoned and wait in Recover and the sidebar's Resume.

## Needs You

A rail item after Sessions (an inbox tray) opens a panel listing every session waiting on the user, headed "NEEDS YOU · N"; its badge counts the rows (hidden at 0, `99+` above 99), and the rail never switches to it on its own.

The list is plain Rust (`needs_you.rs`) over the sidebar model, drawn by `needs_you_view.rs`. A session is listed as **Asking** while its status is `AwaitingInput`, and as **Ended** while it is `Error` or `Stopped` and its leaf is still flagged; parked and abandoned sessions never are.

A row shows the status glyph, the container name in its accent, the session's label and the time waited.

## Gates

A rail item after Source control (`Activity::Gates`, selector `activity-gates`) opens a panel of the gate slots on This PC's daemon host. It is a rail view plus a footer pill, not a Dashboard tab. The item shows only while This PC's daemon lists `gate_state` and has pushed a gate state, and only a 64-bit Windows daemon with the gate installed does (it checks on each poll, so the item, pill and panel hide and return live, with no restart); another host's state is ignored, and the state is cleared on This PC's `Welcome` and when its connection closes.

A daemon reports gate state, idle included, while the gate is installed on its host and the gate's state folder exists; an installed PC that has not yet run a gate still shows the item, and a leftover state folder alone does not. The item's badge (`gates-badge`) counts busy plus held slots across the local pools in the accent colour, and is hidden at 0.

The model is plain Rust (`gates.rs`) and the panel is `gates_view.rs`. `Activity::Gates` sits before `Sessions`, which stays the last `#[serde(other)]` variant, so an older build reading a saved `"activity": "gates"` shows Sessions. `RootView::shown_activity` reads a stored Gates as Sessions while there is no state, and keeps the stored value for the state's return.

The panel shows only the daemon host's gates, headed `GATES · <machine>` with its core count, at the other panels' 26 px header height; a tailnet host's slots and an aggregate across machines are never shown.

Each local pool, heavy first, has a header (`HEAVY · 2 of 3 busy`, busy counting busy and held), a slot-count stepper and its slots by index, with any slot past the count last, shown only because it has a claim. The stepper (`gates-step-up-<kind>`, `gates-step-down-<kind>`) sets the count from 1 to 64 and sends `SetGateSlotCount`, one write per pool at a time; a refusal shows under the pool. Its tooltip names the default for this machine. A slot is one of four states:

- Busy: two lines. Line one is the slot name in muted text (`heavy 0`), the short command (the program's file name without folder or extension, then the rest) and, right-aligned, the time held from the claim's start. Line two, muted and ellipsized, is the folder label (the last two path components) and the holding gate's last log line. The tooltip carries the full command, the full folder, the log path, the ceiling and the process count.
- Held: a slot taken by a gate with no live claim, drawn as one line with `held` in ochre.
- Free: one muted line, `free`.
- Stale: a free slot whose claim file names a process that is gone, `free · stale pid <n>`.

A click on a busy row opens its log in the OS default app on This PC, and its right-click menu copies the command, the folder or the log path (a part the gate did not report is a disabled row). There is no Stop gate item: gate-state has no stop API, and a stop would bring job-object code into the daemon.

Gates waiting for a pool are listed under it with their folder, command and time waited, oldest first. Below the pools sit the critical block (who holds the critical gate and how many wait), the remote and builder pools, and the queue of tickets, oldest first.

The history comes from `GateHistory`, a separate pull of This PC's daemon. Recent runs lists up to five runs that are running or ended in the last 2 h, running ones first and then newest end first, open runs and journal runs merged by pid and process start, covered runs left out because their parent's row shows the work.

A row leads with a result glyph: `✓` ok, `◉` running, `✕` failed, `⏱` timed out (a failure at status 124), `⏸` abandoned and `·` for any other state. A failed, timed-out or abandoned row is a bad row, washed and barred in the danger colour with its word on line two.

Last 7 days lists the first four summary rows of passed runs by repo and command; its header folds it, and the fold state lives in memory only. Neither block is saved.

A busy row, a waiting gate and a queue ticket append the usual time after the time held or waited (` / 4m`), the `p50_seconds` of the summary row whose command key, repo and remote flag match the gate's own; the whole time turns the danger colour while it runs over the usual, and a gate with no matching row shows no usual.

The footer pill `Gates <taken>/<total>` (`footer-gates`), shown while This PC has a gate state, counts taken slots over the local pools' counts, and a click shows the panel. While the history holds a run that failed or timed out in the last 10 minutes the pill carries a danger-coloured tail, ` · ✕ failed · <repo> · <ago> ago`, the repo left out when unknown.

History is requested when the view opens, every 15 s while it shows and every 60 s while it is hidden and a gate state is known, one request at a time (a new one waits for the unanswered one). A refusal is logged at info with no toast.

The panel repaints every second while a time on it still reads in seconds, else every 30 s. Driver selectors: `gates-panel`, `gates-header`, `gates-pool-<kind>-title`, `gates-slot-<kind>-<index>`, `gates-recent`, `gates-week`, `gates-week-toggle`, `gates-menu`, `footer-gates`, `footer-gates-tail`.

## Text viewer

A text file a terminal path link's link menu "Open in viewer" row, a plain click on a Markdown viewer link or the Fetch file… dialog opens goes to a viewer tab (`viewer_tab.rs` the model, `viewer_tab_view.rs` the view, `viewer_text.rs` the plain-Rust core) unless the file is not viewable.

`viewer_text::decide` probes the file on the background executor and picks the viewer or the external route: a file over 2 MiB, a NUL in the first 8000 bytes, or bytes past those 8000 that are not valid text (UTF-8 or BOM'd UTF-16 via `encoding_rs`) go external. A file over 2 MiB opened from a link or fetch shows the Info toast "Too large for the viewer, opened externally".

- The tab is read-only: a header (file name whole, folder dimmed) with Open in default app, Reveal, Copy path and Copy all (disabled until the file has loaded), a line-number gutter, and a virtualised list of rows 1.4 × the font size high. Syntax colours are always on and a very long line is clamped. A `:line` target scrolls to that line.
- A `.md` or `.markdown` tab opens rendered (`viewer_md_view.rs`): headings, styled paragraphs, nested lists with markers and task boxes, quotes, code blocks coloured in the terminal mono font, tables, rules, raw HTML as muted mono text, images as their alt text, and inline code as a background chip in the body font. The view is a virtual list with a row per code line, list item and table row, so only visible rows are built.
- A click on a link in the rendered view follows it (`RootView::follow_md_link`): an http or https link opens in the browser, and a file link opens that file through the viewer routing (another viewer tab, or the external app), resolved against the Markdown file's folder with any `#fragment` ignored. Any other scheme and a network path raise the Error toast "Couldn't open" with "Only http and https links open from a Markdown file."
- A `#slug` link scrolls the tab so that heading's row is at the top, a heading inside a list or quote included, and an unknown slug does nothing.
- On a tab showing a copy fetched from a remote host, a file link opens by the fetched route and only files under the download folder open: a link resolving outside it raises "Couldn't open" with "Only files in the folder for fetched files open here.", and nothing opens or is sent to the host. Siblings are never fetched, so a missing one gives "No file found for {path}". A tab whose file is not available on this PC follows no link.
- Its header has a Rendered | Source toggle, shown once the file's text has loaded. A click sets that tab's mode and saves `viewer_markdown_rendered` (default true) in native-ui.json; other open tabs keep their mode and new Markdown tabs open in the saved mode. A `path.md:<line>` link opens that tab as Source at the line without changing the saved default.
- A Markdown file over 512 KiB opens as Source with both toggle buttons disabled ("Too large to render as Markdown").
- The Source view (any non-Markdown file, or Markdown in Source mode) selects whole lines (`LineSelection` in `viewer_tab.rs`, handlers in `viewer_tab_view.rs`).

  A left press on a row's gutter number or text selects that line and gives the keyboard to the viewer, Shift+click extends from the anchor, and dragging with the left button extends to the row under the pointer, or to the edge row in view once the pointer is past the list's top or bottom (no auto-scroll); a left release anywhere ends the drag.

  Selected rows are tinted in the text input's selection colour. Ctrl+A selects every line and Esc clears. Ctrl+C copies the selected lines (`ViewerTab::selected_lines`) without gutter numbers, joined with `\n` and with no trailing newline whatever the file's line endings, and shows the usual "copied" chip; with nothing selected it copies nothing.

  Rendered Markdown has no selection, and switching to Rendered clears it. A re-read clamps the selection to the new line count, and one that lands as a banner clears it.
- Find (`viewer_find.rs` the plain-Rust matching and `FindState`, the bar in `viewer_tab_view.rs`) works in the Source view of a tab with text. Ctrl+F opens a one-row bar under the header, or gives an open bar the keyboard again: a query field (placeholder "Find"), a count ("n of m", "0 of 0" with no hit, blank with an empty query) and Previous, Next and Match case buttons.

  Matching is case-insensitive until Match case is on, and updates as you type. The current match starts at the first one at or after the top visible line and is scrolled to the centre. Enter or F3 goes to the next match, Shift+Enter or Shift+F3 to the previous, both wrapping. Every match gets a background tint and the current one a stronger accent tint.
- Esc in the find field closes the bar and returns the keyboard to the tab; Esc in the body clears a selection, else closes the bar. Ctrl+F on a rendered Markdown tab switches that tab to Source and opens find without changing the saved `viewer_markdown_rendered`; on a tab with no text (a banner) it does nothing.
- A file that cannot be shown draws a banner instead of text: too large, binary, not decodable, missing, or not available on a remote host (a restored viewer tab reads nothing there).
- Making a viewer tab the active tab (not a window focus) re-reads its file in place when the file's modified time or size differs from the last read, after one stat on the background executor. Unread, loading and not-available tabs are skipped. There is no hashing, so a same-size rewrite inside one mtime tick is missed until the next change or a re-open.
- A reload keeps the scroll, and rendered Markdown keeps its top row, including any scrolling done while the reload was reading. The selection is clamped to the new line count, find re-runs with its query kept, and the `:line` target is not applied again.
- A reload that finds the file gone or unreadable shows "The file is gone or cannot be read. Showing the last read." over the last lines (their colours and rendered document still finish if they were still being worked out); a debug log line, "the viewer could not stat the file", is written when the stat fails.

  A reload that finds the file too large, binary or undecodable shows that state's banner instead of the lines, and the file is not read again on later activations until its modified time or size changes.
- Opening or re-fetching a file whose viewer tab is already open re-reads it. Open in default app and Reveal take the same route as a link (`open_by` with the tab's recorded `Origin`), so the remote gate and the fetched-copy check apply, and a script is viewed but still asks "Run <name>?" before it runs.

### Design decisions

- **A viewer is a daemon-stored tab kind** (`TabContent::Viewer`), not a client-only tab or a modal: it reuses the pill, activation, close, restore and undo that diff tabs already have, where a client-only kind would touch every `tabs()` call site and a modal would block the terminals.
- **Ctrl+click on a path opens its app, Ctrl+Shift+click offers a choice**: Ctrl+click goes to the external app, and the link menu's first row is the same app (VS Code at the line for a `:line` link, the OS default app for a plain path), beside the viewer and the containing folder. It names no editor choice, so a later editor setting changes no stored data.
- **A file is viewable text when it is at most 2 MiB (the diff engine's limit), has no NUL in its first 8000 bytes, and is UTF-8 or BOM'd UTF-16.** The sniff decides, not an extension allowlist: the extension only picks the syntax language and the Markdown mode. Anything else goes external, which is no worse than before; there is no lossy fallback decoding.
- **Markdown opens rendered, with a persisted Source toggle**, so a construct the renderer draws wrongly is one click from the source; files over 512 KiB open as Source to bound the cost. The parser is `pulldown-cmark` with default features off (pure Rust, an event model that maps straight onto blocks). The viewer never fetches an image or any other network resource, so images show their alt text.
- **Selection is line-granular**: GPUI has no selectable-text element, and whole lines cover copying a block while Copy all covers the rest. Character selection is not offered.
- **Executable and script files are viewed, not run**: the viewer is safer than handing them to the OS, and its Open in default app button still asks "Run <name>?" first.
- **The extension to language map lives in `viewer_text.rs`** because the daemon's `language_for_path` (`git_inspect.rs`) is out of the client's reach; the test `every_language_id_has_a_grammar` keeps every id it returns backed by a grammar in `syntax.rs`.
- **A reload checks modified time and size on tab activation** rather than watching the file, so an idle viewer costs nothing and a fetched copy, which changes only when fetched again, needs no watcher.

## Fetched files

- Files fetched from a remote host are saved under the `remote-files` root (`daemon_client::remote_files_dir()`), as `<host MagicDNS name, lower-cased>/<repo-name>/<rel-path>` (`ssh-<host string, lower-cased>` instead of the name for an SSH host, so the two kinds never share a folder). That folder form is only the path: every fetch toast and the Fetch file… popup's "Waiting for <host>…" name the host as the user typed it, an SSH host's full `user@host` string or a tailnet host's name, and the connection-lost, offline and older-host toasts use it too; names Windows cannot hold are sanitised, and `..`, drive prefixes and leading separators are refused. Nothing under the root is pruned.
- A fetch streams into a hidden `.fetch-<launch stamp>-<n>.part` beside the target, created with create-new and deleted only by the fetch that created it, and is renamed over the target on done. Fewer bytes than announced is an error; more is saved. An error, a cancel, a failed write or a lost or switched connection deletes the part and toasts `Couldn't fetch <file>`.
- One fetch per target: a second fetch to the same path (case-insensitive on Windows) toasts `Already fetching <file>`.
- A Ctrl+click on a terminal path link on a remote host, or a pick from its link menu, sends `FetchFile` for the link's readings (`fetch_link.rs`, `RootView::fetch_path_link`). A **reading** is one way to take the link's path as a file under a repo or worktree of the pane's session: each candidate, longest first; an absolute host path is matched against the session's member worktrees, a relative one is read against the pane's cwd first, then against each member worktree. A bare or relative name that follows an absolute path on the same terminal line is read first against that path's folder (the nearest one), on This PC and on a remote host.

  `.` and `..` are resolved as text, and a path outside every root gives no reading. A standalone shell has no members, so it uses the deepest registered repo holding its cwd.

  A link that may leave the session's own roots (the first place of some candidate is held by no root) first asks the host `ListSessionFolders` and takes its readings over what `SessionFolders` lists: the session's repos and every folder `git worktree list` names for them, which the daemon checks again at fetch time. The `Fetching <file> from <host>` toast shows while it asks. A link inside the roots sends no ask, the Fetch file… popup keeps its member roots, and a host without `session_folders` keeps the warning below and sends no ask.
- Fetches from two worktrees with the same `rel` land at one `<host>/<repo>/<rel>` copy, as member worktrees do.
- The readings of one link are a **probe group**: their stats and transfers are sent one at a time, and a reading the host rejects before the transfer starts (no such file) moves on to the next. A reading the host starts is the link's file, and its later failure is reported as any fetch's. The saved copy opens by the `:line` rule above.
- A link shows one toast for the whole group, `Fetching <file> from <host>`, updated in place as readings advance. On a host that sends folders it shows at once on the pick, before the host answers its first stat: a file fetch then updates that same toast, a folder replaces it with the folder toast, and a warning replaces it. When every reading fails the Fetching toast is dismissed and one `Couldn't fetch <file>` error carrying the last error is all that remains (also on a lost connection and when an old host refuses a folder link); a reading missing before the transfer starts shows nothing of its own. With no reading at all, or a pane with no session, nothing is sent and a warning `Couldn't fetch <file>` says `Not inside a repo or worktree of this session.` After the host's folder list holds no reading, the detail is `<path> is outside <repo> and its git worktrees.` for one repo, `<path> is outside this session's repos and their git worktrees.` for several, `This shell isn't in a repo on <host> or one of its git worktrees, so <path> can't be fetched.` for a shell in none, and `Couldn't read the git worktrees on <host>: <reason>.` when the listing failed. A link that reads only as a repo or worktree root, missing on the host, warns `Couldn't fetch <name>` with the detail `<name> is not on <host>.` instead.
- The file's toast shows the transfer the way the Fetch file… popup does: once the host reports the size its detail reads `0 B of <size>`, then `<received> of <size>`, refreshed on every chunk, and the toast card draws its progress bar under the detail (no bar before the size is known; the folder toast has none). It carries a Cancel button from the click until the download is done: Cancel stops the fetch, deletes the part, drops the link's other readings and shows no other toast. Closing it with × keeps it closed for the rest of the fetch. After Done it keeps its detail, has no actions and is no longer sticky (it stays up while it can be cancelled).
- The ⋯ menu's **Fetch file…** row, right after Shell… (selector `sidebar-more-fetch-file`, no shortcut), shows only on a remote host with a focused pane and opens a modal (`fetch_dialog.rs` the model, `fetch_dialog_view.rs` the view).

  The scope is a repo root of the focused session, read once when the popup opens: a muted caption naming the repo for one root, a button per root for several (default the root holding the session's cwd), and "No repo for this session" with Fetch disabled for none. The field is relative to that root (placeholder `src/main.rs:42`, hint "Relative to <repo>. Add :line to open at a line.").
- The typed path is read like a link's: a trailing `:line[:col]` is split off (`links.rs` `split_path_position`), `\` becomes `/` and `.` segments are dropped. An absolute host path under the chosen root has the root stripped; one outside it is an inline error naming the root, and an empty path or a `..` segment is refused inline. Path problems show on Enter and clear on the next edit; Fetch stays disabled until scope and path are valid.
- The popup shows the fetch as a 6 px progress bar with "Waiting for <host>…" until the size is known, then "<n> of <size>". Errors (the daemon's, a refused download path, "Already fetching <file>") show inline under the field and leave the popup open; while the popup shows a fetch it pushes no `Fetching` toast and no failure toast.
- Cancel and Esc cancel the fetch (`CancelFetch`, the part deleted, no toast) and close; a backdrop click does nothing. Once the last chunk has reached the writer the fetch is finishing: Cancel is disabled and Esc ignored, and on the save the popup closes and then opens the file (so a run confirm can show). A lost connection closes the popup with every other dialog under the connection overlay (the part deleted, no toast); closing it any other way cancels its active fetch first.
- A fetched file opens through its own route (`Origin::Fetched` in `open_view.rs`), checked to lie under the download root, while every other local open on a remote host stays refused.

  It then opens as a link does: in a viewer tab when `decide` says viewable, else in VS Code at `path:line:col` when a line is given, else in the default app, with the run confirm for files that run code. Re-fetching a file whose viewer tab is open re-reads it. A relative `RUSTLING_TULIP_REMOTE_FILES_DIR` is made absolute at startup.
- **Folder fetch**: on a host whose `Welcome.features` lists `folder_fetch`, a Ctrl+click on a path link first sends `StatPath` for a reading, and the answer decides: a folder is fetched whole (`FetchFolder`, `RootView::try_start_folder_fetch`), a missing path moves on to the next reading, and anything else goes through the file flow above. A link to the worktree or repo root itself reads as the root (`fetch_link.rs`) and fetches the whole folder; a reading of the root is never fetched as a file.

  A folder lands at `<root>/<host>/<repo-name>/<rel-path>` (a root at `<root>/<host>/<repo-name>`). The host's tar.zst stream is unpacked on a thread of its own (`folder_unpack.rs` `run_unpacker`) into a stage `.{id}.part` beside the target, and on done the stage replaces any earlier copy of that folder.
- A folder fetch has one sticky toast with a Cancel button: `Fetching folder <name> from <host>` until the host answers `FolderFetchStarted`, then `Fetching folder <name> from <host> (<files> files, <size>)` with the detail `<done> of <size>`, updated as the stream unpacks. Closing it with × keeps it closed for the rest of that fetch, and its Cancel goes with it; the `Fetched folder` and error toasts still show.

  Once the host has sent Done the toast drops its Cancel and its detail reads `Finishing: <done> of <size>`, refreshed every 250 ms from the unpacker's count until the outcome arrives (no wakeups during the transfer itself). Done turns it into `Fetched folder <name>` with the detail `<files> files from <host>` and a Reveal button that shows the folder in Explorer (the toast stays); a fetched folder is never opened on its own.
- **Fetch whole folder**: on a host that lists `folder_fetch`, a plain fetched file's done toast replaces its `Fetching <file> from <host>` toast with `Fetched <file>`, the detail `from <host>` and one button, Fetch whole folder; the file still opens as before. Plain means not a page's media file, not a page waiting on its media and not a Fetch file… popup fetch. The button fetches the file's parent folder, or the repo or worktree root for a file directly in it (`file_fetch::parent_folder_request`), with the usual folder toast and Cancel and no stat first (`RootView::fetch_remote_folder` is the folder twin of `fetch_remote_file`); a host that no longer sends folders gets the older-host warning below instead. `FetchRegistry` holds each done toast's action (`DoneAction`) while the toast shows.
- Cancel (before Done) stops the unpacker, sends `CancelFetch`, deletes the stage and closes the toast. An error or a lost connection removes the stage and the folder toast and shows `Couldn't fetch <name>` with the host's reason as its detail (a ceiling refusal, for one).
- A host without `folder_fetch` cannot send a folder: a link to a root shows the warning `Couldn't fetch <name>` with the detail `<host> runs an older rustling-tulip that cannot send folders. Update it to fetch folders.`, and so does an old daemon's `… is a directory` answer to a link's file fetch.
- **Page media**: when a fetched `.html` or `.htm` that opens when done is saved, the client also fetches the relative media files the page names (`html_media.rs` `page_media`: `src`, `srcset`, `poster`, `data` and `link` `href` attributes, and `url()` and `@import` in `<style>` and `style=`) into the download root at the same repo-relative place, so the page opens with its media beside it. This is the media batch, and the page opens only after every media fetch has ended.
- A reference resolves against the page's folder and must stay inside the repo root; `data:`, `http(s):`, `//` and site-absolute `/x` references are skipped. A stylesheet the page links is read one level for its own `url()` and `@import` (`stylesheet_media`).
- At most 4 media fetches are in flight. Caps: 200 references per page, 25 MiB per file, 256 MiB per batch. A file over its cap is cancelled with `CancelFetch` and counts as skipped; once the batch cap is hit, the rest and any a later stylesheet names are skipped.
- A media file another page's batch is already fetching counts as done; a file already on disk is fetched again. Clicking the page again while its media fetch runs toasts `Already fetching <page>`.
- One toast covers the batch: `Fetching <page> and its media (n of m)`, dismissed when the page opens, or replaced in place by one Warning `Some of <page>'s media didn't load` ("{n} of {total} files failed or were skipped."). A media file never gets its own toast.
- A lost connection mid-batch deletes the media part files, does not open the page and shows one Error `Couldn't fetch <page>'s media` ("The connection was lost."). A page saved after its connection closed opens without its media, with that message as a Warning.

## Sizing

Controls grow to fit their contents: a button, row, card, toast or dialog takes the width and height its text needs, wrapping text a user must read whole rather than cutting it off. A fixed or capped size is the exception, chosen where there is a reason (a column that must line up, a window edge, a list that scrolls), and that reason is written beside the cap in the code.

## Window

The window's restore rect, maximized flag and monitor are saved in native-ui.json and restored on that monitor (the primary when it is gone); fullscreen is not restored. The title reads `(N) Tab — rustling-tulip` with N the active tab's sessions that need you (`Tab — rustling-tulip` at zero), or `(busy/total)` / `(idle/total)` in those count modes, set 350 ms after its last change. Closing the window runs the quit flow (keep running, stop keeping worktrees, stop removing them with per-session branch fate, or abandon), waiting for `shutdown_ack`.

Closing a tab, closing a pane but keeping its session, and moving a pane to an existing tab each leave an entry on the undo shelf (bottom centre, 8 s, at most 3, newest on top).

An entry holds a whole-tab snapshot of every tab it touched, and Undo sends `RestoreTabSnapshot` for a tab that still exists or `RestoreTab` at its old index for one that is gone. A tab this client has asked to remove (closing it, closing its last pane, moving its only pane out) counts as gone from the send until its removal arrives, so an Undo pressed inside that round trip still restores it, bringing back splits and ratios exactly.

Moving the only pane via "Move this pane to a new tab", or via the Move-panes dialog with every pane ticked, marks the source tab closing the same way. A refused `MovePane` or `ExtractToNewTab` clears the mark, so Undo sends `RestoreTabSnapshot` and spawns aimed at the tab go into it. A pane whose session has since gone comes back empty.

The shelf clears when the connection drops or a new `Welcome` arrives.

## Copy and toasts

A toast or a line of copy says only what the screen does not already show. It does not narrate a state change the user caused or can see: a pane that became a shell, a page that opened, a dialog that closed.

A toast is for something that happened out of view, that failed, or that needs an action the user cannot otherwise reach. An error or a refusal always gets one.

In every in-app toast card a long title wraps inside the card, and × stays in the card's top-right corner.

## Windows and pop-outs

A pop-out is an extra window of the one client process: one `RootView` holding one connection per host, and each pop-out's root (`PopoutView`, `popout_view.rs`) holds a weak handle to it and draws from it, so every window whose last draw read the `RootView` repaints with it. A pop-out holds a pane, a whole tab (a grid or a diff) or a session that has no pane. The wire does not change, since the daemon's layout still holds a popped pane in its tab; the open pop-outs live only in `native-ui.json`.

`popouts.rs` keys a pop-out by what it holds: `Pane { tab_id, pane_id }`, `Tab { tab_id }` or `Session { session_id, host }` (`host` absent for This PC's session), kept in open order. A pane and a tab belong to This PC, the layout home; `PopoutKey::hosts` lists the hosts whose sessions a pop-out shows, and a pop-out's restore waits for those hosts' session lists. Opening one again raises the first. A pop-out that would share content with an open one raises that one instead and its Pop out row is dimmed "Already in a pop-out": a session already shown by a pane or session pop-out, or a pane and the tab that holds it.

A viewer tab is refused ("Viewer tabs can't be popped out"). A pane keeps its id when it moves in the main window, so its pop-out follows it to its new tab.

A pop-out opens 1100×720 (minimum 700×400), centred on the main window's display; each further one opens 32 px right and down of the one before it. Its title is the session's label or the tab's name, and a session pop-out whose session the daemon has removed reads "Session not found". Only the main window's close runs the quit flow; closing a pop-out docks it back.

Dock back is the close of every kind: a pane returns to its grid, a tab's pill loses its mark, a session pop-out simply closes. It sends nothing, so it never stops a session or removes a tab. A pane pop-out closes by itself when its pane leaves every tab, and a tab pop-out when its tab does; a session pop-out stays open after its session stops. Pop-outs have no Pop out button of their own, and their only app shortcuts are Ctrl+Shift+M and Ctrl+Shift+U on their pane and Ctrl+Shift+P, which opens the jump palette in the main window.

The main window keeps the popped content's place as a card, which is not a terminal and holds no keyboard. A popped pane's grid slot draws a card with the session's label, "Popped out to its own window", Focus window and Dock back; a popped tab draws the same card over its body while it is the active tab, and its pill shows a muted ↗ ("Popped out"). Focus window raises the pop-out and focuses its terminal or diff.

A pane pop-out's toolbar has the status glyph, the label, the tab it came from, the member and runtime chips, a two-step Stop and Dock back.

A tab pop-out has its own toolbar (the tab's name, Dock back) and no tab strip; it draws the tab's whole grid, with splits, divider drags, pane drops and menus working inside it, or a diff tab's own view, which moves over without a refetch. In it Pop out on a pane is dimmed, and empty panes have New session… and Shell here dimmed "Spawn from the main window". A session pop-out has Stop and Close window.

A pop-out's terminal takes part in `tabs::size_drivers`, so only one view of a session answers terminal queries, and a popped tab's panes are sized and focused from the pop-out whichever tab the main window shows. The grid's bounds (`window_layouts.rs`) and the drag state are keyed by window. A drag stays inside the window it started in: on Windows the press captures the mouse to that window, so panes move between windows by Dock back and Move to ▸, never by a cross-window drop.

A pop-out's terminal or diff takes its window's keyboard when the window opens and on Focus window. Docking back a tab that is the main window's active tab returns the keyboard to its focused pane or diff. Showing a session that a pop-out holds (a leaf click, a jump) raises that pop-out and clears attention instead of placing the session again, and a session shown in the active pop-out's focused terminal counts as seen.

Menus, dialogs and toasts open in the window that asked (`overlay_owner.rs` records each overlay's window, and a closing window drops its overlays). A toast shows in the window the user last interacted with, else the main window.

The terminal slot a session pop-out draws is `popout:<host key>:<id>` for a remote session (This PC's is `popout:<id>`), and the id is read after the last `:`, since an SSH host key holds colons, so one id on two hosts is two slots. A session pop-out's saved key carries the host as well.

`native-ui.json` keeps the open pop-outs in open order, each with its key and its window's place (`window_state.rs`), saved as the window moves or resizes with the layout's 500 ms debounce.

Once per launch, when the tabs and sessions have both arrived (a remote session's pop-out, and a pane or tab pop-out holding a remote session, waits for that host's session list), the client reopens them in saved order behind the main window at their saved places, on the primary display when the monitor is gone and at the cascade place when the entry never moved.

A restore leaves the keyboard in the main window and raises it only if it was active, and an entry whose pane, tab or session is gone is dropped (a pane that moved reopens under its new tab). A saved pane pop-out whose remote session is gone, or is being forgotten, never opens; `native.log` records at info "a saved pop-out's pane is gone or being forgotten; dropped". A reconnect reopens nothing.

Quitting closes the pop-outs with the app after saving the open set, and the exit dialog counts sessions only. Closing every window, the main one included, keeps the pop-outs for the next launch. A missing `popouts` key or a value that is not a list loads as empty, and an entry whose key does not decode is dropped alone.

## Jump palette

Ctrl+Shift+P (Cmd+Shift+P too on macOS; Alt held, or Ctrl and Cmd together, is not the key) opens the jump palette from anywhere, a focused terminal included: the root key capture takes it before the terminal sees it (`is_quick_jump_key`, `quick_jump_view.rs`). In a pop-out it opens in the main window, which comes forward. It never opens while a menu, a dialog or Settings holds the main window. Esc, the key again or a press outside the panel closes it and gives the keyboard back to the active pane. The key is Ctrl+Shift+P rather than Ctrl+K so Ctrl+K stays the terminal's kill-to-end.

The palette is main-window only, as the spawn dialog is, so it has no `Overlay` variant. The state (entries, ranking, highlight, Enter's `JumpAction`) is plain Rust in `quick_jump.rs`, unit-tested; `quick_jump_view.rs` draws and routes keys; `RootView::jump_to` runs the action.

- **Panel**: 560 px wide, 64 px under the window's top, a query field (placeholder "Jump to a pane, tab, session or repo") over rows that scroll past twelve. Up and Down move the highlight, Enter or a click jumps.
- **Rows**, across every connected host: `[PANE]` (each pane on screen in any tab, by its session's label), `[TAB]`, `[SESSION]` (a sidebar session in no pane), and `[REPO]`, `[WS]` and `[DIR]` (each sidebar container; `[DIR]` also tags a registered folder that is not a git repo); a row of another host ends ` · host`. A `[SHELL]` row, `Open shell on {host name}`, is offered for each connected host, This PC included (a host that is not online is left out); it matches by its text and its host name but draws no ` · host` suffix.
- **Order**: with an empty query, panes and tabs by last focus (an in-memory history, lost on quit), then tabs never focused each with its panes, then sessions in no pane, then containers in sidebar order, then the `[SHELL]` rows in host order. A typed query ranks with `fuzzy.rs` (the spawn Target list's matcher), the kind tags never matched and the host name a second, lower-ranked field. With no match one dimmed row reads "No matching pane, tab, session or repo", and Enter keeps the palette open.
- **Jumping**: a pane row focuses that exact pane (`show_session_on`), and a popped pane or tab brings its window forward; a tab row shows the tab; a session row places the session as a sidebar click does; a shell row opens a plain shell on that host as the host header's `+ Shell` does (`quick_shell_on`: This PC in the remembered quick-shell folder, a remote host in its daemon's default folder, each with the host's Default shell). A repo, workspace or folder row reveals its sidebar row, doing only what is needed: expanding the sidebar, showing Sessions, switching the Tabs view to Repos, setting the filter to All and unfolding its host; then it focuses the row and scrolls the sidebar to it. Rows vary in height, so the sidebar scrolls the container's group to the top (gpui `scroll_to_top_of_item`) only when its row is not fully in view.
- **Preselected target**: a jump to a repo or workspace makes it the Target of the next New Session opened from the toolbar, `+ Session` or Ctrl+Shift+N (`spawn_form::initial_target` takes it ahead of the focused pane's session). It clears on a click on another sidebar row, a leaf or a host header, on a pane focus, on a change of the sidebar's view or filter, and when its container leaves the registry; a New Session dialog that opens with it uses it up.

Specs: `ui_quick_jump.rs`; `native-shot jump` draws the open palette.

## Keyboard reachability

Settings → Appearance and the appearance editor share one set of keyboard stops. Tab and Shift-Tab leave the hex and filter fields for the next or previous stop, as the Worktrees path field does, rather than staying inside the field.

Stops run in reading order, column 1 then column 2: per colour section (Accent, then Background; the App level has none, so its Tab goes from the Theme row to the UI font filter) the preset swatch line, the recent swatch line (only when recents exist), the hex field, Apply (while enabled) and the reset link (while enabled); then the font filter and the family list; size −, size + and the size reset link; the four "Terminal weight" buttons (Regular, Medium, SemiBold, Bold) and the weight reset link (while the level sets a weight); then Close, in the session, repo and workspace editor only.

Disabled stops are skipped. The family row has no reset link; the list's Reset row covers it.

Each swatch line is one stop, landing on the chosen swatch, else the first; Left and Right move along it and stop at the ends without wrapping, Enter or Space picks. The family list is one stop, landing on the chosen family, else the first row: Up and Down move a highlight that skips headers, stops at the ends and scrolls into view, Enter or Space picks. After a filter edit the highlight stays on the same family while it is listed, else moves to the first row.

A keyboard-focused repo, workspace or tab row opens its container menu with Shift+F10 or the Menu key, anchored at the row's bottom-left with the first enabled row highlighted. Up and Down move through enabled rows and wrap, Home and End jump to the ends, Enter or Space runs the highlighted row (the same action a click runs, `container_menu_rows` in `session_menu.rs`), Tab does nothing, and Escape closes the menu and returns the keyboard to the row. A right-clicked menu opens with no highlight; the first Down highlights. Folding the sidebar closes an open container menu, and the menu reads keys only while it holds the keyboard.

Picking a swatch, by mouse or keyboard, adds its colour to the recent colours (deduped, at the front) once the level takes the change; a recent swatch's tooltip reads "Recent color #rrggbb". A press that disables its own stop (Apply, a reset link) hands the keyboard to the next enabled stop after it. A click on any Appearance control moves the keyboard stop there, and closing Settings clears its stop.

The editor walks the same stops, Close included, and draws the focus ring on its focused stop. It opens with no stop focused: Tab lands on the first stop and Shift-Tab on Close. The ring wraps, from Close to the first stop and from the first stop back to Close. Enter or Space on Close closes the editor, Tab leaves the hex and filter fields with the typed text kept, and Esc closes the editor whatever stop has focus.

The stop order, ring step (`step`), where focus goes when a press disables its stop (`after_lost`, shared by Settings and the editor), cursor and highlight logic is plain Rust in `appearance_stops.rs`, unit-tested; Settings keeps its one focus slot, `settings_control`.

When a daemon echo or re-read removes the focused Settings control from the Tab ring (Worktrees Reset, Remote access Autostart, OK or Apply once nothing is pending, an agent field a rule disables), the keyboard moves to the next stop in that page's full order (`settings_stop_order`) instead of falling back to the tab list.

The footer's OK, Apply and Cancel end the ring before the search box and the tab list. If the user has moved focus elsewhere, nothing moves. The rule runs at render time (`RootView::render` calls `keep_settings_keyboard`).

A text field without the keyboard draws no selection. A field built with its text selected shows the selection once it takes focus, and typing still replaces the text (`text_input.rs`, `painted_selection`).

Menus and modals keep to the window and hand the keyboard back. A context menu opens at its anchor and snaps inside the viewport, and its frame never grows past 60% of the window's height: a longer menu scrolls its rows instead (`session_menu.rs` `menu_frame`, `MENU_MAX_SHARE`). Confirm dialogs open on their safe option — Cancel, Keep running, Ignore, or a pane-only close — and every close path, Esc included, returns the keyboard to the pane.

Esc has deliberate exceptions. It never dismisses the layout chooser (the import modal in "Tab layouts" does: Esc and its ✕ both keep the layout), and it is ignored while a recovery or an exit is in flight. In a session rename it leaves the menu open and returns to its rows rather than closing them.

## macOS

The client builds and runs on macOS (arm64), packed as an unsigned app bundle (`tools/installer/README.md` "macOS app and disk image"); the open work and the Mac mini runs are in [plans/macos-compat.md](./plans/macos-compat.md) "Native client". What is true off Windows today:

- The daemon and tracer sit beside the client exe (`Contents/MacOS/` in the bundle), and the daemon runs from a cached copy under the binaries folder, as on Windows. Config, data, binaries, worktrees and updates all share `~/Library/Application Support/dev.leftos.rustling-tulip/` (a path with a space; [on-disk.md](./on-disk.md)).
- Sessions work: a shell and a Claude session start under `rt-tracer`, which the daemon reaches over a Unix socket in the temp folder, and a Claude session's hooks reach the daemon.
- Autostart is a LaunchAgent (`daemon_client::autostart`).
- Notifications: macOS has no OS toasts, so every Needs you and Finished toast is the app's own toast window whatever `toast_style` says ("The app's own toasts"). Pairing prompts still go to the OS notifier and show nothing (RT-1032). Focus / Do Not Disturb and full-screen apps are not checked (RT-1036). A real Mac check is open (RT-1030).
- Secrets: the daemon refuses to seal an env secret, so a secret reaches a session as an `${env:NAME}` row, and the summarizer cannot read a saved key ([env-secrets.md](./env-secrets.md) "macOS"). Tailnet device tokens are not stored either; the client logs that there is no store off Windows.
- Signing and notarization are deferred (RT-665).

## Tests

Three tiers, all Rust tests:

- **UI specs** (`apps/native/tests/ui/`, one binary with a module per spec file): in-process, headless GPUI through the `test-support` feature (`VisualTestContext`), never touching the user's mouse or keyboard. `RootView::with_transport` takes a `Transport` (`RootDeps.open_host`), a factory from a `Target` to the `NetCommand` / `NetEvent` channel pair that it calls for This PC at construction and again for each remote host the window connects, so specs hand it `support::fake_transport`, script a fake daemon (`tests/support/mod.rs`), inject `DaemonMessage`s and assert on the `ClientMessage`s sent, grid text, selection and clipboard.

  `ui_dir` and the clock are injected, so specs never write the real native-ui.json. The test platform shapes text as fixed 0.6 em glyphs, so specs assert on cells, never on font pixels. Specs that rely on focus events call `window.activate_window()` first.

  A view names an element a spec or the headless driver must find with `.driver_id(|| ...)` (`DriverId`, `apps/native/src/driver_id.rs`), never `.debug_selector`; the one exception is a scroll container, which keeps `.debug_selector` because the extra child `driver_id` adds would scroll with it and join its content size. Without the off-by-default `driver` Cargo feature (never in the installer build) `driver_id` only forwards to `debug_selector`. With it, each named element also records its bounds in `driver::registry` (`lookup`, `names`): `Entry.bounds` is the padding box in window coordinates, so a border drawn outside it is not included, and `Entry.visible` is that box clipped to the content mask, zero-sized when an ancestor hides it. `ui_driver_registry` runs only with `--features driver`.
- **Live e2e** (`tests/e2e_live.rs`, `tests/e2e_recover.rs`, `tests/e2e_remote.rs`, `tests/e2e_ssh.rs`, `tests/e2e_multi_host.rs`, `.\rt.ps1 native-e2e`): the same harness against a real daemon whose config, binaries and worktrees dirs are all under `.tmp/`, set on the child with `Command::envs`, never process-wide. Specs create sessions through a clone of the client's `NetCommand` sender. A spec using a fake agent CLI (fake-claude for Claude) with no `node` on PATH fails, never skips.

  A live spec's own hang guard equals nextest's 300 s kill, so a spec waiting on a condition uses an ordering barrier, such as a `DumpScreen` on the same connection, rather than polling `daemon.log`.

  A live window is shaped like production's. `Harness::open_live` connects This PC to the daemon under test. `Harness::open_hosts` (`tests/support/live.rs`) opens the window with This PC on its own isolated home daemon (`LiveDaemon::start("<name>-home")`) and each remote host on a real `Net` thread, dialled through the saved hosts that `open_hosts` writes into the home's `native-ui.json` (a tailnet host whose name a saved host may not hold is dialled once the window is open, as the picker dials it). A `LiveHostSpec` names the remote's target, the config dir of the daemon it reaches and its TLS roots; `LiveHosts` hands back the client side of each host's connection (`client(&HostKey)`, newest last).

  `open_hosts` waits for every connecting daemon's tab layout or first-connect question and presses Start empty on any chooser that shows, so a spec's clicks reach the window. `Harness::place_shell_on(&HostKey)` presses `+ Shell` on a host's header and returns the pane its shell lands in. Each daemon is its own `LiveDaemon::start(<unique name>)`, since its roots, tracer pipe prefix and binaries dir all derive from that name (a daemon whose binaries dir is not under `.tmp/` would reap the installed app's tracers). The fake ssh shim holds the state of one daemon per process, and any ssh alias reaches it.
- **OS smoke** (`tests/smoke_window.rs`, `.\rt.ps1 native-smoke`): launches the real exe with `RUSTLING_TULIP_OFFSCREEN_WINDOW`, which opens it cloaked and never activated, so it never takes focus or covers the user's work: the window carries `WS_EX_NOACTIVATE` and opens at the bottom of the Z order, and a cloak that fails never shows it, the process exiting with code 3 (`offscreen::CLOAK_FAILED_EXIT`; the `shot` and `diff_bench` examples do the same). Before launch the spec writes the client's `client-id-native` and lays out its sessions for that id over its own socket, so the first-connect chooser never dims the probes.

  Input is posted to the HWND, each key only after the shell has echoed the previous one: an attach probe posts Space until it echoes and the screen holds still, then each letter waits until the typed line equals the text so far (a Space waits for scrollback growth), and the whole line is checked before Enter.

  Posted key-downs are not ordered like a real keyboard (Space and Enter are sent at key-down while letters arrive later as `WM_CHAR`), so a stalled UI thread let them overtake queued letters. Every wait in the spec is a 120 s hang guard, never a timing assumption.

  A script that posts clicks takes each point as two scalar parameters (`-X`, `-Y`), or as an array declared `[ValidateCount(2,2)]`, and refuses a point outside the window's `GetClientRect`: `pwsh -File` passes `150,108` to an `[int[]]` parameter as one string, which once put a click at x=19036. `smoke_posted_click_on_the_rail_switches_the_panel` guards that a posted click on the cloaked window acts.

  A posted move is followed at once by `WM_MOUSELEAVE` (gpui's Windows event loop), so UI shown only while the pointer is over the window, such as the sidebar's hover controls, never shows under posted input; specs set it in process with `RootView::set_window_hover_override`.

  `.\rt.ps1 native-smoke` builds and runs the smoke specs with `--features driver`. The driven specs launch the exe as a driven run (`RUSTLING_TULIP_DRIVER=1`) and use the endpoint's pointer methods: `driven::smoke_driver_click_switches_the_rail_panel`, `driven::smoke_driver_drag_moves_the_sidebar_divider`, `driven::smoke_driver_wheel_scrolls_a_pane_back` and `driven::smoke_driver_right_click_opens_a_menu`.

  The live no-focus check, `driven::live_drive_leaves_the_foreground_and_cursor_alone`, drives a client with `click`, `type_text`, `key`, `drag`, `wheel` and `screenshot` and asserts the desktop's foreground window and cursor position are unchanged afterwards; it fails when there is no foreground window, since an empty desktop would hide a steal. It runs only through `.\rt.ps1 native-drive-check [-HandsOff]` (`native-smoke` excludes it), which `.gate/desktop.toml` `patterns` routes to a builder's logged-on desktop and which refuses on this PC without `-HandsOff`. The drag and wheel bodies it shares with the pointer specs are helpers in `smoke_window.rs` (`drag_sidebar_divider`, `wheel_pane_up`, `type_scrollback_loop`, `submit_scrollback_loop`).

  The live toast check, `driven::live_drive_app_toasts_show_on_top_without_focus`, runs through the same verb: a driven client with `RUSTLING_TULIP_DRIVER_TOASTS=1` shows the app's own toast windows while its main window stays cloaked, and the spec asserts a Needs-you toast shows visible, topmost, `WS_EX_NOACTIVATE` and not cloaked, with the foreground window and cursor unmoved. A Settings control below the fold of the smoke window is scrolled into view with `wheel` first (`scroll_into_view`).

  `smoke_keys_posted_while_the_client_stalls_reach_the_shell_in_order` suspends the client's UI thread (`SuspendThread`) right after the `o` of `echo` is posted, so the Space after it must wait for the thaw, which reproduces a load-only fault without a CPU burn.

  Pixels are read with `PrintWindow(PW_RENDERFULLCONTENT)` from the threaded show and probed for known UI colours and for a change in the pane after typing; the spec checks the window is still cloaked and not foreground after each capture. `smoke_window_has_noactivate_and_sits_below_foreground` checks the extended style and that the foreground window is above the smoke window in the Z order.
- **Screenshots** (`examples/shot.rs`, `.\rt.ps1 native-shot [<view>] [-Out <path>]`): not a test tier but the way to look at a change.

  It opens the real window cloaked over `RootView::with_transport` and a fake daemon behind a `Transport` scripted in the example (four repos, a workspace, seven sessions in every status, a split tab, a diff tab), drives it to the view with the app's own keys (a posted click for the rail), waits for two equal captures (5 s at most), and writes `.tmp\shots\<view>.png` with the smoke tier's `PrintWindow` capture.

  No daemon starts and no config dir is read. The Working spinner animates on wall-clock time, so two shots differ inside that glyph and nowhere else.

The e2e and smoke tiers are `#[ignore]`d in the normal nextest run and run only through their `rt.ps1` verbs, under `nextest --run-ignored only`. A probe or dev daemon never runs with default dirs, where its client attaches to the user's real sessions and resizes their PTYs: it sets all of `RUSTLING_TULIP_CONFIG_DIR`, `RUSTLING_TULIP_BINARIES_DIR` and `RUSTLING_TULIP_WORKTREES_DIR` to `.tmp/` dirs, as `native-e2e` does. `daemon_client::isolation::check_isolated` is that rule as code: it passes only when the three variables are each set to an absolute folder with a `.tmp` folder strictly above it, and otherwise returns the first `NotIsolated` (variable and `Reason`).

### Driver endpoint

A driven run is a launch with `RUSTLING_TULIP_DRIVER=1`. The gate (`apps/native/src/driver_gate.rs`, compiled in every build) decides first in `main`, before tracing starts or any folder, log or registry entry is touched. Unset or empty, the client runs as usual. A driven run needs a build with the `driver` feature, `RUSTLING_TULIP_OFFSCREEN_WINDOW` set, the three isolated dirs passing `check_isolated`, `RUSTLING_TULIP_REMOTE_FILES_DIR` passing `check_isolated_var` (an absolute folder under a `.tmp` folder, so fetched files never reach the owner's downloads), and each registered agent's binary override variable set. The overrides are required so a driven run never falls back to a real agent CLI on PATH: they point at the fakes by default, and at a real CLI only when the driver MCP's `launch` is given an `env` naming one.

A cloaked run shows none of the app's own toast windows, except a driven run that also sets `RUSTLING_TULIP_DRIVER_TOASTS=1` (`driver_gate::driver_toasts_wanted`, read at each toast): its toasts show on the desktop it runs on, for the live toast check. Any other value keeps them unshown, and it never refuses a run.

A cloaked run (`offscreen::requested()`, which every driven run, the smoke tier and `shot` set) opens nothing on the desktop: `open::opener_for` hands `RootDeps.open` a `LoggingOpener`, so a Ctrl+clicked URL or path, Open in VS Code, reveal in folder and a folder open only log `a cloaked window would open <kind>: <target>` to `native.log` (kinds `url`, `vscode`, `vscode_folder`, `vscode_workspace`, `default_app`, `reveal`) and return success. What a link resolves to still reads the real file system. The native pickers likewise open no dialog.

A cloaked run (`offscreen::requested()`) never reads or writes the owner's login entry (`HKCU\...\Run\rustling-tulip-daemon`): `RootView::new` gets an in-memory `Autostart` (`remote_access::autostart_for`, `MemoryAutostart`) that starts unticked, and a driven run skips the startup `refresh_registration()` in `main`.

Any other value of `RUSTLING_TULIP_DRIVER`, or any condition unmet, refuses the run: it logs `driver run refused: <reason>` to stderr only and exits with code 4 (`offscreen::DRIVER_REFUSED_EXIT`).

Once the window is open, a driven run listens on the named pipe `rt-driver-<pid>` (`apps/native/src/driver/pipe.rs`). Its DACL grants only the current user's SID, it refuses remote clients, and a name already held is fatal (exit 4), never retried under another name.

Each line is one request in the format of `apps/native/src/driver/protocol.rs`, and gets one reply line, in order. A line over 64 KiB is answered with `bad_params` under id 0, and then the connection closes. Requests run one at a time on the UI thread (`apps/native/src/driver/endpoint.rs`), and each reply waits for a frame drawn after its request, at most 5 s. When no frame draws in time, or the window closes, the handler's own reply is still sent, an ok object result carrying `"drawn": false`.

Once a frame has drawn with the window cloaked, the client writes its discovery file `%TEMP%\rustling-tulip-driver\<pid>.json` (`{"pid", "pipe", "started_at", "version"}`, `started_at` being the process creation time as a `FILETIME`) by temp file and rename. It removes the file when the app quits, and first deletes each file there whose pid is not running or whose `started_at` is not that pid's creation time.

`screenshot` takes no params. It captures the cloaked window with `PrintWindow` on a worker thread to `<config dir>/driver-shots/<pid>-<n>.png`, `<n>` counting from 1 in each run, and replies `{"path", "width", "height"}`. It refuses a window that is not shown, is not cloaked by the client (`DWM_CLOAKED_APP`), is the foreground window, belongs to another process, or captured black, and a capture that does not finish within 10 s. The discovery file waits for the same shown and app-cloaked state, and for the pipe's listener to exist.

An error reply names a code (`unknown_method`, `bad_params`, `not_found`, `not_visible` or `refused`), a message and sometimes a hint. The methods, sorted:

| Method | Params | Result | Errors |
|---|---|---|---|
| `action` | `name`, `args?`; `add_repo` takes `path`, a local folder added as a repo exactly as the folder picker's answer would be, after the host path checks | `{"action": name}` | `bad_params` for an unknown name (the hint lists the names) or an `add_repo` path the host checks reject (nothing is sent; the message says why); `refused` for `open_spawn` while another dialog is open; `not_found` for an unknown tab or pane id |
| `click` | a target (`x`, `y` or `element`), `button?`: `left` (default) or `right`, `count?`: 1 (default) or 2 | `{"at": {"x", "y"}}` in logical px | target errors as below; `bad_params` for a `count` other than 1 or 2 or an unknown `button` |
| `drag` | `from`, `to`: each a target object, `steps?`: 2..=64 (default 8) | `{"from", "to"}`, each a point | target errors as below, prefixed `from:` or `to:`; `bad_params` for `steps` outside 2..=64. Every step moves more than 3 px when the distance allows |
| `find` | `prefix?` | the registry's names starting with `prefix`, sorted, each `{"name", "bounds", "visible"}` | none |
| `key` | `keys`: one keystroke, such as `ctrl-,` | `{"pressed": keys}` | `bad_params` for more than one keystroke or an unreadable one |
| `move` | a target (`x`, `y` or `element`) | `{"at": {"x", "y"}}` | target errors as below |
| `pane_text` | `pane?` | `{"pane", "lines", "text"}`: the visible rows only, never scrollback; `text` is those rows as one string with a soft-wrapped line joined (no newline where it wrapped), `lines` the grid rows as drawn, one string each; the default pane is the active tab's focused pane, else its first | `not_found` for an unknown pane (the hint lists the active tab's panes) or a tab with no pane |
| `panic` | none | none: panics on the UI thread, as a fault in a real start would (driver builds only; it proves the start guard) | none |
| `paste` | `text` | `{"pasted": n}`: the text pasted into whatever holds focus as Ctrl+V (Cmd+V on macOS) pastes it, newlines included; the clipboard is put back as it was, or left holding the text when it was empty | `bad_params` for an empty text |
| `ping` | none | `{"version"}` | none |
| `screenshot` | none | `{"path", "width", "height"}` | `refused` as above; the in-process handler also refuses it, since only the pipe answers it |
| `state` | none | the window's size and scale, `active_tab`, `tabs`, the shown tab's `panes`, `sessions` and `overlay` | none |
| `type_text` | `text` | `{"typed": n}`, one printable character per keystroke, into whatever holds focus | `bad_params` for any control character (U+0000 to U+001F, U+007F), the hint saying to press Enter, Tab or Escape with `key` |
| `wait_for` | `until`, `timeout_ms?` (default 5000, clamped to 100..=60000), `interval_ms?` (default 100, clamped to 20..=1000) | always ok: `{"met", "waited_ms", "last"}`, `last` being the final value the predicate read | `bad_params` ("bad until: ...") for a malformed predicate |
| `wheel` | a target (`x`, `y` or `element`), `notches`: ±1..=273, positive scrolling up | `{"at": {"x", "y"}}` | target errors as below; `bad_params` for 0 or a count out of range |

The pointer methods (`click`, `drag`, `move`, `wheel`; `apps/native/src/driver/pointer.rs`) post window messages to the client's own hwnd, with logical px converted to physical client pixels, and each adds `"drawn": false` when the frame wait times out. A target is a point (`x` and `y`) or an `element` (a registry name, aimed at the centre of its visible box), never both. `bad_params` covers a missing or double target ("give a point or an element to aim at", "... not both"), a half point ("a point needs both x and y"), a non-finite number and a point outside the window ("the point (x, y) is outside the WxH window"). An unknown element is `not_found` ("no element <name>", the hint listing near names), an element a clipping ancestor hides is `not_visible`, and a window with no handle is `refused`.

Posted input cannot carry modifiers, since gpui reads them from `GetKeyState`: any pointer request with `modifiers` is `refused` ("posted pointer input cannot carry modifiers; press a chord with key, or use action"). A posted move is followed by `WM_MOUSELEAVE`, so hover-only UI needs `action` `set_hover`. Posted pointer input reaches only a real window, so the in-process UI specs cover the refusals only, and the driven smoke specs prove the rest on the real exe.

`action` names are `open_settings`, `new_shell`, `open_spawn`, `toggle_sidebar`, `select_tab` (`{"id"}`), `focus_pane` (`{"id"}`), `show_activity` (`{"name"}`: `sessions`, `needs_you`, `source_control` or `gates`, which shows the sessions panel while This PC has no gate state) `set_hover` (`{"value"}`: `true`, `false` or `null`) and `add_repo` (`{"path"}`: an existing folder on This PC, added as the folder picker would add it).

A `wait_for` predicate (`until`) is one of `{"state": "<dotted path>", "equals": <json>}`, `{"state": path, "exists": bool}`, `{"pane_text": {"pane", "contains"}}` and `{"element": "<registry name>", "visible": bool}`. A numeric path segment indexes an array, and `exists` means non-null. `pane_text.contains` matches against the same joined `text` that `pane_text` replies, so a match survives a soft wrap. The loop runs in the endpoint between frames (`apps/native/src/driver/wait.rs`), so it never blocks the UI thread, and it is answered only over the pipe.

### Driver MCP server

`tools/rt-driver-mcp/` is a stdio MCP server (hand-rolled JSON-RPC 2.0, one message per line) over the driver endpoint, so an agent can launch an isolated client, drive it and look at it. The repo's `.mcp.json` registers it as `rt-driver`, started by `tools/rt-driver-mcp/launch.ps1`. It is a development tool, never in the installer.

`launch.ps1` runs the installed copy and never builds. `tools/rt-driver-mcp/install.ps1` builds the release exe through the gate, copies it to `%LOCALAPPDATA%\leftos\rustling-tulip\data\driver-mcp\<version>-<first 12 hex of its SHA-256>\` (an existing folder is left alone) and names that folder in `current.txt` beside them. With nothing installed, `launch.ps1` exits saying to run `install.ps1`. A running server keeps its own folder, so an install never replaces it.

Tools, a fixed surface of five, all keyed by a session name the caller picks (there is no default session):

- `launch {session, build_dir?, repo_root?, shell?, env?}`: takes a **shadow copy** of the driven client, the daemon and the tracer from the build dir (default `target/test-release`) into `<repo_root>/.tmp/driver/<session>-<server pid>/bin/`, starts an `IsolatedDaemon` (`crates/dev-daemon`) under that folder, starts the client from the copy with `RUSTLING_TULIP_DRIVER=1`, `RUSTLING_TULIP_OFFSCREEN_WINDOW=1` and `RUSTLING_TULIP_REMOTE_FILES_DIR` at the session's `remote-files` folder, waits for its discovery file and pings it. A build dir without the driver build is refused, the message naming the build commands. The daemon's fake agent CLIs come from `repo_root` too (each plugin's fake under that checkout), so `repo_root` must be a rustling-tulip checkout, never only a folder with a `.tmp`. `shell` is `"cmd"` (the default: the daemon runs `cmd.exe` with a fixed prompt and echo) or `"default"` (the daemon uses its Default shell setting with shell integration on); any other value is refused with `shell must be "cmd" or "default", not "<value>"`. `env` is a JSON object of name to string, set on the isolated daemon and the client after the isolation variables, for a run against a real Claude or the phone app; only `RUSTLING_TULIP_CLAUDE`, `RUSTLING_TULIP_TAILSCALE`, `RUSTLING_TULIP_PWA_DIR` and `RUSTLING_TULIP_TAILNET_DIR` are accepted, and the config, binaries and worktrees folders stay isolated under `.tmp` whatever is set. A name off the list (`env may only set …, not "<name>"`), a non-string value, an empty value, a non-object and a `RUSTLING_TULIP_TAILNET_DIR` that is not an absolute path under a `.tmp` folder are each refused. It replies `{session, pid, pipe, scratch, scratch_repo}`; `scratch_repo` is an empty folder at `<parent of the checkout>\.tmp\rt-driver\<session>-<server pid>\repo` for the run's repos (outside the checkout, see [testing.md](./testing.md) "Reproducing a terminal fault"), whose session folder is removed at `stop`; the server's pid keeps a crashed server's leftover folder and another server's from blocking a launch, and a launch is refused only while that exact folder already exists.
- `call {session, method, params?}`: any endpoint method; an unknown one is refused listing the methods.
- `batch {session, steps}`: calls the steps in order and stops at the first error, replying `{passed, steps, failedAt}`. `call` and `batch` both refuse an `add_repo` path inside the checkout.
- `screenshot {session}`: the endpoint's `screenshot` as MCP image content (the PNG) plus its path.
- `stop {session}`: stops that session's client and daemon.

A launch whose `env` sets `RUSTLING_TULIP_CLAUDE` (a real Claude) logs the CLI in with the **driver token**, never the owner's `~/.claude`. The isolated daemon refuses to start when any agent's home variable ends up outside a `.tmp` folder, which is why `CLAUDE_CONFIG_DIR` is not accepted in `env`. The token is set on the isolated daemon only (`DaemonSpec.daemon_only_env`, never on the client) as the Claude plugin's OAuth token variable, and the scratch home's `.claude.json` is seeded with `hasCompletedOnboarding` and `theme` unless one exists. With no token stored, such a launch is refused naming `tools/rt-driver-mcp/set-driver-token.ps1`. The owner stores the token once, by hand: the script asks for the output of `claude setup-token` and pipes it to `rt-driver-mcp.exe set-token`, which keeps it in one Credential Manager entry (service `rustling-tulip-driver`, user `driver-token`) and never echoes it. Accepted risks: the token sits in the isolated daemon's environment for the run, so a shell pane in that run can print it; a driven run's headless spawns get no login; nothing sweeps the scratch-repo folder of a crashed run.

A tool failure is a result with `isError`, never a JSON-RPC error. An endpoint or session error appends the **error feed**: the last 20 lines of the session's `native.log`. When stdin closes, the server stops every session. Its own log goes to stderr and to `<repo_root>/.tmp/driver/rt-driver-mcp-<pid>.log`; stdout carries only JSON-RPC.

The live spec `driver_mcp_launch_ping_screenshot_stop` (`tools/rt-driver-mcp/tests/server.rs`, `#[ignore]`d) launches a real session, pings it, takes a screenshot and stops it; [testing.md](./testing.md) gives its command. The modules are `tools.rs` (the tools), `launch.rs` (shadow copy, spawn, discovery), `session.rs` (a live session and the feed), `pipe.rs` (the endpoint's pipe client) and `rpc.rs` (the JSON-RPC loop).
