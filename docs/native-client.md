# Native client

The desktop client is `apps/native` (binary `rustling-tulip-native`): GPUI (Zed's UI framework) with `alacritty_terminal` for the terminal grid. It replaced the Tauri/WebView2 app, which is retired and kept as history on the `tauri` branch (tag `tauri-last`). The daemon, tracer and `crates/protocol` are shared and unchanged by the client.

This doc records the decisions a change to the client needs to know; what each feature must do is in the [parity checklist](./plans/native-client-parity.md), and open work is in [plans/MAIN.md](./plans/MAIN.md). How the pieces fit together: [architecture.md](./architecture.md).

## Stack

- **GPUI 0.2.2 + `alacritty_terminal` 0.26.** The client moved off the web stack; GPUI draws natively and `alacritty_terminal` supplies a mature VT parser and grid. Iced is the fallback if GPUI's API churn becomes a problem.
- **Crate rules.** `apps/native` is a main-workspace member under the workspace lints, prek clippy, `cargo nextest run` and `cargo deny check`. `main.rs` is a thin binary over the library `rustling_tulip_native`, so specs link the library.
- **Testable core, thin view.** State a feature adds (sidebar tree, split tree, tab list, key mapping, span building, forms, dialogs' focus rings) lives in plain-Rust modules with unit tests; the GPUI `*_view.rs` renders it and forwards events. Every feature mounts into `RootView` (`lib.rs`), the hotspot concurrent items rebase over.
- **Clipboard** goes through GPUI's own API (no `arboard`).
- **Folder picker**: `folder_picker.rs` is the client's own Windows folder and file dialog, copied from GPUI 0.2.2's `file_open_dialog` (Apache-2.0) because GPUI's `PathPromptOptions` has no start folder: it adds `SetFolder`, so Add repo opens at the folder the last added repo sits in (`last_repo_dir`), Shell… at its typed folder or the quick-shell folder, and the worktrees Browse at its field; its file mode filters to the file types the caller names (a `FileFilter`): `.code-workspace` for the workspace creator's Browse, which remembers its own folder (`last_vscode_dir`) separately from the repo folder, and `.txt` / `.md` or a variable's own extensions for the preset wizard's pickers. A start folder is checked off the UI thread and dropped when it is missing or takes over 2 s (an offline share). Off Windows it falls back to GPUI's picker with no start folder.
- **Repos and the no-repos states**: + Repo ("Add repo…") and + Workspace sit in the sidebar toolbar's `⋯` menu beside Shell…; the 30 px row stays + Session, + Shell, `⋯`. With no repos or workspaces the sidebar shows "No repos or workspaces yet." over an Add repo button, the main area's empty state gains Add repo beside Spawn a session and Open shell, and the spawn dialog (Ctrl+Shift+N, or any entry without a locked target) opens in a no-repos state with Add repo and Spawn disabled, turning into the form on the first repo that arrives; + Session and Spawn a session stay disabled. `AddRepo` carries no `request_id`, so a refusal is the generic error toast. Right-clicking a repo's or workspace's row opens its container menu, whose last row, below a separator, is a danger `Remove repo` / `Remove workspace`: with no live session the first click arms the row (`Confirm: remove repo…` / `Confirm: remove workspace…`) and the second unregisters; with live sessions the first click opens `Remove repo?` / `Remove workspace?` instead, naming the container over a body reading `Running sessions move to Detached.` and one row per owned live session as `label (agent)`, answered with `Cancel` (focused), `Remove anyway` (unregister, leaving them running under Detached) or `Stop and remove` (a cleanup-free `StopSession` each, then the removal). A workspace's own sessions are those whose `workspace_id` is it; a repo's are those whose first member repo is it, outside any workspace; a plain shell is never listed. A removal is silent and closes the dialog once the daemon's list no longer holds the container, a refusal is the generic "Daemon error" toast with the dialog left open and the arm dropped, and Esc, Enter, Space and Tab drive the dialog without reaching the terminal.

  The menu's first row is `Spawn session`: the spawn dialog held on that container, with the target picker showing it alone and Open in left free.

  When the container has a stored config, `Launch last again ▸` follows: that submenu replaces the rows with `‹ Back`, `Current tab`, `New tab`, one row per grid tab by name, then `Edit first…` (the spawn dialog prefilled and locked to the container instead of a replay).

  Then `Appearance…` and `Launch preset…`, `Launch preset…` lists the container's presets (repo and workspace containers alike): a loading row until the daemon's `Presets` reply arrives, a failed row when it errors (replaced only by that menu's own reply) and a none-defined row; picking a preset opens the preset wizard.

  Below a separator sit `Open in Explorer`, `Open in VS Code` and `Copy path`; the danger Remove row follows below another separator. Explorer and Copy path act on a repo's folder; a workspace has no single folder, so both are disabled with the tooltip `This container has no folder`, as is VS Code when a workspace yields neither a linked file nor a folder.

  VS Code opens a repo's folder; a workspace opens its linked `.code-workspace` file when one is set, else its member folders in member order as one multi-root window (`--add` for each after the first), skipping members with no folder. When VS Code is missing, the folder opens in the file manager or the workspace file in its default app, under the `VS Code not found` warning toast.

  A repo or workspace whose stored spawn config has launched before draws a two-line 46 px row: the name line over a muted last-launch summary (`container-<key>-summary`) of `agent · mode · target · model · authority` (or `trusted` instead of the authority), then `N env`, absent parts omitted, with the tooltip `Last launch: <summary>`; a never-launched row stays 30 px.

  A click focuses the container row and folds it; while the sidebar holds keyboard focus the focused row draws the 2 px `ACCENT` ring (`container-<key>-focus`), Up and Down move that focus among the visible container rows, Enter and Space fold, and Esc clears it and returns the keyboard to the terminal. The focus also clears on a Repos/Tabs switch and when its container leaves the list.

  A repo's or workspace's row shows a launch ▶ at its right while the pointer is over it or it holds the keyboard focus (`container-<key>-launch`, hover `Launch last again in the current tab`); it replays without folding the row.

  A double-click on the row replays into the current tab too: its first click still folds or unfolds the row, and its second replays instead of folding again. Two launch gestures for one container within 500 ms count as one, so a double-click or a repeated ▶ launches once.

  With no stored config, both open the spawn dialog locked to the container; a trusted config opens the dialog prefilled, after the `Review trusted launch` warning toast; a worktree config waits for the daemon's fresh `SuggestBranchName`, replaying with that name (a reply is matched by its `request_id`, and a timeout raises `Couldn't pick a branch name for launch-last`), while an in-place config replays at once.

  A captured config drops the one-shot answers a launch gave — the worktree-collision policy (back to `Reuse`) and an in-place target's `checkout_strategy` (back to `None`) — so a replay, a duplicate, a recovery or a resume never acts on a collision or dirty tree nobody was shown.

  A tab container's row has its own right-click menu, one row, `Spawn session here`, on a grid tab only; a diff tab's menu has no rows. It fixes Open in to that tab and starts the dialog on the target of the tab's first session, when it has one, leaving the target picker free; if the tab goes while the dialog is open, the lock drops and placement falls back to the current tab, else a new one.

  A DIR or SH container draws a folder banner under its row while expanded (`container-<key>-banner`): the folder path on one truncated line (`container-<key>-path`), then `Add repo` (`container-<key>-add-repo`, hover `Add repo: <folder>`) and, once the folder's scan answers with a suggestion, `Add workspace` (`container-<key>-add-workspace`, hover `Add workspace: <suggested name>`). The links keep their room while the path ends in `…`.

  The banner folds with its container, and only DIR and SH containers draw one: a repo, workspace, tab, Unbound or Detached container never does, nor an SH with no cwd.

  `Add repo` registers that folder straight away (`AddRepo { path, name: None }`), opening no picker and leaving the toolbar's Add repo… start folder (`last_repo_dir`) alone. `Add workspace` accepts the scanned `VscodeWorkspaceSuggestion` as it stands (`AcceptVscodeWorkspaceSuggestion { watch: false }`), with no creator dialog and no `needs 2 repos` gate.

  The client sends `ScanVscodeWorkspaces` once for each distinct DIR or SH folder on a connection, keyed by the folder's normalized path (case-folded on Windows): a folder first seen in a session list or update, or regrouped by a repo or workspace registry change, is scanned then, and the same folder is never rescanned. Answers for a folder are dropped on `Welcome` and while the connection overlay is up, so a reconnect scans again.

  An expanded Detached container shows: `These sessions are still running, but their repo or workspace is no longer registered. Resume one from its row, or stop it from its header.` The toolbar's `⋯` menu gains `Resume all abandoned (N)` under a separator when N ≥ 2, sending `ResumeAllAbandoned`.

  While one of its leaves still runs, the banner also carries a two-click `Stop all` chip (`detached-stop-all`, hover `Stop every session still running in this container`): the first click arms it to `Confirm: stop all` (`Click again to stop every running session`), the second stops every leaf that still runs, and Esc disarms it.

  The chip is absent while every leaf is stopped or the activity rail is on another panel, and an arm is dropped when the container or the sidebar folds, or the rail leaves Sessions.

- **Workspace creator** (`workspace_creator.rs` model, `workspace_creator_view.rs` view): `Add workspace…` follows `Add repo…` in the `⋯` menu; under two repos it draws muted with `needs 2 repos` and does nothing, and the menu's tooltip names only the rows shown. It opens `New workspace`, with `From repos` and `From VS Code workspace` tabs; From repos needs a name and at least two ticked members, and says `No repos registered yet.` when none exist.

  From VS Code workspace parses the picked `.code-workspace` file, showing `Parsing workspace file…` then the suggested name and its folders in file order with `registered` / `will register` badges under the `Workspace name` label; a parse failure shows the daemon's message inline, else `Failed to parse workspace file.`. The file picker filters to `.code-workspace` on Windows and opens at `last_vscode_dir`, else `last_repo_dir`, storing the picked file's folder.

  Create keeps the dialog open until a `Workspaces` broadcast holds the trimmed, case-insensitive name; an `Error` with no `request_id` shows inline with the typed name and ticks intact and raises no toast, while a routed `Error` takes the generic path.

- **VS Code workspace detected** (`vscode_suggestion.rs` model, `vscode_suggestion_view.rs` view): the daemon's suggestions queue and show one at a time. The prompt shows the file path in monospace, `<path> references N folders. Create a rustling-tulip workspace named <name> with these members?` with the name bold, then the folder badges.

  The buttons are `Not now` / `Create` / `Create & watch` (tooltip `watch the file and re-sync members`), dismissed by ✕ (`Dismiss suggestion`) or Esc; `Create & watch` sends the watch flag, and answering shows the next queued prompt.

- **Preset wizard** (`preset_wizard.rs` model, `preset_prompts.rs` prompt parsing, `preset_launch.rs` preview grouping, job registry and toast text, `preset_wizard_view.rs` view): a modal opened from the container menu's `Launch preset…`. Its stages walk the preset's prompt source (a prompts file through a filtered file picker, a folder, inline text or GitHub issue ranges, limited to the sources the preset allows) and then its prompted variables (text, folder and file with `Pick…` and `Clear`, case-insensitive toggles). The last stage is Preview: `{n} prompt(s) ready to spawn.` (plus ` → {t} tab(s).` when the preset groups by tab), the prompts as `[n] first line` under `Tab i of m` headers, a `Max panes per tab` field (hidden without tab grouping; blank takes the preset's cap, a preset cap of 0 counts as 1; input that is not a whole number of 1 or more disables Launch with an inline message; read-only while scripts run) and a `Scripts to run` section listing each script command with its variables filled in. Launch runs the scripts on the daemon first, then sends `LaunchPreset` with a client-made job id and closes the dialog; a script failure stays on Preview with the error inline, and the button reads `Retry script(s) & launch …`.

  Progress outlives the dialog. A job registry in `RootView` tracks only the jobs this window started, so another window's launch raises no toast here. Each job has one sticky toast, `Launching {preset}` with `{created} of {total} sessions · {tabs created} of {tabs} tabs`, a thin progress bar (`notice_view.rs`) and a red `Cancel` button (`CancelPresetLaunch`), replaced in place by a `Launched {preset}` or `Cancelled {preset}` toast; a failed job raises one sticky warning, `Preset launch failed: {preset}`, with the daemon's reason. Closing a running job's toast keeps it closed until the job ends.

  Success and canceled toasts stay timed and keep `Select` and a red `Stop all` until they fade; a failed launch's toast is sticky until ×. A job leaves the registry when its terminal toast closes, times out or is pushed out. On `Welcome` running jobs and their toasts drop, and ended ones keep theirs. Toast buttons are generic (`ToastSpec::actions`, selectors `toast-action-<toast id>-cancel|select|stop-all`).

  `Select` tints the job's sessions in the sidebar (palette `LAUNCHED_TINT`) and shows the Sessions view; on a running launch the tint follows the job, so sessions it makes later are tinted as they arrive. A user's session click (sidebar leaf or Needs You row) or `Welcome` clears the tint; a programmatic selection does not. It only highlights. `Stop all` stops the job's live created and partial sessions with no confirm and keeps their worktrees; on a running launch it sends `CancelPresetLaunch` first. `Cancel` leaves the toast once pressed. For a tab-grouping launch the first tab the job creates is shown once its id is known.

  A non-optional prompted variable is required and a toggle never is: `Next` stays disabled with the tooltip `Fill in: <labels>` until each is filled. The last stage's `Next` is disabled with the tooltip `Preview and launch arrive with the next update`. Esc, a lost connection or a new `Welcome` closes the wizard.

## Daemon connection and protocol

- The client ensures the daemon through `crates/daemon-client` (`ensure_running`, passing `NATIVE_PROTOCOL_VERSIONS` from `net.rs`). A running daemon is reused when its supported versions intersect the client's, even from another build, so the client never fights another client over a stale binary; a daemon sharing none is retired through `/shutdown` and replaced, and its tracer sessions reattach.
- daemon.json carries `supported_versions` (`#[serde(default)]`; an older file reads as its scalar `protocol_version`).
- The native client speaks only the current protocol version (23), and the daemon's `supported` lists only that version; there is no TypeScript mirror on `main`.
- **Client identity**: the native client keeps its id in the file `client-id-native` and sends it in `Hello`; the daemon keys its tab layout on it.
- **Reconnect**: backoff 0.5 s → 10 s, a standby-resume watchdog, a connecting overlay with "Restart daemon", and a footer pill with a troubleshooting flyout. After a user-chosen shutdown the client never reconnects or respawns the daemon.
- **Request ids**: a client that must match a reply to its request sets the optional `request_id` (spawn, duplicate, scrollback, appearance, git reads, spawn previews, checkout prompts, session history, recovery, env names, branch-name suggestions, and the tab requests `CreateTab` / `MergeTabs` / `MovePane` / `ExtractToNewTab` / `SplitPane`, whose id comes back only on the refusing `Error`, which a refused split also logs at warn as `tab layout request failed`); the daemon echoes it only to the requester (CLAUDE.md, "Wire-protocol gotchas"). A new tab, merge or move-to-new-tab arms a pending create (an ordered queue of request ids; the oldest is consumed when a new tab arrives, which becomes active); the refusing `Error` disarms its id and a `Welcome` forgets every armed one, so a refused request never makes the next arriving tab active. The client also keeps tab-layout requests in flight per tab (a split; a move, for its source and destination tab): the tab's next `TabUpdated` ends the oldest entry, `TabRemoved` ends all of them, the refusing `Error` ends its own, and `Welcome` forgets every one; closing a tab's last pane while one is in flight does not mark the tab closing. Adding one is additive; a reply without one (an older daemon) falls back to matching by content.

  The spawn dialog's `SuggestBranchName` asks without one, so every suggestion for its target still reaches it, while a launch-last wait takes only the reply carrying its own id.

- Unknown daemon message types are logged with their tag and skipped; a frame that fails to decode is logged as an error.
- The client logs to `logs/native.log`, rotated on each launch.

## Persistence

Machine-local UI state lives in native-ui.json in the config dir (`UiState` in `sidebar.rs`; the field list is in CLAUDE.md, "Where things live on disk"). Tab layouts, session appearance overrides and host settings such as keep-awake and the worktrees root live on the daemon, so every client sees them. Saves are debounced (layout and tab font sizes 500 ms) and flushed on quit.

Settings → Worktrees edits the daemon's worktrees-root override, and shows `Saved` only once the daemon has echoed the last save. Manage worktrees (opened from that tab) lists the root's groups titled by their `.rt-group` name, deletes one group or every stale one, and "Launch session here" opens the spawn dialog with the target locked and that worktree pinned (the spawn form's `Lock`, which a duplicate prefill reuses). Folder and file pickers go through `RootDeps.pick_folder` / `RootDeps.pick_file`, so specs inject fakes: GPUI's test platform cannot prompt.

## Tab layouts

A client's tabs and their split trees are daemon-side and keyed by client id (`state.rs` `ClientLayout`), so two clients can show the same sessions in different tabs and layouts. A tab's layout type is a `RearrangeLayout`; `TabEntry.picked_layout` records the type last picked for that tab, and holds only while the user has not arranged the tab's panes by hand since.

A pick marks the tab with `RearrangeTab`; an `ExtractToNewTab` that names a layout marks its new tab too (the first-connect chooser's overflow tabs, the Move-panes dialog; the chooser's first tab is rearranged). The remembered type is the one the daemon actually built, so a wire layout it does not know is kept as `Balanced`.

While a tab is untouched since its pick, the daemon rebuilds it on every pane addition or removal: `SplitPane`, `ClosePane`, a session-removal close across each client's tabs (`close_session_panes`), the source of `ExtractToNewTab`, and both sides of a cross-tab `MovePane`. A rebuild keeps pane ids, their order and unbound panes.

A concrete grid keeps its column count (a three-column pick with a fourth pane is three plus one) and carries `aspect: None`. The automatic pick names no count at all: the tab menu's `Auto` row (the Grid submenu's, and the flat row a two-pane tab shows), the first-connect chooser's `Auto` shape, the Move panes dialog's `Auto` shape and Ctrl+Shift+G all send `RearrangeLayout::Grid { cols: 0, aspect: Some(<pane area width / height>) }`, on an additive `#[serde(default)]` field and without a protocol bump. The daemon keeps the tab automatic and fits the columns to that aspect with the aspect-aware best fit (`crates/daemon/src/tabs.rs::best_fit_grid_cols`, moved there from the client), falling back to `ceil(sqrt(N))` when no aspect is known: an older client's bare `cols: 0`, the `AutoGrid` preset and the all-sessions `InitLayout` build. Every later rebuild re-picks from the aspect the tab remembers, so adding or removing a pane keeps the grid fitting its area.

While a tab stays automatic, a window resize re-sends its automatic layout with the pane area's new aspect after a 250 ms debounce (`apps/native/src/lib.rs::schedule_auto_grid_resend`, `AUTO_GRID_RESIZE_DEBOUNCE`; `apps/native/src/tabs.rs::auto_grid_resends` skips a tab whose stored aspect is within 0.01 of the new one), so a drag settles as one re-pick. The daemon treats a repeat automatic rearrange of an already-automatic tab as a re-fit: it rebuilds over every pane the tab holds, keeping the empty (unbound) panes and the tab's untouched mark and adopting the new aspect, where a first pick and any fixed pick still drop the unbound panes as a tidy-up. A tab pinned to a fixed count keeps it, and a resize never touches it.

`SetPaneRatio` (a divider drag) and any same-tab `MovePane`, a swap included, clear the flag, after which panes keep the sizes they have. `MergeTabs`, `CreateTab` and `InitLayout`'s own build leave it unset, a preset launch clears it, and undo snapshots and cloned layouts carry it as is.

The client sends no `SetPaneRatio` for a divider press that stays within 3 logical px of where it landed, so a click on the handle does not count as a resize. A tab update that rebuilds the dragged tab's split tree renumbers its splits, so the client ends the in-flight drag instead of sending its held path.

## Drag model

`apps/native/src/drag.rs` is the plain-Rust half of every drag. `DragPayload` is a `Pane`, a `Tab`, a `Container` or a `Leaf`. `drop_edge` maps the pointer's fraction of a pane to a `PaneDropEdge`: the outer band (`OUTER_BAND`, 0.12) on a side that touches the grid boundary (`tabs::outer_edges`, within 0.5 px), the nearer outer edge at a corner; the centre box (`CENTRE_LOW` 0.35 to `CENTRE_HIGH` 0.65) is `Replace`; otherwise the half on the nearer axis.

`pane_drop` builds the `MovePane` with its undo label (`undo::MOVED_PANE`, or `undo::SWAPPED_PANES` for a same-tab centre drop). It sends nothing for a diff or missing tab, a pane a grid does not hold, a self-drop, a non-pane payload, or a same-tab drop onto the facing half of the source's own split sibling, which would rebuild the same tree.

A pane drag starts from the header's drag area: the title, the glyph and the empty stretch, not the buttons, chips, Stop or exit code, whose press goes to `press_on_header_control`. `drag::pane_target` finds the pane under the pointer and its edge from the pane rects, so the shown tab's grid carries one drop layer over it (`grid_view.rs`): it does not occlude the panes, and it stops mouse propagation only while a drag runs, so terminals get no mouse reports then. A refused drop (what `pane_drop` sends nothing for) shows no overlay and sends nothing; an accepted one goes out through `send_pane_move`, the path the pane menu's Move to ▸ shares.

The overlay (`drag::drop_overlay`) is the accent at 22% over the half with a 1 px border, a strip 14% deep at 40% with a 2 px border for an outer edge, or the centre inset 12% on every side with a `Swap panes` badge. The ghost is a pill of the header's label (`Empty pane` for a pane with no session) on `GROUND` at 78% with the pane's accent border. Esc cancels the drag whichever element has focus (the root's key capture), and a tab update that arrives mid-drag ends it when it touches the drag's source tab or the shown tab. A drop lands only in the tab the drag started in.

`reorder` moves one id before or after another (`Side` from the pointer's half of the row or pill); `reorder_tabs` and `reorder_containers` build `ReorderTabs` / `ReorderContainers` and give none when the order would not change.

## Settings

The Settings modal's tab list reads General, Notifications, Spawn defaults, Worktrees, Appearance and App title, then a non-selectable `Agents` group row and the Claude, Codex and Cursor pages. The group row is a label only: no page, click, hover or keyboard stop.

Spawn defaults holds "Trusted launch by default"; the Claude page holds "Claude approval mode" and "Claude provider"; the Codex page holds "Codex sandbox mode" and the "Report status from Codex hooks" toggle (off by default, its hint naming `--dangerously-bypass-hook-trust`); the Cursor page shows "No settings yet."

While trusted launch is on, every agent row is locked and carries a note; the provider and hooks notes say the choice stays in effect. The hooks choice is `agents.codex.hooks` in native-ui.json and a Codex spawn sends it as `AgentOptions::Codex.hooks`; a duplicated or prefilled config's own value wins.

## Terminal

- **Scrollback-first attach**: `LoadScrollback` with live output buffered meanwhile; an 8 s request timeout with retries after 2 s and 4 s, each with its own `request_id`, and a reply to an older id dropped. When the daemon restarts the forwarder (`forwarder_restarted: true`) the held-back output is discarded, since it is already in the history. The logical scrollback cap is 5000 lines.
- **Size and replies**: only one pane per session (its size driver) answers terminal queries, so a session shown in two panes gets each reply once. A query that ends the loaded history is answered unless live output follows it, which keeps a fresh ConPTY shell from sitting blank.
- **Copy and paste**: Ctrl+C copies with a selection, else sends ^C; Ctrl+Shift+C copies; copy on select is a saved setting (default on); paste on Ctrl+V and Ctrl+Shift+V, bracketed when the child asks. Shift+drag selects even under mouse reporting. OSC 52 `c` stores reach the system clipboard; reads are answered empty and stores in replayed history are dropped.
- **Keys and text input**: Shift+Enter sends `\` + CR for Claude and shells, `\n` for Codex and Cursor. GPUI gives Space no `key_char`, so `keys.rs` maps Space and Shift+Space itself; Alt+Space stays unmapped so Windows opens the system menu. Text arrives through an `EntityInputHandler` on the pane, so dead keys, AltGr and IME composition work: a composition is drawn underlined at the cursor even when the program hides it, and dropped on blur or stop; a dead key is not reported to GPUI as a composition, because GPUI would then hide Enter, Backspace, Esc and arrows from the pane. Ctrl+Alt with a non-alphanumeric character types it (AltGr on layouts GPUI doesn't know); Ctrl+Alt+letter or digit sends ESC+char.
- **Links**: `links.rs` ports the Tauri detector (URLs, absolute, UNC and relative paths with `:line:col`, stitched across soft and hard wraps and TUI borders within ±64 rows). Links underline only while Ctrl is held; Ctrl+click wins over mouse reporting. A path with `:line` opens in VS Code with `-g`, otherwise in the OS default handler. A path Windows flags as dangerous, or with a script or executable extension, asks "Run <name>?" first. A UNC path opens only for a host behind a mapped drive or listed in `unc_hosts` in native-ui.json, which the client reads on each click and never writes.
- **Shell integration**: OSC 133 and 633 marks drive per-command gutter dots (ok / fail / unknown) anchored to absolute rows through scroll, reflow and trim, with a menu to copy the command, the output or both, and to re-run (typed without Enter).
- **Theme and fonts**: every UI colour is a token in `palette.rs` (the Petal values, with contrast floors pinned by its tests). The terminal uses a fixed palette with ANSI colours contrast-adjusted against the background (`theme.rs`), on a built-in ground of #0C0B0E; the built-in session accent is Coral #F07A62, with six accent presets (Coral, Rose, Ochre, Periwinkle, Sky, Lilac); a program's OSC 11 background and OSC 12 caret colour win. The interface draws in Schibsted Grotesk (`fonts::UI_FAMILY`, set on the root view and the tooltip view; the terminal font picker never lists it). Geist Mono, Fira Code, JetBrains Mono and Cascadia Code are bundled for terminals, and Schibsted Grotesk at 400 to 700 for the interface (OFL, `assets/fonts/`); a family resolves against the installed list, falling back to Geist Mono, Cascadia Mono, Consolas, then Courier New.
- **Status glyphs**: a session's status draws as a shape as well as a colour (`status_glyph.rs`, tinted SVG layers in `assets/icons/status-*.svg`) in sidebar leaves, pane headers, Needs You rows, the tab bar's busy pill and the footer: a spinning arc while working, an amber diamond with `?` while asking, a faint hollow ring while spawning, a small dot when idle or stopped (dimmed), a red dot with `×` on error. An agent session (never a plain shell) whose turn ends (working to idle) while this client is not showing it focused is an **unseen turn** and shows a green hollow ring until its leaf is clicked or a focused pane shows it; any other status clears it. The unseen set is per window and not saved.
- **Petal chrome**: the look follows the user's Petal canvas, https://claude.ai/artifact/B5hxrVTyyR635CQecEpG2N, saved in `docs/plans/canvases/petal/` (a board per view; the Dashboard, Settings → Alerts, Conversation and phone boards are targets for the waves that build those features). The rail is 52 px on `SUNKEN` with 36 px tiles and a 2 px coral active bar; the tab bar 38 px on `SURFACE`, the active tab on `GROUND`; the footer 28 px on `SUNKEN`. Panes are cards with an 8 px radius, 6 px apart inside 6 px of padding (`PANE_GUTTER`; the sidebar and source-control handles keep `DIVIDER_WIDTH`), the terminal inset by the 1 px border with square inner corners. - **Truncating text with `…`**: gpui 0.2.2's text element reuses its cached shaping whenever a measure call carries no wrap width (`elements/text.rs`), and taffy's first measure of a flex child never carries a definite one, so `.truncate()` and nowrap + `text_ellipsis` clip mid-letter without an `…`, and wrap + `text_ellipsis` + `line_clamp(1)` can vanish outright in a stacked split, whose panes get a 0-width pass first. No view calls `.truncate()`; one-line text goes through `ellipsis.rs`, which has two shapes. `ellipsized(id, text, drawn)` is for a content-sized box that shrinks (the pane title, chips, sublines, the diff path): an invisible copy sizes the box to the whole text, and an absolutely positioned copy, laid out once at the box's final width, draws the `…`. `truncating(id, text)` (wrap on, `text_ellipsis`, `line_clamp(1)`) is for a `flex_1` or block row outside the pane grid (panel rows, heads, the footer), where the width is definite once flex settles; a site whose spec shows `truncating` drawing whole text in a narrow box uses the pair instead (the source-control picker went the other way: the pair drew whole there). Text that runs past its box by about a pixel now ends in `…` where the old clip hid the sliver. The source-control section head is two lines, repo then branch, each cut on its own. The in-process harness's fake text layout hides the cause, so specs read the drawn text: in debug builds each helper records its `TextLayout` under its id once a test calls `ellipsis::enable_probe()`, and `ellipsis::drawn_text(id)` returns it; `tests/ui/ui_ellipsis.rs` holds one spec per site.

## Source control and diffs

- Status, badge counts and diffs are keyed by (repo, worktree path), so worktree and main-tree counts never overwrite each other. Stashes are one list per repo.
- Git reads carry a `request_id`, so a failed read shows in its own section rather than as a toast; a write whose status refresh fails is answered with `GitWriteError`, so pending state always clears.
- **Diff engine**: `similar` computes line and inline word diffs on the client from the full texts `FileSnapshot` sends (Patience under a 2 s deadline; word spans skipped for a side over 1000 bytes). The daemon refuses a side that is binary or over 2 MiB, with the reason in `FileSnapshot.unavailable`.
- **Diff view**: a custom GPUI element, side-by-side only, rendering aligned rows in one `uniform_list` (synced scroll for free; hunk navigation is `scroll_to_item`; F7 / Shift+F7), with a 10 px overview ruler at its right edge marking each hunk (Ochre mixed, `WAITING` insert-only, `DIFF_DELETE` delete-only). Measured in release on 5k lines and 500 hunks: model build 2.6 ms, first drawn rows 58 ms, worst scroll draw 7.2 ms.
- **Diff tab header**: the file name first, whole, then its folder dimmed; the folder truncates with `…` before the name does, and the full path is in the tooltip. Below 900 px of header width the Whitespace and Highlight toggles show icons instead of labels; the change buttons are 24 px icon squares.
- **Syntax highlighting**: syntect 5.3 plus two-face 0.5 with fancy-regex (no C dependency), six token classes in Petal's diff colours (keywords Rose, functions Periwinkle, types and numbers Ochre, comments `SUBTLE`, strings `LILAC`; `TokenClass::color` in `syntax.rs`), independent of the terminal's ANSI palette and each at least 4.5:1 on the diff ground. It runs on the background executor after the uncoloured diff shows, stops past 20,000 lines, a line over 10,000 bytes or 2 s, and is a saved toggle. Cost measured in release: +1.29 MB on the exe (+5.6%), 570 ms for 5k lines of Rust. PowerShell is not coloured: two-face drops that grammar without onig.

## Notifications

OS toasts go through `tauri-winrt-notification` with no registered app id, so they show under a generic sender until the native installer exists. The one toast is `Needs you`, raised when the daemon's `Attention { AwaitingInput }` arrives (a question, a permission prompt or a plan approval); its body is the session's label. Stopped and errored sessions raise no toast: their `Stopped` and `Error` attentions still drive the sidebar `!` badge and the Needs You panel's Ended rows.

The Notifications tab has a `Needs you` toggle and a `Skip notifications when` row: `Session on screen` (the default), `Window focused` or `Never`. Session on screen skips when the client window is focused and a pane of the active tab shows the session; an active diff tab, or any dialog, modal or pane menu open over the panes, means nothing is on screen. Window focused skips whenever the window is focused, and Never never skips. Each window decides for itself, and a session marked "Don't count as busy" still notifies.

The setting is `notifications.awaiting_input` and `notifications.skip_when` (`on_screen`, `focused` or `never`) in `native-ui.json`. An unknown or non-string `skip_when` loads as `on_screen` with a warn line in `native.log`, and the rest of the file still loads. The tab also shows Windows' read-only toast state with a link to Windows' settings.

## Session recovery

A "Recover sessions" button sits on the activity rail above the Settings gear, with a badge counting unexpected ends (`TracerLost`) not yet recovered; an entry counts until it is recovered, from the dialog or the sidebar's Resume, or pruned after 7 days, and Dismiss does not clear it. The client asks for the history (`ListSessionHistory`) on every `Welcome` and keeps the daemon's broadcasts. The dialog (`recover.rs` model, `recover_view.rs` view) lists the last 7 days newest first: losses at an unknown time, then bursts of losses within 60 s of each other ("7 sessions lost at 11:29"), then the other ends collapsed behind "Show N other recent sessions". Unrecovered losses are pre-ticked; a row already recovered, or with no conversation to resume, is disabled with its reason. Each row offers its conversation candidates (the known id, else the newest) and, for plain-shell rows and rows with no spawn config, a "Recover as" choice limited to what the folder allows. A Codex or Cursor row has one fixed choice, its own agent, and says which way it goes: "Codex session, resumes its conversation", "…, fresh run: no conversation recorded" or "…, fresh run: its conversation is gone"; it offers no Claude transcripts, a DeepSeek row offers only Claude options ("DeepSeek sessions recover as Claude."), a row that would start a fresh run is not pre-ticked, and one with no spawn settings is disabled with "no spawn settings recorded". Sessions still in the sidebar's Abandoned group are listed too, and recovering one hands its panes to the new session (the daemon rebinds them), as the sidebar's Resume does; a per-session claim on the daemon stops the two paths recovering the same session twice. The rest of a run's recovered sessions are placed once every one of their snapshots has arrived, in one pass so no two share a pane, where a normal spawn would go; an answer that comes after the 120 s timeout or after the dialog closed is still placed. After a partial failure only the failed rows stay, re-ticked, with their messages.

## Needs You

A rail item after Sessions (an inbox tray) opens a panel listing every session waiting on the user, headed "NEEDS YOU · N"; its badge counts the rows (hidden at 0, `99+` above 99), and the rail never switches to it on its own. The list is plain Rust (`needs_you.rs`) over the sidebar model, drawn by `needs_you_view.rs`. A session is listed as **Asking** while its status is `AwaitingInput`, and as **Ended** while it is `Error` or `Stopped` and its leaf is still flagged; parked and abandoned sessions never are. Rows run longest wait first by the snapshot's `status_since` (the daemon's stamp of the last status change, kept across a reattach), rows with no stamp next, ended rows last, ties in sidebar order. A row shows the status glyph, the container name in its accent, the session's label and the time waited; line two reads "Waiting for input" (with the terminal title when it has one), "Error", "Exited with code N" or "Stopped". A click is a leaf click: it focuses or places the session's pane and clears the flag, so an Ended row leaves while an Asking row stays until the question is answered; right-click opens the session menu.

## Window

The window's restore rect, maximized flag and monitor are saved in native-ui.json and restored on that monitor (the primary when it is gone); fullscreen is not restored. The title reads `(M/N) Tab — rustling-tulip`, set 350 ms after its last change. Closing the window runs the quit flow (keep running, stop keeping worktrees, stop removing them with per-session branch fate, or abandon), waiting for `shutdown_ack`.

Closing a tab, closing a pane but keeping its session, and moving a pane to an existing tab each leave an entry on the undo shelf (bottom centre, 8 s, at most 3, newest on top). An entry holds a whole-tab snapshot of every tab it touched, and Undo sends `RestoreTabSnapshot` for a tab that still exists or `RestoreTab` at its old index for one that is gone; a tab this client has asked to remove (closing it, closing its last pane, moving its only pane out) counts as gone from the send until its removal arrives, so an Undo pressed inside that round trip still restores it, bringing back splits and ratios exactly (moving the only pane via "Move this pane to a new tab", or via the Move-panes dialog with every pane ticked, marks the source tab closing the same way; a refused `MovePane` or `ExtractToNewTab` clears the mark, so Undo sends `RestoreTabSnapshot` and spawns aimed at the tab go into it); a pane whose session has since gone comes back empty. The shelf clears when the connection drops or a new `Welcome` arrives.

## Keyboard reachability

Settings → Appearance and the appearance editor share one set of keyboard stops. Tab and Shift-Tab leave the hex and filter fields for the next or previous stop, as the Worktrees path field does, rather than staying inside the field.

Stops run in reading order, column 1 then column 2: per colour section (Accent, then Background) the preset swatch line, the recent swatch line (only when recents exist), the hex field, Apply (while enabled) and the reset link (while enabled); then the font filter and the family list; size −, size + and the size reset link; the bold checkbox and the bold reset link; then Close, in the session, repo and workspace editor only.

Disabled stops are skipped. The family row has no reset link; the list's Reset row covers it.

Each swatch line is one stop, landing on the chosen swatch, else the first; Left and Right move along it and stop at the ends without wrapping, Enter or Space picks. The family list is one stop, landing on the chosen family, else the first row: Up and Down move a highlight that skips headers, stops at the ends and scrolls into view, Enter or Space picks. After a filter edit the highlight stays on the same family while it is listed, else moves to the first row.

Picking a swatch, by mouse or keyboard, adds its colour to the recent colours (deduped, at the front) once the level takes the change; a recent swatch's tooltip reads "Recent color #rrggbb". A press that disables its own stop (Apply, a reset link) hands the keyboard to the next enabled stop after it. A click on any Appearance control moves the keyboard stop there, and closing Settings clears its stop.

The editor walks the same stops, Close included, and draws the focus ring on its focused stop. It opens with no stop focused: Tab lands on the first stop and Shift-Tab on Close. The ring wraps, from Close to the first stop and from the first stop back to Close. Enter or Space on Close closes the editor, Tab leaves the hex and filter fields with the typed text kept, and Esc closes the editor whatever stop has focus.

The stop order, ring step (`step`), where focus goes when a press disables its stop (`after_lost`, shared by Settings and the editor), cursor and highlight logic is plain Rust in `appearance_stops.rs`, unit-tested; Settings keeps its one focus slot, `settings_control`.

Menus and modals keep to the window and hand the keyboard back. A context menu opens at its anchor and snaps inside the viewport, and its frame never grows past 60% of the window's height: a longer menu scrolls its rows instead (`session_menu.rs` `menu_frame`, `MENU_MAX_SHARE`). Confirm dialogs open on their safe option — Cancel, Keep running, Ignore, or a pane-only close — and every close path, Esc included, returns the keyboard to the pane.

Esc has deliberate exceptions. It never dismisses the layout chooser, and it is ignored while a recovery or an exit is in flight. In a session rename it leaves the menu open and returns to its rows rather than closing them.

## Tests

Three tiers, all Rust tests:

- **UI specs** (`apps/native/tests/ui/`, one binary with a module per spec file): in-process, headless GPUI through the `test-support` feature (`VisualTestContext`), never touching the user's mouse or keyboard. `RootView::with_transport` takes the `NetCommand` / `NetEvent` channel pair, so specs script a fake daemon (`tests/support/mod.rs`), inject `DaemonMessage`s and assert on the `ClientMessage`s sent, grid text, selection and clipboard. `ui_dir` and the clock are injected, so specs never write the real native-ui.json. The test platform shapes text as fixed 0.6 em glyphs, so specs assert on cells, never on font pixels. Specs that rely on focus events call `window.activate_window()` first.
- **Live e2e** (`tests/e2e_live.rs`, `tests/e2e_recover.rs`, `.\rt.ps1 native-e2e`): the same harness against a real daemon whose config, binaries and worktrees dirs are all under `.tmp/`, set on the child with `Command::envs`, never process-wide. Specs create sessions through a clone of the client's `NetCommand` sender. A fake-claude spec with no `node` on PATH fails, never skips.
- **OS smoke** (`tests/smoke_window.rs`, `.\rt.ps1 native-smoke`): launches the real exe with `RUSTLING_TULIP_OFFSCREEN_WINDOW`, which opens it cloaked and never activated, so it never takes focus or covers the user's work. Before launch the spec writes the client's `client-id-native` and lays out its sessions for that id over its own socket, so the first-connect chooser never dims the probes. Input is posted to the HWND, keys 100 ms apart (closer spacing reordered letters under load). Pixels are read with `PrintWindow(PW_RENDERFULLCONTENT)` from the threaded show and probed for known UI colours and for a change in the pane after typing; the spec checks the window is still cloaked and not foreground after each capture.
- **Screenshots** (`examples/shot.rs`, `.\rt.ps1 native-shot [<view>] [-Out <path>]`): not a test tier but the way to look at a change. It opens the real window cloaked over `RootView::with_transport` and a fake daemon scripted in the example (four repos, a workspace, seven sessions in every status, a split tab, a diff tab), drives it to the view with the app's own keys (a posted click for the rail), waits for two equal captures (5 s at most), and writes `.tmp\shots\<view>.png` with the smoke tier's `PrintWindow` capture. No daemon starts and no config dir is read. The Working spinner animates on wall-clock time, so two shots differ inside that glyph and nowhere else.

The e2e and smoke tiers are `#[ignore]`d in the normal nextest run and run only through their `rt.ps1` verbs, under `nextest --run-ignored only`. A probe or dev daemon never runs with default dirs, where its client attaches to the user's real sessions and resizes their PTYs: it sets all of `RUSTLING_TULIP_CONFIG_DIR`, `RUSTLING_TULIP_BINARIES_DIR` and `RUSTLING_TULIP_WORKTREES_DIR` to `.tmp/` dirs, as `native-e2e` does.
