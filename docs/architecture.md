# Architecture

rustling-tulip orchestrates many parallel `claude` CLI sessions across single repos and multi-repo workspaces from one native window. A long-lived daemon owns every PTY and child process; the desktop client is only a client, and sessions outlive it. Nothing in the repo calls the Anthropic API: the daemon shells out to the CLI. Open work is in [plans/MAIN.md](./plans/MAIN.md); the native client's design decisions are in [native-client.md](./native-client.md).

## Overview

```
┌────────────────────────┐          ┌────────────────────────────┐
│  Native client (GPUI)  │  WS+JSON │  Daemon (long-lived)       │
│  - alacritty_terminal  │ ───────► │  - Session supervisor      │
│    panes               │ ◄─────── │  - PTY pool (ConPTY)       │
│  - Activity rail       │          │  - rt-tracer.exe sidecar   │
│  - Source control      │          │  - Worktree orchestrator   │
└────────────────────────┘          └──────────┬─────────────────┘
                                               │ spawns
                                               ▼
                                    ┌────────────────────────────┐
                                    │  claude CLI                │
                                    │  (interactive or headless) │
                                    └────────────────────────────┘
```

The wire protocol is JSON over a WebSocket: loopback by default, and TLS on the host's tailnet addresses when remote access is on (`crates/protocol/src/lib.rs`); the current version and the versions still supported are in `protocol-version.json`. The daemon binds only loopback and, with remote access on, the host's own tailnet addresses; it never listens on `0.0.0.0`. The daemon accepts several clients at once, each with its own connection and its own tab layout.

## Several hosts

One native window shows This PC and every saved tailnet and SSH host at once; the user-facing rulings are in [native-client.md](./native-client.md) ("Several hosts"). The shape in code:

- **One connection per host.** `RootView` holds a `HostConn` per host (`hosts.rs`): its command sender, `Connection` state, handshake, daemon id and that host's settings mirrors (`HostMirrors`: keep-awake, remote status, launch commands, agent settings, worktrees root). Each host runs its own `Net` thread, unchanged inside, and a per-host forwarder tags every `NetEvent` with its `HostKey`. `RootDeps.open_host` is the factory from a `Target` to the command and event channel pair: production spawns a `Net`, the UI specs hand out fake channels, the live tier real ones (`Harness::open_hosts`).
- **Host keys.** `HostKey` (`target.rs`) is `Local` or `Remote(key)`, built from a `Target` (`HostKey::of`). On the wire a host is the `host: Option<String>` of `Target::host_key()` (a tailnet host's lower-cased MagicDNS name or `ssh:<host string>`, `None` for This PC), and the client keys every per-host fact by `(HostKey, id)`.
- **Sending.** `send_to(host, msg)` has no default host: tab and layout messages go to `Local`, everything else to the host that owns what it names, found by the sidebar lookups that return the host. A menu or dialog opened on a row carries its host from the click (`MenuContainer::Repo(key, HostKey)`, `Workspace(key, HostKey)`, the preset wizard, the delete-worktree and repo-remove dialogs, the spawn dialog's target, the pane-close dialog) and never looks the host up by id, since one id or key can exist on two hosts; a sidebar leaf, its buttons, its session notices and the pane-close dialog act on the session's own host the same way, and none falls back to This PC. A pane's terminal sends through a per-host `HostSender`, which a reconnect re-points without rebuilding the pane.
- **Per-host slices and mirrors.** `SidebarModel` holds a `HostSlice` per host (repos, workspaces, sessions, dispatch runs, agents and the orders and sets kept from them); a remote host's container keys are `{host key}::{key}`, and the `Sessions`, `Repos` and `Workspaces` folds replace only the sender's slice. `reset_host(host)` drops one host's mirrors and what showed its sessions on that host's `Welcome`; a remote host's disconnect clears nothing, so its rows stay dimmed.
- **This PC is the layout home.** Its daemon holds every tab of the window, and `GridNode::Pane` gains `host: Option<String>` (`None` is this daemon), carried by the requests that name a session (`CreateTab`, `SplitPane`, `ReplacePaneSession`) and by `OpenDiffTab`. A remote daemon supplies sessions only, and its own layout for this client is ignored. The daemon never checks a pane's session against its registry, so a foreign pane needs no exemption there; `ForgetHostSessions`, `RebindHostSessions` and `RehostPanes` are the additive messages the client uses to keep those panes right.
- **Same daemon twice.** `Welcome.daemon_id` (a UUID in the daemon's config dir, feature `daemon_id`) lets the client rank two connections that reach one daemon (`hosts.rs` `rank`, `drop_if_duplicate`: This PC, then saved order) and drop the lower-ranked one, whichever welcomed first.
- **Not part of the model.** `SwitchTarget`, `last_target` and a boot target do not exist: the window never switches a connection to another host.

## What it does

- **Sessions**: interactive Claude sessions, plain shells, and headless Claude sessions (`claude --print --output-format stream-json`, parsed into status, tokens, cost and a recent-actions log; the native client spawns none and has no view of one; the one stream view it draws is a followed dispatch run's, `dispatch_view.rs`, below in "Dispatch runs"). Claude is the only agent; other agents come back as plugins (`agent-plugins.md`). A Claude session may be routed to DeepSeek by a per-session Claude provider (Anthropic by default).

  Status (working, awaiting input, idle, stopped) comes from Claude Code's hooks once a session turns hook-driven, injected through a settings file at spawn, and from rules over the session's rendered screen (the screen engine), which also read a session whose hooks never run. A quiet screen that still shows the spinner stays working. The `background` flag beside idle is set by a `Stop` hook and by the screen's footer rules (shells or subagents still running).

  A plain shell keeps its own output classifier until it is hook-driven or its screen shows an agent; a screen that shows one, however it was started, makes the shell an agent session (Chat and Summary on) until the agent exits (`session-runtime.md` "Session status").

  An interactive Claude session runs in the user's shell (agent in shell): the shell is the PTY child under the unchanged tracer, and once its prompt is quiet the daemon clears the input line and types `<cd to the start folder> && <the quoted claude command line>` (`server/spawn/shell.rs`, `inject.rs`), the path Recover's shell-running-`claude --resume` already takes.

  The pane stays a usable shell after Claude exits and the session ends only when the shell exits (a worktreeless one that exited by itself closes, one with a worktree shows the exited overlay).

  The command line is the plugin's `interactive_args` with the absolute program path, quoted for the shell family (PowerShell, cmd, Nushell, fish, POSIX sh), then the host's launch-command extras and the spawn's own `extra_args` (quoted per shell; see "Agent launch command"). The initial prompt or a preset's script is not on it: it is typed into Claude's TUI once Claude is up (hook-driven, or the screen reads Claude) and dropped after 15 s, except that a startup dialog (the folder-trust dialog) holds it until the composer reads ready (`session-runtime.md`). The plugin's `EnvPlan` and the env rows apply to the shell, so commands run after Claude see them, a DeepSeek session's routing variables included.

  The gate is the plugin's `AgentCaps.shell_resume` (Claude sets it). A plugin without it, a shell the daemon cannot type into safely (unknown, a cmd line with `%` or `!`, legacy PowerShell argument passing) and headless runs keep the direct spawn with the agent as the PTY child.

  Rejected: the tracer starting a shell after its child exits, which rewrites the tracer's one-child job, kill and `Exited` path; and launching through the shell's startup arguments, which needs a script per shell, `cmd /K` the least predictable.

  The record stays Interactive with agent Claude, its spawn config and conversation id, so Restart, Resume, auto-resume and Recover work unchanged, and its status runs on the plain-shell watcher. `program_name` follows the child: the shell's label once Claude has ended, `claude` again on its next `SessionStart` or when the screen shows the agent again. `agent_in_shell` and `shell_label` are mirrored into the sidecar so a reattach runs the shell's watcher.

  Claude has ended when its `SessionEnd` hook arrives with a reason other than `clear`, else when `hand_shell_back` sees the prompt return. The daemon then sends the additive one-shot `AgentExited { session_id }` once per agent run on the session-event stream, and the native client does not fold it: Chat and Summary grey from `program_name` in the `SessionUpdated` the hand-back broadcasts, and nothing is raised since the pane visibly became a shell (`docs/native-client.md`, "Agent exited into its shell"). Keep-awake and idle exit see the live shell: Always holds while it lives, When busy only while it prints.

  A session awaiting input, or an agent that finishes its turn with no background work left, raises an OS notification in each native client, unless its skip setting says the owner is already looking at the session.
- **Workspaces**: a named set of registered repos, created from repos or from a VS Code `.code-workspace` file. A workspace session runs one agent with its cwd in the first member's worktree and `--add-dir` for every other member; worktrees keep the members' relative paths (layout in [on-disk.md](on-disk.md)).

  Only `members[0]`'s repo hooks load: an `--add-dir` root's `.claude/settings.json` hooks are not read. A `.code-workspace` file found beside a repo is offered as a workspace.

  A workspace created with Create & watch stores `watch_vscode_workspace` and follows its linked file: the file is parsed once when the daemon starts and each change after a 750 ms debounce, a new folder is registered as a repo, a removed folder leaves the members but keeps its repo, and the file's folder order becomes the member order. It broadcasts only when the members or the registry changed, and re-validates the workspace under its write lock, so a removed workspace never returns and a rename or relink stands.
- **Survivable sessions**: every interactive and shell session runs under `rt-tracer.exe` (`rt-tracer` off Windows), so a daemon restart or upgrade reattaches to live sessions and replays their ring. A lost tracer leaves its session abandoned (Resume / Dismiss) rather than discarded.
- **Auto-update**: the native client checks GitHub Releases at launch and every hour, downloads a newer release's installer (on macOS, its zip) in the background and verifies its SHA-256 against the release's `.sha256` asset; the footer then offers `Restart to update`, which runs the installer (on macOS, unpacks the zip beside the app and starts the staged daemon's `apply-update`), swaps the client and daemon files (`rustling-tulipd apply-update`) or the whole app bundle and relaunches the client while sessions keep running in their tracers.

  A newer client retires an older-build daemon, and never retires a newer one (see [auto-update.md](./auto-update.md)).

  Each session's lifecycle task (`session.rs` `attach_lifecycle`) is the single consumer of its PTY output: it forwards each chunk to every attached client's own channel (`deliver_chunk`), then appends it to the scrollback ring, so a `LoadScrollback` snapshot and the live output after it meet with no gap. A client fed from a fresh `broadcast` receiver instead would miss whatever arrives while the snapshot reads the file, and a session on an older tracer loses its ConPTY startup `ESC[6n`, which blocks the child forever.

  The session's exit travels through the same lifecycle queue as its last item (`Chunk | Exited`), so every output chunk reaches clients and scrollback before the task handles the exit inline (`handle_exit`): the history entry, `Stopped`, and clearing the pending scrollback snapshot request.

  A queue that closes without `Exited` is `TracerLost`, and a client's live receiver closes at the exit. A per-session scrollback gate (`SessionRegistry.scrollback_gates`, `delete_session_dir`) lets discard and dismiss delete `sessions/{id}/` so no later append or terminal-state save recreates it.
- **Session history and recovery**: every ended session gets a history entry (how it ended, its spawn config, its conversation id), kept 7 days; at startup each dead non-headless sidecar with no entry gets one (`TracerLost` with an unknown end time, or its true end from the tracer log), before the rest is backfilled from tracer logs; `RecoverSessions` respawns chosen entries, including sessions still in the Abandoned group.

  After the handshake (the listener is bound, so the resume never delays it) the daemon resumes by itself, with no prompt, no off switch and no retry, one at a time (`auto_resume`), each of those lost-at-start sessions that qualifies.

  A session qualifies when it is a non-headless interactive Claude session with a spawn config, its own conversation id and an existing transcript, whose worktree pins resolve, whose in-place checkout is still on its branch and whose pinned worktree no other live session holds (`auto_resume_refusal` and `auto_resume_request`).

  A session whose tracer log shows `Exited` or `StoppedByUser` was not lost and is never resumed. It restarts with `--resume <its own conversation id>`, never the newest conversation in its folder, in its old panes, and the entry is marked recovered.

  Every lost session has its `TracerLost` entry before anything spawns, so a second start never resumes one twice. Plain shells, a session with no conversation or transcript, an unpinnable target, a failed spawn, an in-place checkout on another branch and a worktree in use stay abandoned in Recover. Idle exit is held off while this runs, and a user's Resume racing it wins.

  When the pass finishes the daemon broadcasts `ResumeReport { resumed, left_in_recover }` (the sessions this start resumed, and those it refused or failed to resume, which stay in Recover); a client connecting later gets it with its initial state, each client id hears it at most once per daemon run, and nothing is sent for a start with nothing to resume or with both counts 0.

  A Claude entry resumes with `claude --resume` in the session's start folder (`history::entry_folder`: a plain shell recovers where it last was, an interactive session where it started, wherever its shell went), with the options it ran with (the entry's `options`, an older entry's trust folded into the bypass choice), and a DeepSeek entry never recovers as a shell.

  A tracer-log import fills those options from the log, inferring the DeepSeek provider from `--model`. A shell-hosted agent's tracer log carries an agent note with the agent, options, extra folders and conversation id, which the import reads first, so the entry comes back as that agent and not a plain shell.

  A multi-folder standalone recovery passes the extra folders as `--add-dir`; the native client offers it from the rail's Recover dialog (`docs/native-client.md`, Session recovery).

  A resumed session (auto-resume or a leaf Resume) keeps the old record's user name and appearance (a session with no rename keeps its new default label), and its id replaces the old id in place in each container's `session_order`, broadcast as `SessionsReordered`.

  A leaf Resume of an abandoned interactive Claude session continues its own conversation (`--resume`) when its transcript exists; without one, for a plain shell, when its pinned worktree folder is gone or when a live session holds that worktree, it reruns the unpinned request (worktree recreated or the in-use refusal, first prompt replayed).

  A manual Resume proceeds when worktrees cannot be pinned, as Restart does; auto-resume keeps its stricter refusal. The Recover dialog path (`finish_recovery`) does not carry name, look or place.
- **Chat mirror**: a Claude session can be shown as a chat beside its terminal: the user's messages, the agent's answers, one card per tool call, quiet rows for turns nobody typed, and the session's prompts answered with buttons. The chat is a mirror over the live terminal session, not a second agent process: the terminal stays the source of truth, a terminal pane and a chat pane (or a phone) of one session can be open at once, and the chat runs no `claude` of its own.

  Only the Claude plugin supplies the mirror's parts, so a session of another agent is refused a chat. The plugin also classes each tool call as `ChatEntry::Tool.tool_kind` (`read`, `search`, `run` or `other`; missing decodes as other, an unknown value as `ToolKind::Unknown`; additive, no protocol bump), which the client's Compact mode folds on; its table is in `crates/agents/claude/src/chat_entries.rs`. Wire details are in [wire-protocol.md](wire-protocol.md); the client is in [native-client.md](./native-client.md) "Chat and summary panes".

  Every fact the chat shows has one owner, and none is taken from a second source as a fallback that could disagree. History (user messages, answers, tool calls and results, receipts, turn ends) is the session's transcript `<conversation id>.jsonl`, tailed: the only complete and ordered record, and it holds turns taken in the terminal.

  Session state, the composer state and the open dialog with its numbered options come from the status watcher's screen grid, read by the plugin's rules and dialog parsers, since options exist only on the screen and several prompt ends fire no hook.

  That a prompt is pending, and its structured text, is hook `pending_input`; a card is drawn from the parser's reading, and the hook's kind only checks the answers against it. The one text the card takes from the hook is a Plan card's body when the screen's is empty (the plan box scrolled off): the hook's plan text, with its first non-blank line as the subject when that is empty too, filled in after the prompt id is computed. A dialog with no hook (folder trust, a new MCP server) still gets a card, and a `pending_input` with no dialog on the screen gets none.

  Live answer text comes from the MessageDisplay hook; thinking duration, Interrupted, the Heads up notice, overlays and the mid-turn subagent and shell counts come from the screen, which the transcript lacks.

  Everything that knows Claude Code's formats sits in the Claude plugin behind `agent_api`, each trait method defaulting to "unsupported" (which is how a plugin without them gets no chat): `chat_entries.rs` turns a transcript record into chat entries, `dialogs.rs` holds the dialog parsers, the composer reader, the running-work counters and the answer recipes, and `hooks.rs` plus `hook_vocabulary.rs` carry MessageDisplay.

  The daemon keeps only what any agent's mirror would need: `transcript_tail.rs`, `chat_mirror.rs`, `chat_answer.rs`, `server/chat.rs` and the glue in `screen/dialogs.rs`. A Claude Code change then shows as a failed fixture test or a refused answer, not a wrong option chosen.

  The Dashboard answers a waiting row's prompt through the same runner without a chat mirror: `ClientMessage::AnswerPrompt` is handled in `server/dashboard.rs`, which checks the record (same `status_since` and `pending_input`, before and again under the typing lane) and the screen (the dialog's content matches the pending prompt, the option is inside its list), maps the choice to the dialog's own option digit (`TypeSomething` and `DenyWithText` to the chat answers of the same names, refused for another prompt kind) and has `chat_answer.rs` type it.

  The transcript tailer is its own module that knows nothing of chat entries (the file-path index and a subagent watcher read through it too). It follows one file from a byte offset, wakes on a file-watcher event and a 1.5 s size poll (a transcript folder that does not exist yet is not a warning: the tail retries the folder watch on each poll tick until it exists, and any other watch failure warns once and is not retried), holds a partial last line until its newline arrives, starts over when the file shrinks or is replaced, parks while no client is connected, and runs only while some connection has loaded the session's chat or summary.

  The mirror follows the session record's conversation id, so a `clear`, `resume` or `compact` `SessionStart` moves it to the new file, which opens with the system row "Conversation cleared".

  Rebuilding follows a few rules. Entries stay in file order, in a reply and in appends alike, so a live chat and a reload agree. `user` records with text and `queued_command` attachments are user messages (the task-notification form is skipped; Claude Code's `<pasted_content …>` wrapper, whose real closer carries the id, is unwrapped with the blank lines it left at the ends trimmed, and a whitespace-only paste makes no entry), and a turn nobody typed (a finished background shell or agent, a `!` command, slash-command output, an interrupt, a compaction) is a quiet system row.

  `tool_use` blocks are tool cards that their `tool_result` attaches to by `tool_use_id`; an AskUserQuestion result or a plan approval becomes a receipt. A signed, empty `thinking` block is a thinking row with the record's own duration. Subagent records are not merged into the chat, and entry text is capped (tool inputs 4 KiB, results 8 KiB, a cut result ending in a line that says how many lines or characters it dropped), with a reply carrying the newest 500 entries.

  The dialogs with cards are permission, AskUserQuestion (single choice, multi-select, Type something, review), plan approval, folder trust and the Heads up notice; previews, Rewind, the detailed transcript, `/model`, `/btw` and the slash popup are only recognised, and the composer says to open the terminal. The composer state is ready, working, draft, dialog or overlay. A message is typed as one bracketed paste and Enter.

  While a turn runs it goes straight to the CLI's own queue and the chat shows it dimmed as pending until the transcript's record arrives. The daemon never holds a message: one the screen cannot take now (a pending prompt, a dialog, a draft in the box in any view, an overlay, unknown state, an ended agent) is refused at once, so the user sees why and the text stays in the composer.

  While a dialog is up the chat types nothing but its answer, and an answer can carry text, which the client takes from the card's own box, never the composer (`AllowWithText` is Tab, the text, Enter; `DenyWithText` presses No, waits for the box, then sends the text under the same lane turn).

  An answer is a recipe the plugin gives per dialog and answer, as data pinned by fixture tests: the keys that work were measured per dialog and differ from the hook's suggestions (a permission option is its digit with no Enter, a multi-select toggles by digit and submits from its Next row, folder trust moves the cursor with Up and Down because digits do nothing).

  The runner types it group by group with a screen check after each, stops when the screen does not move, a check fails or the owner types, and never sends Esc Esc (it opens Rewind) or ctrl+c. An answer clears a hook-driven record's pending prompt only once the screen shows that prompt gone and its kind matches, and is never an owner key.

  The agent in view is Claude Code's terminal showing one subagent's transcript in place of the main conversation, where the prompt's next Enter would go to that subagent.

  The plugin reads whether an agent is in view and which of the box, the agents panel or the tasks pill holds the keys, and gives one key per step to return to main (Down to the panel, Enter on `main`, Up to the box) or to reopen an agent, checking the screen after each and never sending Esc, Left or Enter on an empty box.

  The status watcher returns every Claude session to main when a Heads up notice is up, an AskUserQuestion closes, or the box holds the notice's own draft, so the answer reaches the main agent; a chat send and an answer do the same first.

  A draft in the subagent's box is saved with `ctrl+s` before the switch and restored in its own view afterwards. The stash is one slot shared by every view and a second `ctrl+s` silently replaces the first, so the watcher stashes only when no `› stashed` shows; with a stash held and a draft present it does not switch and the client is told `WaitingInMain`.

  When the agent cannot be reopened, or has finished, the draft goes into main's box and the client is told `DraftReturnedToMain`. A box holding the notice's own "Chat in main session" draft is carried across unsaved.

  The mirror runs while any connection has loaded the chat or the summary, on one tail, one entry map and the status watcher's own grid; the chat never resizes the PTY, and a key typed in the terminal and an answer from the chat meet on the same screen, whichever lands first moving the dialog and the other being refused.

  A shell-hosted agent that has ended keeps its last conversation read-only until the next `SessionStart`; after a daemon restart the reattached session's watcher rebuilds its grid from the replay and a client's next load re-reads the transcript, a live line held only in memory being filled in by it.

  Live answers come from the MessageDisplay hook, installed with the others: each call carries a completed piece of an answer (a message may arrive as several), joined in `index` order with nothing between them and sent at most every 100 ms as an `Answer { live: true }`. The first piece arrives well before the transcript's record and the TUI's frame, so live text matters for long answers and adds nothing to short ones.

  When the transcript has the answer, the mirror matches the live line's prompt key to the `promptId` on the prompt's `user` record and replaces the live entry; a Claude Code without the hook shows the answer when the transcript gets it.

  The running-work strip makes the background state visible, so a quiet chat is never taken for an idle session.

  At a turn's end the `Stop` payload's `background_tasks` (a shell with its command, a subagent with its type) and its one-shot `session_crons` (a wakeup time computed from the schedule) are kept on the session record; mid-turn the plugin's `read_work` counts running subagents (agents-panel rows other than `main` showing running figures) and the mode line's shell item from the screen, and a dialog, overlay or the panel holding the keys leaves the last count.

  The record owns each item's identity, age and command or type, and the screen only pads with placeholders when its count is higher and never removes an item. A task leaves when a later `Stop` stops listing it or its `<task-notification>` arrives in the transcript, and the agent's end clears the lot. `ChatWork` goes only to chat and summary loaders, on load, after the first transcript read and on each change, never on a timer and not on the session snapshot.

  The summary view is one line per stretch of work. A stretch is a turn (it starts at a user prompt, never at an "Interrupted" notice, which falls inside the previous turn), split for a long turn into windows counted from its first time ([0, 5 min), [5, 15), [15, 30), then 30-minute windows), and keeps the range of entry ids it covers so expanding it shows exactly those entries.

  A line is the summarizer's `notification` (at most 100 characters) written through the Dashboard summarizer's queue, cache and daily cap, requested with the queue key `<session>#summary` over text shaped by `prompt::shape`; a closed stretch is requested at once, the open one after 30 s without change or at its turn's end, only the newest 20 unanswered closed stretches go in a whole-summary send, and an unchanged digest is never requested again.

  With no provider key, a failure or the cap reached, the line is a template (the turn's first non-blank user line, trimmed, its duration and tool count), so the view ships without a key. The open question is pinned at the top, answered from the same card as in the chat.
- **Secret env rows**: a spawn dialog env row under a secret key (`KEY`, `TOKEN`, `SECRET` or `PASSWORD` segment, or ticked Secret) is sealed before the spawn config is captured: its value moves into Windows Credential Manager and every stored file and echo carries `${secret:<id>}`, resolved again at each spawn and respawn; startup seals older files and sweeps unreferenced ids (see [env-secrets.md](./env-secrets.md)).
- **Claude provider**: the Claude selection's options carry a `provider` (Anthropic, DeepSeek, or `Unknown` for a value this build does not know); it is part of the stored spawn config (`SpawnConfig.agent`, an `AgentSelection`), so Recover, Restart, the sidebar's Resume and Duplicate keep it, and the snapshot reports it as a chip in `agent_chips` (text `DeepSeek`, tip "Runs on DeepSeek", from `agent_api::session_chips`).

  The daemon builds the routing environment at each spawn from the Claude plugin's built-in provider table (`crates/agents/claude/src/providers.rs`, not user-editable), before any git work, so a refused spawn leaves no worktree. The tuning defaults (model variables, context size) yield to a spawn's env rows.

  The locked keys (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_DEEPSEEK_SESSION`, `DEEPSEEK_API_KEY`) and any variable the provider removes from the child are refused in the rows. A plain shell refuses a non-Anthropic provider.

  The key (`DEEPSEEK_API_KEY`, process environment then Windows user scope, `user_env.rs`) is read at each spawn and goes only into the child's environment: the routing variables are never stored in `meta.json`, history, `state.json` or the wire, and the spec types print variable names, never values. A PTY child inherits the daemon's whole environment, so removed variables go through `PtySpawnSpec.env_remove`.

  Every PTY spawn also drops the variables a parent agent session leaves in the environment: each plugin lists its own in `Agent::inherited_session_vars` (default none; Claude's eight are `CLAUDECODE`, `CLAUDE_CODE_*` and `CLAUDE_PID`), and `tracer_client::inherited_session_vars()` unions them over `agent_registry::all()`.

  The removal covers plain shells and `conversations/pre_create.rs` too, so a daemon started from a terminal inside an agent session still spawns top-level sessions with their own transcripts; a spawn's env row that sets one keeps it.

  A DeepSeek history entry recovers as Claude only, with the provider inferred from `--model` for a tracer-log import. The native client draws the snapshot's `agent_chips` on the leaf and the pane header (`docs/native-client.md`).
- **Worktrees**: spawns create or reuse a worktree per member under a machine-local root. Branch names are daemon-picked `wt/<adjective>-<noun>` names that no member repo already uses. Fork points resolve to the remote-tracking base (`main` → `origin/main`), with a background fetch and a "commits behind" preview; an existing worktree or a leftover branch is offered as reuse or recreate, never bound silently.

  Worktrees are addressed by path, so a worktree left by a gone session can be launched into. Duplicating a worktree session spawns the clone on a fresh branch. Restart of an exited session and Resume of a parked one rerun in the session's own worktree and branch (`DuplicateSession.same_checkout`, which a `ResumeSession` to a host listing `resume_session` asks for itself), and an interactive Claude session continues its conversation (`--resume`) while its transcript still exists, else starts a fresh one.
- **Discard with branch fate**: deleting a worktree reaps its branch when the commits already landed on the base or its remote by ancestry or patch equivalence (`git cherry`); otherwise the confirm names each member's branch and offers keep or delete.
- **Source control**: per-worktree changed files, staging, commit, discard, stashes, paginated history, commit detail, open in forge, and side-by-side diffs, refreshed by a `.git` watcher that ignores objects, logs and build directories and parks while no client is connected.
- **Remote (tailnet) access**: opt-in and off unless `remote.json` says otherwise (`{enabled, port}`, default port 8787). The daemon serves the host's own tailnet addresses over TLS with the `tailscale cert` certificate, through a separate router that serves `/ws`, `/health` and the phone app's static files (see below); an upgrade must name the host in `Host` and carry no foreign `Origin`, shutdown and remote-access configuration are refused on such a connection, and idle exit is held while remote access is on.

  The tailnet router answers every other path from the phone app's folder (`crates/daemon/src/server/pwa_static.rs`, tower-http `ServeDir` in a fallback); the loopback router serves none of it. Only GET and HEAD are served, any other method answers 404 with an empty body.
  The folder is `RUSTLING_TULIP_PWA_DIR`, else `pwa/` in the install folder the daemon is given (`Dirs::bin_templates`; `Contents/Resources/pwa` when that folder is a macOS bundle's `Contents/MacOS`), else `pwa/` beside the running exe; it is read in place and never copied into the binaries cache.
  An extension-less path that is not a file (a deep link such as `/s/<id>`) gets `index.html` with 200, never under `/assets/`; a missing asset stays 404. With no folder or no `index.html`, page requests answer 503 `text/plain` "The phone app is not installed with this daemon." (checked per request), and the listener logs one warning at start.
  Every static answer carries a strict CSP (`default-src 'none'` with `'self'` for scripts, fonts, connections, manifest and workers, `style-src 'self' 'unsafe-inline'` because xterm.js writes its own style rules at runtime, `img-src 'self' data:`), `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`, and no CORS headers; a 200, 206 or 304 under `/assets/` is `Cache-Control: public, max-age=31536000, immutable`, anything else `no-cache`.

  A client turns it on and off live with `ConfigureRemote { enabled, port }` (no restart; a port change while on restarts the listener; a tailnet connection is refused it), which the daemon writes to `remote.json` and answers by broadcasting `RemoteStatus`, also pushed at connect.

  Its `state` (`RemoteState`) is one of off, starting, not installed, not running, other Windows user, not connected, Tailscale error, HTTPS disabled, host tagged (nothing bound, no certificate asked for), certificate failed, port in use, bind failed, or serving with the name, port and the certificate's expiry.

  `crates/tailnet` wraps the CLI and the owner rule; a connection presents a device token rather than the `daemon.json` token. A tailnet `Hello` without a valid device token gets `Welcome` and then `DevicePairFailed { reason: "device not approved" }`, and stays open as a pairing connection (`Welcome.features` lists `device_pairing`).

  A pairing connection gets no layout, forwarders or initial state, is not counted in the client count, and accepts only `DevicePairRequest`, `DevicePairCancel` and `DevicePairRedeem`. It closes 10 s after `Welcome` with no request, once its request ends, after 16 frames that are not pairing steps, or on a 4th request.

  Approval is made from a loopback client only (`ListPendingDevices`, `ApproveDevice`, `DenyDevice`, `MintDevicePairCode`, `ListDevices`, `RevokeDevice`, `ForgetDevice`; a tailnet connection is refused them), which sends the code back to the approver and `DevicePairDecided` to the waiting device; the device redeems the code and gets its `DeviceToken` once, then the connection closes.

  `rustling-tulipd pair` (`cli_pair.rs`) is the command-line way to the same code, for an owner reached over SSH: it reads `daemon.json`, connects to the running daemon's loopback `/ws`, sends `MintDevicePairCode`, prints `Pairing code: <code>` with its lifetime and exits.

  It takes no instance lock, rotates no log and sweeps no binary cache, so it runs beside a live daemon, and gives the whole exchange 10 s. The code works once, for one device, and only for a device whose pairing request is already waiting on the host. On Windows the daemon is a GUI-subsystem exe, so `pair` attaches the parent console before writing (output may land after the shell prompt returns; a redirected stdout or stderr such as `> code.txt` is kept, and only a null handle gets the console).

  `rustling-tulipd bridge` (`cli_bridge.rs`) is what an SSH client runs on the host: it relays one compact JSON protocol message per line between stdin and stdout and the loopback daemon's `/ws`, starting the daemon first when none runs (`daemon_client::ensure_running_for_bridge`, which starts it in the user's own logon through a scheduled task when the user is logged on at the host, else directly; `docs/daemon-cli.md`) and filling the `Hello` token from the host's handshake, so the token never leaves the host.

  It exits 0 when the daemon closes the WebSocket, and after stdin EOF once the daemon has closed or 5 s have passed (it relays replies still in flight and sends its Close only then, since the daemon drops queued replies once it reads one); a daemon it starts on Windows inherits none of its handles, so the SSH channel closes about 2 s after the bridge exits. On failure it prints one stderr line `rustling-tulipd bridge: <error>`, leaves stdout empty and exits 1. It starts no tracing, takes no instance lock, rotates no log, creates no folders and attaches no console.

  Turning remote access off drops every waiting request and code, and each waiting device is told `DevicePairDecided { Expired }`.

  A tailnet connection, served or pairing, ends with the listener server (the bound address) that accepted it: remote access turned off or its port changed, Tailscale down, the host becoming tagged, HTTPS disabled, the certificate lost, an address vanishing, a supervisor panic, or the server task ending on its own.

  It gets a WebSocket Close within 2 s (`SERVER_ENDED_CLOSE_LIMIT`) even if the peer stopped reading, and then the socket is dropped; a served connection drops its queued output, a pairing connection sends what is queued first. A certificate reload or a rename does not close it, and loopback connections are never touched.

  A served tailnet `Hello` stamps the device's `last_seen` in `devices.json`.

  `RevokeDevice` marks the record blocked (`revoked: true`) and closes every served tailnet connection of that device with a WebSocket Close, also when the flag write fails (the reply is then an `Error`).

  A blocked device is refused at `DevicePairRequest` and at redeeming a code with `DevicePairFailed { reason: "device not approved" }`, and `ApproveDevice` for its request is an `Error`; only `ForgetDevice` (loopback only, answered with `Devices`) removes the record and so clears the block. `DeviceInfo.connected` counts a device's served connections (`Welcome.features` lists `device_block`), and the daemon pushes `Devices` to loopback connections whenever that count changes.
- **Remote file fetch**: `FetchFile` streams a file under a registered repo, a session worktree or any folder `git worktree list` names for the repo in chunks, confined by one path-confinement helper (`FetchFile`, `FetchFolder` and `StatPath` add the listed folders in `server/folder.rs`; `GetFileSnapshot` and the git messages keep the narrow rule). `ListSessionFolders` (`Welcome.features` lists `session_folders`) tells a client which folders a session's Ctrl+click may fetch from; the check at fetch time is the boundary.
- **Remote folder fetch**: `FetchFolder` sends a folder under a registered repo or session worktree as one zstd-compressed tar over the same `FileChunk` stream (`crates/daemon/src/folder_pack.rs`, `server/folder.rs`), confined like `FetchFile`; `StatPath` says whether a path is a file, a folder, missing or other. The walk follows no link and leaves out links, other non-file entries, non-Unicode names, `.git` and the ignored folders (`node_modules`, `target`, `.venv`, caches); a folder past the file or byte ceiling is refused before `FolderFetchStarted { resolved_path, files, bytes }`. `Welcome.features` lists `folder_fetch`. On the client, a Ctrl+click on a path link on such a host stats its readings first (`StatPath`) and fetches a folder whole into the download root, unpacking into a stage beside the target under a sticky progress toast with Cancel; anything else keeps the file fetch, and a host without the feature gets a warning for a folder link. A plain fetched file's done toast offers Fetch whole folder (its parent folder, or the root) and a fetched folder's done toast offers Reveal; `RootView::fetch_remote_folder` is the folder sink, with no stat first.
- **File tail**: `TailFile` follows a file a session's command writes (`crates/daemon/src/file_tail.rs`, `server/tail.rs`): `FileTail` carries its last 64 KiB, then each append, with `reset` when the file shrank, was replaced or came back; `UntailFile`, the connection closing or the session going stops it. A path resolves against the session's working folder and must sit, with symlinks followed and re-checked before every read, inside the session's own folders (its members' worktrees, a standalone spawn's folder and extra folders); a missing file is waited for; a connection follows at most 4 files (`limit_reached`). The Claude plugin names each Bash or PowerShell call's log and redirect targets on `ChatEntry::Tool.tail_paths` (`crates/agents/claude/src/tail_paths.rs`); `Welcome.features` lists `file_tail`. The native client draws it as the Tail boxes under a chat's tool cards (`apps/native/src/chat_tail.rs`, [native-client.md](./native-client.md) "Chat and summary panes").

  The native client's sink (`RootView::fetch_remote_file`) saves it under the machine-local `remote-files` root and opens it; a Ctrl+click on a terminal path link on a remote host reaches it (`fetch_link.rs` works out the readings; on a host that sends folders the click first asks what the path names with `StatPath`, and a folder goes through the folder flow), and so does the ⋯ menu's "Fetch file…" popup (`fetch_dialog.rs`, `fetch_dialog_view.rs`), a modal with progress, Cancel and inline errors.

  A fetched HTML page that opens when done also fetches the relative media it names before it opens (`html_media.rs`, the media batch in `file_fetch.rs`).
- **Agent launch command**: a host setting per agent (`SetAgentCommand`, saved as `agent_commands` in `state.json`, sent as `AgentCommands` at connect and after each save, feature `agent_commands`) with a Program and Extra arguments, read at each interactive spawn so Restart, Resume and auto-resume use the current one; headless runs ignore it. Each agent's Settings page edits its own (`settings_view.rs`). A spawn's own `extra_args` (feature `spawn_extra_args`) go after the agent's arguments and these extras, interactive agent sessions only, and are stored with the spawn config so replays keep them; when the extras end in a comment or continuation or hold a shell operator, a spawn with its own arguments launches the agent directly rather than typing the line.
- **Default shell**: a host setting (`SetDefaultShell`, saved as `default_shell` in `state.json`, sent as `DefaultShell` at connect and after each save, feature `default_shell`) naming the shell plain-shell sessions run and that hosts an interactive agent: Automatic, an installed common shell or a Custom command; `ListShellChoices` returns what the host has (`ShellChoices`). It is read at each spawn, after `RUSTLING_TULIP_SHELL` and before Automatic (`server/spawn/shell.rs` `resolve_shell_program`, `docs/session-runtime.md`; design `docs/plans/default-shell.md`).

  Extra arguments go after the plugin's argv and are refused on save when they hold a control character, an unclosed quote or a flag the plugin lists in `reserved_args()`.

  A direct spawn splits them by POSIX shell-word rules; the typed shell form types the program word bare (so an alias resolves; Nushell types it as `^word`), the plugin's arguments quoted and the extras verbatim. `RUSTLING_TULIP_CLAUDE`, a blank Program or one naming an existing file keeps the quoted absolute path, extras still applied; cmd with `%` or `!` in the extras falls back to the direct spawn.

  A remote client may edit it (it is not in `host_only_refusal`): an approved tailnet device can already type any command into a shell session, so the setting grants nothing new. A session's `program_name` and the history import keep the agent's name whatever program the command names.
- **Agent selection and settings**: a spawn names its agent and options as `SpawnRequest.agent` (an `AgentSelection`; none is a plain shell), and the daemon validates them through the registry's plugin before any work, refusing "This daemon has no agent `<id>`.", "An agent session needs an agent." and "A plain shell runs no agent."; a preset without an agent runs `default_agent()`.

  `SetAgentSettings { agent, options }` validates, saves `agent_settings` in `state.json` and broadcasts `AgentSettings`. At connect the daemon sends `Agents` (the descriptors), `AgentSettings`, `Repos`, then `Sessions`.
- **Claude accounts**: the daemon holds several Claude Code logins, polls each one's 5-hour and weekly usage, switches the machine's active login by hand or on its own, and every client watches and switches over the wire (`ListAccounts`, `Accounts`, `AccountsUpdated`, `SwitchAccount`, `AccountEvent`; `docs/wire-protocol.md`).

  The `accounts` feature is listed on 64-bit Windows and macOS only: not on Linux, 32-bit Windows or in an elevated daemon, and a client hides its accounts surfaces without it.

  One account is active for the machine, and a switch rewrites Claude Code's live credential under Claude Code's own lock pair, so every running `claude`, interactive and headless, picks the new account up on its next message with no restart. Sessions never get their own `CLAUDE_CONFIG_DIR`, so transcripts, the recover dialog and status tailing keep reading one Claude home (`claude_home` in `crates/agents/claude/src/transcripts.rs`).

  The store lives in the machine-local data folder (`docs/on-disk.md`) and starts empty; the user adds logins in Settings › Accounts, either by capturing the login `claude` holds now or through the daemon-driven login. Accounts are OAuth only: the crate reads an `api_key` record but neither polls nor switches to it. Credentials and tokens never cross the wire to any client, and none reaches a log line or `state.json`.

  Remote clients see usage, switch the active account and change auto-switch on or off and its rules. Adding, removing, aliasing and the login stay local: a tailnet connection is answered `local_only`, and the native client disables those controls on a `Remote` `Welcome.origin` with "Only on the machine running the daemon". The SSH bridge counts as `Local`.

  Auto-switch runs in the daemon, off by default and whether or not a client is connected, using the crate's rules. While it is on, the engine holds a lease file in the store, so two engines on one store (two daemons) cannot both switch; the one without the lease reports `Paused` with the holder as its reason. Codex and Cursor sessions, and Claude sessions on another provider, are untouched by a switch.

  The Claude plugin's account service calls Anthropic's OAuth account endpoints (usage, profile, token refresh) directly, with synchronous reqwest transports built per call on a blocking thread: HTTPS only, no proxy, no redirects, bodies capped at 64 KiB, tokens never logged, the base URL injectable only for tests. This is the one place the repo makes a direct Anthropic call, and no model call is made.

  The crate's rules hold and the daemon must not bypass them: a refresh token is one-time, so a refresh POST is never retried and the active account is refreshed only under Claude Code's lock pair; no network call runs under a lock; every HTTP status returns `Ok` from a transport.

  `CLAUDE_SECURESTORAGE_CONFIG_DIR` set makes the crate refuse to refresh, and an `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` in the daemon's environment overrides the credential file for every session it spawns; the daemon shows either as the reason switching has no effect.

  Paid fallback and prepaid balances are not surfaced.

  The crate (`crates/agents/claude/accounts/`, `publish = false`; its README.md holds its behaviour) is reached only through the Claude plugin, since app code never names an agent. The daemon's `accounts/snapshot.rs` maps the plugin's `agent_api` rows to protocol rows, so the daemon never names the crate's types.

  The poller (`crates/daemon/src/accounts/driver.rs`) parks while no client is connected and no engine is live; shutdown asks it to stop for up to 15 s and `run()` waits up to 20 s for it. The plugin keeps an in-memory usage history for the fleet verdict (`pace::fleet`), lost on a daemon restart.

  The daemon-driven login (`StartAccountLogin`, `CancelAccountLogin`, `AccountLogin`) runs the plugin's login command (`claude auth login --claudeai` with `CLAUDE_CONFIG_DIR` at a scratch folder) as a visible terminal session in the sidebar, so the user finishes the browser login there. At most one runs at a time.

  When the session exits with code 0 the daemon captures the scratch login with `capture_login_from`, which leaves the store's active account as it was, and removes the scratch folder. A cancel, a failure, a 10-minute timeout and the daemon's shutdown end it the same way without a capture. On macOS the scratch login lives in a Keychain item the plugin deletes (`discard_login`).
- **Gates view**: the daemon host's gate slots, shown on the activity rail and in a footer pill (`FEATURE_GATE_STATE`, `GateState`, `GateHistory`). On 64-bit Windows the daemon reads the gate's state with the `gate-state` crate and pushes it to clients on change, polling every 2 s while a client is connected and parking at zero clients; the view is [native-client.md](./native-client.md) "Gates".

  The wire types are the daemon's own, converted from gate-state's, so a change to the gate's claim files never reaches the protocol; every field past the ids is defaulted and the enums carry `Unknown`, so the feature is additive with no protocol bump. A daemon on another platform lists no `gate_state` and starts no poll. On 64-bit Windows each poll first checks that the gate is installed (`gate.exe` under the Program Files root's `gate\bin`, from `GATE_LAUNCHER_PROGRAM_FILES` when non-empty else `%ProgramFiles%`, or under `%LOCALAPPDATA%\gate\bin`, the two paths `tools/gate.ps1` uses; `GATE_BOX_EXE` is not consulted) and reports no state when it is not, so the view hides and returns without a restart and the requests are refused (`served` in `server/gate.rs`); a check that fails other than "not found" is logged as a warning and counts as not installed. An elevated daemon polls whatever its own `LOCALAPPDATA` and `Local\` namespace hold, which may differ from the user's gates.

  Only the daemon host's gates are sent, headed with its machine name; a tailnet client sees the host's slots, never its own machine's, and never an aggregate.

  `SetGateSlotCount` is local only like account administration and runs `apply_slot_count` on a blocking thread; the poll stays the only publisher, since the write signals a repoll and the next push carries the new count. The daemon never caches the counts, and the client and ops-tower may both write `slot-counts.json`, each write being gate-state's atomic per-kind read-modify-write. There is no Stop gate: gate-state has no stop API, and a stop would bring Windows job-object code back into the daemon.

  The history read (`GateHistory`) is a separate pull: the daemon holds one `JournalCache` behind a `Mutex`, reads it under `spawn_blocking`, and maps a worktree folder to its repo through the registry (`RepoFolders`; `<repo>.wt\<name>` is `<repo>`). A journal read error answers empty lists and never takes the slots down, and the daemon never calls the journal writers.

  The Dashboard takes gate holds under sessions and gate ticks in the activity tracks from the daemon-side state on `Hub`, never from the wire message.
- **Dispatch runs**: the daemon lists the runs the user's dispatch tool is making (`claude -p` implementer runs) so a client can watch one and stop it, without the tool ever needing the daemon.

  The tool writes one live-run file per `claude` process into one live-run folder (`RUSTLING_TULIP_DISPATCH_DIR`, else the Claude plugin's `live_runs_dir`; [on-disk.md](./on-disk.md) "The dispatch live-run folder").

  The daemon watches it (`dispatch_runs/watch.rs`), tails each run's `stream` file (`tail.rs`; each line also parses into the run's transcript log, `transcript_log.rs`, which a `FollowTranscript` reads), and sends `DispatchRuns`, `DispatchRunUpdated` and `DispatchRunRemoved` when `Welcome.features` lists `dispatch_runs` ([wire-protocol.md](./wire-protocol.md)).

  A tab pane can follow a run (`PaneFollow`), and the native client draws a run as a `DS` leaf and a followed pane as `dispatch_view.rs` ([native-client.md](./native-client.md)).

  The decisions that last:
  - A separate message family, not a session mode: `SessionMode` has no `Unknown`, so a new mode would be a breaking change, and a run posing as a headless session would need a "not a dispatch" guard on every session path (history, recovery, sidecars, attention, tab placement), since the daemon does not own the process.
  - The daemon persists nothing of a run: the live-run folder and the stream files are the state, and a restarted daemon rescans and replays each stream from byte 0. The one exception is a pane's `follow` in the tab layout; the daemon never clears it when its run goes (the pane keeps the last snapshot), only at startup, after the first scan, for a local pane whose run is not live.
  - Liveness is the process guard (`guard.rs`): the child's pid plus its creation time, compared exactly on Windows (`child_start`), else the process's start time within a window of `started_at`. Dead only on evidence, and unknown counts as alive, so a run stays listed and its file is kept; a run whose child is found dead is dropped and not listed again while the daemon runs. Its file, which protects the stop marker beside it, is deleted only once the file's runner (the dispatch tool's own process, `runner_pid`) is dead or not recorded: exact creation time when `runner_start` is recorded, else a start no later than 5 s after `started_at`; an unknown runner keeps the file.
  - Stop writes the stop marker before it kills the child's tree (`server/dispatch_runs.rs`), holding the guard's process handle open across the kill on Windows so the pid cannot be reused in between. The marker lets the tool record the run as stopped and skip its automatic resume, which a bare kill would trigger.
  - A linked run counts as the dispatching session's background work through one shared set (`dispatch_runs/links.rs`, `DispatchLinks`): `SessionRecord::snapshot()` reports `background` while a live run's `session_id` equals the session's conversation id, never written into the record's own flag; [session-runtime.md](./session-runtime.md).
  - A live run does not keep the daemon running (`idle_exit.rs` is unchanged); a linked one makes its session read as busy to keep-awake.
  - The agent name stays out of the daemon: the default folder comes from the plugin (`Agent::live_runs_dir`) and the stream is parsed through the registry (`parse_headless_line`).
- **Host behaviour**: the daemon holds an idle-sleep inhibitor as the `keep_awake_mode` host setting says (`SetKeepAwakeMode`; Off never holds, When busy, the default, holds while a session is busy by the client's own busy set, Always holds while any session has a live child).

  A second daemon on the same config dir exits at once. The startup reap and binary-cache GC touch only tracers and binaries this config dir owns. The login entry runs `rustling-tulipd --detach`, which copies itself into the binary cache and starts that copy.

## Non-goals

- Sub-agent / Task-tool interception or isolation. A subagent's transcript is viewed read-only, never messaged or stopped.
- A chat that drives its own `claude --print --input-format stream-json` child as a two-way peer. The chat is a mirror of the live terminal session; a peer would restart the agent on each view switch and could not run beside the terminal.
- Auto-discovery of repos: the registry is manual.
- Attach from outside the tailnet by internet exposure or a relay. The tailnet listener is the one way in from another machine today ([plans/remote-access.md](./plans/remote-access.md)); clients over OpenSSH are planned (RT-530, [plans/ssh-remote.md](./plans/ssh-remote.md)).
- Cloud sync of the registry or sessions.
