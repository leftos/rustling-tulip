# Architecture

rustling-tulip orchestrates many parallel `claude` CLI sessions across single repos and multi-repo workspaces from one native window. A long-lived daemon owns every PTY and child process; the desktop client is only a client, and sessions outlive it. Nothing in the repo calls the Anthropic API: the daemon shells out to the CLI. Open work is in [plans/MAIN.md](./plans/MAIN.md); the native client's design decisions are in [native-client.md](./native-client.md).

## Overview

```
┌────────────────────────┐          ┌────────────────────────────┐
│  Native client (GPUI)  │  WS+JSON │  Daemon (long-lived)       │
│  - alacritty_terminal  │ ───────► │  - Session supervisor      │
│    panes               │ ◄─────── │  - PTY pool (ConPTY)       │
│  - Activity rail       │          │  - rt-tracer.exe sidecar   │
│  - Source control      │          │  - Worktree orchestrator   │
└────────────────────────┘          └──────────┬─────────────────┘
                                               │ spawns
                                               ▼
                                    ┌────────────────────────────┐
                                    │  claude CLI                │
                                    │  (interactive or headless) │
                                    └────────────────────────────┘
```

The wire protocol is JSON over a WebSocket: loopback by default, and TLS on the host's tailnet addresses when remote access is on (`crates/protocol/src/lib.rs`); the current version and the versions still supported are in `protocol-version.json`. The daemon binds only loopback and, with remote access on, the host's own tailnet addresses; it never listens on `0.0.0.0`. The daemon accepts several clients at once, each with its own connection and its own tab layout.

## What it does

- **Sessions**: interactive Claude sessions, plain shells, and headless Claude sessions (`claude --print --output-format stream-json`, parsed into status, tokens, cost and a recent-actions log; the native client has no headless view and spawns none). Claude is the only agent; other agents come back as plugins (`plans/agent-plugins.md`). A Claude session may be routed to DeepSeek by a per-session Claude provider (Anthropic by default).

  Status (working, awaiting input, idle, stopped) comes from Claude Code's hooks once a session turns hook-driven, injected through a settings file at spawn, and from rules over the session's rendered screen (the screen engine), which also read a session whose hooks never run. A quiet screen that still shows the spinner stays working.

  A plain shell keeps its own output classifier until it is hook-driven or its screen shows Claude.

  A session awaiting input, or an agent that finishes its turn with no background work left, raises an OS notification in each native client, unless its skip setting says the owner is already looking at the session.
- **Workspaces**: a named set of registered repos, created from repos or from a VS Code `.code-workspace` file. A workspace session runs one agent with its cwd in the first member's worktree and `--add-dir` for every other member; worktrees keep the members' relative paths (layout in CLAUDE.md, "Where things live on disk").

  Only `members[0]`'s repo hooks load: an `--add-dir` root's `.claude/settings.json` hooks are not read. A `.code-workspace` file found beside a repo is offered as a workspace.

  A workspace created with Create & watch stores `watch_vscode_workspace` and follows its linked file: a change is parsed after a 750 ms debounce, a new folder is registered as a repo, a removed folder leaves the members but keeps its repo, and the file's folder order becomes the member order. It broadcasts only when the members or the registry changed, and re-validates the workspace under its write lock, so a removed workspace never returns and a rename or relink stands.
- **Survivable sessions**: every interactive and shell session runs under `rt-tracer.exe`, so a daemon restart or upgrade reattaches to live sessions and replays their ring. A lost tracer leaves its session abandoned (Resume / Dismiss) rather than discarded.
- **Session history and recovery**: every ended session gets a history entry (how it ended, its spawn config, its conversation id), kept 7 days and backfilled from tracer logs; `RecoverSessions` respawns chosen entries, including sessions still in the Abandoned group. A Claude entry resumes with `claude --resume`, on the provider it ran on (`HistoryEntry::claude_provider()`; a tracer-log import infers it from `--model`), and a DeepSeek entry never recovers as a shell. A multi-folder standalone recovery passes the extra folders as `--add-dir`; the native client offers it from the rail's Recover dialog (`docs/native-client.md`, Session recovery).
- **Secret env rows**: a spawn dialog env row under a secret key (`KEY`, `TOKEN`, `SECRET` or `PASSWORD` segment, or ticked Secret) is sealed before the spawn config is captured: its value moves into Windows Credential Manager and every stored file and echo carries `${secret:<id>}`, resolved again at each spawn and respawn; startup seals older files and sweeps unreferenced ids (see [env-secrets.md](./env-secrets.md)).
- **Claude provider**: `AgentOptions::Claude` carries a `provider` (Anthropic, DeepSeek, or `Unknown` for a value this build does not know); it is part of the stored spawn config, so Recover, Restart, the sidebar's Resume and Duplicate keep it, and the snapshot reports it as `claude_provider`. The daemon builds the routing environment at each spawn from a built-in provider table (`agents/providers.rs`, not user-editable), before any git work, so a refused spawn leaves no worktree: the tuning defaults (model variables, context size) yield to a spawn's env rows, the locked keys (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_DEEPSEEK_SESSION`, `DEEPSEEK_API_KEY`) and any variable the provider removes from the child are refused in the rows, and a plain shell refuses a non-Anthropic provider. The key (`DEEPSEEK_API_KEY`, process environment then Windows user scope, `user_env.rs`) is read at each spawn and goes only into the child's environment: the routing variables are never stored in `meta.json`, history, `state.json` or the wire, and the spec types print variable names, never values. A PTY child inherits the daemon's whole environment, so removed variables go through `PtySpawnSpec.env_remove`. Every PTY spawn also drops a parent Claude Code session's variables (`PARENT_SESSION_VARS` in `tracer_client.rs`: `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, the messaging socket and token, …), so a daemon started from a terminal inside a Claude session still spawns top-level sessions with their own transcripts; a spawn's env row that sets one keeps it. A DeepSeek history entry recovers as Claude only, with the provider inferred from `--model` for a tracer-log import. The daemon lists `claude_provider` in `Welcome.features`; the native client disables the provider choice against a daemon that does not, and shows a `DeepSeek` chip on the leaf and the pane header (`docs/native-client.md`).
- **Worktrees**: spawns create or reuse a worktree per member under a machine-local root. Branch names are daemon-picked `wt/<adjective>-<noun>` names that no member repo already uses. Fork points resolve to the remote-tracking base (`main` → `origin/main`), with a background fetch and a "commits behind" preview; an existing worktree or a leftover branch is offered as reuse or recreate, never bound silently. Worktrees are addressed by path, so a worktree left by a gone session can be launched into. Duplicating a worktree session spawns the clone on a fresh branch.
- **Discard with branch fate**: deleting a worktree reaps its branch when the commits already landed on the base or its remote by ancestry or patch equivalence (`git cherry`); otherwise the confirm names each member's branch and offers keep or delete.
- **Source control**: per-worktree changed files, staging, commit, discard, stashes, paginated history, commit detail, open in forge, and side-by-side diffs, refreshed by a `.git` watcher that ignores objects, logs and build directories and parks while no client is connected.
- **Remote (tailnet) access**: opt-in and off unless `remote.json` says otherwise (`{enabled, port}`, default port 8787). The daemon serves the host's own tailnet addresses over TLS with the `tailscale cert` certificate, through a separate router that serves only `/ws` and `/health`; an upgrade must name the host in `Host` and carry no foreign `Origin`, shutdown and remote-access configuration are refused on such a connection, and idle exit is held while remote access is on.

  A client turns it on and off live with `ConfigureRemote { enabled, port }` (no restart; a port change while on restarts the listener; a tailnet connection is refused it), which the daemon writes to `remote.json` and answers by broadcasting `RemoteStatus`, also pushed at connect. Its `state` (`RemoteState`) is one of off, starting, not installed, not running, other Windows user, not connected, Tailscale error, HTTPS disabled, host tagged (nothing bound, no certificate asked for), certificate failed, port in use, bind failed, or serving with the name, port and the certificate's expiry.

  `crates/tailnet` wraps the CLI and the owner rule; a connection presents a device token rather than the `daemon.json` token (device approval is TS.3b).
- **Remote file fetch (daemon half)**: `FetchFile` streams a file under a registered repo or session worktree in chunks, confined by one path-confinement helper that `GetFileSnapshot` and `GetFileDiff` share.
- **Host behaviour**: the daemon holds an idle-sleep inhibitor while any session has a live child (`keep_awake`, default on); a second daemon on the same config dir exits at once; the startup reap and binary-cache GC touch only tracers and binaries this config dir owns; the login entry runs `rustling-tulipd --detach`, which copies itself into the binary cache and starts that copy.

## Non-goals

- Sub-agent / Task-tool interception or isolation (viewing a subagent's transcript read-only is planned).
- Auto-discovery of repos: the registry is manual.
- Attach from outside the tailnet by internet exposure, SSH tunnelling or a relay. The tailnet listener is the one way in from another machine ([plans/remote-access.md](./plans/remote-access.md)).
- Cloud sync of the registry or sessions.
