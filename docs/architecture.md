# Architecture

rustling-tulip orchestrates many parallel `claude` CLI sessions across single repos and multi-repo workspaces from one native window. A long-lived daemon owns every PTY and child process; the desktop client is only a client, and sessions outlive it. Nothing in the repo calls the Anthropic API: the daemon shells out to the CLI. Open work is in [plans/MAIN.md](./plans/MAIN.md); the native client's design decisions are in [native-client.md](./native-client.md).

## Overview

```
┌────────────────────────┐          ┌────────────────────────────┐
│  Native client (GPUI)  │  WS+JSON │  Daemon (long-lived)       │
│  - alacritty_terminal  │ ───────► │  - Session supervisor      │
│    panes               │ ◄─────── │  - PTY pool (ConPTY)       │
│  - Activity rail       │          │  - rt-tracer.exe sidecar   │
│  - Source control      │          │  - Worktree orchestrator   │
└────────────────────────┘          └──────────┬─────────────────┘
                                               │ spawns
                                               ▼
                                    ┌────────────────────────────┐
                                    │  claude CLI                │
                                    │  (interactive or headless) │
                                    └────────────────────────────┘
```

The wire protocol is JSON over a WebSocket: loopback by default, and TLS on the host's tailnet addresses when remote access is on (`crates/protocol/src/lib.rs`); the current version and the versions still supported are in `protocol-version.json`. The daemon binds only loopback and, with remote access on, the host's own tailnet addresses; it never listens on `0.0.0.0`. The daemon accepts several clients at once, each with its own connection and its own tab layout.

## What it does

- **Sessions**: interactive Claude sessions, plain shells, and headless Claude sessions (`claude --print --output-format stream-json`, parsed into status, tokens, cost and a recent-actions log; the native client has no headless view and spawns none). Claude is the only agent; other agents come back as plugins (`plans/agent-plugins.md`). A Claude session may be routed to DeepSeek by a per-session Claude provider (Anthropic by default).

  Status (working, awaiting input, idle, stopped) comes from Claude Code's hooks once a session turns hook-driven, injected through a settings file at spawn, and from rules over the session's rendered screen (the screen engine), which also read a session whose hooks never run. A quiet screen that still shows the spinner stays working.

  A plain shell keeps its own output classifier until it is hook-driven or its screen shows Claude.

  An interactive Claude session runs in the user's shell (agent in shell): the shell is the PTY child under the unchanged tracer, and once its prompt is quiet the daemon clears the input line and types `<cd to the start folder> && <the quoted claude command line>` (`server/spawn/shell.rs`, `inject.rs`), the path Recover's shell-running-`claude --resume` already takes.

  The pane stays a usable shell after Claude exits and the session ends only when the shell exits (a worktreeless one that exited by itself closes, one with a worktree shows the exited overlay).

  The command line is the plugin's `interactive_args` with the absolute program path, quoted for the shell family (PowerShell, cmd, POSIX sh). The initial prompt or a preset's script is not on it: it is typed into Claude's TUI once Claude is up (hook-driven, or the screen reads Claude) and dropped after 15 s. The plugin's `EnvPlan` and the env rows apply to the shell, so commands run after Claude see them, a DeepSeek session's routing variables included.

  The gate is the plugin's `AgentCaps.shell_resume` (Claude sets it). A plugin without it, a shell the daemon cannot type into safely (unknown, a cmd line with `%` or `!`, legacy PowerShell argument passing) and headless runs keep the direct spawn with the agent as the PTY child.

  Rejected: the tracer starting a shell after its child exits, which rewrites the tracer's one-child job, kill and `Exited` path; and launching through the shell's startup arguments, which needs a script per shell, `cmd /K` the least predictable.

  The record stays Interactive with agent Claude, its spawn config and conversation id, so Restart, Resume, auto-resume and Recover work unchanged, and its status runs on the plain-shell watcher. `program_name` follows the child: the shell's label once Claude has ended, `claude` again on its next `SessionStart`. `agent_in_shell` and `shell_label` are mirrored into the sidecar so a reattach runs the shell's watcher.

  Claude has ended when its `SessionEnd` hook arrives with a reason other than `clear`, else when `hand_shell_back` sees the prompt return. The daemon then sends the additive one-shot `AgentExited { session_id }` once per Claude run on the session-event stream, and the native client raises a timed toast offering to close the session (`docs/native-client.md`, "Claude exited into its shell"). Keep-awake and idle exit see the live shell: Always holds while it lives, When busy only while it prints.

  A session awaiting input, or an agent that finishes its turn with no background work left, raises an OS notification in each native client, unless its skip setting says the owner is already looking at the session.
- **Workspaces**: a named set of registered repos, created from repos or from a VS Code `.code-workspace` file. A workspace session runs one agent with its cwd in the first member's worktree and `--add-dir` for every other member; worktrees keep the members' relative paths (layout in CLAUDE.md, "Where things live on disk").

  Only `members[0]`'s repo hooks load: an `--add-dir` root's `.claude/settings.json` hooks are not read. A `.code-workspace` file found beside a repo is offered as a workspace.

  A workspace created with Create & watch stores `watch_vscode_workspace` and follows its linked file: a change is parsed after a 750 ms debounce, a new folder is registered as a repo, a removed folder leaves the members but keeps its repo, and the file's folder order becomes the member order. It broadcasts only when the members or the registry changed, and re-validates the workspace under its write lock, so a removed workspace never returns and a rename or relink stands.
- **Survivable sessions**: every interactive and shell session runs under `rt-tracer.exe`, so a daemon restart or upgrade reattaches to live sessions and replays their ring. A lost tracer leaves its session abandoned (Resume / Dismiss) rather than discarded.

  Each session's lifecycle task (`session.rs` `attach_lifecycle`) is the single consumer of its PTY output: it appends each chunk to the scrollback ring, then forwards it to every attached client's own channel, so a `LoadScrollback` snapshot and the live output after it meet with no gap. A client fed from a fresh `broadcast` receiver instead would miss whatever arrives while the snapshot reads the file, and a lost ConPTY startup `ESC[6n` leaves the child blocked forever.
- **Session history and recovery**: every ended session gets a history entry (how it ended, its spawn config, its conversation id), kept 7 days; at startup each dead non-headless sidecar with no entry gets one (`TracerLost` with an unknown end time, or its true end from the tracer log), before the rest is backfilled from tracer logs; `RecoverSessions` respawns chosen entries, including sessions still in the Abandoned group.

  After the handshake (the listener is bound, so the resume never delays it) the daemon resumes by itself, with no prompt, no off switch and no retry, one at a time (`auto_resume`), each of those lost-at-start sessions that is a non-headless interactive Claude session with a spawn config, its own conversation id and an existing transcript, whose worktree pins resolve, whose in-place checkout is still on its branch and whose pinned worktree no other live session holds (`auto_resume_refusal` and `auto_resume_request`).

  A session whose tracer log shows `Exited` or `StoppedByUser` was not lost and is never resumed. It restarts with `--resume <its own conversation id>`, never the newest conversation in its folder, in its old panes, and the entry is marked recovered.

  Every lost session has its `TracerLost` entry before anything spawns, so a second start never resumes one twice. Plain shells, a session with no conversation or transcript, an unpinnable target, a failed spawn, an in-place checkout on another branch and a worktree in use stay abandoned in Recover. Idle exit is held off while this runs, and a user's Resume racing it wins.

  When the pass finishes the daemon broadcasts `ResumeReport { resumed, left_in_recover }` (the sessions this start resumed, and those it refused or failed to resume, which stay in Recover); a client connecting later gets it with its initial state, each client id hears it at most once per daemon run, and nothing is sent for a start with nothing to resume or with both counts 0.

  A Claude entry resumes with `claude --resume` in the session's start folder (`history::entry_folder`: a plain shell recovers where it last was, an interactive session where it started, wherever its shell went), with the options it ran with (the entry's `options` and `trusted`, which a tracer-log import fills from the log, inferring the DeepSeek provider from `--model`), and a DeepSeek entry never recovers as a shell.

  A multi-folder standalone recovery passes the extra folders as `--add-dir`; the native client offers it from the rail's Recover dialog (`docs/native-client.md`, Session recovery).

  A resumed session (auto-resume or a leaf Resume) keeps the old record's user name and appearance (a session with no rename keeps its new default label), and its id replaces the old id in place in each container's `session_order`, broadcast as `SessionsReordered`.

  A leaf Resume of an abandoned interactive Claude session continues its own conversation (`--resume`) when its transcript exists; without one, for a plain shell, when its pinned worktree folder is gone or when a live session holds that worktree, it reruns the unpinned request (worktree recreated or the in-use refusal, first prompt replayed).

  A manual Resume proceeds when worktrees cannot be pinned, as Restart does; auto-resume keeps its stricter refusal. The Recover dialog path (`finish_recovery`) does not carry name, look or place.
- **Secret env rows**: a spawn dialog env row under a secret key (`KEY`, `TOKEN`, `SECRET` or `PASSWORD` segment, or ticked Secret) is sealed before the spawn config is captured: its value moves into Windows Credential Manager and every stored file and echo carries `${secret:<id>}`, resolved again at each spawn and respawn; startup seals older files and sweeps unreferenced ids (see [env-secrets.md](./env-secrets.md)).
- **Claude provider**: the Claude selection's options carry a `provider` (Anthropic, DeepSeek, or `Unknown` for a value this build does not know); it is part of the stored spawn config (`SpawnConfig.agent`, an `AgentSelection`), so Recover, Restart, the sidebar's Resume and Duplicate keep it, and the snapshot reports it as a chip in `agent_chips` (text `DeepSeek`, tip "Runs on DeepSeek", from `agent_api::session_chips`).

  The daemon builds the routing environment at each spawn from the Claude plugin's built-in provider table (`crates/agents/claude/src/providers.rs`, not user-editable), before any git work, so a refused spawn leaves no worktree: the tuning defaults (model variables, context size) yield to a spawn's env rows, the locked keys (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_DEEPSEEK_SESSION`, `DEEPSEEK_API_KEY`) and any variable the provider removes from the child are refused in the rows, and a plain shell refuses a non-Anthropic provider.

  The key (`DEEPSEEK_API_KEY`, process environment then Windows user scope, `user_env.rs`) is read at each spawn and goes only into the child's environment: the routing variables are never stored in `meta.json`, history, `state.json` or the wire, and the spec types print variable names, never values. A PTY child inherits the daemon's whole environment, so removed variables go through `PtySpawnSpec.env_remove`.

  Every PTY spawn also drops a parent Claude Code session's variables (`PARENT_SESSION_VARS` in `tracer_client.rs`: `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, the messaging socket and token, …), so a daemon started from a terminal inside a Claude session still spawns top-level sessions with their own transcripts; a spawn's env row that sets one keeps it.

  A DeepSeek history entry recovers as Claude only, with the provider inferred from `--model` for a tracer-log import. The native client draws the snapshot's `agent_chips` on the leaf and the pane header (`docs/native-client.md`).
- **Worktrees**: spawns create or reuse a worktree per member under a machine-local root. Branch names are daemon-picked `wt/<adjective>-<noun>` names that no member repo already uses. Fork points resolve to the remote-tracking base (`main` → `origin/main`), with a background fetch and a "commits behind" preview; an existing worktree or a leftover branch is offered as reuse or recreate, never bound silently.

  Worktrees are addressed by path, so a worktree left by a gone session can be launched into. Duplicating a worktree session spawns the clone on a fresh branch. Restart of an exited session and Resume of a parked one rerun in the session's own worktree and branch (`DuplicateSession.same_checkout`), and an interactive Claude session continues its conversation (`--resume`) while its transcript still exists, else starts a fresh one.
- **Discard with branch fate**: deleting a worktree reaps its branch when the commits already landed on the base or its remote by ancestry or patch equivalence (`git cherry`); otherwise the confirm names each member's branch and offers keep or delete.
- **Source control**: per-worktree changed files, staging, commit, discard, stashes, paginated history, commit detail, open in forge, and side-by-side diffs, refreshed by a `.git` watcher that ignores objects, logs and build directories and parks while no client is connected.
- **Remote (tailnet) access**: opt-in and off unless `remote.json` says otherwise (`{enabled, port}`, default port 8787). The daemon serves the host's own tailnet addresses over TLS with the `tailscale cert` certificate, through a separate router that serves only `/ws` and `/health`; an upgrade must name the host in `Host` and carry no foreign `Origin`, shutdown and remote-access configuration are refused on such a connection, and idle exit is held while remote access is on.

  A client turns it on and off live with `ConfigureRemote { enabled, port }` (no restart; a port change while on restarts the listener; a tailnet connection is refused it), which the daemon writes to `remote.json` and answers by broadcasting `RemoteStatus`, also pushed at connect.

  Its `state` (`RemoteState`) is one of off, starting, not installed, not running, other Windows user, not connected, Tailscale error, HTTPS disabled, host tagged (nothing bound, no certificate asked for), certificate failed, port in use, bind failed, or serving with the name, port and the certificate's expiry.

  `crates/tailnet` wraps the CLI and the owner rule; a connection presents a device token rather than the `daemon.json` token. A tailnet `Hello` without a valid device token gets `Welcome` and then `DevicePairFailed { reason: "device not approved" }`, and stays open as a pairing connection (`Welcome.features` lists `device_pairing`).

  A pairing connection gets no layout, forwarders or initial state, is not counted in the client count, and accepts only `DevicePairRequest`, `DevicePairCancel` and `DevicePairRedeem`. It closes 10 s after `Welcome` with no request, once its request ends, after 16 frames that are not pairing steps, or on a 4th request.

  Approval is made from a loopback client only (`ListPendingDevices`, `ApproveDevice`, `DenyDevice`, `MintDevicePairCode`, `ListDevices`, `RevokeDevice`, `ForgetDevice`; a tailnet connection is refused them), which sends the code back to the approver and `DevicePairDecided` to the waiting device; the device redeems the code and gets its `DeviceToken` once, then the connection closes.

  `rustling-tulipd pair` (`cli_pair.rs`) is the command-line way to the same code, for an owner reached over SSH: it reads `daemon.json`, connects to the running daemon's loopback `/ws`, sends `MintDevicePairCode`, prints `Pairing code: <code>` with its lifetime and exits. It takes no instance lock, rotates no log and sweeps no binary cache, so it runs beside a live daemon, and gives the whole exchange 10 s. The code works once, for one device, and only for a device whose pairing request is already waiting on the host. On Windows the daemon is a GUI-subsystem exe, so `pair` attaches the parent console before writing (output may land after the shell prompt returns; a redirect such as `> code.txt` is kept).

  Turning remote access off drops every waiting request and code, and each waiting device is told `DevicePairDecided { Expired }`.

  A tailnet connection, served or pairing, ends with the listener server (the bound address) that accepted it: remote access turned off or its port changed, Tailscale down, the host becoming tagged, HTTPS disabled, the certificate lost, an address vanishing, a supervisor panic, or the server task ending on its own. It gets a WebSocket Close within 2 s (`SERVER_ENDED_CLOSE_LIMIT`) even if the peer stopped reading, and then the socket is dropped; a served connection drops its queued output, a pairing connection sends what is queued first. A certificate reload or a rename does not close it, and loopback connections are never touched.

  A served tailnet `Hello` stamps the device's `last_seen` in `devices.json`.

  `RevokeDevice` marks the record blocked (`revoked: true`) and closes every served tailnet connection of that device with a WebSocket Close, also when the flag write fails (the reply is then an `Error`). A blocked device is refused at `DevicePairRequest` and at redeeming a code with `DevicePairFailed { reason: "device not approved" }`, and `ApproveDevice` for its request is an `Error`; only `ForgetDevice` (loopback only, answered with `Devices`) removes the record and so clears the block. `DeviceInfo.connected` counts a device's served connections (`Welcome.features` lists `device_block`).
- **Remote file fetch**: `FetchFile` streams a file under a registered repo or session worktree in chunks, confined by one path-confinement helper that `GetFileSnapshot` and `GetFileDiff` share.

  The native client's sink (`RootView::fetch_remote_file`) saves it under the machine-local `remote-files` root and opens it; a Ctrl+click on a terminal path link on a remote host calls it (`fetch_link.rs` works out the readings), and so does the ⋯ menu's "Fetch file…" popup (`fetch_dialog.rs`, `fetch_dialog_view.rs`), a modal with progress, Cancel and inline errors. A fetched HTML page that opens when done also fetches the relative media it names before it opens (`html_media.rs`, the media batch in `file_fetch.rs`).
- **Agent launch command**: a host setting per agent (`SetAgentCommand`, saved as `agent_commands` in `state.json`, sent as `AgentCommands` at connect and after each save, feature `agent_commands`) with a Program and Extra arguments, read at each interactive spawn so Restart, Resume and auto-resume use the current one; headless runs ignore it. Settings > Claude edits it (`settings_view.rs`).

  Extra arguments go after the plugin's argv and are refused on save when they hold a control character, an unclosed quote or a flag the plugin lists in `reserved_args()`.

  A direct spawn splits them by POSIX shell-word rules; the typed shell form types the program word bare (so an alias resolves), the plugin's arguments quoted and the extras verbatim. `RUSTLING_TULIP_CLAUDE`, a blank Program or one naming an existing file keeps the quoted absolute path, extras still applied; cmd with `%` or `!` in the extras falls back to the direct spawn.

  A remote client may edit it (it is not in `host_only_refusal`): an approved tailnet device can already type any command into a shell session, so the setting grants nothing new. A session's `program_name` and the history import keep the agent's name whatever program the command names.
- **Agent selection and settings**: a spawn names its agent and options as `SpawnRequest.agent` (an `AgentSelection`; none is a plain shell), and the daemon validates them through the registry's plugin before any work, refusing "This daemon has no agent `<id>`.", "An agent session needs an agent." and "A plain shell runs no agent."; a preset without an agent runs `default_agent()`. `SetAgentSettings { agent, options }` validates, saves `agent_settings` in `state.json` and broadcasts `AgentSettings`. At connect the daemon sends `Agents` (the descriptors), `AgentSettings`, `Repos`, then `Sessions`.
- **Host behaviour**: the daemon holds an idle-sleep inhibitor as the `keep_awake_mode` host setting says (`SetKeepAwakeMode`; Off never holds, When busy, the default, holds while a session is busy by the client's own busy set, Always holds while any session has a live child); a second daemon on the same config dir exits at once; the startup reap and binary-cache GC touch only tracers and binaries this config dir owns; the login entry runs `rustling-tulipd --detach`, which copies itself into the binary cache and starts that copy.

## Non-goals

- Sub-agent / Task-tool interception or isolation (viewing a subagent's transcript read-only is planned).
- Auto-discovery of repos: the registry is manual.
- Attach from outside the tailnet by internet exposure, SSH tunnelling or a relay. The tailnet listener is the one way in from another machine ([plans/remote-access.md](./plans/remote-access.md)).
- Cloud sync of the registry or sessions.
