# Wire protocol

The rules of the daemon/client protocol that the types in `crates/protocol/src/lib.rs` do not show. When to bump the version is in [CLAUDE.md](../CLAUDE.md), "When to bump `protocol-version.json`"; adding a message follows the `add-protocol-message` skill.

- All binary payloads (PTY input/output, scrollback) cross the wire as `data_b64`. Don't add raw-bytes fields.
- The `Hello` message must be the first thing a client sends after WS upgrade. New clients send both `protocol_version` (scalar back-compat) and `protocol_versions: Vec<u32>`. The daemon picks the highest mutually supported version from its `SUPPORTED_PROTOCOL_VERSIONS` const and echoes it in `Welcome.protocol_version`. An empty intersection or token mismatch closes the connection.

  `Hello.auth_token` is the daemon's `daemon.json` token on a loopback connection; on a tailnet connection the daemon never compares it to that token, and the value is the device's own token. A tailnet connection has 10 s to send `Hello`; the loopback listener keeps the un-timed handshake. A tailnet connection also gets a WebSocket Close when the listener server that accepted it ends (remote access turned off or its port changed, among others); loopback connections never do. A tailnet connection (served or pairing) is also pinged every 15 s and closed after 3 unanswered pings (no miss counts while one of its requests is being handled), and closed when one frame takes longer than 30 s plus 1 s per 64 KiB to send; a loopback connection, the SSH bridge's included, is never pinged and never has a send timed out.

  A tailnet `Hello` whose token is not a valid device token (none, unknown, another node's, revoked, the daemon's own, or an unreadable store) is not an `AuthFailed`: it gets `Welcome`, then `DevicePairFailed { reason: "device not approved" }`, and stays open as a pairing connection.

  An elevated daemon (token at High integrity or above) also checks each loopback `/ws` upgrade: it finds the peer's pid from the established loopback TCP row and admits only a peer whose integrity is at or above the lower of its own level and High. A lower peer, or one it cannot look up, gets `AuthFailed` carrying `daemon_client::ELEVATED_DAEMON_REFUSAL`; `/shutdown` and `/hook` answer 403 with the same text (`crates/daemon/src/integrity.rs`, `server/handshake.rs`). A tailnet connection is not checked, and an ordinary daemon checks nothing.

  That connection accepts only `DevicePairRequest` / `DevicePairCancel` / `DevicePairRedeem` (anything else gets the same `DevicePairFailed`), and `ListPendingDevices`, `ApproveDevice`, `DenyDevice`, `MintDevicePairCode`, `ListDevices`, `RevokeDevice` and `ForgetDevice` work on loopback only (a tailnet connection gets `Error "device approval is local-only"` for `ForgetDevice`). `DumpScreen` is loopback only too: a tailnet connection gets `Error "screen dump is local-only"`.

  `RevokeDevice` blocks the device and closes every served tailnet connection of it with a WebSocket Close, also when the flag write fails (the reply is then an `Error`).

  A blocked device's `DevicePairRequest` and redeem get `DevicePairFailed { reason: "device not approved" }`, and `ApproveDevice` for its request gets `Error "this device is blocked; forget it before approving it again"`; only `ForgetDevice` clears a block, answered with `Devices`. Every `Devices` message carries `DeviceInfo.connected`, the device's served connection count. `Devices` is also pushed, unprompted, to every loopback connection whenever an approved device's served-connection count changes (its connection registers in the handshake, and it ends for any reason); a tailnet connection is never sent it.

  Web Push is for paired phones on the tailnet. A daemon that lists `web_push` (`FEATURE_WEB_PUSH`) in `Welcome.features` serves this contract: `GetPushStatus { request_id }` (`get_push_status`), `RegisterPush { registration, needs_you, finished, hold_at_desk?, request_id }` (`register_push`, `registration` tagged by `kind`: `web_push { endpoint, p256dh, auth }`, an unknown kind decoding as `Unknown`) and `UnregisterPush { request_id }` (`unregister_push`) are each answered by `PushStatus { vapid_public_key, endpoint, needs_you, finished, hold_at_desk, request_id }` (`push_status`, `endpoint` omitted when none is registered). `hold_at_desk` is optional on the wire and reads true when absent (in a registration, in a status, and in the status when nothing is registered); it asks that the subscription's pushes wait while the owner is at the desk (`docs/session-runtime.md` "Phone pushes").

  A `registration` may also be `apns { token, environment, p256dh, auth }`, its `environment` `production` or `sandbox` (an unknown one decoding as `unknown`), or `fcm { token, p256dh, auth }`. A daemon that lists `web_push` stores either for a paired tailnet device and answers it with its `device_token` (an older one refuses either with `invalid_request`, as an unknown kind), refusing with `invalid_request` a token that is empty, over 512 characters or (APNs) not hexadecimal, and an `unknown` environment; it pushes to them only once it lists `relay_push` (`FEATURE_RELAY_PUSH`).

  A `PushStatus` for such a subscription carries `device_token`, the registered APNs or FCM token (omitted when none, as for a Web Push subscription or nothing registered), which the phone app compares with its current token to re-register.

  A daemon that lists `client_presence` (`FEATURE_CLIENT_PRESENCE`) in `Welcome.features` takes `ReportPresence { active }` (`report_presence`), which it never answers: a desktop client sends it on connect and whenever its answer changes, `active` meaning its window is focused and its own machine had keyboard or mouse input in the last 180 seconds. The daemon stores nothing, and a closed connection stops counting. A client sends it only to a daemon that lists the feature.

  A daemon that lists `perf_monitor` (`FEATURE_PERF_MONITOR`) in `Welcome.features`, which it does only on Windows and macOS, where the sample has an OS source (`perf/os.rs`), takes `WatchPerf { on }` (`watch_perf`), which subscribes this connection to the machine's CPU and RAM sample (`on` true) or unsubscribes it (false), and never answers it. A subscribed connection, and only it, is sent `Perf { sample }` (`perf`) every 2 s, `sample` being `{ at, interval_ms, machine: { cpu_percent, mem_used_bytes, mem_total_bytes } }` with `interval_ms` echoing the tick; a connection that subscribes right after the last watcher left is sent its first sample at once.

  `cpu_percent` is a percent of the whole machine (all cores together are 100) and is `null` on the first sample after a subscribe, which has no previous reading to compare with, and when a delta is zero; memory is in bytes. The sample is the whole machine only, never a session or a process.

  Any connection may subscribe, tailnet and SSH included, since it is read-only. The daemon reads nothing while no connection is subscribed. The daemon does not yet list the feature, because it has no OS source to read, so a client must not expect samples.

  A daemon that lists `resume_session` (`FEATURE_RESUME_SESSION`) in `Welcome.features` takes `ResumeSession { session_id, request_id? }` (`resume_session`) and picks how to resume by the session's state (`resume_route` in `crates/daemon/src/server/sessions.rs`). A parked session, or one that is stopped or in error, is rerun as a Restart is: a duplicate that keeps the busy exclusion and the checkout and continues the agent's conversation while its transcript exists (a `DuplicateSession` with `carry_busy_excluded` and `same_checkout`). An abandoned session is resumed in place, as `ResumeAbandoned` does. Success is the new session's `SessionUpdated` echoing `request_id`, and the client still places the new session and discards the original of a rerun. A refusal is an `Error` echoing `request_id`: `invalid_request` for a session that is still running, `not_found` for an unknown one, `resume_failed` for an abandoned resume that failed; a failed rerun is the usual `ActionFailed` of a spawn. A client sends it only to a daemon that lists the feature, and to an older one keeps sending the `DuplicateSession` recipe for a parked or stopped session and `ResumeAbandoned` for an abandoned one; `ResumeAbandoned` also stays for Resume all.

  A daemon that lists `launch_last` (`FEATURE_LAUNCH_LAST`) in `Welcome.features` takes `LaunchLast { target, request_id? }` (`launch_last`) and launches the stored last spawn config of the repo or workspace `target` names, as the desktop's Launch last replays it (`SpawnConfig::to_replay_request`): a worktree config on a fresh branch name the daemon picks, and a folder that is no git repository in place, on no branch. `target` is a `ContainerRef`.

  It is refused with an `Error` echoing `request_id`: `not_found` "No such repo or workspace.", `spawn_refused` when the container has no stored config ("<name> has no last launch yet."), when the config is headless, when a branch name can't be picked, or when an in-place launch would need a checkout over uncommitted changes, and `invalid_request` for a standalone config. Success and failure are a spawn's: the new session's `SessionUpdated` echoing `request_id`, or `ActionFailed`.

  A daemon that lists `spawn_extra_args` (`FEATURE_SPAWN_EXTRA_ARGS`) in `Welcome.features` reads `SpawnRequest.extra_args` and `SpawnConfig.extra_args`: a list of strings, omitted when empty and read as none when missing. The arguments go after the agent's own arguments and the host's Settings launch-command extras, on an interactive agent session only. A spawn that carries them on a plain shell or a headless run is refused "Extra arguments apply only to an interactive agent session.", one that repeats a reserved flag "`<flag>` is set by rustling-tulip; remove it from the extra arguments.", and one holding a control character "Extra arguments cannot contain a newline or other control character.", each as `ActionFailed` titled "Extra arguments refused". On the typed shell line each argument is quoted for the shell; when the Settings extras end in a comment or a continuation, or hold `;`, `|`, `&`, a backtick, `<`, `>` or `<#`, a spawn with its own arguments launches the agent directly instead. The arguments are stored with the spawn config (see `on-disk.md`), so Duplicate, Restart, Launch last and recovery replay them. A client sends the field only to a daemon that lists the feature.

  A daemon that lists `new_session` (`FEATURE_NEW_SESSION`) in `Welcome.features` takes `NewSession { target, initial_prompt?, request_id? }` (`new_session`) and starts an interactive session in the repo or workspace `target` (a `ContainerRef`) with the container's last agent: its last spawn config's agent, else the repo's `last_agent`, else the first workspace member's, else the default agent. The options are that config's when its agent matches, else the host's Settings values, else none, with the bypass choice cleared (`AgentDescriptor::clear_bypass`). The session runs in a worktree on a fresh suggested branch; a folder repo that is no git repository runs in place, and a workspace with no git member is refused.

  It is refused with an `Error` echoing `request_id`: `not_found` "No such repo or workspace."; `invalid_request` when `initial_prompt` is missing ("A new session needs a first prompt.") or spans more than one line; `spawn_refused` when the container has no git repo to start a worktree in, when the branch suggestion fails (its error text), or when the checkout has uncommitted changes. Success and failure are a spawn's: the new session's `SessionUpdated` echoing `request_id`, or `ActionFailed`.

  A daemon that lists `preset_job_repeat` (`FEATURE_PRESET_JOB_REPEAT`) answers a `LaunchPreset` whose `job_id` names a job it still holds (any running job, or one of the 32 most recently finished) with that job's latest `PresetLaunchJobUpdated`, to the sender only, and starts no second job; the answer is sent before any later update of that job reaches the sender. A blank `job_id` is a new job every time. A client resends an unanswered preset launch with its `job_id` only to a daemon that lists the feature: an older one starts the batch again.

  A build that predates `web_push` answers a push request from a paired tailnet device with `Error` code `unsupported_message`, echoing its `request_id`. A device with no unrevoked record for its stable id (including one blocked, forgotten or re-paired while its register or unregister was being stored, which is undone and answered `this device is not paired`), an unknown `kind`, and an endpoint that is not `https` on a push-service host get `invalid_request`; a push folder, key or store that fails gets `internal`. On any daemon, a loopback connection sending a push request gets `Error` code `invalid_request`, and an unpaired tailnet connection is on the pairing channel, where only pairing messages are answered.

  `Welcome.features` is the daemon's capability list: a client keeps unknown strings and asks only about ones it knows (`Connection::supports`), and a feature is listed only once the daemon fully honours it (`DAEMON_FEATURES` in `crates/daemon/src/server/handshake.rs`).

  `Welcome.origin` (`local` or `remote`; an unknown value decodes as `Unknown`, and it is omitted when absent) tells the client which listener accepted it: the loopback listener and the SSH bridge are `local`, the tailnet listener (pairing connections included) is `remote`. Only the daemon sets it, and it is a hint for the client's UI: the daemon's own checks use the connection's auth, never this value. The native client reads it as `Connection::origin()`.

  `Welcome.build_version` is the daemon build's release (`protocol::BUILD_VERSION`, the workspace version) and `Hello.client_version` is the client's own; both are optional and omitted when absent, and an older peer sends neither. `Hello.client_kind` (`native` for the desktop client, `phone` for the web app, omitted from the CLIs and tools; an unknown value decodes as `Unknown`) says what opened the connection. The native client keeps the host's version as `Connection::build_version()` and draws it, with a Behind tag when the host's release is older than its own, in the Connections dialog and Settings' host selector; a version that does not parse as semver is not drawn. The daemon logs `client_version` and `client_kind` in its handshake line and keeps them, with `client_features`, in its record of live connections (see `UpdateConnectedClients`); it acts on nothing else in them. No feature string goes with these fields, since a field's absence already says an older peer.

  `ListAccounts { request_id }` (`list_accounts`) is answered by `Accounts { accounts, auto, request_id }` (`accounts`) to the requester only, on any origin.

  `accounts` holds the host's saved accounts, ordered accounts first and then the rest by number, each with its saved 5-hour and 7-day usage, status, fetch time and last error; an OAuth account whose latest poll failed shows `token_expired`, `relogin_required` or `unavailable` and keeps its saved windows, only finite numbers are sent, and `accounts` is `[]` when the store cannot be read or the host holds no accounts service.

  A daemon lists `accounts` in `Welcome.features` only when it holds an accounts service: on 64-bit Windows and macOS, where the Claude plugin's account locks work, and not on Linux, 32-bit Windows or in an elevated daemon. A client hides its accounts surfaces when the feature is absent. `AccountsUpdated { accounts, auto }` (`accounts_updated`) is broadcast to every connected client when a poll finishes, or a write's refresh finishes, and the mapped snapshot differs from the cached one (the first successful poll always broadcasts); `ListAccounts` answers from that cache. A connection whose state stream lagged also gets `AccountsUpdated` from the cached snapshot, and nothing before the first poll.

  The account writes are `SwitchAccount { number, request_id? }` (any origin) and, local origin only, `AddCurrentLogin { request_id? }`, `RemoveAccount { number, request_id? }`, `SetAccountAlias { number, alias?, request_id? }` and `SetAccountOrder { order, request_id? }`.

  A write that succeeds is answered to the requester with `Accounts { accounts, auto, request_id }` after the driver re-reads the store (it waits up to 10 s, then answers from the cache), and other connections get `AccountsUpdated` only when the snapshot changed.

  A write that fails is answered with `Error { code, message, request_id }`, the code one of `account_busy`, `account_draining`, `account_unknown`, `account_refused`, `account_unsupported` or `account_failed`; a host with no account service answers every write `account_unsupported`.

  A tailnet connection that sends one of the four admin messages, or one of the two login messages below, gets `Error { code: "local_only" }` with no `request_id`. Remove refuses the active account and the live login.

  The daemon-driven login is `StartAccountLogin { request_id? }` and `CancelAccountLogin { request_id? }`, both local origin only, and it answers with `AccountLogin { state, session_id?, message?, request_id? }` (`account_login`). `state` is `started`, `succeeded`, `failed` or `cancelled`, and a value the client does not know decodes as `Unknown`.

  A start is answered at once to the requester with `AccountLogin` `started` (its `session_id` is the login's terminal session, which the user finishes the login in) echoing `request_id`, never with `Accounts`, since a login runs for minutes.

  At most one login runs at a time: a second start gets `Error { code: "account_busy" }`, and a start while the daemon shuts down gets `account_draining`. A host with no accounts service answers both messages `account_unsupported`.

  Every connection then hears the run end as one broadcast `AccountLogin` (`succeeded`, `failed` or `cancelled`, `request_id` absent, `message` saying why when there is more to say), and the requester of a start or a cancel also gets its terminal state directly echoing its `request_id`.

  A cancel with no login running is answered `account_refused`, and one while the login is starting or finishing `account_busy`. A login that succeeds changes the store, so the other connections also get `AccountsUpdated` as for any write.

  `auto` is `null` on a host that holds no accounts service (it does not list `accounts`) and otherwise carries the settings file's state: `enabled` is `false` until the user turns auto-switch on (a missing settings file or key reads as off), and `paused_reason` names a settings file that could not be read, its defaults then standing in.

  `auto`'s `strategy` is `best` (the account with the most headroom) or `consume_first` (the one whose weekly window resets soonest), and a value the client does not know decodes as `Unknown`; `rate_window_minutes` is the span the fleet forecast reads usage rise over, 30, 60, 120 or 180, and it is `null` from a daemon that does not send it.

  `SetAutoSwitch { enabled?, threshold_pct?, request_id? }` (`set_auto_switch`, any origin) turns auto-switch on or off, sets the usage, in percent, at which it switches away, or both; a field left out keeps its value. It is answered like the other writes. One that sets neither field is answered `Error { code: "account_refused", message: "nothing to change" }`, a threshold the host refuses is answered `account_refused` with the host's reason, and a host with no accounts service answers `account_unsupported`.

  `SetAutoSwitchRules { hysteresis_pct?, cooldown_secs?, strategy?, rate_window_minutes?, request_id? }` (`set_auto_switch_rules`, any origin) sets auto-switch's rules: the hysteresis, in percentage points, usage must fall back before an account counts as recovered, the least seconds between two switches, how the engine picks its target (`best` or `consume_first`) and the span the fleet forecast reads usage rise over, in minutes (30, 60, 120 or 180); a field left out keeps its value. It is answered like the other writes. One that sets no field is answered `Error { code: "account_refused", message: "nothing to change" }`, a rule the host refuses is answered `account_refused` with the host's reason, and a host with no accounts service answers `account_unsupported`.

  A daemon that lists `account_events` in `Welcome.features` (always together with `accounts`) broadcasts `AccountEvent { event }` (`account_event`) to every connected client, any origin, when something happens to the host's accounts. `event` is tagged by `kind`: `switched { from, to, trigger }` (`from` is `null` when the login was no stored account; `trigger` is `manual` for a `SwitchAccount` that moved the login, sent after the write's refresh and before its answer), `all_exhausted { earliest_reset_at? }`, `quarantined { number }`, `unquarantined { number }` and `halted { message }`; a kind the client does not know decodes as `Unknown`. Only `switched` with trigger `manual` is sent today.

  A daemon that lists `gate_state` (`FEATURE_GATE_STATE`) in `Welcome.features` pushes the host's gate slots as `GateState { state }` (`gate_state`), `state` being `null` when there is no gate state (a host without the gate installed has none, though it still lists the feature; there `SetGateSlotCount` and `GateHistory` are refused with `Error { code: "unsupported_message" }`, as on a daemon without gate support), and answers two requests to the requester alone.

  `SetGateSlotCount { kind, count, request_id? }` (`set_gate_slot_count`, local origin only) sets a pool's slot count, 1 to 64, and a `null` count clears it back to the gate's formula; it is answered `GateSlotCountSet { kind, count, request_id? }` (`gate_slot_count_set`) once written, a count outside 1 to 64 with `Error { code: "invalid_request" }` and a failed write with `gate_write_failed`, both echoing `request_id`, and a tailnet connection with `Error { code: "local_only" }` with no `request_id`, like the other local-only messages.

  `GateHistory { request_id? }` (`gate_history`) is answered `GateHistory { request_id?, runs, open, summary }`: the recent runs, every open run, and one summary row per repository, command and remote flag.

  It is served on tailnet connections too, and a journal the daemon cannot read is answered with all three lists empty, never an `Error`; a daemon without gate state answers `Error { code: "unsupported_message" }`, echoing `request_id`.

  The native client asks This PC only: once when the Gates view opens, then every 15 s while it shows, and every 60 s while a gate state is known and the view is hidden, one request at a time; a refusal echoing that id is logged at info, with no toast.

  A daemon that lists `dispatch_runs` (`FEATURE_DISPATCH_RUNS`) in `Welcome.features`, which it does only when a live-run folder is watched, sends `DispatchRuns { runs }` (`dispatch_runs`) after `Sessions` on connect, then `DispatchRunUpdated { run }` and `DispatchRunRemoved { run_id }` to every connection as the runs change; a connection that lags is sent the full `DispatchRuns` list again.

  A `DispatchRunSnapshot`'s `status` is `starting` until the run's stream shows its first status event, then `working`, `stopping` from a Stop until the run's removal, and `ended` after the stream's final status (the file usually goes moments later); an unknown value decodes as `Unknown`, and every field after `status` is defaulted. The tailer folds each 250 ms poll's lines into one `DispatchRunUpdated` per run, and updates and removals are sent in the order the runs changed, so `DispatchRunRemoved` is sent at most once per run and no update follows it. `main_checkout` is the worktree's main checkout, resolved by the daemon, absent for a plain checkout or an unreadable worktree.

  `DispatchRunSnapshot.subagents` is the run's own subagents, a `Vec<SubagentSnapshot>` (`#[serde(default, skip_serializing_if = "Vec::is_empty")]`, below) riding `DispatchRuns`, `DispatchRunUpdated` and the resync. A run's subagents are listed apart from a session's because a run is not a session and outlives its host; a client follows one only when the run's snapshot lists it.

  `FollowTranscript { source, request_id? }` (`TranscriptSource::DispatchRun { run_id }`, `TranscriptSource::Subagent { session_id, agent_id }` or `TranscriptSource::RunSubagent { run_id, agent_id }`; an unknown source decodes as `Unknown`) follows a transcript read-only: a run's stream lines, or a subagent's transcript file, parsed into `ChatEntry`s by the agent plugin's chat parser, the same one the chat mirror uses. No new message or entry type carries a subagent's transcript.

  The daemon answers with `Transcript { source, entries, hidden, request_id }`, the newest 500 entries with `hidden` counting the dropped ones, and registers the follower under the same lock the log folds under, so every later `TranscriptAppend { source, entries, ended }` is sent after the answer and none is lost or doubled. An append goes to followers only; an entry whose id is held replaces it in place (a tool result re-sends its call's entry), any other is added.

  A shrunk or replaced stream sends followers an unsolicited `Transcript` (`request_id` `None`), which replaces what they hold; a removed run sends `TranscriptAppend` with `ended` true. `UnfollowTranscript { source }` stops it, and a closed connection's follows are dropped.

  A `Subagent` or `RunSubagent` follow answers with the same `Transcript`, then `TranscriptAppend { source, entries, ended: false }` as the subagent's transcript file grows.

  Only the agent id comes from the client: for a session the folder, conversation and env rows come from the host session's record, for a run from the run's entry (its worktree and `agent_session_id`, with the env rows of the session that dispatched it), and the agent plugin builds the path, so the subagent need not be in the `subagents` list.

  The daemon reads the file from its start once per (owner, agent) however many connections follow, and stops when the last follower unfollows or disconnects. Removing the session, or the run, sends each follower of its subagents `TranscriptAppend { entries: [], ended: true }`; a subagent that finishes is not `ended`, since a resume appends to the same file.

  A follow of a run not listed is answered `Error { code: "not_found", message: "No dispatch run {run_id}" }`, and a subagent follow whose session or run is not held, whose run has named no conversation yet, or whose agent id the plugin refuses `Error { code: "not_found", message: "unknown subagent: {session_id or run_id}/{agent_id}" }`.

  A follow of an unknown source is answered `Error { code: "unsupported_message", message: "This daemon cannot follow that transcript source." }` even on a daemon that watches no folder, and a run follow on a daemon that watches no folder answers `unsupported_message` too, each with the `request_id`. A tailnet connection may follow any source, as it may follow a run: it is read-only.

  `SubagentSnapshot` is one row of a subagent list: `agent_id` and, all defaulted, `parent_agent_id`, `depth` (1 for a first-layer subagent), `agent_type`, `description`, `model`, `effort`, `state` (an `AgentState`, `Unknown` for a value the client does not know), `end_status`, `started_at` and `finished_at`. A list is in tree order, each first-layer subagent oldest first followed by its subtree. The rules for what is listed are in [session-runtime.md](./session-runtime.md) "Subagent list".

  The list rides the snapshots rather than a message of its own, `SessionSnapshot.subagents` and `DispatchRunSnapshot.subagents`, so it reaches every client through `Sessions`, `SessionUpdated`, `DispatchRuns`, `DispatchRunUpdated`, the lag resyncs and `Welcome`'s initial state, and a removed session or run takes its subagents with it.

  The snapshot carries only fields that change when a subagent starts, finishes or first replies. All of it is additive with no `Welcome.features` entry and no version bump: a daemon that sends no `subagents` draws no rows, and a client follows a subagent only when a snapshot lists it.

  `StopDispatchRun { run_id, request_id? }` (`stop_dispatch_run`, served on tailnet connections too, as a session stop is) stops a live run: the daemon broadcasts the run as `Stopping`, writes its stop marker, kills its process tree, and the run's removal follows as `DispatchRunRemoved`. It sends no reply on success. A run that is gone or is no longer its process is answered `ActionFailed` titled "The run already ended", and a failed kill "Could not stop the run", each to the requester alone, echoing `request_id`; a Stop for a run already `Stopping` does nothing. A daemon that watches no folder answers `Error { code: "unsupported_message" }`.

  The gate types (`GateState`, `GateSlot`, `GateClaim`, `GateHistoryRun` and the rest) are the daemon's own, converted from gate-state's, so a change to the gate's files never reaches the protocol: every field past the ids is defaulted.

  `GateClaim`, `GateWaiting` and `GateQueueTicket` carry `command_key` (gate-state's normalized command, the same key as `GateCommandSummary.command`) and `repo` (the entry's folder's repository, by the rule `GateHistory` uses), both defaulted, so a client finds an entry's usual time in the summary.

  The enums (`GateSlotKind`, `GateSlotState`, `GateRunState`) decode a value the client does not know as `Unknown`.
- A pane or tab content that names a session on another daemon carries the optional `host` (`GridNode::Pane`, `TabContent::Diff`, and `CreateTab`, `SplitPane`, `ReplacePaneSession`, `OpenDiffTab`; omitted when absent, and absent means this daemon). The daemon stores the string and never interprets it. A local session removal, the startup tab prune and the abandoned-session rebind touch only panes with no `host`, and a diff tab opened with `host` set skips the repo registry check. `ForgetHostSessions { host, session_ids, all, request_id }` closes that host's listed sessions' panes (or all of its panes) in the sender's layout only, as a local removal does (a forget that matches no pane writes nothing, and one from a client with no layout yet creates none), and a failed layout write answers `Error` with code `tab_refused` and the `request_id`. `RehostPanes { from, to, session_ids, request_id }` (`to` absent is this daemon) is sent only to This PC and rewrites the `host` of each pane in the requester's layout only whose host is still `from` and whose session is in `session_ids`, with one `TabUpdated` per changed tab; no match sends nothing, and a failed layout write answers the same `tab_refused` `Error`.
- `UnbindHostPanes { host?, request_id? }` and `BindHostSessions { host?, session_ids, arrangement, request_id? }` (`unbind_host_panes`, `bind_host_sessions`) act on this client's tabs, which This PC's daemon keeps, remote hosts' panes included, so a client sends both to This PC and never to the host; `host` absent means This PC. Both ride the tab domain's `handle` and answer with `TabUpdated` / `TabRemoved`, or `Error` with the `request_id` on a refusal.

- The chat messages (`crates/daemon/src/chat_mirror.rs`, `crates/daemon/src/server/chat.rs`, design in `docs/architecture.md` "Chat mirror"): `LoadChat` answers `Chat { entries, hidden, screen, request_id }` with the newest 500 entries (`CHAT_REPLY_CAP`), or `Error` `not_found` "unknown session: <id>" or `unsupported_message` "chat is not offered for agent `<id>`"; a missing transcript gives an empty `Chat`. Entries keep the transcript's order. A `Tool` entry's `summary` is empty when the call has nothing to summarise, and a client names the tool by its `name`. A fresh mirror's first reply is empty: the tail's first read is applied without per-line sends, and when it ends every chat loader gets one unsolicited `Chat` (below) and every summary loader one unsolicited `Summary`. A connection's loader carries a chat flag and a summary flag: chat messages go only to chat loaders, `Summary` and `SummaryAppend` (`crates/daemon/src/summary_lines.rs`, one `StretchLine` per turn or window of a long turn) only to summary loaders, and the mirror lives while any loader holds either.

  `ChatWork` (the running-work strip's subagents, shells and wakeup, built in `crates/daemon/src/chat_work.rs`) goes to every chat or summary loader once: to a new loader right after its reply, to all after the first transcript read, and on each change, never on a timer.

  `ChatAppend { entries, removed }` goes to loaders only; `removed` (serde default) lists ids that leave the chat, so one append carries a transcript answer and the live id it replaces. A live answer is `Answer { id: "live:<message key>" or "live:prompt:<prompt key>", live: true }`, its pieces joined in index order with nothing between them (each piece carries its own line breaks) and sent at most every 100 ms (the first at once); a live line without a prompt key is not shown, and lines that arrive before the first read ends are held until it does. A user prompt in the transcript ends the live answers of every other prompt (their ids go in `removed` of the append carrying it), and a later piece of an ended prompt is dropped under any message key, held pieces included; a `TurnEnd` transcript entry ends its prompt's live answers the first time it is applied, whether or not their transcript copy matched them (their ids go in `removed`), a re-read turn end removes nothing, a late piece of an ended message is dropped, and a new message key under the same prompt makes a new live answer; a live-line follower that lags reads on from the oldest line its channel still holds. A replacement is sent to a loader only for an entry at or after the first entry its last `Chat` carried (its reply or the latest reset), so a client never gets one for a row it does not hold.

  An unsolicited `Chat` (`request_id: None`, newest 500 and `hidden`) is a full reset, sent when a tail's first read ends (if anything changed), when a restarted transcript has been re-read, and for a new conversation id once the new file's first read ends (at once when it has no transcript path), opening with the system row "Conversation cleared" (id `cleared:<id>`, only when both conversations are known). `ChatScreenChanged` goes to loaders only, on a change beyond the cursor; prompt ids are `p<n>` from one daemon-wide counter and stay while the same dialog is up, `composer: unknown` means no reading yet, and a plain-shell check feeds no chat.

  `ChatAnswer` types a prompt's recipe (`crates/daemon/src/chat_answer.rs`, spawned from `server/chat.rs`) under the session's typing lane, `busy` at once while a send or another answer holds it. A `prompt_id` that is not the mirror's current prompt and the screen's prompt identity is refused `chat_refused` "the prompt is no longer up". The text is checked (`check_typed_text`, no control character at all) and the recipe built before any key, and the terminal returns to main first only while no dialog is up.

  After each key group the runner waits up to 3 s for a settled reading that holds the step's `ScreenExpect` (a `SameDialog` step needs the dialog visibly changed, an unreadable screen never counts), and no movement, a failed check, an owner key or the 30 s ceiling stops it with no further key.

  Once the answered prompt is gone, `SessionRegistry::clear_answered_prompt_if` (shared with the daemon's subagent-dialog edge; `SendInput` no longer calls it, and its `automatic` flag decides nothing about a prompt) clears a hook-driven record's `AwaitingInput` and `pending_input` only when the pending prompt's kind matches the answered one; a Heads up never clears, and an answer is never an owner key. `DenyWithText` presses No, waits for the box to be ready, then sends the text under the same lane turn (`inject::type_message_under`) and is refused in an agent's view. Refusals are `chat_refused`, or `invalid_request` for an empty answer or one holding a control character.

  `ChatSend` types the text into the PTY (`inject::type_message`, spawned from `server/chat.rs`) and has no success reply: the text is checked first (`\r\n` becomes `\n`; empty text, C0, DEL or C1 control characters and text over 64 KiB are `invalid_request`).

  The send then takes the session's typing lane (`busy` at once when a send or answer holds it, or while the session's first prompt is held behind a startup dialog, "This session's first prompt is still waiting to be typed."; else after waiting 250 ms), gates on the settled screen and refuses with `chat_refused` for a pending hook prompt, a draft in the box in any view, a dialog, an overlay, unknown state or an agent ended in its shell.

  An open agent view is driven to main key by key and gated again; the text then goes in as a bracketed paste, and under the record and screen locks the send re-checks (no dialog, paste shown, no owner key since it began, no pending prompt), adds a pending chat entry and presses Enter. The entry is `ChatEntry::User { id: "pending:<n>", pending: true }`, sent to loaders just before the Enter and removed, oldest first by trimmed text, when the transcript's `user` or `queued_command` record arrives (the `ChatAppend` carries its id in `removed`), or by a restart, a conversation switch or the mirror's drop; a `/` or `!` command adds none. A send is never an owner key. `UnloadChat` and a closing connection unload; the tail stops when the last loader leaves, an ended session's chat stays loaded read-only, and only the session's removal drops it. Every send to loaders happens under the one mirror lock, taken inside the screen grid lock and never the reverse; the `connection.rs` guard (`connection_watches`) unloads a connection's chats when it drops.
- A file fetch from a remote host is `ClientMessage::FetchFile { id, repo_id, worktree_path: Option<String>, path }`, `path` relative to the repo root or worktree. The daemon answers `FileFetchStarted { id, resolved_path, size }`, then `FileChunk { id, seq, data_b64 }` chunks of about 256 KiB, then `FileFetchDone { id }`, or `FileFetchError { id, error }` at any point (a directory, a missing or unreadable file, a path rejected by confinement). `resolved_path` is the daemon's canonical path, so on Windows it starts with `\\?\` and the client strips that before showing it. `ClientMessage::CancelFetch { id }` stops the stream; a closed socket stops it too.

  The path must lie inside a registered repo root, a folder under the app's worktrees root, or a folder `git worktree list` names for the repo (`FetchFile`, `FetchFolder` and `StatPath` only; `server/folder.rs`): the daemon rejects `..` segments and absolute paths lexically, canonicalizes the joined path and requires it to start with the canonical root, so a symlink out is refused. A listed folder matches in any separator or case spelling on Windows; a `\\?\` or 8.3 spelling is not a listed folder. A `worktree_path` that is not listed is refused as `worktree_path {wt} is not a git worktree of {repo name}`, and a failed `git worktree list` as `couldn't read the git worktrees of {repo name}: {reason}`. `FetchFile` naming the worktrees root, or a folder under it with no `.git`, is refused as `FetchFolder` is. The git messages and `GetFileSnapshot` keep the narrow rule (a registered repo root or a session worktree), and every rejection names the path and the reason. Reads run on a blocking task through a bounded channel into the connection's send queue, so a slow client applies backpressure and PTY output keeps priority. No size cap applies to a file fetch.
- A folder fetch is `ClientMessage::FetchFolder { id, repo_id, worktree_path, path }` (`path` `""` or `"."` is the root), offered only when `Welcome.features` lists `folder_fetch`. It shares `FetchFile`'s id space, confinement, `CancelFetch` and backpressure. The daemon scans first and refuses with one `FileFetchError` before anything else for a refused path, a target that is not a folder, or a folder past 20 000 files or 512 MiB. Otherwise it answers `FolderFetchStarted { id, resolved_path, files, bytes }` (the scan's counts, uncompressed), then `FileChunk`s carrying one zstd level-1 tar (every chunk but the last exactly 256 KiB), then `FileFetchDone`, or `FileFetchError` at any point (`packing {name}: {io error}`, `packing the folder: {io error}`). The walk follows no link and leaves out links, entries that are neither files nor folders, non-Unicode names, `.git` and the ignored folders (`node_modules`, `target`, `.venv`, caches, at any depth); a listed file that cannot be opened is skipped with a `daemon.log` debug line. `ClientMessage::StatPath { id, repo_id, worktree_path, path }` is answered with `PathStat { id, kind, size }` (`kind` is `file`, `dir`, `missing` or `other`); a refused path answers `missing`, never told apart from an absent one.

- `SessionSnapshot` is the canonical session shape — daemon emits `Sessions` (list), `SessionUpdated` (single), `SessionRemoved` (id only). Don't add ad-hoc session-shaped messages elsewhere.

- A client that needs to know which reply answers its request sets the optional `request_id` on `SpawnSession` / `DuplicateSession` / `ResumeSession` / `LaunchLast` / `NewSession` / `LoadScrollback` / `SetSessionAppearance`.

  The daemon echoes it only on the reply it sends to that requester (`SessionUpdated` or `Scrollback`, `CheckoutConfirmRequired` when an in-place spawn needs a checkout confirm, or `Error` / `ActionFailed` on failure).   The spawn previews `PreviewSpawn` / `PreviewWorkspaceSpawn` take one as well; it comes back on their `SpawnPreview` / `WorkspaceSpawnPreview` reply, or on the `Error` when the preview fails. Broadcasts never carry it. A spawn's, a duplicate's and an appearance change's `SessionUpdated` echo travels on the requester's ordered session-event stream (`SessionEvent::Updated` carries its origin connection), so the requester gets one copy, carrying the id, and it never overtakes an older broadcast.

  A `SpawnSession` carrying a `request_id` is journalled per device (a tailnet peer's stable id, or a local connection's client id; a local connection with no client id, such as the daemon's own CLI verbs, is not journalled) for 10 minutes, at most 256 per device, so a retry after a dropped connection makes no second session.

  A repeat that arrives while the first is still spawning gets no answer then; its connection is kept on the journal entry, and when the spawn ends it gets what the first send came to. After it spawned, the repeat gets `SessionUpdated` echoing the `request_id` with the session's current snapshot, or a failure "That session has ended." when the session is gone. After it failed, the repeat gets the same failure again. A request refused before the spawn (an invalid request, or one answered `CheckoutConfirmRequired`) is not journalled.

  A `LaunchLast` or `NewSession` carrying one shares the same journal, in the same id space, and is checked against it first: a repeat is answered from the journal before the stored config is looked up or any check runs, so a launch that already made a session is never refused on its resend. A new one then passes its own refusals, the request's checks and one checkout preflight before it is journalled. The journal is in memory and does not survive a daemon restart.

  A connection whose session-event stream lags is sent a fresh `Sessions` list, then its spawn replies again with their `request_id`; one whose tab-event stream lags is sent its client's fresh `Tabs` list. A `Scrollback` with `forwarder_restarted: true` means the old forwarder has stopped and the new one starts after this reply, so output a client held back before it is already in the history. A `Scrollback` with no `request_id` is a resync: when one session's queued output on a connection would pass 4 MiB (`PTY_SESSION_BUDGET`), its forwarder drops the live feed and, once that queue drains, sends one fresh snapshot (or, if the session exited meanwhile, its file scrollback with `forwarder_restarted: false`); the native client drops it while the pane's own load is pending and otherwise starts the pane over from it as a fresh attach.

  The tab-layout requests `CreateTab` / `MergeTabs` / `MovePane` / `ExtractToNewTab` / `SplitPane` / `ClosePane` / `SwapPanes` / `ReorderTabs` / `RehostPanes` take one too; it comes back only on the `Error` that refuses the request (success is a broadcast `TabUpdated` or `TabRemoved`, which carries none), and a refusal without one still gets `Error { request_id: None }`. `ListSessionHistory`, `RecoverSessions` and `ListEnvNames` echo theirs on their `SessionHistory`, `RecoverResult` and `EnvNames` replies. `ListPresets` echoes its id on `Presets` and on the `Error` (code `presets_failed`) that answers a failed list; the native container menu fills its preset rows only from the reply carrying its own id.

  `AnswerPrompt` (the Dashboard's, `crates/daemon/src/server/dashboard.rs`) maps its `PromptChoice` to the dialog's own option digit (`Option { index }` is `index + 1`, Allow the "Yes" option, AllowAlways the don't-ask-again option and refused when the dialog shows none, Deny the "No" option, never Esc; `TypeSomething { text }` and `DenyWithText { text }` map to the chat answers of the same names, a daemon that takes them lists `typed_prompt_answers` in `Welcome.features`, and another prompt kind refuses them as `invalid_request`) and types it with the chat answer runner under the typing lane, with no chat mirror. Before and again under the lane it requires the record's `status_since` to equal `since` and `pending_input` unchanged, the dialog's content to match the pending prompt (a permission's summary in its subject or body, a question's text and leading option labels) and the option to be inside the list. It has no success reply; a refusal is an `Error` with the request id: `not_found`, `no_screen`, `invalid_request` "that answer does not fit the prompt on screen", `chat_refused` "the prompt is no longer up" (the record moved), `chat_refused` "Couldn't read this prompt; answer it in its pane." (the record still waits but the screen's dialog cannot be read) or `busy`. Each refusal also logs an info line `dashboard answer refused` in `daemon.log` with `session_id`, `code` and `why` (`record_moved`, `no_pending`, `not_this_dialog`, `unreadable`, `lane_recheck`), never the prompt's text.

  `LoadChat` and `LoadSummary` echo theirs on `Chat` and `Summary` and on the `Error` that refuses the load; `ChatSend` and `ChatAnswer` have no success reply and take one only to name the `Error` that refuses them, which the native chat routes back to the composer or card it answers. Neither `ChatAppend` nor an unsolicited `Chat` or `Summary` carries one.

  `GetSessionDetail` echoes its id on `SessionDetail`, and on the `Error "unknown session: <id>"` that answers a session the facts cache does not hold. `SuggestBranchName` echoes its id on `BranchNameSuggestion`, and on the `Error` that answers a failed suggestion. `SetAgentCommand`, `SetAgentSettings` and `SetDefaultShell` take one too; it comes back only on the `Error` that refuses the request (success is the `AgentCommands` / `AgentSettings` / `DefaultShell` broadcast, which carries none), and the native Settings modal routes each refusal to the apply it answers, placing a launch-command or worktrees-root refusal by its code (`launch_program_refused`, `launch_args_refused`, `worktrees_root_refused`).
